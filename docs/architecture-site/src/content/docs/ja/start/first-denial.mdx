学習可能な拒否は、Upstream への接続が作られる前に Gateway で止まります。Gateway は、量を制限した秘密情報を含まない根拠を保持し、ホスト側のレビューキューを案内します。保持された通信が完全一致の許可または拒否になるのは、利用者が明示的に判断し、ポリシー全体の検証が完了した後だけです。元のリクエストが自動的に再試行されることはありません。

ここでは、拒否からホスト上のレビュー、意図的な再試行までを順に追います。先に[クイックスタート](../quickstart/)を完了するか、ホストと Workspace のコマンドが分離されていることを確認してください。

## 拒否を時間順に追う

1. Gateway はリクエストを受けたネットワークインターフェースとホスト所有のプリンシパルレジストリから Context/プロジェクトプリンシパルを導出します。
2. リクエスト本文を含まない形に正規化したポリシー入力を作り、OPA へ一度問い合わせます。
3. OPA は、許可規則のない通信を拒否します。
4. Gateway は Broker 管理の秘密情報を解決せず、宛先の DNS 名前解決も Upstream への接続も行いません。
5. Gateway は情報量を制限した `403` レスポンスを返します。示すのは固定されたホスト側のレビューコマンドであり、操作用の参照ではありません。
6. 秘密情報を含まない拒否の根拠が、保持期間を制限したレビュー対象に加わります。同じ通信を繰り返し観測しても新しい権限は生まれず、一つにまとめられます。

## レビューは発見、許可と拒否は操作

信頼するホストで実行します。

```sh
tobari policy review
```

TTY のフローでは保留中の通信を確認し、一つの Context に対する完全一致の判断を準備します。一式をレビューした後に一度だけ **Apply** を押してください。Apply 前にキャンセルすると何も変わりません。リダイレクトされたレビューは読み取り専用です。

```sh
tobari policy review --format json
```

機械から利用する場合は、不透明な `pcy_...` 参照を変更せず、一つの操作へ渡します。

```sh
tobari policy allow --id <pcy-id>
# or
tobari policy deny --id <pcy-id>
```

表示順、ホスト名のラベル、手作りした識別子は権限になりません。操作では、保持された参照を解決し、それが現在の拒否を表すことを確認します。次に、所有者だけがアクセスできるポリシーデータを変更し、集約後のポリシー全体をテストして、リビジョン付きの完全なバンドルを一つだけ有効にします。検証または有効化に失敗した場合は、直前に検証済みだったポリシーが引き続き使われます。

## 「完全一致の」が意味する範囲

学習済み規則は次に結び付きます。

- 安定した Context ID
- ホストが発行したプロジェクト ID
- スキーム
- 宛先ホストとポート
- HTTP メソッド
- パス

リクエスト本文は意図的に含めません。本文だけが異なる二つのリクエストには、同じ許可規則が適用されます。Tobari はプロンプト、JSON の内容、アップロードデータ、フォーム本文を調べて、リクエストの意図を推測しません。

完全一致の学習済み拒否は基本デフォルト拒否と異なります。基本拒否は許可が一致しなかったことを意味します。明示的な完全一致の拒否は信頼するホストの判断を記録し、保留中学習可能な候補として繰り返し現れません。どちらもリクエストを止めます。

## 判断を修正する

現在の学習済み規則を確認します。

```sh
tobari policy rules
```

現在の判断一つを削除するには、その不透明な規則 ID を変更せずコピーします。

```sh
tobari policy reset --id <policy-rule-id>
```

リセットは許可対象を許可せず、再実行もしません。その許可対象をデフォルト拒否に戻します。その後、同じ拒否が観測されれば再びレビューできます。

関連する完全一致規則が十分に集まると、Tobari は範囲を限定し、テストで裏付けたパス接頭辞の集約候補も提示します。

```sh
tobari policy compactions
tobari policy compact --id <policy-compaction-id>
```

集約は自動ではありません。一致すべき例を保ち、接頭辞の外側にある隣接パスを検証用リクエストとして確認します。ただし、有限のテストで将来のすべてのパスが安全だと証明することはできません。

## 失敗時の動作

- OPA が利用できない、または OPA のレスポンスが無効な場合はサービス障害となり、外部の接続先への接続は作られません。
- 不変のスキーム、クラスター、プリンシパル、認証情報結び付けの障害は診断であり、学習可能な候補ではありません。
- 期限切れまたは古い候補参照は拒否されます。キューから候補を再取得してください。
- ポリシーが並行して変更されると、古い操作または集約は推測せず失敗します。
- 完全なポリシーが無効なら、直前に有効だったポリシーは変わりません。
- 変更が確定していても結果が不確かな場合は、再実行する前に読み取り専用の状態確認で整合を取る必要があります。変更操作コマンドを盲目的に繰り返さないでください。

## 保証と制限

Tobari は、観測した通信が自動的に権限へ変わらず、通常の学習済み判断が完全一致かつプロジェクトに結び付いたままであることを保証します。一方で、接続先が信頼できるかは判断しません。本文内の機微情報を検査せず、すでに許可された接続先へ Workspace から読めるデータを送ることも防ぎません。

## まとめ

拒否とは、停止された許可対象と上限のある根拠です。信頼するホストで不透明な参照に対する操作を実行したときだけポリシーが変わります。検証は全体が成功した場合だけで、再試行は常に意図的な新しいリクエストです。

## 理解を確認する

<summary>二つの POST リクエストでプロジェクト、ホスト、ポート、メソッド、パスは同じですが、JSON 本文が異なります。ポリシー候補は二つになりますか？</summary>

いいえ。本文はポリシー識別情報 dimension ではないため、同じ通常の HTTP 操作を表します。

</details>

<details>
<summary><code>ポリシーリセット</code> は完全一致の拒否を許可に変えますか？</summary>

いいえ。学習済みの判断を取り除き、その許可対象を基本デフォルト拒否に戻します。

</details>

<details>
<summary>許可操作の途中でポリシー検証が失敗すると、どうなりますか？</summary>

候補は部分的に有効化されません。直前の検証済み集約ポリシーが active のまま残り、後で有効な操作が完了するまでリクエストは拒否されます。

</details>
