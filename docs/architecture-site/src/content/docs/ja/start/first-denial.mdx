未許可の HTTP/HTTPS 通信は、接続先へ到達する前に Gateway で拒否されます。Gateway は宛先・ポート・メソッド・パスなど、レビューに必要な情報だけを記録し、ホスト側のレビューコマンドを返します。利用者が許可または拒否を確定し、ポリシー全体の検証が終わるまで権限は変わりません。元のリクエストも再送されません。

ここでは、拒否の発生からホスト側のレビュー、新しいリクエストとしての再試行までを順に追います。先に[クイックスタート](../quickstart/)を完了するか、ホストと Workspace のコマンドを別々の場所で実行することを確認してください。

## 拒否を時間順に追う

1. Gateway は、リクエストを受けたネットワークインターフェースと、ホストが管理するプリンシパル登録簿から Context とプロジェクトを特定します。
2. リクエスト本文を含まない形に正規化したポリシー入力を作り、OPA へ一度問い合わせます。
3. OPA は、一致する許可ルールがない通信を拒否します。
4. Gateway は Auth Broker が管理する認証情報を解決せず、宛先の DNS 名前解決も、接続先への接続も行いません。
5. Gateway は情報量を制限した `403` レスポンスを返します。レスポンスに含まれるのは、固定されたホスト側のレビューコマンドです。権限変更に使う不透明な参照値は Workspace へ渡しません。
6. 秘密情報を含まない拒否情報が、保持期間を制限したレビュー対象に加わります。同じ通信を繰り返し観測しても新しい権限は生まれず、一つの候補にまとめられます。

## レビューと権限変更を分ける

Workspace セッションを終了する必要はありません。エージェントを待たせ、別の信頼するホスト端末で実行します。

```sh
tobari policy review
```

対話型ターミナルでは、保留中の通信を確認し、一つの Context に対する完全一致の判断を準備します。一式をレビューした後に一度だけ **Apply** を押してください。Apply 前にキャンセルすると何も変わりません。出力をリダイレクトした場合、レビューは読み取り専用です。

```sh
tobari policy review --format json
```

プログラムから使う場合は、不透明な `pcy_...` 参照を変更せず、そのまま一つの操作へ渡します。

```sh
tobari policy allow --id <pcy-id>
# or
tobari policy deny --id <pcy-id>
```

表示順、ホスト名のラベル、手作りした識別子は権限になりません。操作では、保持された参照を解決し、それが現在の拒否を表すことを確認します。次に、所有者だけがアクセスできるポリシーデータを変更し、集約後のポリシー全体をテストして、リビジョン付きの完全なバンドルを一つだけ有効にします。検証または有効化に失敗した場合は、直前に検証済みだったポリシーが引き続き使われます。

## 完全一致ルールが固定する条件

学習済みルールは次に結び付きます。

- 安定した Context ID
- ホストが発行したプロジェクト ID
- スキーム
- 宛先ホストとポート
- HTTP メソッド
- パス

リクエスト本文は意図的に含めません。本文だけが異なる二つのリクエストには、同じ許可ルールが適用されます。Tobari はプロンプト、JSON の内容、アップロードデータ、フォーム本文を調べて、リクエストの意図を推測しません。

明示的な完全一致の拒否は、既定拒否とは意味が異なります。既定拒否は、許可ルールが一致しなかったことを表します。明示的な拒否は、信頼するホストの判断を記録し、保留中の候補として繰り返し現れないようにします。どちらの場合も、リクエストは接続先へ届きません。

## 判断を修正する

現在の学習済みルールを確認します。

```sh
tobari policy rules
```

現在の判断を一つ削除するには、その不透明なルール ID を変更せずコピーします。

```sh
tobari policy reset --id <policy-rule-id>
```

`policy reset` は通信を許可せず、再実行もしません。指定した完全一致ルールを削除し、その通信条件を既定拒否へ戻します。その後、同じ拒否が観測されれば再びレビューできます。

関連する完全一致ルールが十分に集まると、Tobari は範囲を限定し、テストで裏付けたパス接頭辞の集約候補も提示します。

```sh
tobari policy compactions
tobari policy compact --id <policy-compaction-id>
```

集約は自動ではありません。一致すべき例を保ち、接頭辞の外側にある隣接パスを検証用リクエストとして確認します。ただし、有限のテストで将来のすべてのパスが安全だと証明することはできません。

## 失敗時の動作

- OPA が利用できない、または OPA のレスポンスが無効な場合はサービス障害となり、外部の接続先への接続は作られません。
- スキーム、クラスター、プリンシパル、認証情報の結び付けに関する変更不能な障害は診断であり、学習可能な候補ではありません。
- 期限切れまたは古い候補参照は拒否されます。キューから候補を再取得してください。
- ポリシーが並行して変更されると、古い操作または集約は推測せず失敗します。
- 完全なポリシーが無効なら、直前に有効だったポリシーは変わりません。
- 変更が確定している可能性がある一方で結果を確認できない場合は、再実行する前に読み取り専用の状態確認で整合を取る必要があります。変更操作を盲目的に繰り返さないでください。

## 保証と制限

Tobari は、観測した通信を自動的に権限へ変えません。通常の学習済みルールは、完全一致かつ一つのプロジェクトに結び付いたままです。一方、接続先そのものが信頼できるかは判断しません。本文内の機微情報を検査せず、すでに許可された接続先へ Workspace から読めるデータを送ることも防ぎません。

## まとめ

拒否された通信は接続先へ送られず、レビューに必要な情報だけがホスト側へ残ります。ポリシーが変わるのは、信頼するホストで不透明な参照を使い、許可または拒否を確定したときだけです。変更はポリシー全体の検証後に有効になり、再試行は常に新しいリクエストとして行います。

</details>

<details>
<summary><code>policy reset</code> は完全一致の拒否を許可に変えますか？</summary>

いいえ。学習済みの判断を削除し、その通信条件を既定拒否へ戻します。

</details>

<details>
<summary>許可操作の途中でポリシー検証が失敗すると、どうなりますか？</summary>

候補は部分的に有効化されません。直前に検証済みだった集約ポリシーが有効なまま残り、後で正しい操作が完了するまでリクエストは拒否されます。

</details>
