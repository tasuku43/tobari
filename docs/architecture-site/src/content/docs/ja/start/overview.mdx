Tobari は、コーディングエージェントをプロジェクト専用の Workspace で実行し、未許可の HTTP/HTTPS 通信を Gateway で拒否します。拒否された通信は信頼するホストでレビューし、Context、プロジェクト、宛先、ポート、メソッド、パスが一致するルールとして許可または拒否します。許可後も、元のリクエストは再送されません。

Tobari は、Docker コンテナの起動を簡略化するだけのツールではありません。作業対象のディレクトリ、プロジェクト専用ネットワーク、共有の Gateway・OPA・Auth Broker を組み合わせ、ファイルへのアクセスと外部通信の権限を別々に管理します。このページでは、五つの構成要素と、Tobari が保護しない範囲を最初に整理します。読み終えたら[インストール](../install/)へ進めます。

## 最初に押さえる境界

エージェントは、作業対象のディレクトリを読み書きできます。Tobari が制限するのは、その外側にあるホスト環境と、未許可の外部通信です。作業対象外のホストファイルや Docker の制御機能は Workspace へ渡さず、Workspace ごとに内部ネットワークを分けます。HTTP/HTTPS 通信は共有の Gateway を必ず経由します。

<SystemMap headingLevel={2} compact />

図は次の順番で読んでください。

1. **Workspace** 内のプロセスが、プロキシを使って HTTP/HTTPS リクエストを送ります。
2. **Gateway** がリクエストを受け、ホストが管理するネットワーク状態から通信主体（プリンシパル）を特定します。
3. **OPA** は、Context、プロジェクト、スキーム、宛先、ポート、メソッド、パスを使って通信を判断します。リクエスト本文は、ポリシーの判断項目には含まれません。
4. **Auth Broker** は、Gateway が Tobari の Broker ハンドルを認識した場合だけ参加します。ポリシー判断前に扱うのは、秘密情報を含まない結び付け情報だけです。静的な認証情報の解決、Datadog トークンの選択や更新、AWS の認証情報エクスポートや署名は、許可後にだけ行います。
5. 許可後、**Workspace** ではなく **Gateway** が外部の**接続先**へ別の接続を開きます。

判断を返すのは OPA です。Gateway はその判断に従って、リクエストを拒否するか、接続先への通信を開始します。

## 最初の具体例

`/work/example` のエージェントが次を試すとします。

```sh
curl -X PUT https://example.com/quickstart
```

この通信条件に一致するルールがなければ、Gateway は学習可能な `403` を返します。件数と内容を制限した、秘密情報を含まないレビュー情報を保持し、信頼するホストで実行するコマンドをエージェントへ示します。自動承認はありません。利用者は Workspace から出て `tobari policy review` を実行し、通信条件を確認して許可または拒否を確定します。再試行は、確定後に新しいリクエストとして行います。

このルールは「エージェントが example.com を自由に使ってよい」という意味ではありません。レビューした Context、プロジェクトのプリンシパル、HTTPS の接続先とポート、HTTP メソッド、パスに結び付きます。

## 境界の外に置くもの

サポート対象の Docker 構成では、次の権限や情報を、信頼しない Workspace プロセスへ渡さないよう設計しています。

- 作業対象のディレクトリ外にあるホストファイル
- Docker ソケットと Docker の制御機能
- ほかの Workspace と、その永続ホーム
- Gateway を迂回して公開インターネットへ出る直接経路
- Auth Broker が管理する認証情報の本体
- ホストが所有するポリシーのレビューと有効化の経路

Gateway、OPA、プリンシパル登録簿、Broker の結び付けから有効な判断を確立できない場合、関連するリクエストは拒否します。OPA の障害が許可に変わることはありません。

<span id="boundary-does-not-protect"></span>

## Tobari が保護しないもの

Tobari は次を保証しません。

- 作業対象のディレクトリ内にあるファイルを、その Workspace のプロセスから守ること
- 利用者が許可した接続先へ、Workspace のプロセスが送るデータ
- 同じ Workspace 内にあるプロセス同士の分離
- 重複するプロジェクトルート間で、互いのホストファイル変更が見えないこと
- ホスト、カーネル、Docker、Gateway、OPA、Auth Broker が侵害された後の保護
- 生の TCP、UDP、HTTP/3、Git over SSH など、通常の HTTP/HTTPS 以外の通信

プロキシ設定を無視するクライアントには、サポート対象となる外部への直接経路がないため、接続は失敗します。Tobari CA を信頼しない証明書固定の HTTPS クライアントも、Gateway を迂回せずに失敗します。

## 現在の実装状態

**実装済み:** 再利用できる Context に結び付いた Workspace、プロジェクト専用の内部ネットワーク、Gateway と OPA による通信制御、完全一致の拒否レビュー、ガイド付きと高度なポリシーモード、Context ごとのランタイムレシピ、ツール自身による認証、保持型の管理アダプター（managed adapter）、厳格なスキーマ 1 の静的 Broker プロバイダー、レビュー済みの組み込み GitHub・AWS・Datadog 認証情報取得処理です。組み込みのスキーマ 2 プランでは、非公開のホスト側コンパニオンを使う上限付きの AWS SigV4 と、Broker 内で行う Datadog US1 OAuth の更新に対応しています。

ソースツリーとテストには、両方のスキーマ 2 プランが含まれています。ただし、`versions.env` で現在選ばれる Gateway と Auth Broker のダイジェストは、以前の AWS Identity Center 経路までを含む成果物に固定されています。AWS のコンソールログインと Datadog のリクエスト経路は、その後に実装されました。この二つはソースには存在しますが、成果物のダイジェストをレビューして更新するまでは、標準クラスターで有効になりません。[コンポーネントのバージョン](../../reference/component-versions/)では実際に選ばれる成果物を確認でき、[サプライチェーン](../../security/supply-chain/)ではソースとランタイムの識別情報を別々に確認する理由を説明しています。

この文書では、マニフェストで任意に選べる署名・更新処理、任意の OAuth ヘルパー、プロバイダー操作に対するポリシー、Git 認証情報ヘルパー、プロバイダーまたは Context ごとの複数アカウント、追加の組み込みプランを、現在利用できる機能として扱いません。

## まとめ

Tobari は、作業対象のディレクトリへの読み書きを認める一方、ホスト環境と外部通信への権限を別に制御します。Workspace が自分自身へ権限を追加することはできません。ホストが Context とプロジェクトを特定し、OPA が通信を判断し、Gateway がその判断を強制します。Auth Broker は、許可された通信に限って、宣言済みの認証処理をポリシー判断後に実行します。

## 理解を確認する

<details>
<summary>プロセスが <code>HTTPS_PROXY</code> を無視すると、インターネットへ直接到達しますか？</summary>

いいえ。サポート対象の構成では、Workspace は専用の内部 Docker ネットワークだけに参加します。プロジェクトネットワークと外部通信の両方へ接続するのは Gateway だけなので、プロキシを無視した接続は失敗します。

</details>

<details>
<summary>OPA の許可応答自体が、リクエストを接続先へ送信しますか？</summary>

いいえ。OPA は判断を返します。Gateway がその判断を強制し、許可後にだけ接続先への通信を開始します。

</details>

<details>
<summary>Tobari は作業対象のディレクトリをエージェントから保護しますか？</summary>

いいえ。作業対象のディレクトリは、意図的に読み書き可能な状態でマウントされます。Tobari はその外側にある権限を制限しますが、作業対象を読み取り専用にはしません。

</details>

意外な回答があったら、[境界の外に置くもの](#boundary-protects)と[Tobari が保護しないもの](#boundary-does-not-protect)を読み直してください。
