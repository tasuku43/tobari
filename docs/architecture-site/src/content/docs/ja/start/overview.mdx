Tobari は、コーディングエージェントをプロジェクト専用の Workspace で実行し、未許可の HTTP/HTTPS 通信を Gateway で拒否します。拒否された通信は信頼するホストでレビューし、Workspace Template、プロジェクト、宛先、ポート、メソッド、パスが一致するルールとして許可または拒否します。許可後も、元のリクエストは再送されません。

Tobari は、Docker コンテナの起動を簡略化するだけのツールではありません。作業対象のディレクトリ、プロジェクト専用ネットワーク、共有の Gateway・OPA を組み合わせ、ファイルへのアクセスと外部通信の権限を別々に管理します。このページでは、standard の4つの構成要素と、Tobari が保護しない範囲を最初に整理します。読み終えたら[インストール](../install/)へ進めます。

## 最初に押さえる境界

エージェントは、作業対象のディレクトリを読み書きできます。Tobari が制限するのは、その外側にあるホスト環境と、未許可の外部通信です。作業対象外のホストファイルや Docker の制御機能は Workspace へ渡さず、Workspace ごとに内部ネットワークを分けます。HTTP/HTTPS 通信は共有の Gateway を必ず経由します。

<SystemMap headingLevel={2} compact />

図は次の順番で読んでください。

1. **Workspace** 内のプロセスが通常の HTTP/HTTPS リクエストを送ります。クライアント側のプロキシ設定を使わず、上限付きの合成 DNS 応答と閉じた出力経路が TCP をそのプロジェクトの Gateway へ届けます。
2. **Gateway** がリクエストを受け、カーネルが観測した Workspace の送信元エンドポイントと、ホスト管理の登録簿から通信主体（プリンシパル）を特定します。
3. **OPA** は、Context、スキーム、宛先、ポート、メソッド、パスを使って通信を判断します。Workspace、root、CWD、directory は routing と provenance にだけ使われ、リクエスト本文と同様に Policy Memory の identity には含まれません。
4. 許可後、**Workspace** ではなく **Gateway** が外部の**接続先**へ別の接続を開きます。native authentication は元の request に保持されますが、OPA と audit には入りません。

判断を返すのは OPA です。Gateway はその判断に従って、リクエストを拒否するか、接続先への通信を開始します。

## 最初の具体例

`/work/example` のエージェントが次を試すとします。

```sh
curl -X PUT https://example.com/quickstart
```

この通信条件に一致するルールがなければ、Gateway は学習可能な `403` を返します。件数と内容を制限した、秘密情報を含まないレビュー情報を保持し、信頼するホストで実行するコマンドをエージェントへ示します。自動承認はありません。利用者は Workspace から出て `tobari review permissions` を実行し、通信条件を確認して許可または拒否を確定します。再試行は、確定後に新しいリクエストとして行います。

このルールは「エージェントが example.com を自由に使ってよい」という意味ではありません。レビューした Context、HTTPS の接続先とポート、HTTP メソッド、パスに結び付きます。同じ Context の sibling Workspace は同じ完全一致 rule を共有します。

## 境界の外に置くもの

サポート対象の Docker 構成では、次の権限や情報を、信頼しない Workspace プロセスへ渡さないよう設計しています。

- 作業対象のディレクトリ外にあるホストファイル
- Docker ソケットと Docker の制御機能
- ほかの Workspace の runtime と専用 network、および別 Context の永続 Home
- Gateway を迂回して公開インターネットへ出る直接経路
- 別 Context の native credential state
- ホストが所有するポリシーのレビューと有効化の経路

Gateway、OPA、プリンシパル登録簿から有効な判断を確立できない場合、関連するリクエストは拒否します。OPA の障害が許可に変わることはありません。

<span id="boundary-does-not-protect"></span>

## Tobari が保護しないもの

Tobari は次を保証しません。

- 作業対象のディレクトリ内にあるファイルを、その Workspace のプロセスから守ること
- 利用者が許可した接続先へ、Workspace のプロセスが送るデータ
- 同じ Context Home を共有するプロセスや sibling Workspace 同士の分離
- 重複するプロジェクトルート間で、互いのホストファイル変更が見えないこと
- ホスト、カーネル、Docker、Gateway、OPA が侵害された後の保護
- 生の TCP、UDP、HTTP/3、Git over SSH など、通常の HTTP/HTTPS 以外の通信

通常の直接ソケットを使うクライアントは Gateway のポリシー境界へ到達し、外部への直接経路は得られません。Tobari CA を信頼しない証明書固定の HTTPS クライアントは、Gateway を迂回せずに失敗します。

## 現在の実装状態

**実装済み:** reusable Workspace Template-bound Workspace、project internal network、Gateway/OPA mediation、
immutable source access、Workspace Template-owned canonical policy data、完全一致 denial review、固定 Tobari evaluator、
Workspace Template runtime recipe、Claude Code と Codex の tool-native authentication です。

release surface の CLI release が公開・lock する service image は Gateway だけです。repository development は content-addressed local image を使います。この release site は release contract だけを説明します。[コンポーネントのバージョン](../../reference/component-versions/)では成果物の契約を確認でき、[サプライチェーン](../../security/supply-chain/)ではソースとランタイムの識別情報を別々に確認する理由を説明しています。

マニフェストで任意に選べる署名・更新処理、任意の OAuth ヘルパー、外部サービス操作に対するポリシー、Git 認証情報ヘルパー、外部サービスまたは Workspace Template ごとの複数アカウント、追加の未レビュー組み込みプランは対応外です。

## まとめ

Tobari は、作業対象のディレクトリへの読み書きを認める一方、ホスト環境と外部通信への権限を別に制御します。Workspace が自分自身へ権限を追加することはできません。ホストが Context と Workspace principal を特定し、OPA が Context-owned Policy Memory で通信を判断し、Gateway がその判断を強制します。native credential は Context Home に残り、許可された request でだけ転送されます。

## 理解を確認する

<details>
<summary>プロセスが HTTPS の直接ソケットを開くと、Gateway を通らずインターネットへ到達しますか？</summary>

いいえ。サポート対象の構成では、Workspace は専用の内部 Docker ネットワークだけに参加します。合成 DNS と Workspace の出力ガードが通常の TCP を Gateway の透過リスナーへ送り、そこで同じ接続先検証と OPA 判断を適用します。対応しない非 HTTP 通信は閉じたまま失敗します。

</details>

<details>
<summary>OPA の許可応答自体が、リクエストを接続先へ送信しますか？</summary>

いいえ。OPA は判断を返します。Gateway がその判断を強制し、許可後にだけ接続先への通信を開始します。

</details>

<details>
<summary>Tobari は作業対象のディレクトリをエージェントから保護しますか？</summary>

Workspace Template の immutable creation-time Boundary が `read-only` または `read-write` を選び、
CLI omission default は `read-write` です。read-only は selected live bind だけに適用し、
Workspace home/tmpfs や host source の別 writer には適用しません。

</details>

意外な回答があったら、[境界の外に置くもの](#boundary-protects)と[Tobari が保護しないもの](#boundary-does-not-protect)を読み直してください。
