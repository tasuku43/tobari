## このページの使い方

各シナリオについて、回答を開く前に自分の言葉で説明してください。「許可される」「拒否される」だけでなく、どのコンポーネントが判断または強制し、どの境界が関係するかまで答えます。

先に[学習ガイド](../learning-path/)をたどってください。分からない回答が多い場合は、文章を暗記するのではなく、各回答のリンク先へ戻ってください。

## 1. Docker ラッパーだけではない理由

開発者が「Tobari は便利な `docker run` コマンドにすぎない」と言いました。何が抜けていますか？

<details>
<summary>回答</summary>

ランタイムコンテナは、失われても復元できる実装要素の一つにすぎません。Tobari はほかにも、Workspace Template に結び付いた論理 Workspace、ホストが発行するプロジェクト principal、専用の内部ネットワーク、Gateway による通信経路の強制、OPA ポリシー、拒否内容のレビューと一括有効化、永続ホームと状態を管理します。[システム全体像](../../how-it-works/system-overview/)を参照してください。

</details>

## 2. 直接ソケットを開く

プロセスが公開 IP へ直接接続します。サポート対象の構成ではどうなりますか？

<details>
<summary>回答</summary>

外部への直接経路は得られません。Workspace の出力ガードは TCP をそのプロジェクトの Gateway へ送り、透過リスナーが有効な HTTP/TLS の接続先と同じ OPA 判断を要求します。公開 IP だけを指定した接続や非 HTTP 通信は、閉じたまま失敗します。[信頼境界](../../security/trust-boundaries/)を参照してください。

</details>

## 3. 判断と強制

OPA が `allow` を返しました。外部の接続先への接続を実際に開くコンポーネントはどれですか？

<details>
<summary>回答</summary>

Gateway です。OPA が正規化された HTTP 通信を判断し、Gateway が結果を通信経路へ強制して、外部の接続先へ別の接続を作ります。[リクエストの流れ](../../how-it-works/request-journey/)を参照してください。

</details>

## 4. OPA が停止する

リクエストの評価中に OPA が利用できなくなりました。可用性を優先してリクエストを許可しますか？

<details>
<summary>回答</summary>

いいえ。Gateway はサービス障害を返し、外部の接続先へは接続しません。ポリシー判断を得られない、形式が不正、または利用できない場合は、通信を拒否します。[リクエストの流れ](../../how-it-works/request-journey/)を参照してください。

</details>

## 5. HTTPS の検査

HTTPS クライアントが Tobari 経由で `api.example.com` へ接続します。暗号化はどこで終わり、どこから再び始まりますか？

<details>
<summary>回答</summary>

透過的な検査により、Workspace のクライアントと Gateway の間に TLS 接続 A が作られ、Tobari CA を使って Gateway で終端します。通信が許可されると、Gateway は証明書を別途検証した TLS 接続 B を外部の接続先へ作ります。最後の区間を平文 HTTP で送るわけではありません。[HTTPS と TLS](../../how-it-works/https-and-tls/)を参照してください。

</details>

## 6. 同じ通信条件、異なる本文

二つのリクエストで Workspace Template、プロジェクト、スキーム、ホスト、ポート、メソッド、パスが同じですが、JSON 本文が異なります。別々の学習済みルールが必要ですか？

<details>
<summary>回答</summary>

いいえ。リクエスト本文は、学習済みルールを識別する判断項目ではありません。本文が違っても候補を分割せず、Tobari が本文の意味から権限を推測することもありません。[ポリシー学習](../../how-it-works/policy-learning/)を参照してください。

</details>

## 7. 退出と削除

エージェントが `exit` し、その後、利用者が `tobari workspace delete --id WORKSPACE_REF --confirm=delete` を実行しました。違いは何ですか？

<details>
<summary>回答</summary>

`exit` は接続中のシェルだけを終了し、論理 Workspace、ホーム、Workspace Template との結び付き、ランタイムリソース、ポリシーを残します。`workspace delete` は現在地に最も近い切断済み Workspace と、その Workspace が所有するホーム、コンテナ、ネットワーク、プリンシパル、状態を削除します。プロジェクトファイルと Workspace Template が所有する状態は残ります。[Workspace のライフサイクル](../../how-it-works/workspace-lifecycle/)を参照してください。

</details>

## 8. Workspace Template の切り替え

Workspace A は現在の default Workspace Template に結び付いた Context に属しています。利用者が `tobari template default set --id TEMPLATE_REF` を実行すると、A は新しい既定 Template へ移動しますか？

<details>
<summary>回答</summary>

いいえ。`template default set` は bare root entry と bare `status` が使う既定値だけを変えます。既存 Context の Workspace Template ID binding と Workspace の Context ID binding は変わりません。同じルートで別 Template にbindしたContextへ明示的にenterできます。[Workspace Template と Context](../../guides/workspace-templates-and-contexts/)を参照してください。

</details>

## 9. 同じ URL、別の Workspace

Workspace B が、Workspace A に許可されたものと同じホスト、メソッド、パスを使います。A のルールは B も自動的に許可しますか？

<details>
<summary>回答</summary>

いいえ。学習済みルールは安定した Workspace Template と、ホストが発行したプロジェクトプリンシパルにも結び付きます。B が同じ Workspace Template とプロジェクトの権限を持たない限り、別の一致するルールが必要です。[プロジェクトの識別](../../how-it-works/project-identity/)を参照してください。

</details>

## 10. ログインと通信許可

agent CLI のログインに成功しました。Workspace はすぐにすべての外部 API 経路を呼べますか？

<details>
<summary>回答</summary>

いいえ。ログインは agent CLI が Workspace home に保存します。それでも OPA は通常の HTTP 通信を判断し、完全一致の許可を要求します。ログインに成功しても、通信許可は広がりません。[認証](../../guides/authentication/)を参照してください。

</details>

## 11. Workspace が受け取るもの

Workspace home に agent CLI のログイン状態があります。これは Tobari のポリシー許可ですか？

<details>
<summary>回答</summary>

いいえ。Workspace home は agent CLI が自分のログイン状態を保管する場所です。Tobari は各 HTTP effect を独立に評価し、Gateway は OPA の許可後に元の値を転送します。[認証情報](../../how-it-works/credentials/)を参照してください。

</details>

## 12. 拒否されたリクエスト

agent CLI はログイン済みですが、OPA が HTTP 通信を拒否しました。認証情報の値は接続先へ届きますか？

<details>
<summary>回答</summary>

いいえ。認証情報の値は OPA と監査から除外され、拒否された場合は接続先への接続も作りません。[認証情報の安全性](../../security/credential-security/)を参照してください。

</details>

## 13. 不正な識別子のフォールバック

宣言済みのリクエストヘッダーに、認証情報の値が入っています。Gateway は OPA と監査へその値を渡しますか？

<details>
<summary>回答</summary>

いいえ。認証情報の値は OPA input と audit から除外され、通常の HTTP effect が許可された後だけ元の値が転送されます。[認証情報の安全性](../../security/credential-security/)を参照してください。

</details>

## 14. クラスターの完全削除

すべての Workspace を削除し、`tobari cluster down --purge` を実行しました。Workspace home と host-owned state も削除されますか？

<details>
<summary>回答</summary>

いいえ。`--purge` は、通常のクラスター停止に加えて、共有 Gateway CA と現在有効なポリシーバンドルのボリュームを削除します。Workspace home と host-owned state は残ります。外部サービスのログインは、そのサービスの CLI が管理します。[状態と復旧](../../how-it-works/state-and-recovery/)を参照してください。

</details>

## 15. プロジェクトファイルの保護

エージェントが作業対象のディレクトリ内にあるファイルを削除しました。Tobari の境界が破られたことになりますか？

<details>
<summary>回答</summary>

必ずしもそうではありません。immutable Workspace Template `source_access` が `read-only` または
`read-write` を選び、CLI omission default は `read-write` です。read-only でも host や別 Workspace Template
による live source 変更は観測します。[保証と制限](../../security/guarantees-and-limitations/)を参照してください。

</details>

## 16. 許可済みの接続先へ送るデータ

完全一致の接続先、メソッド、パスが許可されています。本文にソースコードや Workspace から読める秘密情報が含まれていないことを、Tobari は保証できますか？

<details>
<summary>回答</summary>

いいえ。本文は許可後にストリーミングし、通信の許可判断には使いません。許可された接続先は、Workspace が読み取り、送信したデータを受け取れます。[保証と制限](../../security/guarantees-and-limitations/)を参照してください。

</details>

## 17. 信頼する基盤の侵害

Gateway または Docker デーモンが侵害されました。文書化された Workspace の保証は維持されますか？

<details>
<summary>回答</summary>

いいえ。ホスト、カーネル、Docker、Gateway、OPA、host-owned lifecycle state、レビュー済みランタイム設定は、信頼する強制基盤です。agent CLI のログイン状態は Tobari の強制サービスではありません。侵害後まで保護するとは主張しません。[脅威モデル](../../security/threat-model/)を参照してください。

</details>

## 18. ランタイムイメージのコマンド

カスタムランタイムイメージが `CMD ["my-agent"]` を宣言し、そのプロセスが終了しました。`CMD` は論理 Workspace の寿命を決めますか？

<details>
<summary>回答</summary>

いいえ。Tobari は寿命を管理する固定コマンドを明示的に実行し、その子プロセスとして作業セッションを開きます。論理 Workspace と永続ホームは、一つのコンテナが失われた後も残ります。[ランタイムのカスタマイズ](../../guides/runtime-customization/)を参照してください。

</details>

## 19. CLI の正本

手書きのガイドと `tobari help` で引数の説明が違います。どちらが正しいですか？

<details>
<summary>回答</summary>

公開コマンドと呼び出し方法の正本は `cli.Catalog` です。コマンドの振り分け、型付きの引数、ヘルプ、役割、達成結果、復旧方法、生成されるサイトのリファレンスは、すべて Catalog から導出されます。この場合は、手書きのガイドを修正する必要があります。[CLI リファレンス](../../reference/cli/)を参照してください。

</details>

## 20. セキュリティ保証の根拠

「Workspace は OPA へ直接到達できず、OPA の拒否時には外部への通信が発生しない」と説明する場合、どの根拠が必要ですか？

<details>
<summary>回答</summary>

少なくとも、判断の基準となるアーキテクチャとセキュリティの契約、OPA が制御ネットワークだけに参加することを示す Compose とネットワークの実装・テスト、拒否時に外部の接続先へ接続しないことを示す Gateway テスト、外部への直接通信と制御ネットワークの分離を確認する統合テストが必要です。[検証の根拠](../../security/verification-evidence/)の対応表が、保証、強制箇所、テスト、ソースを結び付けます。

</details>

## 追加シナリオ：コピーされたログインファイル

プロセスが Workspace A の agent CLI ログインファイルを Workspace B へコピーし、同じホストへ送ります。重要な確認項目は何ですか？

<details>
<summary>回答</summary>

Gateway は、登録済みでカーネルが観測した Workspace の送信元エンドポイントから B の principal を導出します。ログインファイルをコピーしても B の identity や policy は変わらず、B の通常の HTTP method と path には OPA の許可が必要です。

</details>

## まとめ

各回答を、状態や権限を管理するコンポーネントへ結び付けられれば、現在のモデルを理解できています。ホストが identity を選び、Workspace が作業対象の権限を持ち、OPA がポリシーを判断し、Gateway が通信経路を強制し、agent CLI が Workspace home のログインを所有します。ライフサイクルコマンドは、それぞれが所有する状態だけを変更または削除します。

推測に頼った回答があれば、各回答のリンク先へ戻ってください。正確な引数、スキーマ、保存先、障害、バージョンは[リファレンス](../../reference/cli/)で確認できます。
