title: ツールの認証を設定する
description: 実際に使うツールを認証し、認証状態と外部通信の許可を別々に確認します。
---

前のステップで、Workspace 内からコーディングエージェントを実行できるようになりました。次に、そのツールが必要とする認証を設定します。

最初の一連の導入では Tobari の初期設定をそのまま使います。Context を作ったり切り替えたりする必要はありません。

ここで分けて考えるのは、次の二つです。

- **認証:** ツールがどのアカウントや認証情報を使うか
- **通信ポリシー:** このプロジェクトから、どの HTTP/HTTPS リクエストを送ってよいか

ログインに成功しても通信は自動で許可されません。逆に、通信を許可してもログインが完了するわけではありません。

## まず認証方法を選ぶ

### Tobari が対応する認証をホスト側で行う

Tobari が対応するプロバイダーでは、信頼するホストでログインし、認証情報の本体を Workspace の外に置けます。現在の組み込み経路には、OpenAI アカウントを使う Codex、Anthropic アカウントを使う Claude Code、GitHub、AWS、Datadog があります。所有者が追加したプロバイダーでは、保護された標準入力からのインポートを使う場合もあります。

共有クラスターを起動し、現在の状態を確認します。

```sh
tobari cluster up
tobari auth status
```

対話的にプロバイダーを選ぶ場合は、次を実行します。

```sh
tobari auth login
```

利用するプロバイダーが決まっていれば直接指定できます。

```sh
tobari auth login --provider openai
tobari auth login --provider anthropic
# or: github / aws / datadog
```

OpenAI の組み込みログインは、信頼するホストにあるレビュー対象の Codex CLI を使います。Anthropic の組み込みログインは、同じくホスト側の Claude Code を使います。このソーススナップショットで要求する版は Codex 0.146.0 と Claude Code 2.1.220 です。Workspace 内に入れたエージェントは、認証情報を取得するための信頼済みヘルパーとしては使いません。

ログイン後は、認証情報そのものを表示せずに状態を確認します。

```sh
tobari auth status
```

`auth status` は、プロバイダーの保存状態だけでなく、既存 Workspace に認証用の投影が反映されているかも観測します。**認証操作のたびに無条件で Workspace へ入り直す必要はありません。** 現在の Workspace に再入室が必要な場合は、`auth status` または認証操作の結果に、その対象と実行すべき操作が表示されます。表示された場合だけ、その案内に従ってください。

Codex では Workspace に置く `.codex/auth.json` に実トークンではなくプロジェクト用のハンドルを投影します。Claude Code では `CLAUDE_CODE_OAUTH_TOKEN` に同様のハンドルを渡します。Gateway は、許可された完全一致の通信に限って Auth Broker から実際の認証情報を取得します。

プロバイダーごとの取得方法、AWS や Datadog の動作、ログアウト、インポート、障害時の状態は[認証の詳細](../../guides/authentication/)で説明します。

### ツール自身に認証情報を管理させる

ツールが通常、自分のホームへログイン状態を保存する場合は、Workspace 内でそのツールの公式ログイン手順を使うこともできます。

```sh
cd /path/to/your/project
tobari

# Inside the Workspace
<agent-command> <its-login-command>
```

この方式では、そのツールが保存した認証情報を同じ Workspace 内の別プロセスから読める可能性があります。認証情報の本体を Workspace の外に置きたい場合は、Tobari が対応するプロバイダーでは前のホスト側経路を使ってください。

## 認証後の API 通信も、未許可なら止まる

認証済みのツールが、まだ許可していない HTTP/HTTPS 通信を送ると `policy_denied` になります。これはログイン失敗ではなく、通信ポリシーが別に働いている結果です。

Workspace のセッションを終了する必要はありません。エージェントをそのまま待たせ、**別の信頼するホスト端末**でレビューします。

```sh
tobari policy review
```

宛先、ポート、メソッド、パスを確認して必要な通信だけを許可し、元の Workspace セッションへ戻って新しいリクエストとして再実行します。許可操作が、拒否されたリクエストを自動再送することはありません。

## ここから通常の作業を始める

ここまでで、最初の導入に必要な一連の操作を体験しました。

1. `curl` で拒否 → レビュー → 許可 → 再実行を確認した
2. 実際に使うコーディングエージェントと開発ツールをランタイムへ追加した
3. そのツールに必要な認証を設定し、Workspace への反映状態を確認した

初期設定のまま通常の作業を始められます。エージェントが新しい外部通信を必要としたら、同じホスト側のポリシーレビューを使います。

仕組みを詳しく理解する場合は、[基本モデル](../../how-it-works/mental-model/)または[最初の拒否](../first-denial/)へ進んでください。

## あとで: 設定を分けたくなったら

用途ごとにランタイム、認証設定、ポリシーモードを分けたくなった段階で、Tobari の **Context** を使います。

必要になったときに[設定を分ける（Context）](../../guides/contexts/)を読んでください。Context は、最初の認証済みの実行を成功させるための前提知識ではありません。
