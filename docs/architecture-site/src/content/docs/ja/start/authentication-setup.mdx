---
title: ツールの認証を設定する
description: コーディングエージェントと実際に使う外部サービスを認証し、ログインと外部通信の許可を分けて扱います。
---

前のステップで、Workspace 内からエージェントの実行ファイルを使えるようになりました。認証はそれとは別です。実行ファイルが存在していても、アカウントの認証情報があるとは限りません。

最初の一連の導入では Tobari の初期設定をそのまま使います。別の設定を作ったり、切り替えたりする必要はありません。

ここで重要なのは、次の二つを分けることです。

- **認証:** ツールがどのアカウントや認証情報を使うか
- **通信ポリシー:** このプロジェクトから、特定の HTTP/HTTPS リクエストを送ってよいか

そのため、ログインに成功しても通信が自動で許可されることはありません。

## ツールに合う認証方法を選ぶ

最初に必要になる経路は、大きく二つです。

### ツール自身でログインする

コーディングエージェントや CLI が通常、自分自身でログイン状態を保存する場合は、Workspace に入り、そのツールの公式ログイン手順を実行します。

```sh
cd /path/to/your/project
tobari

# Workspace 内
<エージェントのコマンド> <そのツールのログインコマンド>
```

ツールが作ったログイン状態は、その Workspace に残ります。Workspace のホームは永続するため、通常の `exit` や作業コンテナの置き換えでは失われません。

ツール自身が認証情報を管理する前提で設計されており、その認証情報を Workspace 内に置くことが用途上問題ない場合は、この方法を使います。

### Tobari で対応する外部サービスへログインする

Tobari が対応するレビュー済みの外部サービスでは、信頼するホスト側でログインできます。認証情報の本体は Workspace の外側に置きます。

共有クラスターが動いていることを確認し、現在の認証状態を表示します。

```sh
tobari cluster up
tobari auth status
```

インストール済みの対応サービスから対話的に選ぶ場合は、次を実行します。

```sh
tobari auth login
```

GitHub を直接選ぶ場合は、次のように実行できます。

```sh
tobari auth login --provider github
```

認証後は、認証情報の本体を表示せずに状態を確認します。

```sh
tobari auth status
```

サービスごとの正確なログイン手順は異なります。GitHub、AWS、Datadog、認証情報のインポート、ログアウト、認証情報が通る詳細な経路は、[認証の詳細](../../guides/authentication/)で説明します。

## 認証設定を変更したら、プロジェクトへ入り直す

認証方式によって Workspace の環境へ反映される情報が変わる場合は、現在のセッションを抜けてから入り直します。

```sh
cd /path/to/your/project
tobari
```

その後、エージェントや認証済みの CLI を通常どおり起動します。

## 認証後の最初の API 通信も拒否されることがある

ログインに成功していても、まだ許可していない HTTP/HTTPS 通信をツールが送ると、Tobari は `policy_denied` を返します。

これは想定どおりです。クイックスタートで体験したのと同じ流れを使います。

1. Workspace から出る
2. 信頼するホストで `tobari policy review` を実行する
3. 宛先、ポート、メソッド、パスを確認する
4. 必要な通信条件だけを許可する
5. Workspace へ入り直し、新しいリクエストとして再実行する

認証が Gateway や OPA を迂回することはありません。また、通信を許可してもツールのログインが完了するわけではありません。

## ここから通常の作業を始められる

ここまでで、最初の一連の導入は完了です。

1. `curl` で拒否 → レビュー → 許可 → 再実行を体験した
2. 実際に使うコーディングエージェントと開発ツールをランタイムへ追加した
3. そのツールに必要な認証を設定した

初期設定のまま通常の作業を始められます。エージェントが新しい外部通信を必要としたら、すでに学んだホスト側のポリシーレビューを使います。

仕組みを詳しく理解する場合は、[基本モデル](../../how-it-works/mental-model/)または[最初の拒否](../first-denial/)へ進んでください。

## あとで: 設定を分ける必要が出たら

用途ごとにランタイム、認証設定、ポリシーモードを分けたくなった場合、Tobari ではそれらを **Context** という単位で分けられます。

必要になった段階で[設定を分ける（Context）](../../guides/contexts/)を読んでください。Context は、最初の認証済みの実行を成功させるための前提知識ではありません。
