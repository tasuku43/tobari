## このページで答える問い

**Tobari を一通り体験する最短の手順は何ですか？**

信頼するホストで共有 cluster を起動し、合成 project の Workspace へ入り、一つの request が拒否されるのを確認します。その exact effect をホストでレビューして許可し、再度 entry して意図的に再試行します。

このページを読み終えると、host-owned control command と Workspace 内で実行する command を区別し、`exit` 後に何が残るかを説明できるようになります。

前提: [インストール](../install/)を完了し、interactive terminal を使ってください。以下の command は現在の CLI Catalog と一致します。

## 1. 安全な合成プロジェクトを選ぶ

信頼するホストで実行します。

```sh
mkdir -p quickstart-example
cd quickstart-example
tobari cluster up
```

`/`、home directory 全体、Tobari の configuration/state directory を project root にしないでください。`cluster up` は共有する Gateway、OPA、Auth Broker を起動し、検証します。project Workspace は作成しません。

起動に失敗したら、`tobari doctor` と `tobari cluster status` を実行します。報告された host prerequisite を直してから `tobari cluster up` を再試行し、runtime topology を弱めないでください。

## 2. Workspace へ入る

引き続き合成 project directory から実行します。

```sh
tobari
```

root command は current/default Context に結び付いた Workspace を選択または作成し、interactive shell を開きます。project は read-write で mount されます。Workspace には proxy と CA の設定が渡されますが、Docker control や外部への direct route は渡されません。

Workspace **内** で次の合成 request を実行します。

```sh
curl -sS -w '\nhttp=%{http_code}\n' \
  -X PUT https://example.com/quickstart
```

初期化済み policy は、この exact effect を許可していません。Gateway は secret-free な `policy_denied` response を HTTP `403` で返し、信頼するホストで実行する review command を示します。承認も再試行も行いません。

Workspace から出ます。

```sh
exit
```

`exit` が終了するのは、この attached shell だけです。logical Workspace、persistent home、Context binding、runtime container、project network、learned-policy state は、再利用のため残ります。

## 3. 信頼するホストでレビューする

次を実行します。

```sh
tobari policy review --tail 100
```

TTY では request を選び、その Context、project、host、port、method、path を確認します。exact **allow** action を選びます。その確認によって complete aggregate policy がテストされ、新しい rule が atomically に有効化されます。

redirect または script から利用する flow では、review は読み取り専用です。JSON の opaque ID を変更せずコピーし、reference-bound action を呼び出します。

```sh
tobari policy review --tail 100 --format json
tobari policy allow --id <exact-pcy-id-from-policy-review>
```

placeholder は出力された値に置き換えてください。row の順番から ID を導出したり、request text から再構築したりしないでください。その effect を引き続き遮断する場合は、review UI の deny action または `tobari policy deny --id <exact-pcy-id-from-policy-review>` を使います。

## 4. Workspace へ入り直して、意図的に再試行する

```sh
tobari
curl -sS -w '\nhttp=%{http_code}\n' \
  -X PUT https://example.com/quickstart
exit
```

今回は Gateway が新しい request を active exact rule で評価します。HTTP result は upstream から返ります。Tobari が保証するのは `example.com` の特定の response code ではなく、この exact authorized effect が upstream path へ到達できることです。

別の method、path、Context、project が、この permission を自動的に継承することはありません。body は rule identity に含まれないため、body だけを変えても別の reviewable effect にはなりません。

## 5. 状態を確認して後片付けする

ホストで実行します。

```sh
tobari status
tobari list
tobari delete
tobari cluster down --purge
```

`status` と `list` は観測だけを行います。`delete` は最も近い detached Workspace を、persistent home と所有する runtime resource を含めて削除しますが、project file は決して削除しません。`cluster down` を実行するには、すべての Workspace が削除済みである必要があります。`--purge` を付けると、共有 CA volume と active policy-bundle volume も削除されます。Auth Broker の root key や encrypted Context vault は削除されず、provider logout でもありません。

attached session を意図的に終了させる場合に限り、`tobari delete --force` を使ってください。`--force` は attachment safety guard を迂回しますが、削除対象を広げません。

## 失敗時の動作

- `tty_required`: root の `tobari` entry には interactive terminal を使います。
- `workspace_selection_stale`: `tobari` をもう一度実行し、更新された候補から選びます。
- `image_not_found` または `incompatible_image`: `tobari context show` で Context を確認し、entry 前に compatible runtime を build または復元します。
- `policy_denied` (`403`): Workspace から出て、ホストでレビューします。retry loop を回さないでください。
- `credential_handle_invalid` (`403`): current projection を受け取るため、いったん出て再 entry します。別の Workspace の handle で代用しないでください。
- OPA、Gateway、Broker が unavailable: request は fail closed します。ホストから調整し、readiness を確認してから再試行します。
- `project_session_attached`: exit 後に `tobari delete` を実行します。終了させる意図がある場合だけ `--force` を使います。
- `cluster_not_empty`: `tobari list` で確認し、各 Workspace をその root/Context から削除してから `cluster down` を再実行します。

## 保証と制限

この workflow が示すのは、一つの exact HTTP effect と lifecycle path です。すべての tool が proxy/CA setting に従うこと、許可した宛先が安全であること、選択した project file が agent から保護されることまでは証明しません。host、Docker、enforcement service、reviewed image は引き続き信頼する前提です。

## まとめ

通常の loop は、entry、作業、拒否の受信、退出、ホストでのレビュー、exact decision の有効化、意図的な再試行です。authentication、policy authorization、Workspace deletion は別々の操作です。

## 理解を確認する

<details>
<summary><code>policy review</code> の前に Workspace を出るのはなぜですか？</summary>

policy review と mutation は、信頼するホスト側の境界に属するからです。Workspace には二つ目の Tobari control path がなく、自分の request を自分で承認できません。

</details>

<details>
<summary>最初の <code>exit</code> 後も残るものは何ですか？</summary>

logical Workspace、home、Context binding、runtime resource、principal registration、policy が残ります。終了するのは現在の shell/exec session だけです。

</details>

<details>
<summary>許可操作は、拒否された HTTP リクエストを再実行しますか？</summary>

いいえ。policy を検証して有効化します。再度 entry し、新しい request を明示的に送信します。

</details>
