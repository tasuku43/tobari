対応する macOS または Linux ホストで、公開リポジトリから `tobari` をビルドして配置します。共有サービスを起動する前に、Docker と実行環境の前提条件を `tobari doctor` で確認します。

以下の操作では Workspace を作成しません。CLI をビルドして配置し、ホスト側の条件を読み取り専用の診断で確認します。Tobari を初めて使う場合は、Docker コンテナだけで保護範囲が決まるわけではないため、先に[概要](../overview/)を読んでください。

## 対応する前提条件

次が必要です。

- Docker が対応するアーキテクチャの macOS または Linux
- Docker Engine 24 以降
- Docker Compose v2
- ソースビルドでは `go.mod` が宣言するバージョンの Go ツールチェーン
- リポジトリのビルドコマンドを実行する [Task](https://taskfile.dev/)
- レビュー済みの Gateway、Auth Broker、ランタイムイメージがローカルにない場合、それらを取得できるレジストリへのアクセス

Docker Desktop 固有の API は必要ありません。Colima、Lima ベースの Docker コンテキスト、標準的な Linux Docker Engine は、同じ Docker CLI アダプターを使います。VM 内のデーモンから、プロジェクトルートと Tobari の XDG 設定・状態パスの両方をバインドマウントできる必要があります。詳しくは [Colima と Lima](../../guides/colima-and-lima/)を参照してください。

## CLI をビルドし、実行する成果物を確認する

公開リポジトリをクローンし、まず通常の CLI をビルドします。

```sh
git clone https://github.com/tasuku43/tobari.git
cd tobari
task build
bin/tobari version --format json
```

`version` は、ソースコミット、ランタイム解決経路、必要な Gateway / Auth Broker API と、選択中の成果物が互換かどうかを表示します。共有サービスを起動する前に、この結果を確認してください。

**現在のソーススナップショットでは、ソースが要求する Gateway API 4 / Auth Broker API 3 に対して、通常ビルドが参照するレビュー済み公開ダイジェストは一世代前です。** 通常の `bin/tobari` は、この不一致を検出するとクラスター起動前に停止します。互換する公開ダイジェストが発行されるまで、現在のチェックアウト自体を試す場合は、リポジトリ所有の開発用成果物を明示的に使います。

```sh
task build:dev
TOBARI_SOURCE_ROOT=$PWD
tobari() { "$TOBARI_SOURCE_ROOT/bin/tobari-dev" "$@"; }
tobari version --format json
```

この関数は現在のホストシェルだけで `tobari` を `bin/tobari-dev` に結び付けます。以降のクイックスタートも同じシェルで実行してください。互換するレビュー済み成果物を選べる公開版では、この開発用の切り替えは不要です。

通常の公開バイナリを配置する場合、生成物は `bin/tobari` です。`PATH` 上のディレクトリへ配置できます。

```sh
install -m 0755 bin/tobari ~/.local/bin/tobari
```

Go の標準的なインストール方法も利用できます。

```sh
go install ./cmd/tobari
```

未検証で更新されるイメージタグへ置き換えて互換性検査を回避しないでください。共有サービスの識別情報は、レビュー済みの不変なダイジェストまたは明示的なリポジトリ開発経路から選ばれます。

## 何も起動せずに確認する

シェルが実行するファイルが、意図したものか確認します。

```sh
command -v tobari
tobari version --format json
```

続けて、利用予定のプロジェクトから読み取り専用のホスト診断を実行します。

```sh
tobari doctor
```

`doctor` は Docker、必要なパス、イメージ、ポリシー、プロバイダーマニフェスト、ルート鍵と Broker 状態、残留物を観測します。クラスターの起動、認証情報の修復、Workspace の作成、ポリシーの有効化は行いません。

現在のディレクトリ以外を調べる場合に限り、`tobari doctor --root PATH` を使ってください。対応する出力形式と障害コードを含む正確な CLI 仕様は、Catalog から生成される [CLI リファレンス](../../reference/cli/)にあります。

## インストールで変わること、変わらないこと

バイナリのビルドまたはコピーだけでは、次の処理は行われません。

- Gateway、OPA、Auth Broker の起動
- Workspace の作成またはプロジェクトのマウント
- 外部通信の許可ルールの作成
- プロバイダーへのログイン
- Docker を必要とする操作を実行する前の、バイナリへの Docker アクセスの付与

次の明示的な境界は `tobari cluster up` です。このコマンドは共有サービスを調整し、レビュー済みイメージを取得する場合があります。ルートの `tobari` 入室コマンドが、そのクラスターを暗黙に起動または修復することはありません。

## よくあるインストール失敗

| 観測したこと                     | 意味                                                                        | 安全な次の手順                                                                                |
| -------------------------------- | --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `tobari: command not found`      | バイナリのディレクトリが `PATH` にありません。                              | 正確なディレクトリを追加するか、`PATH` 上のディレクトリへバイナリを配置します。               |
| Docker/Compose 検査が失敗する    | 信頼するホストから、必要な Docker CLI の機能を利用できません。              | Docker インストールまたは選択中の Docker コンテキストを直し、`tobari doctor` を再実行します。 |
| イメージを利用できない           | Docker がレビュー済みサービスやランタイムの識別情報を調査・取得できません。 | レジストリと Docker の診断を確認し、ダイジェストを任意のタグへ置き換えないでください。        |
| バインドマウント元を利用できない | VM 上の Docker デーモンからホストパスが見えません。                         | プロジェクトと Tobari の XDG パスを共有し、`doctor` を再実行します。                          |
| 保管庫の横にルート鍵がない       | 既存の暗号化された状態を開けません。                                        | 元の鍵を復元します。Tobari は代替鍵を暗黙に生成しません。                                     |

診断失敗を、広範な Docker マウント、ホストホームのマウント、Workspace 内への Docker ソケットのマウントで回避しないでください。これらの回避策は信頼境界を変えてしまいます。

## 保証と制限

リポジトリのビルドは、Go バージョンと埋め込みサービスの識別情報を固定します。ソースとスナップショットの整合性検査、およびイメージ契約の検査が不整合を検出します。それでもインストールの完全性は、信頼するチェックアウト、ビルドホスト、Docker デーモン、イメージレジストリの経路に依存します。これらの信頼基盤が侵害された後まで、Tobari が自分自身を防御するとは主張しません。

## 理解を確認する

<details>
<summary><code>task build</code> は Gateway を起動したり Workspace を作成したりしますか？</summary>

いいえ。CLI をビルドするだけです。共有サービスは `tobari cluster up` でのみ起動し、Workspace の選択または作成はルートの `tobari` コマンドで行います。

</details>

<details>
<summary>VM のバインドマウントエラーを、ホストのホーム全体をマウントして解決すべきでないのはなぜですか？</summary>

作業対象のプロジェクトルートだけが、意図して読み書き可能にするマウントだからです。ホストホームを広くマウントすると境界外のファイルを公開し、文書化されたセキュリティ上の前提条件を無効にします。

</details>
