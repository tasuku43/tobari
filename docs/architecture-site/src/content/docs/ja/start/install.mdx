対応する macOS または Linux ホストへ、このリポジトリからビルドした `tobari` バイナリをインストールします。Docker Engine 24 以降と Docker Compose v2 を用意し、共有サービスを起動する前にバイナリを確認します。

以下の手順では、公開リポジトリから CLI をビルドし、Workspace を作成せずにホスト側の前提条件を確認します。Tobari を初めて使う場合は、Docker をセキュリティモデル全体だと誤解しないよう、先に[概要](../overview/)を読んでください。

## 対応する前提条件

次が必要です。

- Docker が対応するアーキテクチャの macOS または Linux
- Docker Engine 24 以降
- Docker Compose v2
- ソースビルドでは `go.mod` が宣言するバージョンの Go ツールチェーン
- リポジトリのビルドコマンドを実行する [Task](https://taskfile.dev/)
- レビュー済みの Gateway、Auth Broker、ランタイムイメージがローカルにない場合、それらを取得できるレジストリへのアクセス

Docker Desktop 固有の API は必要ありません。Colima、Lima ベースの Docker コンテキスト、標準的な Linux Docker Engine は、同じ Docker CLI アダプターを使います。VM 内のデーモンから、プロジェクトルートと Tobari の XDG 設定・状態パスの両方をバインドマウントできる必要があります。詳しくは [Colima と Lima](../../guides/colima-and-lima/)を参照してください。

## CLI をビルドして配置する

公開リポジトリをクローンし、宣言済みのビルドタスクを使います。

```sh
git clone https://github.com/tasuku43/tobari.git
cd tobari
task build
```

生成物は `bin/tobari` です。このリポジトリの `bin` ディレクトリを `PATH` に追加するか、すでに `PATH` に含まれるディレクトリへバイナリをインストールします。

```sh
install -m 0755 bin/tobari ~/.local/bin/tobari
```

Go の標準的なインストール方法も利用できます。

```sh
go install ./cmd/tobari
```

リポジトリが管理するランタイム権限の代わりに、未検証で更新されるイメージタグを取得しないでください。共有サービスの識別情報は、CLI に埋め込まれたレビュー済みの不変なダイジェストから選ばれます。

## 何も起動せずに確認する

シェルが実行するファイルが、意図したものか確認します。

```sh
command -v tobari
tobari version
```

続けて、利用予定のプロジェクトから読み取り専用のホスト診断を実行します。

```sh
tobari doctor
```

`doctor` は Docker、必要なパス、イメージ、ポリシー、プロバイダーマニフェスト、ルート鍵と Broker 状態、残留物を観測します。クラスターの起動、認証情報の修復、Workspace の作成、ポリシーの有効化は行いません。

現在のディレクトリ以外を調べる場合に限り、`tobari doctor --root PATH` を使ってください。対応 format と障害コードを含む正確な CLI 契約は、Catalog から生成される [CLI reference](../../reference/cli/)にあります。

## インストールで変わること、変わらないこと

バイナリのビルドまたはコピーだけでは、次の処理は行われません。

- Gateway、OPA、Auth Broker の起動
- Workspace の作成またはプロジェクトのマウント
- 外向き許可規則の作成
- プロバイダーへのログイン
- Docker を必要とする操作を実行する前の、バイナリへの Docker アクセスの付与

次の明示的な境界は `tobari cluster up` です。このコマンドは共有サービスを調整し、レビュー済みイメージを取得する場合があります。ルートの `tobari` 入室コマンドが、そのクラスターを暗黙に起動または修復することはありません。

## よくあるインストール失敗

| 観測したこと                  | 意味                                                                         | 安全な次の手順                                                                                |
| ----------------------------- | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `tobari: command not found`   | バイナリのディレクトリが `PATH` にありません。                               | 正確なディレクトリを追加するか、`PATH` 上のディレクトリへバイナリを配置します。               |
| Docker/Compose 検査が失敗する | 信頼するホストが必要な Docker CLI surface を利用できません。                 | Docker インストールまたは選択中の Docker コンテキストを直し、`tobari doctor` を再実行します。 |
| イメージを利用できない        | Docker がレビュー済みサービス/ランタイム識別情報を調査または取得できません。 | レジストリと Docker の診断を確認し、ダイジェストを任意の tag へ置き換えないでください。       |
| 結び付けパスを利用できない    | VM 上の Docker デーモンからホストパスが見えません。                          | プロジェクトと Tobari XDG パスを共有し、`doctor` を再実行します。                             |
| 保管庫の横にルート鍵がない    | 既存の暗号化された状態を開けません。                                         | 元の鍵を復元します。Tobari は代替鍵を暗黙に生成しません。                                     |

診断失敗を、広範な Docker マウント、ホストホームマウント、Workspace 内の Docker socket マウントで回避しないでください。これらの回避策は trust 境界を変えてしまいます。

## 保証と制限

リポジトリのビルドは Go バージョンと埋め込みサービス識別情報を固定します。ソース/snapshot 検査とイメージ契約検査が drift を検出します。それでもインストールの完全性は、信頼する checkout、ビルドホスト、Docker デーモン、イメージレジストリパスに依存します。これらの信頼基盤が侵害された後まで、Tobari が自分自身を防御するとは主張しません。

## まとめ

リポジトリからビルドした CLI を一つインストールし、信頼するホスト側の前提条件を確認します。共有サービス、Workspace、ポリシー、認証は、それぞれ別の明示的な操作です。

## 理解を確認する

<details>
<summary><code>タスクビルド</code> は Gateway を起動したり Workspace を作成したりしますか？</summary>

いいえ。CLI をビルドするだけです。共有サービスは `tobari cluster up` でのみ起動し、Workspace の選択または作成はルートの `tobari` コマンドで行います。

</details>

<details>
<summary>VM の結び付けエラーを、ホストのホーム全体のマウントで「直す」べきでないのはなぜですか？</summary>

選択したプロジェクトルートが、意図した書き込み可能なプロジェクトマウントだからです。ホストホームを広くマウントすると境界外のファイルを公開し、文書化されたセキュリティ precondition を無効にします。

</details>
