このガイドは、最初に動かし、その直後に実際の作業環境を作る順番にしています。クイックスタートでは `curl` だけを使って拒否とレビューを確認します。その後、コーディングエージェントとプロジェクト用ツールを入れたカスタムランタイムを準備してから、内部構成とセキュリティの詳細へ進みます。

標準ベースランタイムは、境界を確認し、カスタムイメージを作るための土台です。コーディングエージェントは含みません。クイックスタートだけを終えても、実際のリポジトリで使う準備が整ったとは限りません。

## 理解と導入を積み上げる五つの段階

1. **導入:** CLI とホスト側の前提条件を確認し、最初の Workspace を起動する。
2. **実用化:** 最初の拒否をレビューし、カスタムランタイムへエージェントと開発ツールを追加する。
3. **処理順序:** Workspace、Gateway、OPA、Auth Broker、接続先の間を一つの通信がどう進むか追う。
4. **認証・境界・復旧:** 認証情報、保証、対象外、障害後に残る状態を整理する。
5. **正確な仕様:** Catalog から生成される CLI、スキーマ、保存先、バージョン、障害コード、実装を参照する。

## 推奨する 10 ステップ

### 1. 範囲を確認してインストールする

[概要](../overview/)で、Tobari が制御する範囲と保護しない範囲を確認します。続けて[インストール](../install/)を行い、CLI、Docker、ホスト側の前提条件を確認します。

### 2. クイックスタートと最初のポリシーレビュー

[クイックスタート](../quickstart/)で、未許可の通信が拒否され、ホスト側のレビューを経て、完全一致の許可後に新しいリクエストが進むところまで実行します。

続けて[最初の拒否](../first-denial/)を読みます。レビューに残る情報、完全一致ルールが固定する条件、元のリクエストを自動再送しない理由を整理します。

### 3. カスタムランタイムを準備する

[カスタムランタイム](../../guides/runtime-customization/)で、現在の Context が管理する Dockerfile を作り、コーディングエージェントとプロジェクト用ツールを追加します。

ここまで終えると、実際のリポジトリへ入り、選んだエージェントを起動できる状態になります。エージェントの外部通信は、クイックスタートと同じレビュー手順で必要な範囲だけ許可します。

### 4. 五つの構成要素を整理する

[基本モデル](../../how-it-works/mental-model/)を読みます。Workspace、Gateway、OPA、Auth Broker、接続先が、それぞれ何を実行し、どの権限を持たないか確認します。

### 5. Workspace とコンテナの寿命を分ける

[Workspace のライフサイクル](../../how-it-works/workspace-lifecycle/)を読みます。`exit`、ランタイム変更によるコンテナ再作成、`delete`、`cluster down`、`cluster down --purge` の違いを整理します。

### 6. 一つの HTTP/HTTPS 通信を追う

[リクエストの流れ](../../how-it-works/request-journey/)で、Workspace から Gateway、OPA、接続先までを番号順に追います。

続けて[HTTPS と TLS](../../how-it-works/https-and-tls/)で、`CONNECT`、Workspace 側の TLS、ポリシー判断、接続先側の別の TLS セッションを一つの通信として確認します。

### 7. ポリシーがどう増えるか確認する

[ポリシー学習](../../how-it-works/policy-learning/)を読みます。保持された拒否情報、不透明な参照値、完全一致の許可または拒否、ポリシー全体の検証、明示的な集約を整理します。

### 8. 認証と通信許可を分ける

[認証情報](../../how-it-works/credentials/)と[認証](../../guides/authentication/)を読みます。外部サービスへのログインと、HTTP 通信の許可は別の権限です。

コーディングエージェント自身が Workspace のホームへ保存するログイン状態は、同じ Workspace 内のプロセスから隔離されません。Auth Broker が保護するのは、明示的に対応する Broker 経路を使った認証情報です。

### 9. 保証、対象外、復旧を確認する

[保証と制限](../../security/guarantees-and-limitations/)と[信頼境界](../../security/trust-boundaries/)で、各保証が成立する前提と、保護しない範囲を確認します。

[状態と復旧](../../how-it-works/state-and-recovery/)と[トラブルシューティング](../../guides/troubleshooting/)では、終了、コンテナ再作成、障害、削除の後に残る状態と、安全な復旧操作を整理します。

### 10. 理解度を確認する

[理解度チェック](../understanding-check/)に取り組みます。回答を開く前に、各シナリオでどのコンポーネントが判断し、どこで処理が止まり、何が保持されるかを自分の言葉で説明します。

## リファレンスを使うタイミング

基本的な操作と境界を理解した後で、正確な条件を調べるために使います。

- [CLI](../../reference/cli/) は `cli.Catalog` から生成されます。
- [ランタイムイメージ契約](../../reference/runtime-image-contract/)は、カスタムイメージに必要な利用者、ラベル、エントリーポイント、アーキテクチャなどを定義します。
- [設定と状態](../../reference/configuration-and-state/)は、保存場所、所有者、寿命を列挙します。
- [障害と復旧](../../reference/faults-and-recovery/)は、障害コードを安全な次の操作へ対応付けます。
- [コンポーネントのバージョン](../../reference/component-versions/)は、実際に選ばれる成果物を示します。

## 迷った場合の戻り先

- エージェントコマンドが見つからない場合は、[カスタムランタイム](../../guides/runtime-customization/)へ戻ります。
- Workspace と作業コンテナを同じものとして捉えていた場合は、[Workspace のライフサイクル](../../how-it-works/workspace-lifecycle/)へ戻ります。
- OPA が通信を転送するように見えた場合は、[リクエストの流れ](../../how-it-works/request-journey/)へ戻ります。
- ログインによってネットワーク権限も追加されるように見えた場合は、[認証情報](../../how-it-works/credentials/)へ戻ります。
- 「暗号化されている」ことが完全な保護を意味するように見えた場合は、[認証情報の安全性](../../security/credential-security/)へ戻ります。

## まとめ

最初にクイックスタートで境界を確認し、すぐにカスタムランタイムへエージェントと開発ツールを追加します。その後で、通信、認証、セキュリティ、復旧の詳細を読む順番です。これにより、仕組みを学ぶ前に実用上必要な環境を作りつつ、後から各権限の所有者を正確に説明できます。
