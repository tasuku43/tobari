この学習経路では、Tobari が利用者へ提供するものから始め、正確なセキュリティ境界と復旧方法までを順に理解します。一つのリクエストが通る経路を把握した後で、ライフサイクル、ポリシー、認証情報、障害時の動作を学び、最後にリファレンスへ進みます。

前提知識は必要ありません。各ステップでは説明を重複させず、詳しいページへ案内します。

## 理解の五つの段階

学習経路は、次の五段階に分かれています。

1. **目的:** Tobari が開発者のどの作業を支えるか。
2. **最小モデル:** Workspace → Gateway → Upstream と、Gateway の隣にある OPA と Auth Broker。
3. **シーケンス:** Workspace への入室、HTTP/HTTPS、拒否のレビュー、認証情報利用を時間順に理解する。
4. **境界と失敗:** 識別情報と状態を誰が所有するか、障害時に何が拒否されるか、Tobari が何を保護しないか。
5. **正確な仕様:** Catalog から生成される CLI、スキーマ、パス、バージョン、fault code、根拠。

## 推奨する 10 ステップ

### 1. Tobari とは何か

[概要](../overview/)を読みます。エージェントが受け取る権限と、引き続き制御される外向き許可対象を説明できるようにしてください。

### 2. 五つの要素で捉える全体像

[Mental model](../../how-it-works/mental-model/)を読みます。まずは Workspace、Gateway、OPA、Auth Broker、Upstream だけを学びます。

### 3. Workspace のライフサイクル

[Workspace lifecycle](../../how-it-works/workspace-lifecycle/)を読みます。`exit`、`delete`、ランタイム喪失、`cluster down`、`cluster down --purge` を区別します。

### 4. 一つの外向きリクエスト

[Request journey](../../how-it-works/request-journey/)を読みます。プリンシパルの導出、本文を含まない OPA 入力、許可/拒否、別の Upstream への接続、秘密情報を含まない監査を順に追います。

### 5. HTTPS と TLS

[HTTPS と TLS](../../how-it-works/https-and-tls/)を読みます。`CONNECT`、Workspace 側での TLS 終端、それとは別に検証される接続先側の TLS 接続を説明できるようにします。

### 6. ポリシーの拒否とレビュー

[ポリシー学習](../../how-it-works/policy-learning/)と[最初の拒否](../first-denial/)を読みます。完全一致規則、不透明な参照、全体が成功した場合だけ行う有効化、意図的な再試行を説明します。

### 7. 認証と認証情報

[Credential](../../how-it-works/credentials/)と[Authentication guide](../../guides/authentication/)を読みます。認証と通信許可を分けて考えてください。

### 8. セキュリティ上の保証と制限

[保証と制限](../../security/guarantees-and-limitations/)と[信頼境界](../../security/trust-boundaries/)を読みます。すべての保証について、成立する前提と、動作を実際に強制する場所を特定します。

### 9. 状態と復旧

[状態と復旧](../../how-it-works/state-and-recovery/)と[トラブルシューティング](../../guides/troubleshooting/)を読みます。破壊的に見える各コマンドが、実際には何を残すのかを説明します。

### 10. 最終理解確認

[理解確認](../understanding-check/)に取り組みます。シナリオの答えを声に出すか書いて説明してから、回答を開いてください。

## リファレンスを使うタイミング

Reference page は、モデルを理解した後の正確な運用上の問いに答えます。

- [CLI](../../reference/cli/) は `cli.Catalog` から生成されます。
- [設定と状態](../../reference/configuration-and-state/)は、正確な保存場所と寿命を列挙します。
- [プロバイダーマニフェスト](../../reference/provider-manifest/)は、所有者だけが変更できる厳格なスキーマ 1 と、レビュー済みの組み込みスキーマ 2 プランを区別します。
- [障害と復旧](../../reference/faults-and-recovery/)は、障害コードを安全な操作に対応付けます。
- [コンポーネントのバージョン](../../reference/component-versions/)は、リポジトリの正本から生成されます。

パスやスキーマの詳細を覚えるだけでは、所有権を理解したことにはなりません。たとえば `vault.enc` の保存場所を知っていても、OPA が拒否したときに、静的な認証情報の解決、AWS コンパニオンによる処理と署名、Datadog トークンの選択や更新が実行されない理由は説明できません。

## リンク先の説明が予想と違った場合

いったん止まり、直前の概念ページへ戻ってください。特に次の場合です。

- Workspace とコンテナが同じものに見えた場合は、[Workspace、Context、cluster](../../how-it-works/workspace-context-cluster/)へ戻る。
- ログインによってネットワーク権限が作られるように見えた場合は、[Credential](../../how-it-works/credentials/)へ戻る。
- OPA が traffic を転送するように見えた場合は、[Request journey](../../how-it-works/request-journey/)へ戻る。
- 「暗号化された」が完全なセキュリティ保証に聞こえた場合は、[Credential security](../../security/credential-security/)へ戻る。

## まとめ

Tobari は、利用者が得る結果、シーケンス、境界、仕様の順に学びます。この順序には意図があります。Docker の詳細、認証情報スキーマ、障害コードによって、各 step で誰が権限を持つのかが見えなくなるのを防ぎます。

## 理解を確認する

<details>
<summary>障害コードは分かっていても、リクエストが Gateway を通る理由を理解していない場合、まずどこを見ればよいですか？</summary>

障害参照より先に、mental モデルとリクエスト journey を読んでください。失敗した step をどのコンポーネントが所有するか分かっていれば、より安全に復旧できます。

</details>

<details>
<summary>完全なプロバイダーマニフェストスキーマは、いつ読むべきですか？</summary>

三つの認証情報パスと、認証/通信許可の分離を理解した後です。スキーマは段階 5 の参照 detail です。

</details>
