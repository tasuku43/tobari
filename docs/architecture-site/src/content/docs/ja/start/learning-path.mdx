この学習経路では、利用者が得る結果から始め、Tobari の正確なセキュリティ境界と復旧境界までを順に理解します。一つの request path を把握した後で、lifecycle、policy、credential、failure を加え、最後に reference material へ進みます。

前提知識は必要ありません。各ステップでは説明を重複させず、詳しいページへ案内します。

## 理解の五つの段階

学習経路は、次の五段階に分かれています。

1. **目的:** Tobari が開発者のどの task を完結させるか。
2. **最小モデル:** Workspace → Gateway → Upstream と、Gateway の隣にある OPA と Auth Broker。
3. **シーケンス:** Workspace entry、HTTP/HTTPS、拒否のレビュー、credential 利用を時間順に理解する。
4. **境界と失敗:** identity と state を誰が所有するか、何が fail closed するか、Tobari が何を保護しないか。
5. **正確な仕様:** Catalog から生成される CLI、schema、path、version、fault、evidence。

## 推奨する 10 ステップ

### 1. Tobari とは何か

[概要](../overview/)を読みます。agent が受け取る権限と、引き続き制御される outbound effect を説明できるようにしてください。

### 2. 五つの要素で捉える全体像

[Mental model](../../how-it-works/mental-model/)を読みます。まずは Workspace、Gateway、OPA、Auth Broker、Upstream だけを学びます。

### 3. Workspace のライフサイクル

[Workspace lifecycle](../../how-it-works/workspace-lifecycle/)を読みます。`exit`、`delete`、runtime loss、`cluster down`、`cluster down --purge` を区別します。

### 4. 一つの外向きリクエスト

[Request journey](../../how-it-works/request-journey/)を読みます。principal の導出、body を含まない OPA input、allow/deny、別の upstream connection、secret-free audit を順に追います。

### 5. HTTPS と TLS

[HTTPS と TLS](../../how-it-works/https-and-tls/)を読みます。`CONNECT`、Workspace 側 TLS の終端、それとは別に検証される upstream TLS connection を説明できるようにします。

### 6. ポリシーの拒否とレビュー

[Policy learning](../../how-it-works/policy-learning/)と[最初の拒否](../first-denial/)を読みます。exact rule、opaque reference、all-or-nothing activation、deliberate retry を説明します。

### 7. 認証と認証情報

[Credential](../../how-it-works/credentials/)と[Authentication guide](../../guides/authentication/)を読みます。authentication と authorization を分けて考えてください。

### 8. セキュリティ上の保証と制限

[保証と制限](../../security/guarantees-and-limitations/)と[信頼境界](../../security/trust-boundaries/)を読みます。すべての claim について、その precondition と信頼する enforcement point を特定します。

### 9. 状態と復旧

[State と復旧](../../how-it-works/state-and-recovery/)と[トラブルシューティング](../../guides/troubleshooting/)を読みます。破壊的に見える各 command が、実際には何を保持するかを説明します。

### 10. 最終理解確認

[理解確認](../understanding-check/)に取り組みます。シナリオの答えを声に出すか書いて説明してから、回答を開いてください。

## リファレンスを使うタイミング

Reference page は、model を理解した後の正確な運用上の問いに答えます。

- [CLI](../../reference/cli/) は `cli.Catalog` から生成されます。
- [Configuration と state](../../reference/configuration-and-state/)は、正確な store と lifetime を列挙します。
- [Provider manifest](../../reference/provider-manifest/)は、owner-controlled strict schema 1 と、reviewed built-in schema-2 plan を区別します。
- [Fault と復旧](../../reference/faults-and-recovery/)は、code を安全な action に対応付けます。
- [Component version](../../reference/component-versions/)は、repository の正本から生成されます。

path や schema の詳細を、ownership の理解の代わりにしないでください。たとえば `vault.enc` の保存場所を知っていても、OPA deny によって static resolution、AWS companion/signing work、Datadog token の選択または refresh が防がれる理由を説明したことにはなりません。

## リンク先の説明が予想と違った場合

いったん止まり、直前の概念ページへ戻ってください。特に次の場合です。

- Workspace と container が同じものに見えた場合は、[Workspace、Context、cluster](../../how-it-works/workspace-context-cluster/)へ戻る。
- login によって network permission が作られるように見えた場合は、[Credential](../../how-it-works/credentials/)へ戻る。
- OPA が traffic を forward するように見えた場合は、[Request journey](../../how-it-works/request-journey/)へ戻る。
- 「encrypted」が完全な security claim に聞こえた場合は、[Credential security](../../security/credential-security/)へ戻る。

## まとめ

Tobari は、利用者が得る結果、シーケンス、境界、仕様の順に学びます。この順序には意図があります。Docker の詳細、credential schema、fault code によって、各 step で誰が権限を持つのかが見えなくなるのを防ぎます。

</details>
