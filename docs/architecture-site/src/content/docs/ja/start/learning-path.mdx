このガイドでは、Tobari が何を制御するかを最初に確認し、その後で一つのリクエストが通る順序、Workspace の寿命、ポリシー、認証情報、障害時の動作へ進みます。最後に、CLI やスキーマなどの正確な仕様を参照できる状態を目指します。

前提知識は必要ありません。各ページは役割を分けているため、最初からすべての実装詳細を読む必要もありません。

## 理解を積み上げる五つの段階

1. **目的:** Tobari がどの権限をエージェントへ渡し、どの権限をホスト側に残すか。
2. **基本構成:** Workspace、Gateway、OPA、Auth Broker、外部の接続先が何を担当するか。
3. **処理順序:** Workspace への入室、HTTP/HTTPS 通信、拒否のレビュー、認証情報の利用が、どの順番で起きるか。
4. **境界と障害:** 識別情報と状態を誰が所有し、障害時に何が拒否され、何が保護対象外になるか。
5. **正確な仕様:** Catalog から生成される CLI、スキーマ、保存先、バージョン、障害コード、実装根拠。

## 推奨する 10 ステップ

### 1. Tobari が制御する範囲

[概要](../overview/)を読みます。エージェントが読み書きできる範囲と、ホスト側に残る権限を説明できる状態にします。

### 2. 五つの構成要素

[基本モデル](../../how-it-works/mental-model/)を読みます。まずは Workspace、Gateway、OPA、Auth Broker、外部の接続先の役割だけを押さえます。

### 3. Workspace のライフサイクル

[Workspace のライフサイクル](../../how-it-works/workspace-lifecycle/)を読みます。`exit`、`delete`、ランタイムの消失、`cluster down`、`cluster down --purge` の違いを整理します。

### 4. 一つの外部リクエスト

[リクエストの流れ](../../how-it-works/request-journey/)を読みます。プロジェクトの識別、本文を含まない OPA 入力、許可または拒否、接続先への別接続、秘密情報を含まない監査記録を順に追います。

### 5. HTTPS と TLS

[HTTPS と TLS](../../how-it-works/https-and-tls/)を読みます。`CONNECT`、Workspace 側の TLS 終端、それとは別に検証される接続先側の TLS 接続を区別します。

### 6. 拒否のレビューとポリシー変更

[ポリシー学習](../../how-it-works/policy-learning/)と[最初の拒否](../first-denial/)を読みます。完全一致ルール、不透明な参照値、ポリシー全体を検証してから有効化する仕組み、元のリクエストを自動再送しない理由を確認します。

### 7. 認証と認証情報

[認証情報](../../how-it-works/credentials/)と[認証](../../guides/authentication/)を読みます。外部サービスへの認証と、HTTP 通信の許可を別の権限として扱います。

### 8. セキュリティ上の保証と制限

[保証と制限](../../security/guarantees-and-limitations/)と[信頼境界](../../security/trust-boundaries/)を読みます。各保証について、成立する前提、強制するコンポーネント、保護しない範囲を確認します。

### 9. 状態と復旧

[状態と復旧](../../how-it-works/state-and-recovery/)と[トラブルシューティング](../../guides/troubleshooting/)を読みます。終了、削除、障害、再起動の後に残る状態と、安全な復旧操作を整理します。

### 10. 理解度を確認する

[理解度チェック](../understanding-check/)に取り組みます。回答を開く前に、各シナリオでどのコンポーネントが判断し、何が起きるかを自分の言葉で説明します。

## リファレンスを使うタイミング

リファレンスは、基本モデルを理解した後で、正確な運用条件を調べるために使います。

- [CLI](../../reference/cli/) は `cli.Catalog` から生成されます。
- [設定と状態](../../reference/configuration-and-state/)は、保存場所、所有者、寿命を列挙します。
- [プロバイダーマニフェスト](../../reference/provider-manifest/)は、所有者だけが変更できるスキーマ 1 と、レビュー済みの組み込みスキーマ 2 プランを区別します。
- [障害と復旧](../../reference/faults-and-recovery/)は、障害コードを安全な次の操作へ対応付けます。
- [コンポーネントのバージョン](../../reference/component-versions/)は、リポジトリの正本から生成されます。

保存先やスキーマを暗記しても、権限の所有者を理解したことにはなりません。たとえば `vault.enc` の場所を知っていても、OPA が通信を拒否した場合に、静的な認証情報の解決、AWS コンパニオンによる認証情報の取得と署名、Datadog トークンの選択や更新が実行されない理由までは説明できません。

## 説明が予想と違った場合

次のページへ進まず、役割が混ざった箇所まで戻ってください。

- Workspace とコンテナを同じものとして捉えていた場合は、[Workspace、Context、クラスター](../../how-it-works/workspace-context-cluster/)へ戻ります。
- ログインによってネットワーク権限も追加されるように見えた場合は、[認証情報](../../how-it-works/credentials/)へ戻ります。
- OPA が通信を転送するように見えた場合は、[リクエストの流れ](../../how-it-works/request-journey/)へ戻ります。
- 「暗号化されている」ことが完全な保護を意味するように見えた場合は、[認証情報の安全性](../../security/credential-security/)へ戻ります。

## まとめ

Tobari は、目的、構成要素、処理順序、境界、正確な仕様の順に読むと理解しやすくなります。Docker、認証情報スキーマ、障害コードなどの詳細を先に並べず、各段階で誰が権限を持つかを見失わない構成にしています。

## 理解を確認する

<details>
<summary>障害コードは分かっていても、リクエストが Gateway を通る理由を説明できない場合、まずどこを読めばよいですか？</summary>

[基本モデル](../../how-it-works/mental-model/)と[リクエストの流れ](../../how-it-works/request-journey/)です。失敗した段階をどのコンポーネントが所有するか分かっていれば、復旧操作を安全に選べます。

</details>

<details>
<summary>完全なプロバイダーマニフェストのスキーマは、いつ読むべきですか？</summary>

三つの認証情報の経路と、認証と通信許可が別の権限であることを理解した後です。スキーマは、正確な実装条件を調べる段階で参照します。

</details>
