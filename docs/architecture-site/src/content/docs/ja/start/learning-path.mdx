このガイドでは、最小限の通信制御を確認した後、実際に使うコーディングエージェントと開発ツールをランタイムへ追加します。その後で、アーキテクチャ、認証、セキュリティ境界、障害時の動作へ進みます。順番には理由があります。クイックスタートで確認できるのは通信制御であり、実作業に必要なエージェントの導入ではありません。

Tobari の事前知識は不要です。運用上の前提はインストールだけです。各ステップは、同じ説明をここへ重複させず、役割を分けたページへ案内します。

## 理解を積み上げる五つの段階

1. **目的と最初の確認:** Tobari が制御する範囲と、一つの拒否・ホスト側レビューを実際に確認する。
2. **実用できる環境:** コーディングエージェントと開発ツールを含む、Context 管理のランタイムを用意する。
3. **処理順序:** Workspace の寿命、HTTP/HTTPS、ポリシーレビュー、認証情報の利用を時間順に追う。
4. **境界と障害:** 識別情報と状態を誰が所有し、何が拒否され、何が保護対象外になるかを確認する。
5. **正確な仕様:** Catalog から生成される CLI、スキーマ、保存先、バージョン、障害コード、実装、テストを参照する。

## 推奨する 11 ステップ

### 1. Tobari が制御する範囲

[概要](../overview/)を読みます。エージェントへ渡す権限、信頼するホスト側に残す権限、Tobari が仲介する外部通信を説明できる状態にします。

### 2. 最小限のポリシー操作を試す

[クイックスタート](../quickstart/)を完了します。標準ベースランタイムの `curl` を使い、コーディングエージェントを選ぶ前に、拒否、ホスト側のレビュー、完全一致の許可、意図的な再実行を確認します。

クイックスタートではエージェントを導入も検証もしません。確認できるのはポリシーの一連の動作です。

### 3. 実際に使うランタイムを用意する

[カスタムランタイムを用意する](../runtime-setup/)へ進みます。現在の Context が管理する Dockerfile に、コーディングエージェント、その実行に必要な言語ランタイム、プロジェクトの開発ツールを追加します。ビルドと互換性検査を行い、実際のプロジェクト Workspace 内でエージェントのコマンドを確認します。

そのコマンドを実行できるまでは、実際のリポジトリでの作業へ進まないでください。標準ベースランタイムは意図的に最小限です。

### 4. 五つの構成要素を押さえる

[基本モデル](../../how-it-works/mental-model/)を読みます。まずは Workspace、Gateway、OPA、Auth Broker、外部の接続先の役割だけを整理します。

### 5. Workspace のライフサイクルを理解する

[Workspace のライフサイクル](../../how-it-works/workspace-lifecycle/)を読みます。`exit`、`delete`、ランタイムの置き換え、`cluster down`、`cluster down --purge` の違いを整理します。

### 6. 一つの外部リクエストを追う

[リクエストの流れ](../../how-it-works/request-journey/)と [HTTPS と TLS](../../how-it-works/https-and-tls/)を読みます。プロジェクトの識別、本文を含まない OPA 入力、許可または拒否、接続先への別接続、HTTPS の検査で使う二つの TLS セッションを順に追います。

### 7. ポリシーを意図的にレビューする

[ポリシー学習](../../how-it-works/policy-learning/)と[最初の拒否](../first-denial/)を読みます。完全一致ルール、不透明な参照値、ポリシー全体の検証後に有効化する仕組み、元のリクエストを自動再送しない理由を確認します。

### 8. 認証を別の権限として設定する

[認証情報](../../how-it-works/credentials/)と[認証](../../guides/authentication/)を読みます。ランタイムへ入れるツール、外部サービスへの認証、一つの HTTP 通信の許可を、それぞれ別の管理対象として扱います。

### 9. 保証と制限をセットで読む

[保証と制限](../../security/guarantees-and-limitations/)と[信頼境界](../../security/trust-boundaries/)を読みます。各保証について、成立する前提、強制するコンポーネント、障害時の動作、保護しない範囲を確認します。

### 10. 状態と復旧を理解する

[状態と復旧](../../how-it-works/state-and-recovery/)と[トラブルシューティング](../../guides/troubleshooting/)を読みます。シェルの終了、ランタイムの置き換え、サービス障害、Workspace の削除、クラスターの削除後に残る状態を整理します。

### 11. 理解度を確認する

[理解度チェック](../understanding-check/)に取り組みます。回答を開く前に、各シナリオでどのコンポーネントが判断し、何が起きるかを自分の言葉で説明します。

## リファレンスを使うタイミング

リファレンスは、基本モデルを理解した後で、正確な運用条件を調べるために使います。

- [CLI](../../reference/cli/) は `cli.Catalog` から生成されます。
- [ランタイムイメージ契約](../../reference/runtime-image-contract/)は、必須ラベル、ユーザー、エントリーポイント、ビルド、選択の正確な規則を定義します。
- [設定と状態](../../reference/configuration-and-state/)は、保存場所、所有者、寿命を列挙します。
- [プロバイダーマニフェスト](../../reference/provider-manifest/)は、所有者だけが変更できるスキーマ 1 と、レビュー済みの組み込みスキーマ 2 プランを区別します。
- [障害と復旧](../../reference/faults-and-recovery/)は、障害コードを安全な次の操作へ対応付けます。
- [コンポーネントのバージョン](../../reference/component-versions/)は、リポジトリの正本から生成されます。

保存先、スキーマ、イメージラベルを知っていても、権限の所有者を理解したことにはなりません。たとえばランタイム Dockerfile の場所を知っていても、互換性検査の成功後だけ Context の選択が変わる理由や、既存 Workspace が次の入室時にその選択を反映する理由までは説明できません。

## まとめ

実用上の順番は、ポリシーの一連の動作を確認し、利用可能なランタイムを用意し、実際の Workspace 内でエージェントを検証した後に、アーキテクチャ、認証、セキュリティ境界、復旧へ進む形です。`curl` が成功しただけで、コーディングエージェントを利用できる環境まで完成したと誤解しないための順番です。

## 理解を確認する

<details>
<summary>なぜクイックスタートの直後にランタイムを用意するのですか？</summary>

クイックスタートは `curl` で通信制御を確認しますが、標準ベースランタイムにはコーディングエージェントが入りません。現在の Context が、エージェントと必要な開発ツールを含む互換イメージを選択して初めて、実際のリポジトリで作業できます。

</details>

<details>
<summary>イメージへエージェントを追加すると、認証や外部通信の許可も増えますか？</summary>

いいえ。ランタイムに入れるツール、外部サービスの認証、HTTP 通信の許可は別々に管理します。

</details>
