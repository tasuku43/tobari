このリファレンスでは、Tobari のバージョン付き JSON 公開面と厳密な境界を一覧にします。公開 CLI
レポート、永続化するマニフェスト、Gateway のポリシー入力、監査行は、関連するオブジェクトを
記述していても別の契約です。agent CLI のログイン形式は Tobari の公開契約ではありません。

各スキーマは一つの公開面に属します。スキーマ番号はその公開面にだけ属し、現在の公開 CLI
には V1 から V4 のエンベロープがあります。構造化エラーは V2 です。それぞれの公開面では、
担当するパーサー、Catalog の項目、プロトコルの実装が正本です。

## 「スキーマ」が必ずしも JSON Schema を意味しない

Tobari は多くの JSON 契約で、明示的な `schema_version` フィールドと厳密な読み取り処理を
使います。ただし、すべての公開面に正式な JSON Schema 文書があるわけではありません。
ランタイムの入力は Go のパーサーと検証器で検証し、正本となる合成フィクスチャを検査台帳に
記録します。フィクスチャのダイジェストが証明するのはフィクスチャ自体の識別情報であり、
汎用 JSON Schema ではありません。

公開 CLI 出力では、Catalog が JSON エンベロープとスキーマバージョンを宣言します。契約
テストはレンダラーを実行し、生成した `schema_version` を Catalog と比較します。
永続化文書と内部文書では、担当する Domain または Infrastructure の読み取り処理が厳密な
検証を定義します。

フィールドの正確な内容、任意項目、コレクションの対象範囲、出力形式は
[CLI リファレンス](../cli/)で生成します。オブジェクトの名前が同じでも、別のエンベロープの
フィールドを推測してはいけません。

### active authority の契約境界

永続化する immutable authority object と公開する task projection は別の契約です。

```text
Persisted active authority
  authority/{templates,contexts,policy-memory,workspaces}/<id>/<revision>.json
  authority/generations/<digest>.json + authority/active.json
  complete atomic generation schema 1

CLI presentation
  {"schema_version": 1, "template": ...}
  task-owned final Template report schema 1
```

公開する Template、Context、Workspace、entry の結果は task-owned projection であり、
active generation が選択する完全なバイト列ではありません。

## ホストに永続化する契約

| 状態                                     | 現在の契約       |
| ---------------------------------------- | ---------------- |
| active authority generation              | スキーマ 1       |
| managed Runtime library／lifecycle state | スキーマ 1       |
| agent CLI の Context Home                | ツール固有の形式 |
| ベース Runtime メタデータ                | スキーマ 1       |

読み取り処理は、担当する契約に従って、形式不正、上限超過、安全でない状態、未対応の状態を
拒否します。厳密さは公開面ごとに異なります。すべての JSON 読み取り処理が未知のフィールド
を同じように扱うとは限りません。final authority と重要な Runtime 状態では、明示的な
fail-closed 検証を使います。

旧 authority を暗黙には採用しません。通常の読み取りは有効化せずに旧形式を分類し、
明示的かつ plan-bound な `installation migration plan` と
`installation migration apply` の手順を案内して fail closed します。

## Gateway、OPA、監査の契約

| 境界                                            |       現在の契約 | 重要な内容規則                                                                                         |
| ----------------------------------------------- | ---------------: | ------------------------------------------------------------------------------------------------------ |
| Gateway のリクエスト境界                        |       スキーマ 1 | final Context／Workspace とホスト由来の principal、正規化した HTTP 属性。認証情報の値は含まない        |
| Gateway → OPA の判断入力                        |       スキーマ 1 | ホストから導出したプリンシパルと、正規化した HTTP 属性。本文とクライアントの秘密ヘッダーは含まない     |
| Template policy／Policy Memory 入力             |       スキーマ 1 | 公開前に、final Context が所有する厳密な source を検証                                                 |
| Gateway の監査行                                |       スキーマ 1 | 秘密情報を含まない、正規化済みの判断根拠                                                               |
| 学習可能な拒否に対する Gateway の案内レスポンス |       スキーマ 1 | 固定したホストレビュー案内。候補 ID、クエリー、本文、秘密情報は含まない                                |
| agent CLI のログイン値                          | ツール固有の形式 | Context Home に保存され sibling Workspace が共有する。Gateway が許可後に転送し、OPA と監査には含めない |

OPA の出力は Gateway が受け取る判断結果です。OPA 自身は接続先へ接続しません。
不正な、または利用できないポリシー応答は、接続先へ接続する前に安全側に倒して拒否します。

agent CLI のログイン形式は各ツールが管理し、Tobari の公開 JSON 契約には含めません。
Gateway と OPA の公開境界は、正規化した非秘密の判断入力と監査行です。

## 読み取り側の厳密な version 規則

- 完全一致のエンベロープと `schema_version` で動作を選ぶ
- 未知のバージョンは未対応として扱い、既知の最新形式へ黙って変換しない
- 契約上重要な「存在しない」と、明示的な空、0、false の違いを保持する
- 不透明な参照と識別子は完全一致のバイト列として扱い、デコード、正規化、切り詰め、
  再構築をしない
- ラベル、配列の順番、近さ、人向けのインデントから識別情報や関係を推論しない
- サポート対象の公開 CLI 結果の代わりに、内部の状態ファイルを読まない

## 障害と制限

スキーマの不一致は契約違反です。推測して続行してはいけません。
候補の検証に失敗した場合、既知の正しいポリシーとランタイム選択を保持します。不正な
不正な CLI フレームと、形式が Tobari に見える不正な識別子は安全側に倒して拒否します。公開
エラーでは、URL、レスポンス本文、認証情報を含む可能性がある接続先由来の文字列を
除外します。

このページは現在の契約を記録しますが、すべての内部形式を公開拡張点とする
約束ではありません。サポート対象の公開境界は、Catalog と、明示的に文書化した外部
契約だけです。

## まとめ

スキーマの識別は境界ごとに独立しています。別の文書を規定するのは、共有する番号ではなく、
対象に対応した読み取り処理とテストです。

## 理解を確認する

スキーマ番号だけでは、それが適用される公開面を特定できません。

<details>
  <summary>ユーザーポリシーで別の evaluator schema を選べますか？</summary>
  いいえ。ユーザーポリシーは canonical typed data です。Tobari が固定 evaluator
  を選択・検証し、公開前に候補全体をテストします。
</details>

<details>
  <summary>利用側は不透明な参照をデコードして ID を復元できますか？</summary>
  いいえ。その種類の参照を受け取るコマンドへ、検証済みの値を変更せずに
  渡す必要があります。
</details>
