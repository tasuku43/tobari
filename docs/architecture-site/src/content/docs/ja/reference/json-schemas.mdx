このリファレンスでは、Tobari の V1 JSON 公開面と厳密な境界を一覧にします。公開 CLI
レポート、永続化するマニフェスト、Gateway のポリシー入力、
監査行、Broker のソケットフレームは、関連するオブジェクトを記述していても別の契約です。

各スキーマは一つの公開面に属します。初回公開前の Tobari 所有の公開面はすべて V1
です。それぞれの公開面では、担当するパーサー、Catalog の項目、プロトコルの実装が
正本です。

## 「スキーマ」が必ずしも JSON Schema を意味しない

Tobari は多くの JSON 契約で、明示的な `schema_version` フィールドと厳密な読み取り処理を
使います。ただし、すべての公開面に正式な JSON Schema 文書があるわけではありません。
プロバイダーマニフェスト v1 は Go のパーサーと検証器で検証し、正本となる合成フィクスチャを
検査台帳に記録します。フィクスチャのダイジェストが証明するのはフィクスチャ自体の識別情報で
あり、汎用 JSON Schema ではありません。

公開 CLI 出力では、Catalog が JSON エンベロープとスキーマバージョンを宣言します。契約
テストはレンダラーを実行し、生成した `schema_version` を Catalog と比較します。
永続化文書と内部文書では、担当する Domain または Infrastructure の読み取り処理が厳密な
検証を定義します。

フィールドの正確な内容、任意項目、コレクションの対象範囲、出力形式は
[CLI リファレンス](../cli/)で生成します。オブジェクトの名前が同じでも、別のエンベロープの
フィールドを推測してはいけません。

### Context の契約境界

どちらも V1 ですが、契約は別です。

```text
Host configuration
  contexts/<name>/context.json
  Context manifest schema 1

CLI presentation
  {"schema_version": 1, "context": ...}
  public Context report schema 1
```

レポートには、タスクが管理するランタイム、クラスター、完全なシェル設定、秘密情報を
除いた認証状態の解釈が加わります。`context.json` に保存するバイト列そのものでは
ありません。

| Workspace 認証ファイル登録簿                       | スキーマ 1                   |
| ベースランタイムメタデータ                         | スキーマ 1                   |

読み取り処理は、担当する契約に従って、形式不正、上限超過、安全でない状態、未対応の状態を
拒否します。厳密さは公開面ごとに異なります。すべての JSON 読み取り処理が未知のフィールド
を同じように扱うとは限りません。プロバイダー文書、プリンシパルの状態、Broker フレーム、
重要なランタイム状態では、明示的な fail-closed 検証を使います。

初回公開前の移行処理や互換読み取りはありません。V1 以外はすべて未対応として拒否し、
開発中の状態は削除して作り直します。

## Gateway、OPA、監査、Auth Broker の契約

| 境界                                            |           現在の契約 | 重要な内容規則                                                                                         |
| ----------------------------------------------- | -------------------: | ------------------------------------------------------------------------------------------------------ |
| Gateway の認証設定                              |           スキーマ 1 | Context を認識する managed 方式の投影。パスとメタデータは含むが、ポリシー権限は含まない                |
| Gateway → OPA の判断入力                        |           スキーマ 1 | ホストから導出したプリンシパルと、正規化した HTTP 属性。本文とクライアントの秘密ヘッダーは含まない     |
| Guided/Advanced のソースポリシー入力            |           スキーマ 1 | 集約生成処理が、アクティベーション前に厳密な V1 ソースを検証                                           |
| Gateway の監査行                                |           スキーマ 1 | 秘密情報を含まない、正規化済みの判断根拠                                                               |
| 学習可能な拒否に対する Gateway の案内レスポンス |           スキーマ 1 | 固定したホストレビュー案内。候補 ID、クエリー、本文、秘密情報は含まない                                |
| Broker 制御プロトコル                           |           スキーマ 1 | ホスト制御用 Unix ソケット上の、上限付き改行区切り JSON                                                |
| Broker runtime protocol                         |             schema 1 | introspection は non-secret。allow 後の same-revision static resolve 一回が Gateway Unix socket を使用 |
| Workspace の Auth Broker ハンドル               | ハンドルバージョン 1 | 不透明な `tobari-h1_…`。権限を得るためにデコードしない                                                 |

OPA の出力は Gateway が受け取る判断結果です。OPA 自身は接続先へ接続しません。
不正な、または利用できないポリシー応答は、接続先へ接続する前に安全側に倒して拒否します。

二つの Broker プロトコルは、上限付きの改行区切り JSON フレームを使います。
解錠と認証情報のインポートでは、制御フレームの後に、宣言済みの長さ制限を持つ
生のペイロードを運びます。秘密情報を含むそのバイト列は JSON メタデータではありません。

## 読み取り側の厳密な V1 規則

- 完全一致のエンベロープと `schema_version` で動作を選ぶ
- 未知のバージョンは未対応として扱い、既知の最新形式へ黙って変換しない
- 契約上重要な「存在しない」と、明示的な空、0、false の違いを保持する
- 不透明な参照とハンドルは完全一致のバイト列として扱い、デコード、正規化、切り詰め、
  再構築をしない
- ラベル、配列の順番、近さ、人向けのインデントから識別情報や関係を推論しない
- サポート対象の公開 CLI 結果の代わりに、内部の状態ファイルを読まない

## 障害と制限

スキーマの不一致は契約違反です。推測して続行してはいけません。
候補の検証に失敗した場合、既知の正しいポリシーとランタイム選択を保持します。不正な
Broker フレームと、形式が Tobari に見える不正なハンドルは安全側に倒して拒否します。公開
エラーでは、URL、レスポンス本文、認証情報を含む可能性がある接続先由来の文字列を
除外します。

このページは現在の契約を記録しますが、すべての内部形式を公開拡張点とする
約束ではありません。サポート対象の公開境界は、Catalog と、明示的に文書化した外部
契約だけです。

## まとめ

初回公開前の Tobari 所有の公開面はすべて V1 ですが、契約の識別は境界ごとに独立して
います。別の文書を規定するのは、共有する番号ではなく、対象に対応した読み取り処理と
テストです。

## 理解を確認する

スキーマ番号だけでは、それが適用される公開面を特定できません。

<details>
  <summary>
    <code>synthetic-provider-v1.json</code> は正式な JSON Schema ですか？
  </summary>
  いいえ。厳密な Go パーサー、検証、正規化、テストとともに使う
  正規の合成フィクスチャです。
</details>

<details>
  <summary>Advanced ポリシーで V1 以外のスキーマを使えますか？</summary>
  いいえ。集約生成処理はソースとランタイム入力の両方に厳密な V1
  を要求し、Context ごとに分離した候補全体を有効化前にテストします。
</details>

<details>
  <summary>利用側は不透明な参照をデコードして ID を復元できますか？</summary>
  いいえ。その種類の参照を受け取るコマンドへ、検証済みの値を変更せずに
  渡す必要があります。
</details>
