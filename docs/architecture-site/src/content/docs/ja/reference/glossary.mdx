この用語集では、Tobari の実行、ネットワーク、ポリシー、認証、状態、CLI 契約で
使う語を定義します。論理的な実行状態、ホスト管理の設定、共有の実施基盤、ランタイム
コンテナ、認証、通信許可は、管理主体とセキュリティ上の意味が異なるため、別の名前を
使います。

最初の導入には[五つの要素からなるメンタルモデル](../../how-it-works/mental-model/)
を使ってください。正確な用語、または似た用語の区別が必要になったときに、この
用語集へ戻れます。

## 実行と管理主体

### Tobari

製品、実行ファイル、所有主体を表す名前です。Tobari は Workspace と、一つの
インストール内で共有するサービスを準備、制御、管理します。

### Workspace

正規化したプロジェクトルートと安定した Context ID の組み合わせで選ばれる、再利用可能な
隔離リソースです。安定した論理レコード、選択したプロジェクトルート、Context との結び付き、
独立したホーム、調整可能なランタイムリソースで構成されます。「Workspace を出る」
操作はセッションを終了するだけで、論理 Workspace は削除しません。

### プロジェクトルート（project root）

現在の作業ディレクトリから選び、immutable Context `source_access`（CLI default は
`read-write`）に従って Workspace へ mount する正規の
ホストディレクトリです。Tobari は、このルートを読み書きする権限を意図的に Workspace
へ委ねます。Workspace 内のプロセスからファイルを守るスナップショットやオーバーレイは
提供しません。

### Context

安定した不透明な UUIDv7 ID を持つ、ホスト管理の論理実行設定です。エージェントプロファイル、
ランタイムイメージ、ポリシーの方式とソース、許可済みのシェル設定、プロバイダー設定、
独立した暗号化認証情報保管庫を選びます。Workspace は一つの Context へ恒久的に
結び付きます。

### 現在の Context（current Context）

Context セレクターを省略した呼び出しに使うデフォルト Context です。切り替えると、
以後のデフォルト選択だけが変わります。既存 Workspace と Context の恒久的な結び付き
は書き換えず、リクエストの権限にもなりません。

### クラスター（cluster）

一つのインストール内で共有する Gateway、OPA、ロック状態の Auth Broker、共有ネットワーク、
CA ボリューム、集約済みの投影データの集合です。Context がポリシーと認証情報の範囲を
決め、クラスターが読み込み済みの全 Context に対する制御を実施します。

### ランタイムイメージ（runtime image）

Workspace のツールとルートファイルシステムを提供する OCI イメージです。ランタイム API `1`、
`tobari` ユーザー、固定された寿命管理機能、エントリーポイントを備える必要があります。
マウント、ネットワーク、ポリシー、認証情報、論理 Workspace の寿命は決めません。

### 作業コンテナ（work container）

一つの Workspace を現在実体化している Docker コンテナです。イメージや runtime-spec に
差分があれば、Tobari は論理 Workspace、プロジェクトルート、ホームを保ったまま
再作成できます。

### 接続中のセッション（attached session）

子の `docker exec` プロセスを通じて動く、一時的なシェルまたは完全一致コマンド
です。`exit` はこのプロセスだけを終了します。接続状態は Workspace のライフサイクル
状態として永続化されません。

### Workspace ホーム（Workspace home）

一つの Workspace が所有する、独立した書き込み可能なホームです。ツール自身の
ログイン状態や、投影された Auth Broker のハンドルが置かれる場合があります。
セッションの終了後や作業コンテナの再作成後も残り、Workspace の `delete` で
削除されます。

## リクエストの制御

### Gateway

Workspace から透過的に送られた HTTP 通信を受け取り、必要に応じて Workspace 側の TLS を終端し、
ホスト発行の Workspace プリンシパルを導出するコンポーネントです。判断入力から秘密
情報を除き、OPA へ一度問い合わせます。許可された場合だけ接続先への別の接続を開き、
本文をストリーミングします。判断を実施するのは Gateway です。OPA は通信を転送しません。

### OPA

Open Policy Agent です。正規化して本文を除いた一つの HTTP 判断入力を、読み込み済みの
集約した Rego とデータの投影に対して評価し、判断を返します。Workspace への
ネットワーク経路を持たず、接続先へ接続せず、Auth Broker 管理の秘密情報を
解決しません。

### 接続先（upstream）

許可されたリクエストの最終接続先となる HTTP/HTTPS サービスです。HTTPS では、
Workspace 側の TLS 接続を Gateway で終端した後、Gateway がこのサービスへ独立した
検証済み TLS 接続を作ります。

### HTTP 操作（HTTP effect）

ポリシーが許可または拒否する、正規化済みの HTTP 操作です。Context ID、Workspace
ID、ホスト、ポート、HTTP メソッド、パスと、範囲を限定した秘密情報を含まないプロトコル
メタデータで構成されます。リクエスト本文は識別項目ではなく、ポリシー候補を分けません。
Workspace identity を運ぶ内部スキーマのフィールド名は `project_id` のままです。

### TLS 接続 A（TLS connection A）

透過的な検査により、Workspace から Gateway へ張る HTTPS 接続です。Gateway は
Workspace が信頼する Tobari CA に連なる証明書を提示し、ポリシーに必要な HTTP
属性を復号します。

### TLS 接続 B（TLS connection B）

Gateway から接続先へ張る、独立した検証済み HTTPS 接続です。接続 A を
検査しても、Gateway が最終 HTTPS 接続先へ平文 HTTP を送るわけではありません。

### Tobari CA

Gateway が Workspace 側の TLS を終端できるよう、公開証明書を Workspace の
信頼バンドルへ組み込む認証局です。CA を信頼することは通信の前提であり、許可規則
ではありません。証明書ピンニングを行うクライアントは
Gateway を迂回せず、接続に失敗します。

### 安全側に倒して拒否（fail closed）

必要な識別情報、ポリシー、Broker、スキーマ、状態、管理主体の根拠が存在しない、
不正、曖昧、利用不能な場合に、外部通信を拒否することです。リクエストの経路では、
未許可の接続先へ接続しないことを意味します。

## Workspace 識別

### Workspace ID

一つの Workspace にホストが発行する、安定した不透明な ID です。プロジェクトルート
とは異なります。Workspace のヘッダーに書かれた値は、権限の根拠として受け入れません。
内部の永続化と実施プロトコルでは、同じ値にスキーマ V1 の `project_id` を使い続けます。

### Context ID

Context にホストが発行する、安定した UUIDv7 識別情報です。変更可能な表示名
や現在の Context を示すマーカーとは別物です。

### Workspace プリンシパル（Workspace principal）

Workspace 専用ネットワーク上でカーネルが観測した完全一致の送信元エンドポイントから Gateway が導出する、
安定した Context ID と Workspace ID の信頼できる組です。ポリシーと Auth Broker の
ハンドルを使える範囲を決めます。内部実装とスキーマ V1 プロトコルで必要な箇所では、
`project principal` という名前を維持します。

### プリンシパル登録簿（principal registry）

Workspace の送信元エンドポイント、Gateway のエンドポイント、専用ネットワークを、Context と Workspace の識別情報
へ完全一致で対応付ける、ホスト管理のスキーマ 1 対応表です。Gateway にはこの
ディレクトリだけを読み取り専用で渡します。呼び出し元が指定した `X-Tobari-*` の
文字列は、この対応付けの代わりになりません。

### Workspace 専用ネットワーク（dedicated Workspace network）

一つの Workspace が所有する Docker 内部ネットワークです。作業コンテナと
Gateway インターフェース一つだけが参加します。サポート対象の構成では、Workspace は
OPA、Auth Broker、別 Workspace、通常の外部ネットワークへ参加できません。

## ポリシー

### 既定の拒否（baseline deny）

一致する許可規則がない場合の、デフォルトのポリシー結果です。それ以外は有効な
リクエストについて、学習可能で秘密情報を含まない根拠を生成できます。学習済みの
完全一致拒否エントリーとは異なります。

### 学習済み許可（learned allow）

Context、Workspace、ホスト、ポート、メソッド、パスが一致する一つの HTTP 通信に対し、
明示的に有効化した完全一致規則です。信頼するホスト側の操作がポリシー全体を検証し、
アトミックな有効化に成功した場合だけ作られます。

### 学習済み拒否（learned deny）

明示的に有効化した完全一致の拒否です。baseline のデフォルト拒否とは異なり、学習済み
規則の一覧へ現れ、明示的にリセットできます。

### ポリシー候補（policy candidate）

保持している学習可能な拒否の根拠から、決定的にまとめた提案です。権限でも、自動の
変更操作でもありません。本文の内容が違っても別の候補にはなりません。

### 不透明な参照値（opaque reference）

検出コマンドが生成し、対応する一つの実行操作が変更せずに受け取る検証済みの値です。
デコード、再構築、短縮をしたり、表示順で置き換えたりしません。

### ポリシーレビュー（policy review）

候補を確認し、許可、拒否、何もしない、のいずれかを意図的に選ぶ、信頼するホスト側の
手順です。Gateway の拒否レスポンスは、この手順の入口だけを示します。

### ポリシー有効化（policy activation）

ポリシー状態をロックし、対象 Context のソースを検証し、全 Context を含む完全な
投影データをテストし、アトミックに公開して OPA の状態を合わせるホスト側の処理です。
失敗時は、既知の正しい投影データを保持または復元します。

### リセット（reset）

選択した学習済み判断を一つ削除し、一致するリクエストをデフォルト拒否へ戻す操作です。
リセットは許可ではなく、リクエストを再試行もしません。

## 認証と認証情報

### 認証（authentication）

外部サービスの認証情報を確立または保存することです。「どの認証情報を提示できるか」
には答えますが、「この HTTP 通信を Workspace から出してよいか」には答えません。

### 認可（authorization）

通常の HTTP 通信について OPA が判断し、Gateway が実施する許可または拒否です。
ログイン、インポート、プロバイダーのインストール、ハンドルの所持によって、この許可が
付与されません。

### 認証情報プロバイダー（credential provider）

認証情報を取得またはインポートし、保存して、レビュー済みの完全一致リクエストとの
結び付き一つへ適用する外部サービスまたは権限の提供元です。Provider は、その認証情報
を使う Workspace クライアントを表しません。

### Workspace クライアントツール（Workspace client Tool）

Provider が宣言した projection を受け取り、binding に一致する request を送る Workspace
内 client です。組み込み V1 の例は `gh` だけです。Tool 名は provider identity も
network authority も与えません。

### サポート対象の Provider–Tool 対応（supported Provider-Tool pairing）

Provider、Workspace client Tool、取得方式、handle projection、完全一致 request binding
を組み合わせたレビュー済み対応です。組み込み V1 は GitHub/`gh` 一組で、owner provider
は strict stdin import と static projection を使います。

### ツール固有のパススルー（tool-native passthrough）

宣言済みの provider binding に一致しない request のための、Workspace 所有の互換経路です。
ツールは自身の永続 Workspace ホーム内でログインします。Gateway は OPA 入力と監査記録から
認証情報と cookie の値を除き、ポリシー許可後にだけ値を変えず転送します。Workspace は、
このツール管理の秘密情報を読めます。宣言済み binding では `broker_auth_required` で拒否します。

### Auth Broker

Context とプロバイダーごとに、型付きで暗号化した認証状態を保存する共有サービスです。
Workspace に結び付いた不透明なハンドルを発行し、秘密情報を使わずに照会します。
起動時は locked です。Gateway が policy allow を報告した後だけ、同じ static credential
revision を解決します。Broker は Unix socket を持ちますが、Workspace network や TCP
listener は持ちません。

### Broker 管理の認証状態（brokered credential state）

一つの Context vault 内で暗号化する型付き record です。V1 は static primary secret 一つと
revision/handle state を保持します。Workspace や OPA へは投影しません。request-local value
が境界を越えるのは policy allow 後に Auth Broker から Gateway へ渡る場合だけです。

### Broker ハンドル（broker handle）

対象 Workspace へ投影する、バージョン付きの不透明な `tobari-h1_…` 値です。実物の
認証情報ではなく、それだけで十分な権限にもなりません。利用時には Context、
プロジェクト、プロバイダー、認証情報のリビジョン、接続先、送信元ヘッダー、構文の
一致と、その後の OPA の許可が必要です。同じ Workspace 内でハンドルを読める
プロセスは、委ねられた権限の利用を試みられます。Tobari は同一 Workspace 内の
プロセス同士を分離しません。

### 秘密情報を使わない照会（non-secret introspection）

候補ハンドルを検証し、プロバイダー、リビジョン、正規化した結び付きのメタデータだけを
返す、ポリシー判断前の Broker 操作です。実物の秘密情報を公開も解決もしません。

### 解決（resolve）

スキーマ 1 の固定プロバイダー向けに、許可後に実行する Broker 操作です。宣言済みの
宛先 header へ入れる current primary secret を Gateway に返します。deny では resolve call
はゼロです。

### 認証情報リビジョン（credential revision）

現在の Context とプロバイダーの認証情報に対応する、秘密情報を含まないランダムな
識別情報です。置換またはログアウトにより、以前のリビジョン用ハンドルを失効させます。

### 暗号化 Context 保管庫（encrypted Context vault）

安定した Context ID を認証付きデータとして結び付けた、スキーマ 1 の
AES-256-GCM エンベロープです。暗号化したスキーマ 1 ペイロードは、型付きの認証情報
レコード、リビジョン、永続する操作バリア、ハンドルの元レコードを保持します。
暗号化は文書化したルート鍵の前提のもとで、コンテナと Workspace の境界を守ります。
ホスト利用者と鍵の保管基盤の侵害からは守りません。

### インストール用ルート鍵（installation root key）

Context 保管庫を解錠する 32 バイトの鍵です。Linux では所有者だけが読める XDG
状態ファイル、macOS では固定した Keychain 項目に置きます。`cluster down --purge`
でも残ります。

### プロバイダーマニフェスト（provider manifest）

取得方式、Workspace へのハンドル投影、完全一致の HTTPS との結び付き、秘密情報を
伏せる方法を宣言する、厳密で秘密情報を含まないデータ文書です。所有者マニフェストは
schema 1 かつ `stdin_import` だけを使います。GitHub が唯一の reviewed built-in acquisition
plan です。manifest は executable code ではなく、method/path policy を宣言せず、通信許可を
付与しません。

## 状態と公開契約

### ルート索引（root index）

正規のプロジェクトルートと安定した Context ID を、一つの Workspace ID へ対応付ける
永続スキーマ 1 レコードです。最も近いルートを選ぶ前に、Context で対象を絞ります。

### Workspace インスタンス状態（Workspace instance state）

一つの Workspace に対応する、永続スキーマ 1 の論理レコードです。Context との
恒久的な結び付きと、診断用のランタイム識別子を含みます。

### 集約ポリシー投影（aggregate policy projection）

全 Context から組み立て、OPA へ読み取り専用でマウントする、内容で識別される完全な
投影データです。一つの Context の変更が権限として有効になるのは、候補全体を検証して
有効化した後だけです。

### Catalog

コマンドパス、型付き入力、効果、役割、出力、参照の受け渡し、変更操作、
失敗、復旧に関する公開仕様の正本である `cli.Catalog` です。ルーティング、ヘルプ、生成する
CLI リファレンスはここから導出します。

### コマンドの役割（command role）

`utility`、`discover`、`act` のいずれかです。検出操作は不透明な参照を生成
できます。実行操作は、参照結び付き方式またはコマンド管理の固定対象方式
の、どちらか一つだけを持ちます。

### 操作の作用（operation effect）

`read`、`create`、`write` のいずれかです。外部から見えるすべての操作が一つを宣言し、
未知の効果は安全側に倒して拒否します。

### 変更操作契約（mutation contract）

外部への作成または書き込みの前後で必要になる、宣言済みの意図、対象との結び付き、
影響項目、確認済みの結果です。

### ソーススナップショット（source snapshot）

正本となる Gateway と Auth Broker のソースツリーです。CLI はオーケストレーション用に、
バイト単位の一致を検査したランタイムスナップショットを埋め込みます。差分検査により、埋め込み
コピーが二つ目の編集可能な実装になることを防ぎます。

## 混同してはいけないもの

| 同一視しないもの                        | 違い                                                                                                    |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Workspace と作業コンテナ                | Workspace は永続する論理状態。コンテナは交換可能なランタイム                                            |
| Context とクラスター                    | Context は一つの設定と権限の範囲を決め、クラスターは読み込んだ全 Context を共有基盤で制御する           |
| 認証と認可                              | 認証情報が存在しても、OPA は HTTP 通信を拒否できる                                                      |
| CA の信頼とポリシーの許可               | CA の信頼は通信の検査を可能にし、許可は正規化した一つの通信を通す                                       |
| Auth Broker のハンドルと認証状態        | ハンドルは Workspace に結び付き、失効でき、秘密情報ではない。保管庫は固定または更新可能な状態を保持する |
| `exit` と `delete`                      | `exit` は子のセッションを終了し、`delete` は論理 Workspace とホームを削除する                           |
| `cluster down --purge` と `auth logout` | purge は共有ランタイムと CA ボリュームを削除し、logout はローカル認証情報一つとハンドルを削除する       |
| タグとダイジェスト                      | タグは移動可能。ダイジェストは不変な OCI コンテンツを識別する                                           |
| マニフェストとレポートのスキーマ        | 保存する Context マニフェストはスキーマ 1、公開 Context レポートはスキーマ 1                            |

## 障害と制限

これらの定義はサポート対象の実装を説明するもので、Tobari の脅威モデルを広げません。
特に「信頼しない Workspace」は、選択したプロジェクトルートがその Workspace から
保護されることや、明示的に許可した接続先へデータを送れないことを意味しません。

二つの用語が矛盾して見えても、表示順や都合で一方を選ばないでください。規定する契約と
完全一致の境界へ戻って確認します。信頼できる識別情報、スキーマ、管理主体、
ポリシー、認証状態がない、または曖昧なら、Tobari は安全側に倒して拒否します。用語は
権限の代わりにはなりません。

## まとめ

Tobari は、永続する実行識別情報、ホスト設定、共有の制御基盤、ランタイムによる
実体化、認証情報の所持、ネットワークの許可を分離します。完全一致の境界には、対応する
用語を使ってください。

## 理解を確認する

「コンテナ」「Context」「Workspace」は同義語ではありません。

<details>
<summary>プロセスが有効な Auth Broker のハンドルを持っています。認証と通信許可は完了していますか？</summary>

いいえ。認証機能の候補を持っているだけです。Broker が Context、Workspace、
プロバイダー、リビジョン、HTTP との結び付きの一致を確認し、さらに OPA が通常の HTTP
通信を許可した後で、宣言済みの解決、更新、署名処理を実行します。

</details>

<details>
<summary>現在の Context を変更すると、既存 Workspace もその Context へ移りますか？</summary>

移りません。Workspace と Context ID の結び付きは恒久的です。現在の Context は、
セレクターを省略した呼び出しのデフォルトにすぎません。

</details>

<details>
<summary>許可された Upstream 接続を実際に開くのは Gateway と OPA のどちらですか？</summary>

Gateway です。OPA は判断を評価して返しますが、通信を転送しません。

</details>
