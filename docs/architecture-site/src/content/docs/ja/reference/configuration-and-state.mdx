このリファレンスでは、Tobari がホスト上で管理する設定、永続するランタイム状態、共有の読み取り専用投影、Docker リソース、選択したプロジェクト内のファイルを管理主体と寿命ごとに整理します。ランタイムコンテナは Workspace の正本ではありません。

操作ごとの表を使うと、`exit`、`workspace delete`、`cluster down`、`cluster down --purge`、認証情報の置換、Runtime の再ビルドを行った後に何が残るかを確認できます。これらのパスの背後にある所有モデルは、先に [Workspace、Workspace Template、クラスター](../../how-it-works/workspace-template-context-workspace-cluster/)を参照してください。

## ホスト上の三つのルート

```text
Configuration  ${XDG_CONFIG_HOME:-$HOME/.config}/tobari
State          ${XDG_STATE_HOME:-$HOME/.local/state}/tobari
Shared data    ${XDG_DATA_HOME:-$HOME/.local/share}/tobari
```

これらのホストパスは所有者専用として検査され、危険なシンボリックリンク、想定外のファイル種別、所有者、緩すぎるアクセス権は拒否されます。これらと重なるプロジェクトルートは選べません。

設定、状態、共有データのルートは別の寿命を持ちます。編集可能な desired source と、最後に正常に Apply された active authority も別の寿命を持ちます。あるルートの欠落を、別のルートの値から推測して補いません。

## ホストが管理する authority

config root では概念ごとに `templates/<template-id>/{template.yaml,policy.yaml}`、`contexts/<context-id>/context.yaml`、`runtimes/<runtime-id>/{runtime.yaml,source/}` を所有します。directory 名は stable ID、display name は document 内です。file edit だけでは authority は変わらず、Template/Context の Plan と Apply が exact fingerprint を再検証して revision を発行します。`cluster up` は source を Apply せず、最後に正常だった active generation だけを読みます。

active authority は state root の `authority/` 以下に、Template、Context、Policy Memory、Workspace の immutable typed object、完全な `generations/<digest>.json` manifest、小さな `active.json` pointer、recovery journal として概念分離して保持します。reader は一つの完全な generation を検証して選択します。

管理対象 Runtime の成功済み不変 revision と receipt は `state/runtimes/<runtime-id>/` にあります。source edit だけでは revision にならず、`runtime build --id RUNTIME_REF` だけが build boundary です。新 revision の採用には Template の edit と Apply が必要です。

## 永続するランタイム状態

| state root 内のパス             | 契約と寿命                                                                                                                                 |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `authority/`                    | concept ごとの immutable object、完全な generation manifest、検証済み `active.json`、tombstone、recovery journal                           |
| `runtimes/<runtime-id>/`        | immutable Runtime revision、build receipt、lifecycle state                                                                                 |
| Context が管理する Context Home | native login と tool configuration。exit/recreation/Workspace削除後も残り、exact `context delete --id CONTEXT_REF --confirm=delete` で削除 |
| `state.json`                    | shared cluster state と active aggregate receipt。credential value や desired authority は含まない                                         |
| `workspace-authority-policy/`   | 内容アドレス方式の complete policy projection と bounded activation receipt/journal                                                        |
| `runtime/`                      | host-owned Gateway runtime directory。socket は service とともに再作成され、durable credential ではない                                    |
| `runtime/<asset-revision>/`     | materialized Compose、Gateway、OPA、runtime asset                                                                                          |

agent CLI の login 形式は Context Home に残り、同じ Context の sibling Workspace と共有されます。Tobari の共有サービスや公開 JSON の権限にはなりません。Tobari はホストのログイン情報を継承しません。

Workspace Template policy の正本は `policy.yaml` の canonical typed data だけです。現行 schema は `tobari.dev/template-policy/v1` で、`boundary.methods.deny` が terminal Method Boundary、closed な `semantic.protocols` と `semantic.providers` が static module rule を保持します。Context Policy Memory は別の immutable state object です。内部 `data.json` は、検証済みの完全な `cluster-projections/<revision>/` 内でのみ生成されます。固定 evaluator は Tobari に組み込まれ、Docker 管理の policy bundle 内だけに現れます。未知または重複する field、不完全な source set、余分な file、symlink、hardlink、owner drift、安全でない mode は拒否されます。

旧 `v1alpha1` shape は通常の source reader では読めません。専用 decoder は `template migration plan/apply` だけが所有し、desired source を atomic に置換しても active authority は変えません。その後に通常の Template Plan/Apply が必要です。

ホスト所有の設定と状態は、サポート対象プラットフォームの owner/mode 検査で保護します。Linux と macOS では所有者、symlink、schema が安全でないとき fail closed です。同じホスト利用者が侵害された後の保護までは主張しません。共有の読み取り専用 agent profile は `${XDG_DATA_HOME:-$HOME/.local/share}/tobari/profiles` 以下にあります。

Gateway の runtime socket は Gateway container 内だけにあります。固定されたホスト操作はレビュー済み adapter 境界だけへ到達します。この socket はホスト公開サービスでも Workspace mount でもなく、永続する認証情報でもありません。

## Tobari のホストルート外にある状態

選択した実プロジェクトルートは、不変 Workspace Template の `source_access` に従って mount されます。CLI で省略した場合は `read-write` です。このディレクトリは利用者のデータであり、Workspace ライフサイクルの所有物ではありません。Tobari の `workspace delete` と `cluster` コマンドは削除しません。

Docker は作業コンテナ、専用ネットワーク、共有サービス、Gateway CA volume を保持します。Docker inspect は現在の runtime resource を示す evidence ですが、論理 Workspace が存在するかは決めません。その authority は検証済みの active generation にあります。コンテナが消えても有効な論理 state から再作成できますが、Docker resource が残っていることだけを理由に論理 Workspace を発明または採用しません。

## 各操作の後に残るもの

| 操作                                                                    | 変わるもの                                                                        | 残るもの                                                                                                          |
| ----------------------------------------------------------------------- | --------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `exit`                                                                  | 接続中の exec session                                                             | 論理 Workspace、home、policy、ランタイムリソース                                                                  |
| `workspace delete`                                                      | 対象 Workspace の authority、container、network、Workspace-private runtime record | プロジェクトファイル、Context Home と native state、Policy Memory、Workspace Template、クラスター、他の Workspace |
| `workspace delete --id WORKSPACE_REF --confirm=delete --force`          | attached-session guard を一つだけ上書きした同じ削除                               | 対象外のリソースとプロジェクトファイル                                                                            |
| container/network loss                                                  | 次の entry で失われた管理対象 runtime を再調整                                    | 論理 identity、Context binding、home、プロジェクトファイル                                                        |
| `cluster down`                                                          | 共有 container と一時 network                                                     | Workspace Template、policy、Context Home、host-owned lifecycle state、CA                                          |
| `cluster down --purge`                                                  | 共有 runtime、CA、active policy bundle                                            | Workspace Template、policy、Context Home、host-owned lifecycle state                                              |
| `runtime build --id REF`                                                | source snapshot、検証済み immutable revision                                      | Workspace Template と Workspace の identity                                                                       |
| `template.yaml` 編集、`template plan`、`template apply --plan PLAN_REF` | exact Runtime ID+revision を含む Template 全体のレビュー済み revision             | 既存Workspaceのhomeとcontainer（次回entryまで）                                                                   |

標準 Runtime は、CLI に埋め込まれた固定 recipe から、必要な場合にローカルで構築します。release 由来の tag は recipe revision を示す表示・選択 evidence であり、不変 digest authority ではありません。管理対象 Runtime の成功した build は、検査した local image digest を installation-wide history に記録しますが、Workspace Template が保持するのは exact semantic revision binding だけです。

`exit` は接続中の子プロセスだけを終えます。Workspace、作業コンテナ、専用ネットワーク、Context Home、Context、Policy Memory、project files、agent CLI credentials は残ります。`workspace delete --id WORKSPACE_REF --confirm=delete --force` は attached-session guard だけを明示的に上書きし、削除対象の範囲を広げません。`cluster down --purge` も project root、Context Home、Template policy and Context Policy Memory、host-owned lifecycle state を削除しません。

## 障害と復旧

状態を一意に判断できない場合、Tobari は安全側に倒して拒否します。欠けた container は有効な論理 state から再作成できますが、欠けた identity や Context binding は推測しません。policy activation は完全な projection を検証し、失敗時には直前の既知の良好な projection を保持します。

`doctor` は読み取り専用で、修復、移行、削除、ログイン変更を自動実行しません。ホスト状態の所有者・mode・schema が不正なら、代替 authority を作らず停止します。

active generation が不正、Context/Workspace binding が矛盾、または mutation outcome が unknown なら fail closed します。entry は Docker state から replacement record や delete reference を推測しません。中断された source directory、generation、Runtime、installation migration journal は、それぞれの owner 境界で分類します。recovery は exact pre/post fingerprint と完全な generation identity が検証できる場合だけ候補を受理し、それ以外は検証済み original を復元します。

aggregate revision が一致しない場合や policy activation が失敗した場合、exact cluster operation が完了するまで依存する entry/policy operation を止めます。host-owned lifecycle state の欠落も recovery fault であり、新しい authority を静かに発明しません。owner label、runtime spec、記録済み identity が一致しない Docker resource は、削除または adoption の対象になりません。

## 保証と制限

Tobari は、サポート対象のホストと Docker 構成内で、所有関係の検査と論理選択の永続化を保証します。選択したプロジェクトルートのスナップショットや完全性保護は提供しません。Context Home は agent CLI の状態を sibling Workspace 間で保持しますが、Tobari の共有サービスではありません。

重なり合う project root は互いの file change を観測でき、明示的に許可した宛先へ送ったデータを Tobari が後から取り消すこともできません。Context Home は設計上、tool-native authentication state や credential を含み得ます。Tobari は host credential をそこへ copy または broker せず、release surface では agent CLI 自身が owner です。

## まとめ

設定は何を保持するかを示し、Workspace state はどの論理 Workspace が存在するかを示します。Docker は再調整可能な runtime を提供し、プロジェクトルートは利用者のデータとして残ります。

## 理解を確認する

<details>
  <summary>
    <code>cluster down --purge</code> は Context Home や host-owned lifecycle
    state を削除しますか？
  </summary>
  いいえ。共有 runtime、CA、active policy bundle を削除しますが、Context Home と
  host-owned lifecycle state は残ります。
</details>

<details>
  <summary>
    Workspace Template schema と公開 report schema は同じ契約ですか？
  </summary>
  いいえ。一方は永続する host configuration、もう一方は秘密情報を除いた
  task-owned CLI projection です。
</details>

<details>
  <summary>Runtime の再ビルド後に何が残りますか？</summary>
  論理 Workspace identity、Context binding、プロジェクトファイル、Context Home
  が残ります。必要なら次の entry で container を再作成します。
</details>
