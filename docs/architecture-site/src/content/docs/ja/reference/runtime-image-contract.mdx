このリファレンスでは、Tobari Workspace が受け入れる OCI イメージの契約を定義します。
ランタイムを作成または調整する前に、Tobari はランタイム API `1`、固定された寿命管理
機能、`tobari` ユーザー、レビュー済みのエントリーポイントという四つの属性を完全一致で
検査します。

イメージが提供するのはツールとルートファイルシステムです。マウント、リソース、
ネットワーク、Workspace の寿命は、引き続きホストが管理します。最初の導入は、
[カスタムランタイムを用意する](../../start/runtime-setup/)に沿って進めてください。ビルド、選択、復旧の正確な動作は、
[ランタイムの詳細設定](../../guides/runtime-customization/)で説明します。

## イメージに必要な属性

選択するローカルイメージには、次の値が必要です。

| 属性                                        | 必須値                                                        | 存在する理由                                                                             |
| ------------------------------------------- | ------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| ラベル `io.tobari.runtime-api`              | `"1"`                                                         | Workspace とランタイム間のインターフェースを選ぶ                                         |
| ラベル `io.tobari.runtime-lifetime-command` | `"sleep infinity"`                                            | ホスト管理の長時間動作するコンテナプロセスを利用できると宣言する                         |
| イメージのユーザー                          | `tobari`                                                      | イメージの既定値によって、対応する非 root ユーザーの契約が暗黙に変わるのを防ぐ           |
| エントリーポイント                          | `["/usr/bin/tini", "--", "/usr/local/bin/tobari-entrypoint"]` | 公開 CA バンドルを設定し、準備完了を記録し、ホスト指定のコマンドを `tini` の下で実行する |

Tobari は `docker image inspect` でこれらの値を確認します。値がない、順序が違う、
別の値へ置き換わっている場合は互換性がありません。新しい論理 Workspace が
プロジェクト用ホーム、ネットワーク、コンテナ状態を作る前に検査します。

エントリーポイントは公開 Gateway CA 証明書を待ち、システムの信頼バンドルと一時ファイルへ
結合します。その後、コンテナを準備完了と記録し、引数を実行します。CA により通信の
検査が技術的に可能になりますが、ポリシーの許可は与えません。

## ランタイムの動作を誰が管理するか

イメージはバイナリと読み取り専用のルートファイルシステムを提供します。Tobari の
Infrastructure は、セキュリティとライフサイクルの仕様を定めます。

- 選択した live project root 一つを immutable Workspace Manifest `source_access` に従って mount
  （CLI omission default は `read-write`）
- 独立して永続する Workspace ホーム一つ
- プロジェクト専用の保護済み内部ネットワークと Tobari CA の信頼環境
- Gateway の公開 CA ボリューム
- 読み取り専用のルートファイルシステムと、上限付きの一時ファイルシステム
- capability の削除、`no-new-privileges`、Docker ソケットなし
- 固定した CPU、メモリ、PID、コンテナログの上限
- ヘルスチェックと、管理主体を示す安定したラベル
- 最後に指定する `sleep infinity` コマンド

Docker はイメージ名の後に Tobari の寿命管理コマンドを受け取ります。そのため、
イメージの `CMD` は Workspace の存在や寿命を決めません。対話シェルと完全一致のエージェント
コマンドは、それぞれ別の子 `docker exec` です。一つの子プロセスから出ても、論理
Workspace は停止も削除もされません。

イメージはラベルを使って、別のマウント、認証情報、ネットワーク経路、Linux ケイパビリティ、
リソース制限、ポリシーを要求できません。プロジェクトファイルからランタイムイメージを
選ぶこともできません。イメージを選ぶ権限は、結び付いた Workspace Manifest にあります。

## 公式ベースとローカル識別情報

リポジトリの正本となるベースランタイムのメタデータはスキーマ1で、次を宣言します。

- パッケージ `tobari/runtime`、種類 `base`
- ランタイム API `1`
- 寿命管理コマンド `sleep infinity`
- 完全一致のエントリーポイントと `tobari` ユーザー
- サポート対象 `linux/amd64` と `linux/arm64`

ソースビルドのデフォルトは次です。

```text
tobari-runtime:base
```

リリースビルドでは、この名前を埋め込みベースアセットから導出した決定的なタグへ
置き換えます。どちらもレジストリの取得元ではありません。選択した公式ベースがない場合、
Tobari は CLI に固定して埋め込んだ Dockerfile とアセットを展開し、ローカルでビルドして、
カスタムイメージと同じ互換性検査を行います。agent-ready base を GHCR から取得したり、
GHCR へ公開したりしません。

タグは、固定したどのローカルビルドが存在すべきかを識別しますが、OCI ダイジェストでは
ありません。実際にビルドしたバイト列の不変な識別情報には、Docker で検査したローカル
イメージダイジェストを使います。

## インストール全体で共有する Runtime のカスタマイズ

`runtime create --name frontend` は次を作成します。

```text
${XDG_CONFIG_HOME:-$HOME/.config}/tobari/runtimes/frontend/source/
```

所有者専用のソースディレクトリ全体が Docker ビルドコンテキストです。生成する
Dockerfile は公式 Runtime から始まり `USER tobari` へ戻ります。隣にスクリプト、
マニフェスト、設定ファイルを置けます。作成や編集だけでは履歴も Workspace Manifest 参照も変わりません。
ルートと配下には group/other 権限ビットを付けられません。上限は通常ファイル
1,024 件、ディレクトリ 256 件、1 ファイル 32 MiB、全体 64 MiB で、所有者だけが
実行できる `0700` のファイルは有効です。

続いて `runtime build --name frontend` が次を行います。

1. 数値と所有者専用の上限を検証し、リンクや特殊ファイルを拒否する
2. 正規パス、モード、サイズ、バイト列を digest へストリームしながら不変スナップショットを作る
3. ローカル候補イメージ名を導出し、そのスナップショットだけをビルドする
4. 上記の完全一致互換性検査を適用する
5. 不変なローカルイメージのダイジェストを読む
6. 成功した意味的リビジョンを Runtime 履歴へアトミックに追加する

ビルドは Workspace Manifest を変えません。失敗時は履歴を追加せず、同一ソースの再ビルドは成功した
no-op です。Docker BuildKit のキャッシュや未選択候補が残っても、準備済みリビジョンとは報告しません。

選択は別操作の `manifest runtime set --runtime frontend@1` です。次回 Workspace に入るとき、期待する
イメージの識別情報と完全な runtime-spec ハッシュを比較します。差分がある作業コンテナだけを
再作成し、論理的な識別情報、プロジェクトルート、Workspace ホームは保持します。

## 失敗時の動作

| 条件                                             | 結果                                                                                     |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| 公式ベースがローカルで利用できない               | CLI の固定済み埋め込みアセットから一度ビルドし、その後に検査する                         |
| 必須ラベル、ユーザー、エントリーポイントが異なる | `incompatible_image`。初回に入る際の新しい論理 Workspace は作らず、既存状態は残す        |
| source のパス、サイズ、件数、種別、モードが無効  | `runtime_source_invalid` が上限付き相対パスと具体的な修正内容を示し、Docker は実行しない |
| ビルドが失敗                                     | 履歴とすべての Workspace Manifest 参照を変更しない                                       |
| ビルド後の互換性またはダイジェスト検査が失敗     | リビジョンを追加せず、上限付きのビルド診断を確認                                         |
| Workspace Manifest 選択の結果が不明              | 再試行前に `manifest show` を読み、新旧どちらとも決めつけない                            |
| 既存コンテナに runtime-spec の差分がある         | 検証成功後、次に入るとき、所有する作業コンテナだけを完全一致で再作成                     |
| ランタイムコンテナまたはネットワークを失った     | 論理 Workspace 状態とホームは残り、次に入るとき所有リソースを調整                        |

## 保証と制限

互換性検査が証明するのは、宣言済みのローカルイメージのインターフェースです。イメージ内のすべての
プログラムが信頼できることではありません。Workspace 内の悪意あるツールは、委譲済みの
権限で選択したプロジェクトルートを変更し、許可済みのネットワーク通信を利用できます。
Docker Engine、ホストカーネル、イメージのビルド環境、レジストリのサプライチェーンは、
引き続き信頼する前提です。

公式ベースは拡張されることを想定しています。そのエントリーポイントやユーザーを置き換える、
またはラベルだけをコピーした無関係なイメージから始める方法は、サポート対象の
カスタマイズ経路ではありません。

## まとめ

ランタイムイメージは、完全一致の互換インターフェースの後ろでツールを提供します。
Workspace のネットワーク、マウント、リソース契約、寿命を管理するのは、イメージの `CMD`
ではなく Tobari です。公式ベースは固定済み埋め込みアセットからローカルでビルドし、
完成したバイト列の不変な識別情報には検査済みダイジェストを使います。

## 理解を確認する

ランタイムイメージは、Workspace の権限を決める唯一の主体ではありません。

<details>
  <summary>
    互換イメージはラベルの宣言で Docker ソケットを追加できますか？
  </summary>
  いいえ。Infrastructure
  がマウントとセキュリティの完全な仕様を管理します。イメージの
  メタデータはホスト権限を追加できません。
</details>

<details>
  <summary>
    新しい Runtime リビジョンをビルドすると、実行中の Workspace
    コンテナを即座に置き換えますか？
  </summary>
  いいえ。ビルドは履歴を追加するだけです。Workspace Manifest
  へ明示的に選択した後、 次に Workspace へ入るときに作業コンテナを調整します。
</details>

<details>
  <summary>
    Tobari は agent-ready base を GHCR からダウンロードしますか？
  </summary>
  いいえ。公式ベースがない場合、CLI の固定済み埋め込みアセットからローカルで
  ビルドし、完成したイメージを検証します。
</details>
