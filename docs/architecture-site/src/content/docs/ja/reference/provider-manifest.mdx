プロバイダーマニフェストは、Tobari の厳密な Go パーサーが読む、秘密情報を含まない限定的な
設定です。認証情報の取得方式、Workspace へのハンドル投影、完全一致の HTTPS
ヘッダー変換を一つ以上宣言します。実行可能なアダプターではなく、インストールしても
ネットワーク権限は増えません。

このリファレンスでは、所有者マニフェストのスキーマ 1、レビュー済みの組み込みスキーマ 1
計画、Gateway が受け取る正規化済みの投影を扱います。パーサー、Domain の検証、
コレクションの正規化、正本となる合成フィクスチャが仕様の根拠です。この契約を使う
リクエストの流れは、先に[認証情報](../../how-it-works/credentials/)で確認できます。

## 重要な用語

所有者が管理する文書は、`tobari.auth-provider.v1` と `schema_version: 1` を使います。
レビュー済みの組み込み定義も同じ V1 の中で、閉じた型付き計画を使います。Gateway が
受け取る正規化済みコレクションも投影スキーマ 1 です。リポジトリでは、厳密な Go
パーサー、Domain の検証、コレクションの正規化、フィクスチャによって完全一致の形式を
検証します。
**マニフェストの正式な JSON Schema 文書は公開していません。** フィクスチャ台帳を JSON
Schema の検証器と説明しないでください。

Provider は、Workspace で使う Tool とは別の概念です。Provider は外部の認証情報を
提供する主体を表します。Tool は宣言済みの投影を受け取り、対応するリクエストを送る
クライアントです。組み込みマニフェストとコンパイル済みドライバーは、現在一つの完全な
Provider と Tool の組を表します。対応は GitHub/`gh`、AWS/`aws`、Datadog/`pup`、
Chatwork/`cwk` です。現在は各 Provider に対応するクライアントが一つだけです。そのため
Provider を選ぶと Tool が表示され、自動で選ばれます。マニフェストの表示名、環境変数、
隣接する結び付きから、別の対応 Tool を作ることはできません。

所有者が管理するマニフェストは、次の場所に置く、所有者だけが読める通常ファイルです。
シンボリックリンクは使えません。

```text
${XDG_CONFIG_HOME:-$HOME/.config}/tobari/auth/providers/*.json
```

組み込みのプロバイダー ID は置き換えられず、`stdin_import` だけを使えます。レビュー済みの
ホスト側ログインドライバーは GitHub、AWS、Datadog 用です。固定した実行ファイルと動作は、
コンパイル済みの Infrastructure であり、マニフェストの拡張ではありません。利用者の
マニフェストから別の補助実行ファイルや組み込み動作を追加することはできません。

## v1 が担うすべての責務

| セクション               | 宣言できるもの                                                                               | 宣言できないもの                                                             |
| ------------------------ | -------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 識別情報                 | 安定した小文字の `id` と、秘密情報を含まない `display_name`                                  | アカウントの識別情報、認証情報の値、組み込み定義を上書きする権限             |
| `acquisition`            | `stdin_import`、またはレビュー済み組み込み定義の固定ヘルパー ID                              | シェルコマンド、実行ファイルのパス、任意の URL、更新または署名コード         |
| `credential`             | `primary_secret` 一つだけ                                                                    | 複数の秘密情報種別または埋め込みの秘密情報                                   |
| `workspace_projections`  | 上限付きの `env` または `complete_file` 全体のテンプレート。`${HANDLE}` を含むものが一つ以上 | ホストのパス、ファイルの部分変更、プロセス制御変数、未知の置換               |
| `header_bindings.target` | 完全一致する小文字の DNS ホスト、`https`、ポート `1..65535`                                  | ワイルドカード、IP リテラル、経路テンプレート、HTTP メソッドとパスのポリシー |
| `source`                 | 完全一致する小文字のリクエストヘッダーと、認識済みの `raw`、`bearer`、`token` ハンドル構文   | URL、本文、cookie、無関係なヘッダーの一括置換                                |
| `destination`            | 完全一致ヘッダー、`raw`、`bearer`、`token`、`preserve_scheme`、`primary_secret` の使用       | 任意の変換またはプロバイダー SDK 操作                                        |
| `secret_headers`         | source と destination のヘッダーを含む、完全な小文字の除外対象セット                         | 認証ヘッダーをポリシー入力や監査へ残す不完全なセット                         |

使用できるテンプレートのプレースホルダーは `${HANDLE}`、`${PROVIDER_ID}`、
`${DISPLAY_NAME}` です。`complete_file` のパスは、Workspace ホーム下の安全な
相対パスです。Tobari は投影したファイル全体を管理し、既存ファイルの一部だけを
変更しません。

## 正規の合成例

実在するアカウントや認証情報を含まない、リポジトリの正本であるスキーマ v1 フィクスチャです。

<pre tabindex="0">
  <code>{JSON.stringify(providerManifest, null, 2)}</code>
</pre>

Workspace が見るのは、`EXAMPLE_TOKEN` と、プロジェクトに結び付いた不透明なハンドルを
含む生成済みファイルです。import した実物の秘密情報は見えません。

結び付きに一致するリクエストでは、Gateway がハンドルを認識して取り除き、秘密情報を
使わない Broker の照会後に、通常の HTTP 通信を OPA へ問い合わせます。許可後にだけ
秘密情報を一度解決し、宣言済みの宛先ヘッダーへ書きます。拒否時には秘密情報を
解決しません。

## レビュー済みの組み込みスキーマ 1 計画

組み込み V1 契約は汎用的な拡張機構ではありません。レビュー済みの組み込み定義だけが使える型付き
フィールドを追加します。

| Built-in  | 認証情報の kind         | Workspace placeholder                                     | ポリシー許可後の完全一致動作                                                                                                                                                           |
| --------- | ----------------------- | --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `aws`     | `aws_sso_session`       | 三つの AWS 認証情報変数に同じプロジェクト結び付きハンドル | OPA の許可後、Gateway が 8 MiB 以内のリクエスト一つを保持。Broker が専用ホストコンパニオンに固定の AWS CLI 認証情報エクスポートを要求し、標準的なヘッダー方式の SigV4 をローカルで計算 |
| `datadog` | `datadog_oauth_session` | プロジェクト結び付きの bearer ハンドル                    | OPA の許可後、Broker が 5 分の更新時間帯の外にあるトークンを選ぶか、プロキシとリダイレクトを無効にした固定 US1 トークンエンドポイントで、同じレコードの更新を一つ実行                  |

GitHub と Chatwork は、スキーマ 1 の固定ヘッダー動作を維持します。GitHub のログインドライバー
は信頼するホストで実行し、固定認証情報を保存します。Broker イメージ内では動きません。

所有者ファイルは、`aws_sigv4`、OAuth セッション、更新エンドポイント、ホストドライバー、コンパニオン
操作、その他の組み込み動作を宣言できません。組み込み定義を追加するには、製品、
アーキテクチャ、セキュリティ、テストを含むレビュー済み変更が必要です。JSON の編集だけでは
追加できません。

## 検証とコレクションの有効化

マニフェストが空、不正な UTF-8、64 KiB 超、重複または未知のキー、末尾に余分な JSON、
未対応バージョン、フィールドの上限規則違反のいずれかに該当する場合は拒否します。

プロバイダーコレクション全体を決定的に正規化します。次の項目が衝突すると、有効化に
失敗します。

- プロバイダー ID と、大文字小文字を区別しない表示名
- Workspace の環境変数と complete-file のパス
- 完全一致の接続先と source ヘッダーの認識範囲
- より具体的な構文と重複する `raw` 構文
- その他の曖昧な結び付き、または秘密情報の除外契約

有効な文書だけを部分的に採用することはありません。コレクション全体を失敗させ、
曖昧な認証情報の認識規則が Gateway へ届くことを防ぎます。

## インストールが変えるもの、変えないもの

マニフェストを追加すると、プロバイダー定義が検証対象になります。明示的にインポートした後、
ハンドルの投影に利用できます。次のことは行いません。

- 許可規則の追加
- 許可済みのメソッドまたはパスの宣言
- 拒否された通信の再試行
- ハンドル単体を十分な権限にすること
- 実物の秘密情報を OPA または Workspace へ公開すること
- ログアウト時に外部トークンが失効するという保証

ポリシーは、Workspace Manifest ID、プロジェクト ID、ホスト、ポート、メソッド、パスに完全一致で
結び付きます。Broker はさらに、Workspace Manifest、プロジェクト、プロバイダー、認証情報の
リビジョン、正規化済み HTTP との結び付きを確認します。形式不正、古い、場所違い、曖昧な
Tobari 形式のハンドルは安全側に倒して拒否します。別のプロジェクトや Workspace Manifest へコピー
しても失敗します。パススルーへのフォールバックは行いません。同じ Workspace 内の
プロセスは、その Workspace の有効なハンドルを使えます。Tobari は同じ Workspace
内のプロセス同士を分離しません。

## 障害と復旧

プロバイダーの読み込みに失敗した場合は、所有者が管理する不正文書を修正または削除し、
CLI 障害が示す診断またはクラスターコマンドを、そのまま実行します。ファイルの
権限を緩めたり、実行可能なラッパーに変えたりしないでください。

認証情報を置き換えると、古いリビジョンのハンドルを失効させます。影響を受ける
Workspace から出て入り直し、新しいプロセス環境と complete-file の投影を
反映してください。`auth logout` はローカルの認証情報とハンドルを削除しますが、
プロバイダーへは接続しません。

## まとめ

所有者のプロバイダーマニフェストは、厳密で宣言的な、秘密情報を含まないスキーマ 1 の
データです。プロジェクトに結び付いたハンドルの位置を、完全一致の HTTPS 宛先ヘッダー
へ対応させます。レビュー済みのスキーマ 1 計画はコンパイル済みの組み込み定義であり、所有者
による拡張ではありません。どちらもマニフェストからコードを実行せず、HTTP 通信を
許可しません。

## 理解を確認する

有効なプロバイダーマニフェストだけではリクエストが許可されない理由を説明できるはずです。

<details>
  <summary>
    利用者のプロバイダーは <code>curl</code> をログイン
    コマンドとして宣言できますか？
  </summary>
  いいえ。利用者のプロバイダーは、端末に表示されない保護済みの `stdin_import` を
  使います。実行可能なドライバーは、レビュー済みの信頼するホスト側
  Infrastructure であり、マニフェストが提供するコードではありません。
</details>

<details>
  <summary>
    マニフェストは認証情報を <code>GET /v1/items</code> に限定できますか？
  </summary>
  いいえ。メソッドとパスは OPA のポリシーに属します。マニフェストは完全一致の
  HTTPS 接続先とヘッダーの意味だけを宣言します。
</details>

<details>
  <summary>
    二つのプロバイダーが同じヘッダー値を認識できる場合、どうなりますか？
  </summary>
  コレクション全体が曖昧として有効化前に失敗します。順番では選びません。
</details>
