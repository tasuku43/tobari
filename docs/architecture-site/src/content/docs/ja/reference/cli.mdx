このページには、Tobari が公開するすべてのコマンドと、その正確な入力、出力、作用、
参照値の受け渡し、変更操作の契約、障害、復旧操作を掲載します。正本は Go の
`cli.Catalog` です。内容は Tobari の機械可読ヘルプから生成しており、別のコマンド一覧を
手作業で保守しているわけではありません。

概要表示では、達成したい作業からコマンドを選べます。必須入力、既定値、競合条件、
前提、出力範囲、操作が受け取る不透明な参照値（opaque reference）を調べるときは、
完全な契約を開いてください。これらの用語になじみがなければ、機械向け契約より先に
[メンタルモデル](../../how-it-works/mental-model/)を読んでください。

## 契約の読み方

各コマンドには、完全一致するコマンドパスと、一つの完全な仕様があります。

| 項目                              | 意味                                                                         |
| --------------------------------- | ---------------------------------------------------------------------------- |
| 達成結果（Outcome）               | コマンドが完了させる利用者の作業                                             |
| 役割（Role）                      | `utility`、`discover`、`act`                                                 |
| 作用（Effect）                    | `read`、`create`、`write`。未定義の作用は不正                                |
| 入力（Inputs）                    | 個数、省略時の動作、範囲、依存関係、競合条件を含む、型付きの位置引数とフラグ |
| 出力（Output）                    | 形式、フィールド、JSON エンベロープとスキーマバージョン、配信方式、収集範囲  |
| 前提（Prerequisites）             | 操作が成功する前に存在していなければならない状態                             |
| 障害（Failures）                  | 安定した `kind` と `code`、再試行可否、Catalog に宣言された次の操作          |
| 参照値（References）              | 検出操作が生成し、実行操作が変更せずに受け取る不透明な値                     |
| 変更操作契約（Mutation contract） | `create` または `write` の意図、対象との結び付き、影響、確定した結果         |

`utility` は単独で完結する作業を実行します。`discover` は候補を返し、必要に応じて
不透明な参照値も返します。`act` は対象を一つ変更します。実行操作は、必須の参照値を
そのまま受け取るか、コマンド自身が所有する固定対象を一つ使います。識別子を再検出したり、
デコードしたり、組み立て直したりはしません。

ルートのエージェント向けヘルプ（agent help）は、意図的に小さくした機能索引です。
完全な契約を取得するには、コマンドまたは名前空間を完全一致で指定します。

```console
tobari help --format agent
tobari help policy --format agent
tobari help policy allow --format agent
```

ハイフンで始まるフラグ値には、equals 形式を使います。ハイフンで始まる位置引数は、
位置引数専用マーカーの後に置きます。以下に生成される呼び出し構文が、ビルド対象
コミットにおける正本です。

## 障害と復旧の規則

通常のコマンド失敗は、テキストまたはエラー JSON のスキーマ 1 で表示できます。機械向けの
形式は次のとおりです。

```json
{
  "schema_version": 1,
  "error": {
    "kind": "canceled",
    "code": "operation_canceled",
    "message": "The operation was canceled.",
    "retryable": true,
    "retry_after": null,
    "next_actions": [
      {
        "command": "doctor",
        "reason": "Retry when the caller is ready."
      }
    ]
  }
}
```

`kind` は大まかな復旧分類、`code` はプログラムが完全一致で判定する条件です。
`retryable: true` は再試行を検討できるという意味であり、変更操作を安全に再実行できる
証明ではありません。`retry_after` はレート制限の時間枠を示す根拠であり、論理的な
再実行の安全性とは独立しています。変更操作が中断された場合は、コマンドの結果契約と
現在の状態を照合してから再試行してください。

復旧コマンドも Catalog から生成されます。完全一致するコマンドパス、または
`help <exact-path-or-namespace>` です。接続先のエラーに含まれる信頼できない文字列を
付け足してはいけません。

障害境界そのものは、二つの診断によって拒否側に倒れます。
`invalid_fault_contract` は形式不正の構造化障害を置き換え、
`undeclared_fault_contract` は Catalog の宣言と一致しないコマンド障害を置き換えます。
どちらも通常のプロバイダー応答ではなく、Tobari の契約不備を示します。

## このリファレンスの制限

- 安定した機械向けフィールドを変えずに、人向けの文言を改善する場合があります。
- Catalog が記述するのは、サポート対象の公開 CLI です。ベンダーの未加工ルート、Docker
  コマンド、Broker プロトコル、任意の HTTP 呼び出しは公開しません。
- 生成した契約が説明するのは、コマンドの動作です。外部サービスを利用可能にしたり、
  ネットワーク権限を与えたりはしません。
- `complete` という配信方式は、プロバイダーの全履歴を網羅するという意味では
  ありません。収集範囲は別に宣言します。
- ソースから通常ビルドしたバージョンは `dev` です。リリース処理がリリースバージョンと
  ソースコミットを埋め込みます。このページがリリース番号を推測することはありません。

## まとめ

Catalog は公開 CLI の正本です。生成したヘルプが、型付きの呼び出し構文、出力、参照値の
受け渡し、変更操作の事実、障害、復旧を公開します。サイトはその契約を読み取り、
別のコマンド台帳を作りません。

## 理解を確認する

コマンド名をコピーしただけの一覧では、CLI リファレンスとして不十分です。

<details>
  <summary>
    <code>policy allow</code> が不透明な参照値を受け取るのはなぜですか？
  </summary>
  検出と実行を分離するためです。参照値によって、実行操作が対象を再検出、デコード、
  再構築することなく、ホスト側の操作をレビュー済みの候補一つへ結び付けられます。
</details>

<details>
  <summary>
    <code>retryable: true</code>
    なら、失敗した変更操作はすべて繰り返して安全ですか？
  </summary>
  いいえ。これは障害の分類を示すだけです。変更操作がすでに完了した可能性があるため、
  再実行する前に構造化された結果と現在の状態を照合する必要があります。
</details>

<details>
  <summary>引数の既定値と競合条件はどこで確認しますか？</summary>
  コマンドの Catalog
  入力から生成される、完全一致コマンドのエージェント向けヘルプです。
  ルートのヘルプ索引は、その詳細を意図的に省略します。
</details>
