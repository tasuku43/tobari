このページでは、Tobari の安定した障害 `kind`、完全一致する `code`、プロセス終了コード、
再試行用メタデータ、Catalog に宣言された復旧操作を説明します。生成される表の情報源は、
コマンドを完全一致で指定したエージェント向けヘルプです。そのため、公開 CLI 契約との
整合が保たれます。

失敗は `kind` と `code` で分類し、宣言済みの次の操作に従ってください。接続先からの
メッセージや、レート制限の待ち時間だけを見て、変更操作を安全に再実行できると判断しては
いけません。目に見える症状から調べる場合は、
[トラブルシューティング](../../guides/troubleshooting/)を使います。このページは、
機械向けの障害情報から調べるためのリファレンスです。

## 公開される障害エンベロープ

`--error-format json` で出力する CLI の失敗はスキーマ 2 です。

```json
{
  "schema_version": 2,
  "error": {
    "kind": "canceled",
    "code": "operation_canceled",
    "message": "The operation was canceled.",
    "phase": "precondition",
    "change_state": "none",
    "retryable": true,
    "retry_after": null,
    "next_actions": [
      { "command": "doctor", "reason": "Retry when the caller is ready." }
    ]
  }
}
```

`message` は、人が読むために安全化した文字列です。接続先から返されたレスポンス本文では
ありません。実装内部では、ラップされた原因を分類に使えます。ただし、リクエスト URL、
認証情報、安定しない外部サービス文言を含む可能性があるため、公開出力からは除外します。

`phase` は `precondition`、`observation`、`mutation`、`verification`、
`attachment`、`presentation` のいずれかです。`change_state` は
`not_applicable`、`none`、`partial`、`confirmed`、`unknown` のいずれかです。
境界を所有する層が証明できた最も強い事実を表し、二つ目の原因分類ではありません。
変更操作の `partial`、`confirmed`、`unknown` は、必ず宣言済みの読み取り専用状態確認を
最初の復旧操作にします。

## 安定した障害の種類と終了コード

| `kind`           | 終了コード | 復旧分類                                                                   |
| ---------------- | ---------: | -------------------------------------------------------------------------- |
| `invalid_input`  |          2 | 外部へ作用する前にコマンド呼び出しを修正                                   |
| `internal`       |          3 | Tobari の実装またはローカルアダプターの障害を調査                          |
| `authentication` |          4 | 識別情報または認証状態を確立・修復。ネットワーク通信は許可されない         |
| `permission`     |          5 | 呼び出し元に、要求した操作の権限がない                                     |
| `not_found`      |          6 | 必要なローカル対象を検出または作成                                         |
| `ambiguous`      |          7 | 対象を一つ明示的に選択。表示順で選んではならない                           |
| `rate_limited`   |          8 | 信頼できるレート制限時間の根拠に従い、論理的に再試行してよいかを改めて判断 |
| `unavailable`    |          9 | 必要なコンポーネントまたは外部の前提を復元                                 |
| `rejected`       |         10 | リクエストは解釈できたが、現在の契約または状態に違反                       |
| `canceled`       |         11 | 呼び出し元が操作を停止。変更操作は再実行前に現在の状態と照合               |
| `unsupported`    |         12 | 文書化されたサポート対象の経路を使用                                       |
| `contract`       |         13 | 生成側と利用側の契約が不一致。拒否側に倒し、契約を修復                     |

成功時の終了コードは 0 です。`kind` は `code` より広い分類です。作業固有の複数の `code` が、
一つの復旧分類を共有する場合があります。

## 再試行するか決める順序

次の順番で判断します。

1. 操作が読み取り専用か、変更操作かを判断する
2. `retryable` と `retry_after` を読む
3. 変更操作なら `phase` と `change_state` を読み、`partial`、`confirmed`、`unknown` は宣言済みの読み取りで状態確認する
4. 宣言済みの次の操作だけに従う
5. 前提を復元した後、明示的に再試行する

`retry_after` が示すのは、観測したレート制限の時間枠です。`create` や `write` が完了して
いないことの証明にはなりません。一方、再試行不可の障害でも、`status`、
`manifest show`、`doctor` のような読み取り専用の状態確認操作を案内できます。

副作用の完了を確認すると、変更結果は完了確定の境界を越えます。その後に取り消しが
発生しても、成功した操作を再実行してよいことにはなりません。分類できない変更結果は
`unclassified_mutation_outcome` となり、読み取り専用の状態確認を案内します。

## 通信経路の障害は拒否側に倒れる

すべてのネットワーク障害が CLI の障害エンベロープになるわけではありません。
Workspace からは、Gateway の HTTP レスポンスまたは接続失敗として見えます。

| 観測結果                                              | 意味                                                                                                                                  | 接続先へ通信したか                                         |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| 学習可能な HTTP `403` 拒否                            | 正規化した Workspace Manifest、プロジェクト、ホスト、ポート、メソッド、パスが許可規則に一致しなかった。ホストで確認後、明示的に再試行 | いいえ                                                     |
| 学習できない HTTP `403` 拒否                          | 学習対象の境界外、または識別情報が不正。候補にはできない                                                                              | いいえ                                                     |
| ポリシーサービスが利用不能、または判断が不正（`503`） | Gateway が OPA から有効な判断を一つ取得できなかった                                                                                   | いいえ                                                     |
| 許可後の接続先 DNS、TLS、接続、レスポンス障害         | 通信許可には成功したが、その後の別の接続先操作が失敗                                                                                  | 接続を試した可能性がある。Gateway はリクエストを再送しない |

ポリシーによる拒否を学習候補にできるのは、保持した、秘密情報を含まない根拠がある場合
だけです。Gateway のレスポンスに含まれるのは、ホスト側の確認先です。候補を指す参照値でも、
通信権限でもありません。

## 障害契約自体の障害

公開境界には、最後の防御となる二つの契約 `code` があります。

- `invalid_fault_contract`：`kind`、`code`、`message`、時間情報、次の操作が形式不正な
  構造化障害を置き換える
- `undeclared_fault_contract`：コマンドの Catalog 宣言と `code`、`kind`、`phase`、変更状態、再試行可否が
  一致しない障害を置き換える

これらの `code` は、安定しない内部エラーが意図せず公開 API になることを防ぎます。
外部サービス固有の失敗ではなく、Tobari 実装の診断です。

## 保証と制限

Tobari が安定した分類を保証するのは、サポート対象の公開境界だけです。上限付きの診断
として表示する Docker、OPA、外部サービス、OS の文字列は、安定した障害 `code` では
ありません。プログラムで解析しないでください。復旧コマンドで前提を戻せる場合は
ありますが、外部外部サービスでの失効、外部サービスの利用可能性、任意の HTTP 本文を
安全に再送できることは保証しません。

## まとめ

障害の `kind` は復旧分類を選び、`code` は完全一致する条件を識別します。再試行可否や
レート制限の時間情報は、変更結果と現在の状態の照合に代わるものではありません。
Gateway による拒否、OPA の障害、不正な Workspace／principal の結び付きは、いずれも未許可の通信が
接続先へ届く前に失敗します。

## 理解を確認する

「もう一度試す」は、あらゆる障害に使える復旧手順ではありません。

  <summary>
    OPA へのリクエストが時間切れになりました。復旧中に Gateway
    は接続先へ送りますか？
  </summary>
  いいえ。Gateway は OPA から有効な判断を一つ得る必要があります。OPA
  を利用できなければ、 接続先へつなぐ前に拒否側へ倒れます。
</details>

<details>
  <summary>
    変更操作が取り消しを報告しました。終了コード 11 だけで再実行してよいですか？
  </summary>
  いいえ。変更操作の結果と現在の状態を先に調べます。外部への作用が完了した後に、
  取り消しが発生する場合があります。
</details>

<details>
  <summary>
    外部サービスのエラー文字列を Catalog の復旧コマンドへ追加できますか？
  </summary>
  いいえ。復旧コマンドは検査済みの完全一致パスです。接続先からの文言は信頼できない
  データであり、`argv` ではありません。
</details>
