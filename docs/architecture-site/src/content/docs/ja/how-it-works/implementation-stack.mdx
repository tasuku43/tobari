Tobari は、役割ごとの境界に合わせて実装技術を選んでいます。Go はホスト CLI と検証を伴う構成管理を担当します。agent CLI は各自のログイン情報を永続 Workspace home に保存します。Docker はプロセス、ネットワーク、マウントの境界を実現し、mitmproxy と Python アドオンは HTTP/TLS 通信を制御し、OPA と Rego は一般化された HTTP 通信を許可するか判断します。

Tobari は認証情報を保管・解決する別サービスを持ちません。Gateway は OPA の許可後に Workspace 内の agent CLI が用意した元の認証情報を転送します。編集元となる Gateway 正本、埋め込み用の写し、変更不能な OCI イメージ、固定したダイジェストにより、この分離を実行環境への供給経路でも維持します。

この内容は実装者向けです。[状態と復旧](../state-and-recovery/)までの製品動作を前提とし、通常の利用には必須ではありません。

## 技術は信頼境界に従う

### Go CLI

公開 `tobari` 実行ファイルは Go で書かれています。正規化したパスの選択、ドメイン規則の検証、操作と状態変更の契約、アプリケーション層の処理、ホスト状態、Docker の構成管理、同じ入力から同じ結果を出す表示処理、公開コマンドの Catalog を担当します。

インフラストラクチャ層より上の Go コードは、任意の外部サービス API リクエストを作りません。一つのキャンセル制御を、呼び出し回数や時間に上限のある接続実装まで引き渡します。認証情報を含む型はインフラストラクチャ層の外へ出しません。

### Docker Engine と Docker Compose

Docker Engine は実行環境のコンテナ、読み取り専用／読み書き可能なマウント、実行ユーザー、Linux capability（プロセス権限）の削減、読み取り専用のルートファイルシステム、資源制限、外部へ直接出られない内部ネットワーク、ラベル、ボリューム、プロセス実行を提供します。

Docker Compose が管理するのは、共有 Gateway、OPA、共有ネットワーク、CA ボリュームだけです。Workspace ごとのコンテナとネットワークは、実行環境の接続実装が記録に合わせて調整します。完全一致するプロジェクトルートと Workspace Manifest の識別情報、ライフサイクルは、アプリケーション層で扱う必要があるためです。

Docker は信頼する基盤です。「コンテナで動く」という事実だけでは、安全性の根拠になりません。重要なのは、正確なマウント、ネットワーク接続、不要なソケットを渡していないこと、ラベル、実行ユーザー、障害時のテストです。

### mitmproxy Gateway と Python アドオン

mitmproxy は透過的な HTTP/TLS の検査、ストリーミング処理用のフック、接続先との TLS 通信を提供します。Tobari の Python アドオンは、製品固有のプリンシパル照合、本文を含まない OPA 入力、安全側に停止する判断結果の検証、DNS で解決したアドレスの分類と固定、監査記録を追加します。ログイン情報をサービスで扱いません。

ここで Python を使うのは、mitmproxy が提供する、レビュー済みの拡張手段が Python アドオンだからです。Gateway は通信判断を実際の経路へ適用します。ポリシー規則の解釈や、ログイン情報の保存・管理処理は組み込みません。

### OPA と Rego

OPA は共有のポリシー判断サービスです。Rego は Workspace Manifest policy ceiling、既定拒否、Workspace Manifest routing、
学習済み完全一致 allow/deny、credential metadata constraint を表します。first public V1 の
学習済み authority は完全一致のままです。

OPA はリクエスト本文も認証情報の値も受け取らず、外部へ接続するインターフェースを持ちません。判断処理を分けることで、OPA にネットワーク転送権限を与えずに、判断の入力と結果の契約をテストできます。

**Agent CLI のログインと Workspace home。**

agent CLI は自分の認証情報を永続 Workspace home に保存します。Tobari は
provider 固有の認証ストアや専用サービスを持たず、
ログイン情報の形式を解釈しません。Gateway は OPA の許可後に元の値を
転送し、OPA と監査には認証情報の値を渡しません。

### ローカル OCI イメージの境界

Gateway、OPA、mitmproxy のビルド元、agent-ready base は OCI イメージで境界を作ります。上流入力には埋め込み済みバージョン情報の不変ダイジェストを使い、Tobari 管理イメージにはソース由来のローカルタグと検査済みローカルダイジェストを使います。更新され得る `main` や `latest` タグは実行時の権限ではありません。

現在の正確なバージョンとダイジェストは、このページへ複写しません。`go.mod`、`versions.env`、実行環境メタデータから[コンポーネントバージョン](../../reference/component-versions/)へ生成します。

## 編集できる正本から実行用イメージまで

<ConceptDiagram name="image-supply" />

Gateway には編集元となる公開の正本ディレクトリが一つだけあります。

- `gateway/`

CLI は `internal/infra/runtimeassets/assets/` 以下にある実行環境の写しを埋め込みます。バイト単位の差分検査により、正本と一致しない写しの変更を拒否します。埋め込み資材には Compose、OPA ポリシー、実行環境のエントリーポイント、イメージの識別情報、ライセンス資料も含まれます。

CI は正本から複数アーキテクチャ向け OCI イメージを cache-only output で検証します。通常の実行環境はソース由来のローカルイメージをビルドまたは再利用し、検査済みダイジェストと component contract を確認します。image 検証には package-write 権限を与えず、Tobari には OCI 公開 workflow がありません。

## 一つの具体的なリクエストと技術の対応

許可された一つの HTTPS 呼び出しでは、次のように対応します。

1. **Go** は Workspace の Docker ネットワーク、正確なエンドポイント登録簿、CA、DNS 設定、Gateway／Workspace のネットワークガードを調整済みです。
2. **Docker と Linux ネットワーク**は外部への直接通信を防ぎ、TCP を Gateway の透過入口へ届けます。
3. **mitmproxy** は TLS A を終端し、リクエストヘッダーをアドオンへ渡します。
4. **Python Gateway アドオン**は送信元に結び付いたプリンシパルを導出し、一つの矛盾しない接続先を検証して、スキーマ1の入力を送ります。
5. **OPA/Rego** は許可または拒否を返します。
6. credential-bearing request では、**Gateway** が policy 前に認証情報の値を OPA
   と監査から除外し、allow 後に Workspace 内の agent CLI が用意した元の
   値を一度だけ転送します。
7. **mitmproxy** は検証済み TLS B を確立し、allow 済み request を stream します。
8. **Docker log** は host-side review 用の bounded secret-free audit evidence を保持します。

完全な保証を一つの技術だけで実装しているわけではありません。

## 失敗時の動作

- 実行環境またはサービスのイメージが見つからない、または互換性がない場合、安全でない作成より前に検証が失敗します。
- ダイジェスト、ラベル、API、実行ユーザー、エントリーポイントが一致しなければ、安全側に停止します。
- 正本と埋め込み用の写しに差があれば、リポジトリ検査で失敗します。
- 不正な Rego または全 Workspace Manifest の集約は、有効化より前に失敗します。
- OPA または Gateway に障害が起きた場合、Gateway は通信を通さない応答を返します。
- Docker またはホストの障害は、強制基盤を失わせます。Tobari は、その侵害下での保護を主張しません。
- Workspace のホスト状態が壊れている場合、既存の権限を推測せず、安全側に停止します。

## 保証と制限

**契約とテストで保証すること:** 固定されたコンポーネントの役割。通常利用するサービスを不変に識別できること。バイト単位で正本との一致を検査した埋め込み用の写し。Workspace home と agent CLI の境界。補助プロセスに待受ポートや不要なソケットのマウントがないこと。OPA に外部接続経路がないこと。正確な Compose 構成。実行環境の互換性を事前検査すること。

**保証しないこと:** イメージダイジェストだけでコードが安全になること。Docker、カーネル、ホストが侵害された後の分離。利用者が選んだ独自イメージの来歴。GHCR や外部レジストリの可用性。独自の実行環境レシピでインストールした任意ツールのセキュリティレビュー。

## まとめ

Tobari の動作は、複数技術の組み合わせで成り立ちます。Go が検証と構成管理を行い、Docker が境界を実現します。Gateway が HTTP/TLS 通信に判断を適用し、OPA/Rego が許可を判断します。agent CLI は Workspace home でログインを管理し、Gateway は許可後に元の値を転送します。不変な OCI イメージの識別情報と、正本と埋め込み用の写しの一致検査により、配布する実行環境をレビュー可能にします。

製品上の主張を、具体的な技術境界に結び付けて説明できるはずです。

<details>
  <summary>OPA が Gateway から分離されているのはなぜですか？</summary>
  OPA
  は転送や外部接続の権限を持たず、同じ入力に対して同じ結果を返す判断処理を担当します。Gateway
  はリクエスト、TLS、ネットワークの制御を担当し、判断結果を検証します。
</details>

<details>
  <summary>
    agent CLI のログインが Workspace 向け HTTP API を使わないのは なぜですか？
  </summary>
  ログイン情報は agent CLI が Workspace home に保存し、Tobari のサービス
  経路へ公開しないためです。Gateway は OPA の許可後に元の値を転送します。
</details>

<details>
  <summary>
    不変なイメージダイジェストは、実装が安全であることを証明しますか？
  </summary>
  いいえ。レビュー済みの内容をバイト単位で固定し、更新され得るタグへの差し替えを防ぐものです。安全性は引き続き、コード、設定、テスト、信頼の前提、実行環境の基盤に依存します。
</details>

製品の境界が不明確な場合は、[システム全体像](../system-overview/)へ戻ってください。次に[コード構造](../code-architecture/)で、Go リポジトリがこれらの責務を分離する方法を確認します。
