Tobari は、役割ごとの境界に合わせて実装技術を選んでいます。Go はホスト CLI、決められた方法でのプロバイダー認証情報の取得、検証を伴う構成管理を担当します。Docker はプロセス、ネットワーク、マウントの境界を実現します。mitmproxy と Python アドオンは HTTP/TLS 通信を制御し、OPA と Rego は一般化された HTTP 通信を許可するか判断します。

別プロセスの Python Auth Broker は、暗号化した認証状態を管理し、限定されたソケットを通して、ポリシー許可後の認証情報の解決、更新、署名を行います。役割を別プロセスに分けることで、通信転送、ポリシー判断、認証情報の保管を一つの権限に集めません。編集元となる正本、埋め込み用の写し、変更不能な OCI イメージ、固定したダイジェストにより、この分離を実行環境への供給経路でも維持します。

この内容は実装者向けです。[状態と復旧](../state-and-recovery/)までの製品動作を前提とし、通常の利用には必須ではありません。

## 技術は信頼境界に従う

### Go CLI

公開 `tobari` 実行ファイルは Go で書かれています。正規化したパスの選択、ドメイン規則の検証、操作と状態変更の契約、アプリケーション層の処理、ホスト状態、Docker の構成管理、同じ入力から同じ結果を出す表示処理、公開コマンドの Catalog を担当します。

インフラストラクチャ層より上の Go コードは、任意のプロバイダー API リクエストを作りません。一つのキャンセル制御を、呼び出し回数や時間に上限のある接続実装まで引き渡します。認証情報を含む型はインフラストラクチャ層の外へ出しません。

### Docker Engine と Docker Compose

Docker Engine は実行環境のコンテナ、読み取り専用／読み書き可能なマウント、実行ユーザー、Linux capability（プロセス権限）の削減、読み取り専用のルートファイルシステム、資源制限、外部へ直接出られない内部ネットワーク、ラベル、ボリューム、プロセス実行を提供します。

Docker Compose が管理するのは、共有 Gateway、OPA、Auth Broker サービスと、共有ネットワーク、CA ボリュームだけです。Workspace ごとのコンテナとネットワークは、実行環境の接続実装が記録に合わせて調整します。完全一致するプロジェクトルートと Context の識別情報、ライフサイクルは、アプリケーション層で扱う必要があるためです。

Docker は信頼する基盤です。「コンテナで動く」という事実だけでは、安全性の根拠になりません。重要なのは、正確なマウント、ネットワーク接続、不要なソケットを渡していないこと、ラベル、実行ユーザー、障害時のテストです。

### mitmproxy Gateway と Python アドオン

mitmproxy は明示的な HTTP プロキシ、CONNECT/TLS の検査、ストリーミング処理用のフック、接続先との TLS 通信を提供します。Tobari の Python アドオンは、製品固有のプリンシパル照合、認証情報の準備、本文を含まない OPA 入力、安全側に停止する判断結果の検証、許可後の認証処理、DNS で解決したアドレスの分類と固定、監査記録を追加します。

ここで Python を使うのは、mitmproxy が提供する、レビュー済みの拡張手段が Python アドオンだからです。Gateway は通信判断を実際の経路へ適用します。ポリシー規則の解釈や、認証情報保管庫の保存処理は組み込みません。

### OPA と Rego

OPA は共有のポリシー判断サービスです。Rego は既定で拒否する規則、初期権限、Context ごとの振り分け、学習済みの完全一致する許可・拒否規則、認証情報メタデータの制約、安全な共通接頭辞への集約条件を表します。

OPA はリクエスト本文も認証情報の値も受け取らず、外部へ接続するインターフェースを持ちません。判断処理を分けることで、OPA にネットワーク転送権限を与えずに、判断の入力と結果の契約をテストできます。

### Python Auth Broker、ホスト側処理、補助プロセス、Unix ソケット

Auth Broker は、ルート権限を持たない独立した Python デーモンです。認証情報の暗号化、ハンドル発行、結び付きの照合、許可後の処理を、ほかの役割から分けた信頼境界で扱うためです。TCP の待受ポートを持たず、GitHub CLI、AWS CLI、`pup` 実行ファイルも含みません。

所有者だけが使える制御用ソケットと、実行時ソケットを分け、ホストから行うライフサイクル操作と、Gateway がリクエスト処理中に行う限定的なアクセスを隔離します。Workspace と OPA には、どちらのソケットもマウントしません。実行時の通信規約では、ポリシー判断前に結び付きを照合し、許可後にはプロバイダーが宣言した処理だけを実行できます。任意の通信に使える汎用ネットワーク API ではありません。

対話を伴う GitHub、AWS、Datadog の認証情報取得は、信頼するホスト上に固定した Go のインフラストラクチャ実装を通して実行します。各実装は、標準的なインストール場所から識別情報を検査した実行ファイルを見つけ、固定した引数列と、不要な値を取り除いた専用環境を使います。表示する出力に上限を設け、一時状態が片付いたことを検証してから、Auth Broker の制御用ソケットを通して、型が定まった状態を保存します。

ポリシー許可後に、同じ実行ファイルから起動する常駐のホスト認証補助プロセスを使うのは AWS だけです。Auth Broker 専用の `/run/tobari-auth/companion/bridge.sock` は、認証・暗号化され、通信方向を限定した一つの逆向き `docker exec -i` セッションを通して接続します。補助プロセスは待受ポートも、マウント済みのホストソケットも公開せず、組み込み済みの AWS CLI `credential-export` 操作だけを実行します。Datadog の更新ではこの補助プロセスを使いません。Auth Broker は許可後に、完全一致する US1 のトークンエンドポイントへ、プロキシを使わずリダイレクトを拒否する厳格な HTTPS 通信を一度だけ行います。

### 暗号化した Context 保管庫とルート鍵

各 Context 保管庫は、ランダムなノンスと Context／スキーマに結び付く追加認証データを使う、スキーマ1の AES-256-GCM 形式です。暗号化したスキーマ2の内容には、型が定まった静的な秘密、不透明な AWS 状態、Datadog OAuth 状態、版、永続的な再実行防止記録、未加工のハンドルを保存します。インストール用ルート鍵は保管庫の外に置きます。macOS では Keychain、Linux では所有者だけが読める XDG ファイルです。暗号化は、コンテナと Workspace の境界をまたいで保存データが露出する可能性を抑えます。ただし、侵害されたホスト利用者、ルート鍵の保存先、Auth Broker、Gateway からは保護しません。

### OCI イメージと GHCR

Gateway、Auth Broker、OPA、mitmproxy のベース、実行環境のベースは、OCI イメージで境界を作ります。実行時サービスの識別には、埋め込み済みのバージョン情報に記録した不変ダイジェストを使います。更新され得る `main` や `latest` タグは開発や公開の便宜のためにあり、実行時の権限を示すものではありません。

現在の正確なバージョンとダイジェストは、このページへ複写しません。`go.mod`、`versions.env`、実行環境メタデータから[コンポーネントバージョン](../../reference/component-versions/)へ生成します。

## 編集できる正本から実行用イメージまで

<ConceptDiagram name="image-supply" />

Gateway と Auth Broker には、それぞれ編集元となる公開の正本ディレクトリが一つだけあります。

- `gateway/`
- `authbroker/`

CLI は `internal/infra/runtimeassets/assets/` 以下にある実行環境の写しを埋め込みます。バイト単位の差分検査により、正本と一致しない写しの変更を拒否します。埋め込み資材には Compose、OPA ポリシー、実行環境のエントリーポイント、イメージの識別情報、ライセンス資料も含まれます。

CI は正本から複数アーキテクチャ向けの OCI イメージをビルドします。通常の実行環境は、レビュー済みの不変ダイジェストを使います。Pull Request のイメージ検証には、パッケージを書き込む権限を与えません。公開は別の管理されたワークフローで行います。

## 一つの具体的なリクエストと技術の対応

許可された一つの HTTPS 呼び出しでは、次のように対応します。

1. **Go** は Workspace の Docker ネットワーク、プロキシ環境、CA、プリンシパル台帳を調整済みです。
2. **Docker** は外部への直接通信を防ぎ、プロキシ接続を Gateway へ振り分けます。
3. **mitmproxy** は TLS A を終端し、リクエストヘッダーをアドオンへ渡します。
4. **Python Gateway アドオン**はプリンシパルを導出し、スキーマ5の入力を送ります。
5. **OPA/Rego** は許可または拒否を返します。
6. Auth Broker ハンドルの場合、**Unix ソケット越しの Python Auth Broker** がポリシー判断前に秘密を含まない結び付きを照合し、宣言済みの静的認証、AWS、Datadog の処理は許可後にだけ実行します。
7. AWS では**専用のホスト側補助プロセス**が、決められた認証情報の書き出しを一度だけ行い、Auth Broker がローカルで署名します。Datadog の更新では、**Auth Broker からの HTTPS** が完全一致するトークンエンドポイントだけに到達します。通常のリクエストや静的認証情報を使うリクエストには、どちらの経路も不要です。
8. **mitmproxy** は検証済み TLS B を確立し、通常のリクエストをストリーミングするか、上限付きで署名済みの AWS リクエストを一つ送ります。
9. **Docker のログ**は、ホスト側で Go がレビューに使う、上限付きで秘密を含まない監査根拠を保持します。

完全な保証を一つの技術だけで実装しているわけではありません。

## 失敗時の動作

- 実行環境またはサービスのイメージが見つからない、または互換性がない場合、安全でない作成より前に検証が失敗します。
- ダイジェスト、ラベル、API、実行ユーザー、エントリーポイントが一致しなければ、安全側に停止します。
- 正本と埋め込み用の写しに差があれば、リポジトリ検査で失敗します。
- 不正な Rego または全 Context の集約は、有効化より前に失敗します。
- OPA または Auth Broker に障害が起きた場合、Gateway は通信を通さない応答を返します。
- Docker またはホストの障害は、強制基盤を失わせます。Tobari は、その侵害下での保護を主張しません。
- 既存の保管庫があるのにルート鍵が見つからない場合、鍵を置き換えず、ロック解除を拒否します。

## 保証と制限

**契約とテストで保証すること:** 固定されたコンポーネントの役割。通常利用するサービスを不変に識別できること。バイト単位で正本との一致を検査した埋め込み用の写し。分離した認証情報用ソケット。Auth Broker にプロバイダー CLI がないこと。補助プロセスに待受ポートやソケットのマウントがないこと。OPA に外部接続経路がないこと。正確な Compose 構成。実行環境の互換性を事前検査すること。

**保証しないこと:** イメージダイジェストだけでコードが安全になること。Docker、カーネル、ホストが侵害された後の分離。利用者が選んだ独自イメージの来歴。GHCR や外部レジストリの可用性。独自の実行環境レシピでインストールした任意ツールのセキュリティレビュー。

## まとめ

Tobari の動作は、複数技術の組み合わせで成り立ちます。Go が検証と構成管理を行い、Docker が境界を実現します。Gateway が HTTP/TLS 通信に判断を適用し、OPA/Rego が許可を判断し、Auth Broker が認証情報を管理します。不変な OCI イメージの識別情報と、正本と埋め込み用の写しの一致検査により、配布する実行環境をレビュー可能にします。

## 理解を確認する

製品上の主張を、具体的な技術境界に結び付けて説明できるはずです。

<details>
  <summary>OPA が Gateway から分離されているのはなぜですか？</summary>
  OPA
  は転送や外部接続の権限を持たず、同じ入力に対して同じ結果を返す判断処理を担当します。Gateway
  はリクエスト、TLS、ネットワークの制御を担当し、判断結果を検証します。
</details>

<details>
  <summary>
    Auth Broker が Workspace 向け HTTP API ではなく Unix ソケットを使うのは
    なぜですか？
  </summary>
  到達経路を、決められたホスト制御操作と Gateway
  への実行時マウントに限定するためです。Workspace と OPA には、Auth Broker
  へのソケットも TCP 経路も与えません。
</details>

<details>
  <summary>
    不変なイメージダイジェストは、実装が安全であることを証明しますか？
  </summary>
  いいえ。レビュー済みの内容をバイト単位で固定し、更新され得るタグへの差し替えを防ぐものです。安全性は引き続き、コード、設定、テスト、信頼の前提、実行環境の基盤に依存します。
</details>

製品の境界が不明確な場合は、[システム全体像](../system-overview/)へ戻ってください。次に[コード構造](../code-architecture/)で、Go リポジトリがこれらの責務を分離する方法を確認します。
