Tobari の HTTP/HTTPS 通信には、Workspace、Gateway、OPA、Auth Broker、外部の接続先という五つの構成要素が関わります。Workspace から外部の接続先へ到達する経路は Gateway だけです。Gateway は OPA に許可判断を問い合わせ、Auth Broker が管理する認証情報を使う場合だけ、許可後に Auth Broker と連携します。

役割を分けているため、Tobari は単なる Docker のラッパーではありません。Gateway が通信経路を開閉し、OPA がポリシーを判断し、Auth Broker が認証情報の本体を Workspace の外に保持します。ログインできることと、外部通信が許可されることは別です。

Tobari が制御する範囲をまだ確認していない場合は、先に[概要](../../start/overview/)を読んでください。このページでは、Docker ネットワークや TLS の詳細には入らず、五つの役割だけを整理します。

## 五つの構成要素

### 1. Workspace：エージェントが作業する環境

[Workspace](../../reference/glossary/#workspace) は、一つのプロジェクトルートと Context に結び付いた論理的な作業環境です。エージェントは、そのプロジェクトルートを読み書きし、Workspace 専用の永続ホームを使います。実行用コンテナは作り直せますが、Workspace の識別情報や永続状態まで同じタイミングで消えるとは限りません。

Workspace 内のプロセスは信頼しません。作業対象のディレクトリは読み取り、変更、削除できます。一方で、作業対象外のホストファイル、Docker の制御機能、ほかの Workspace、外部への直接経路、Auth Broker が管理する認証情報の本体は渡しません。

### 2. Gateway：通信経路を強制するコンポーネント

Gateway は、Workspace から透過的に送られた HTTP 通信を受け取ります。呼び出し元が申告するヘッダーではなく、ホストが作ったネットワークと登録情報から Context とプロジェクトを特定します。このようにホスト側の事実から確立する通信主体を、プリンシパル（principal）と呼びます。

Gateway は HTTP リクエストを正規化し、OPA に一度だけ問い合わせます。拒否された場合は、接続先への接続を作らずにローカルで応答します。許可された場合は、Gateway 自身が接続先へ別の接続を開き、リクエストを転送します。

OPA はパケットを転送しません。実際の通信を止めたり通したりするのは Gateway です。

### 3. OPA：ポリシーを判断するコンポーネント

通信を許可するか判断する部品です。Open Policy Agent（OPA）は、Context、プロジェクト、スキーム、ホスト、ポート、メソッド、パスなどを使って通常の HTTP 通信を評価します。クエリーと秘密情報を除いたヘッダーも入力されますが、リクエスト本文や認証情報の値は含まれません。

OPA は構造化された許可または拒否を返します。OPA が利用できない場合や、応答の形式が不正な場合は、許可として扱いません。

### 4. Auth Broker：認証情報を Workspace の外で管理するコンポーネント

Auth Broker が参加するのは Broker path だけです。static credential record 一つを encrypted
Context vault に保持し、Workspace へ project-bound opaque handle だけを渡します。

Gateway は policy 前に non-secret binding だけを照合します。OPA が HTTP effect を allow した
後だけ、Auth Broker は同じ static revision を一度解決します。

ログインは認証状態を作成しますが、ポリシールールを追加しません。

### 5. 接続先：許可後に Gateway が接続する外部サービス

外部サービスがリクエストを受け取るのは、OPA が通信を許可し、必要な認証処理が成功した後だけです。HTTPS の場合、Gateway から接続先までは、Workspace 側とは別に検証された TLS 接続を使います。

許可した接続先には、Workspace が読み取れるデータを送信できます。Tobari はリクエスト本文の意味を解析せず、その内容が安全かどうかも判断しません。

## 一つのリクエストを追う

Workspace 内のツールが `PUT https://example.com/api/items/42` を送るとします。

1. ツールは通常の HTTPS URL を開き、保護済みの経路がリクエストを透過的に Gateway へ届けます。
2. Gateway は、カーネルが観測した Workspace の送信元エンドポイントから Context とプロジェクトを特定します。呼び出し元が書いた識別用ヘッダーは信頼しません。
3. Gateway は本文と認証情報を含まないポリシー入力を作り、OPA を呼び出します。
4. 一致する許可ルールがなければ、OPA は拒否します。Gateway は `403 policy_denied` を返し、接続先へ接続しません。
5. 信頼するホストで、保持された通信条件をレビューできます。
6. Context、プロジェクト、ホスト、ポート、メソッド、パスが一致するルールを許可し、新しいリクエストとして再実行した場合に、Gateway は接続先への通信を始めます。

最初のリクエストは権限の申請ではありません。現在のルールに一致すれば通り、一致しなければ拒否される、実際の通信試行です。

## 失敗時の動作

| 失敗                          | 観測される結果                      | 起きないこと                                   |
| ----------------------------- | ----------------------------------- | ---------------------------------------------- |
| 一致する許可ルールがない      | `403 policy_denied`                 | 接続先への接続、自動許可、元のリクエストの再送 |
| OPA が利用不能または不正      | `503 policy_unavailable`            | 別の判断方法への切り替え                       |
| Gateway が利用不能            | 保護済みの接続が失敗                | インターネットへの直接接続への切り替え         |
| 宣言済み binding に実認証情報 | `403 broker_auth_required`          | ポリシーレビュー、互換経路、接続先への通信     |
| Broker ハンドルが不正         | `403 credential_handle_invalid`     | 通常の認証方式への切り替えや接続先への接続     |
| Auth Broker が利用不能        | `503 credential_broker_unavailable` | 認証情報の解決、接続先への通信                 |

## 保証と制限

### このモデルが示す保証

サポート対象の Docker 構成では、Workspace に外部への直接経路はありません。Gateway はリクエストを転送する前に、OPA の許可判断を受け取る必要があります。Auth Broker が扱う固定の認証情報、更新可能な状態、リクエスト用に導出した認証情報は、Workspace と OPA の外に留まります。

### このモデルが示さない保証

作業対象のディレクトリ内にあるファイルは、Workspace のプロセスから保護されません。許可された接続先へ、Workspace から読めるデータを送ることも防ぎません。ホスト、Docker Engine または VM、カーネル、Gateway、OPA、Auth Broker、およびそれらが管理する状態が侵害されていないことを前提とします。一般的な SSH、任意の TCP、UDP、QUIC、DNS、マルウェア対策、同じ Workspace 内のプロセス分離は提供しません。

## まとめ

基本の経路は **Workspace → Gateway → 外部の接続先** です。OPA がポリシーを判断し、Gateway が通信経路を強制します。Auth Broker は必要な場合に限り、許可後に宣言済みの認証処理を一つ実行します。

## 理解を確認する

<details>
  <summary>
    OPA が許可を返した場合、実際に接続先へ接続するコンポーネントはどれですか？
  </summary>
  Gateway です。OPA は判断を返しますが、リクエストを転送しません。
</details>

<details>
  <summary>
    Auth Broker
    のログインに成功すると、そのプロバイダーへの通信も許可されますか？
  </summary>
  いいえ。ログインが作るのは Context が所有する認証状態です。通常の HTTP
  通信には、引き続き OPA の許可が必要です。
</details>

<details>
  <summary>
    Workspace のプロセスは、作業対象のディレクトリに対して何ができますか？
  </summary>
  ファイルを読み取り、変更し、削除できます。作業対象のディレクトリはエージェントへ書き込みを委ねる範囲であり、Workspace
  から保護される範囲ではありません。
</details>
