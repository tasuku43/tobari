Tobari の standard の外向き経路には、Workspace、Gateway、OPA、Upstream の
4つが関わります。project-bound Workspace が HTTP/HTTPS の接続先へ到達する
経路は Gateway だけです。Gateway は通常の exact request effect を許可するか
OPA に問い合わせ、ローカルで拒否するか、別の upstream connection を開きます。

認証とネットワーク権限は別です。Claude Code と Codex はネイティブログイン
状態を Workspace home に保存します。Gateway は Authorization と cookie を
secret request data として扱い、OPA と audit から除外し、allow 後だけ元の値を
変えずに転送します。

## 参加者ごとに図を読む

### 1. Workspace：作業とネイティブログインを実行する場所

Workspace は一つの長期利用する directory-bound Tobari で、永続 home を持ちます。
process は選択した project root を読み書きでき、同じ Workspace に保存された
native credential も読めます。別 Workspace の home、host credential、Docker
control、public network への直接経路は受け取りません。

### 2. Gateway：通信を強制する場所

Gateway は透過的に届く HTTP traffic を受け取り、host-owned registration から
Workspace Manifest/project principal を導出し、decision/audit data から secret request value
を除き、OPA に一度問い合わせます。deny では接続先の DNS lookup や connection
を実行しません。allow では authentication を含む元の request を一つの別接続へ
転送します。

### 3. OPA：判断する場所

OPA は trusted principal、scheme、host、port、method、path から通常の HTTP effect
を判断します。request body や credential value は受け取りません。判断が取得
できない、または不正な場合は permission とみなしません。

### 4. Upstream：要求された接続先

Upstream が request を受け取るのは allow 後だけです。許可された接続先には、
Workspace が読めて送信を選んだ data が届き得ます。Tobari は request body の
意味を検査しません。

## 一つの具体的なリクエスト

tool が `PUT https://example.com/api/items/42` を送るとします。

1. guarded route が request を Gateway へ届けます。
2. Gateway が principal を導出し、body-free・secret-free の判断入力を作ります。
3. OPA が allow または deny を一つ返します。
4. deny では Gateway が `403 policy_denied` を返し、接続先に触れません。
5. trusted-host user は保持された exact effect を review し、明示的に再試行できます。
6. allow では Gateway が元の request を一度転送し、response を中継します。

native login は policy rule を作らず、policy approval は credential を作成・更新
しません。

## 失敗時の動作

| 失敗                     | 観測結果                  | **起きないこと**                      |
| ------------------------ | ------------------------- | ------------------------------------- |
| 一致する rule がない     | `403 policy_denied`       | 接続先 DNS と upstream connection     |
| OPA が利用不能または不正 | `503 policy_unavailable`  | fallback decision                     |
| Gateway が利用不能       | guarded connection が失敗 | public network への直接 fallback      |
| provider が login を拒否 | provider-owned failure    | Tobari による account metadata の合成 |

## 保証と限界

standard の対応 topology では、通常の HTTP/HTTPS を転送する前に Gateway が allow
を受け取り、secret request value が OPA と audit に入らないことを保証します。
project file を Workspace から保護すること、同じ Workspace 内の process isolation、
許可済み接続先への送信防止、host/kernel/Docker Engine/Gateway/OPA 侵害後の保護は
提供しません。

## まとめ

覚える経路は **Workspace → Gateway → Upstream**、判断するのは **OPA** です。
Workspace が native authentication を所有し、その HTTP effect を外へ出せるかは
Gateway が制御します。

  </summary>

  </summary>
  はい。isolation boundary は Workspace であり、その内部で process-level の
  credential isolation は提供しません。
</details>
