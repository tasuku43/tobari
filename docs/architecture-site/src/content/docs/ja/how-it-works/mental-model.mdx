Tobari の外向き通信には、Workspace、Gateway、OPA、Auth Broker、外部の接続先
という五つの主体が関わります。プロジェクトに結び付いた Workspace が
HTTP または HTTPS の接続先へ到達する経路は Gateway だけです。Gateway
は通常のリクエストを許可するか OPA に問い合わせ、Broker が管理する認証情報が
関わる場合にだけ Auth Broker と対話します。

この役割分担があるため、Tobari は単なる Docker のラッパーではありません。
Gateway は通信判断を実施し、OPA はポリシーを判断し、Auth Broker は Broker
管理の実物の認証情報を Workspace の外に保ちます。認証情報を使えることは、
通信が許可されることを意味しません。

Tobari が利用者へ提供するものをまだ知らない場合は、先に[概要](../../start/overview/)を読んでください。以下の図を読むために、Docker、プロキシ、ポリシーの知識は必要ありません。

## コンポーネント間の会話として図を読む

### 1. Workspace：プロジェクトの作業を実行する場所

[Workspace](../../reference/glossary/#workspace) は、ディレクトリに結び付いた、長期間存在する一つの Tobari を利用者向けに表す名前です。選択したプロジェクトルートに対してツールを実行し、専用の永続ホームを持ちます。実行用コンテナは交換できますが、論理的な Workspace とコンテナは同じものではありません。

Workspace 内のすべてのプロセスは信頼できないものとして扱います。プロセスは選択したプロジェクトルートを読み取り、変更できます。一方で、公開インターネットへの一般的な経路、Docker の制御権、別の Workspace への経路、Broker が管理する実物の認証情報は与えられません。

### 2. Gateway：通信を通すか止めるかを実施する場所

Gateway は Workspace のプロキシ通信を受け取ります。信頼できる Context とプロジェクトの識別情報を確立し、HTTP リクエストを正規化して、OPA に一度だけ問い合わせます。その判断を実際の通信経路へ反映するのも Gateway です。拒否された場合は接続先への接続を開かず、ローカルで応答します。許可された場合は接続先への別接続を作り、リクエストをストリーミングします。

OPA はパケットを転送しません。転送するのは Gateway です。

### 3. OPA：許可を判断する場所

[OPA](../../reference/glossary/#opa) は通常の HTTP 操作を評価します。判断材料には、信頼できる Context とプロジェクトの通信主体、スキーム、ホスト、ポート、メソッド、パスが含まれます。クエリーの値と、秘密情報を除いたヘッダーも入力されますが、リクエスト本文や認証情報の値は含まれません。

OPA は構造化された許可または拒否を返します。OPA が利用できない場合や、応答の形式が不正な場合に、許可として扱われることはありません。

### 4. Auth Broker：通信許可ではなく認証情報を管理する場所

Auth Broker が関係するのは、Broker 経由の認証方式だけです。型付きの静的な認証情報または更新可能な認証状態を、暗号化した Context 保管庫に保持します。Workspace へ渡すのは、内容を解釈できずプロジェクトに結び付いたハンドルだけです。Gateway はポリシー判断の前に、秘密を含まない結び付き情報を照合できます。OPA が通常の HTTP 操作を許可した後に限り、Broker は静的な秘密情報を一度だけ解決する、Datadog トークンを選択または更新する、非公開のホストコンパニオンを使って上限付きの AWS リクエスト一件へ署名する、のいずれかを実行できます。

ログインは認証状態を作成できますが、ポリシー規則は追加しません。

### 5. 接続先：リクエストの宛先

接続先のサービスが Gateway からリクエストを受け取るのは、操作が許可された後だけです。HTTPS の場合、最後の区間には別に検証された TLS 接続を使います。許可された接続先は、Workspace が読み取れ、その許可済み経路で送ることを選んだデータを受け取れます。Tobari はリクエスト本文の意味を検査しません。

## 一つの具体的なリクエスト

Workspace 内のツールが `PUT https://example.com/api/items/42` を送信するとします。

1. ツールは設定済みの HTTP プロキシを通してリクエストを送ります。
2. Gateway は呼び出し元のヘッダーではなく、受信したネットワークインターフェースからプロジェクトの識別情報を導出します。
3. Gateway は本文を含まないポリシー入力を作り、OPA を呼び出します。
4. 現在の規則が一致しなければ、OPA は拒否します。Gateway は `403 policy_denied` を返し、接続先には何も到達させません。
5. 信頼できるホスト上で、保持された完全一致の操作を利用者がレビューできます。
6. その Context、プロジェクト、ホスト、ポート、メソッド、パスの組み合わせが許可され、意図的に再試行された場合に、Gateway は接続先への接続を作ります。

最初のリクエストは、許可を自動申請するものではありません。現在の権限に一致すれば進み、一致しなければ失敗する、試行された操作です。

## 失敗時の動作

| 失敗                     | 観測される結果                           | **起きないこと**                                         |
| ------------------------ | ---------------------------------------- | -------------------------------------------------------- |
| 一致する規則がない       | `403 policy_denied`                      | 接続先への接続も自動許可も行われない                     |
| OPA が利用不能または不正 | `503 policy_unavailable`                 | 代替判断は行われない                                     |
| Gateway が利用不能       | プロキシ接続が失敗                       | Internet への直接接続へ切り替わらない                    |
| Broker ハンドルが不正    | `403 credential_handle_invalid`          | そのまま転送する経路へ切り替わらず、接続先へも接続しない |
| Auth Broker が利用不能   | `503 credential_broker_unavailable`      | 解決、更新、署名、接続先への操作のいずれも行われない     |
| AWS/Datadog の結果が不明 | `409 credential_refresh_outcome_unknown` | 自動再実行も、アプリケーションからの接続先への試行もない |

## 保証と制限

### このモデルが保証すること

サポート対象の Docker 構成では、Workspace に外部への直接経路はありません。Gateway はリクエストを転送する前に、許可の判断を受け取る必要があります。Broker が扱う静的な秘密情報、更新可能な状態、リクエスト用に導出した認証情報は、Workspace と OPA の外に留まります。

### このモデルが保証しないこと

選択したプロジェクトルート内のファイルを、Workspace から保護するものではありません。許可された宛先が、Workspace から読めるデータを受け取ることも止めません。ホスト、Docker Engine または VM、カーネル、Gateway、OPA、Auth Broker、およびそれらが管理する信頼対象の状態が侵害されていないことを前提とします。一般的な SSH、任意の TCP、UDP、QUIC、DNS、マルウェア対策、同じ Workspace 内のプロセス分離は提供しません。

## まとめ

基本の経路は **Workspace → Gateway → Upstream** です。**OPA が許可を判断し**、**Auth Broker は必要な場合に限り、許可後に宣言済みの認証操作を一つ実行します**。経路を実際に開閉するのは Gateway です。

## 理解を確認する

認証、ポリシー判断、ネットワーク転送が三つの別の仕事である理由を説明できるはずです。

<details>
  <summary>
    OPA が許可を返した場合、実際に接続先へ接続するコンポーネント はどれですか？
  </summary>
  Gateway です。OPA は判断を返しますが、リクエストを転送しません。
</details>

<details>
  <summary>
    Auth Broker
    のログインに成功すると、そのプロバイダーへの通信は許可されますか？
  </summary>
  いいえ。ログインが作るのは Context が所有する認証状態です。通常の HTTP
  操作には、引き続き OPA の許可が必要です。
</details>

<details>
  <summary>
    Workspace のプロセスは、選択したプロジェクトルートに対して何ができますか？
  </summary>
  そこにあるファイルを読み取り、変更し、削除できます。選択したルートは書き込みを
  委ねた範囲であり、Workspace から保護される内容ではありません。
</details>
