Tobari を通る HTTPS リクエストは、二つの TLS 接続を使います。クライアントは通常の HTTPS URL を使い、固定の合成 DNS 応答と Workspace の保護済み経路が TCP 接続を Gateway の透過リスナーへ届けます。クライアントは Tobari CA の下で Gateway との TLS 接続 A を確立します。Gateway はこの接続を終端し、復号した HTTP 属性を認可に使います。

ポリシーがリクエストを許可すると、Gateway は接続先へ別の検証済み TLS 接続 B
を作ります。最終的な宛先へ平文 HTTP を送るわけではありません。Tobari CA を信頼することと、
ポリシー上の許可を得ることは別です。通信の検査を拒否する、証明書を固定したクライアントは、
Gateway を迂回せず接続に失敗します。前の
[リクエストの流れ](../request-journey/)では、この TLS 分割を処理全体の中に位置付けています。

## HTTPS 通信を順番に追う

### 1. クライアントが Gateway へ到達する

クライアントは通常の HTTPS URL を保ちます。合成 DNS が `198.18.0.10` を返し、既定の TCP 経路がプロジェクトの Gateway を指し、Gateway が透過リスナーへ接続を振り分けます。TLS SNI が最初の HTTPS 接続先を示します。このリスナーへ到達しただけでは、ネットワーク上の許可を得られません。

### 2. Gateway が TLS 接続 A を確立する

Gateway は検査対象の TLS ハンドシェイクを受け取り、Tobari のインストール CA で署名した末端証明書を提示します。Workspace ランタイムは、システム CA 群と公開された Tobari CA から一時的なクライアント用信頼バンドルを作ります。

そのためクライアントは Gateway と **TLS 接続 A** を確立できます。Gateway はこの TLS セッションを終端し、汎用の判断契約に必要な、復号済みの HTTP メソッド、接続先、パス、クエリー、ヘッダーを確認できます。

### 3. Gateway が復号済み HTTP リクエストの許可を確認する

Gateway は Workspace Template とプロジェクトの識別情報を導出し、透過経路では SNI、HTTP の接続先、元のポートが一致することを要求し、認証情報を削除または秘匿化します。本文を含まない正規化済み入力を、一度だけ OPA へ送ります。リクエスト本文は、ポリシー上の識別情報を決める要素ではありません。CA を信頼していても、この判断は省略できません。

拒否された場合や判断に失敗した場合、そのリクエスト用の TLS 接続 B は作られません。

### 4. Gateway が TLS 接続 B を確立する

許可と必要な認証操作が完了すると、Gateway は接続先のアドレスを名前解決して固定します。続けて、要求された接続先へ **TLS 接続 B** を作り、mitmproxy の通常の検証動作で接続先の証明書を検証します。

最終サービスが受け取るのは、Gateway から暗号化された TLS 通信です。ポリシー判断に HTTP 属性が必要なため、信頼する Gateway プロセス内には平文が存在します。しかし、最後のネットワーク区間を平文で送るわけではありません。

### 5. Gateway が許可済みメッセージをストリーミングする

Gateway はヘッダーを転送し、許可済みの本文を TLS 接続 B 経由でストリーミングします。レスポンスは B を通って戻り、Gateway が内容を受け取った後、Workspace のクライアントへ A で再暗号化されます。

## 証明書の具体例

Workspace 内で `curl https://api.example.com/v1/data` を実行するとします。

- `curl` は Tobari CA を含むランタイム用の統合証明書バンドルを信頼します。
- `api.example.com` 用として見える証明書は TLS A に属し、Tobari CA の下で生成されています。
- Gateway は `GET /v1/data` を見て OPA へ問い合わせます。
- 許可された場合、Gateway は TLS B で本物の `api.example.com` の証明書を独立して検証します。

同じクライアントが接続先の証明書または公開鍵を固定している場合、A で提示された証明書は固定値と一致しません。接続は失敗します。Tobari は証明書固定を無効化せず、直接経路も作らず、透過的なそのまま転送へ暗黙に切り替えません。

## CA を信頼しても通信が許可されるわけではない

これらは別々の問いです。

| 問い                                                             | 仕組み                                  | 意味                                                                             |
| ---------------------------------------------------------------- | --------------------------------------- | -------------------------------------------------------------------------------- |
| クライアントは Gateway と検査可能な HTTPS セッションを作れるか？ | ランタイムが Tobari CA を信頼           | Gateway が復号済みリクエストを受け取れる                                         |
| この通常の HTTP 操作は接続先へ進めるか？                         | Gateway が強制する OPA の判断           | Workspace Template、プロジェクト、ホスト、ポート、メソッド、パスが許可されている |
| Authentication 管理の認証情報を解決できるか？                    | 識別子の結び付きすべてと事前の OPA 許可 | 一つのリクエストで宣言済みのヘッダー置換を行える                                 |

動作する CA が解決するのは最初の行だけです。

## 失敗時の動作

- **Tobari CA がない、またはクライアントが信頼しない:** アプリケーションリクエストを認可する前に TLS A が失敗します。
- **証明書の固定:** Gateway が生成した末端証明書が固定値と一致しないため、TLS A が失敗します。
- **OPA による拒否または障害:** Gateway は許可済みの接続先経路を作らず、拒否はローカルで完了します。
- **DNS またはアドレスの検証に失敗:** 安全でない代替宛先へ TLS B を試しません。
- **接続先証明書の障害:** TLS B が失敗します。ポリシー規則を拒否へ変えたり、安全でない再試行を行ったりしません。
- **クライアントが通常の直接ソケットを開く:** 保護済みの透過経路が Gateway の判断へ到達し、TLS の迂回経路にはなりません。

## 保証と制限

**対応する通信で保証すること:** 二つの独立した TLS 接続。ポリシー判断に使える汎用 HTTP 属性。接続先 TLS の検証を維持すること。ポリシー拒否時に接続先への経路を遮断すること。証明書固定を迂回しないこと。

**保証しないこと:** すべての TLS 実装、独自の証明書保管領域、証明書を固定したクライアントとの互換性。Workspace のプロセスと最終サービス間を直接結ぶエンドツーエンド TLS。信頼する Gateway から平文を隠すこと。HTTP/3/QUIC の検査。

リポジトリのテストは、検査対象となる HTTPS の動作、スキームの正規化、CA の利用、直接経路を使った迂回の失敗を検証します。二つのハンドシェイクをパケットキャプチャーし、バイト単位で検証するテストではありません。そのため、二接続という主張は、採用済みのアーキテクチャ判断と固定された mitmproxy 設定にも基づきます。

## まとめ

保護済みの透過入口により、クライアントと Gateway の間に TLS A ができます。Gateway は復号済みの HTTP 属性を認可し、許可後にだけ本物のホストを名前解決して、接続先への検証済み TLS B を別に作ります。CA の信頼、ポリシー上の権限、認証情報を使う権限は、それぞれ別です。

## 理解を確認する

二つの TLS 接続を描き、その間にポリシー判断を置けるはずです。
