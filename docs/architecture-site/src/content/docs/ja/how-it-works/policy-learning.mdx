学習可能なポリシー拒否はリクエストを止め、秘密情報を含まない根拠を残します。
Workspace 自身へ承認を求めることはありません。信頼するホスト上の Tobari が、保持した
根拠を検証し、レビュー用の不透明な完全一致候補を導出します。利用者は許可または
拒否を明示的に選びます。

選択を適用すると、ポリシー全体を検証して新しいリビジョンを途中状態を見せずに有効化します。
有効化に失敗した場合や、候補が古くなった場合は直前のポリシーを維持します。元のリクエストは、
利用者やツールが意図的に実行したときだけ再試行されます。初期状態の拒否、学習済みの完全一致拒否、
リセットは、それぞれ異なる状態と操作です。first public V1 は学習済みの完全一致 authority を
広げません。この流れは確立済みの
[プロジェクト識別](../project-identity/)と[リクエストの流れ](../request-journey/)を利用します。

## 1. 拒否は許可の申請ではない

OPA は Workspace Template policy baseline grant と learned exact allow のどちらにも一致しない effect を
default deny します。default Workspace Template には有限の agent-ready baseline があり、完全な method
policy は Workspace Template が所有します。deny-only や GET-only はその method policy で表します。request
は schema、principal、fixed port、Workspace binding、immutable Workspace Template policy ceiling が有効な
場合だけ learnable になれます。

Gateway は `403 policy_denied` を返します。学習可能なレスポンスが示すのは、信頼するホスト上のレビュー場所と、利用者から見える完全一致の HTTP 操作だけです。自動再試行がないことも明示します。

## 2. 本文と秘密情報を除いて根拠を保持する

Gateway は、上限付きのスキーマ 1 拒否監査を、ローテーションされる Docker ログへ書きます。候補の発見処理は上限付きの末尾だけを読み、厳密に検証した拒否記録だけを受け入れます。

根拠には、Workspace Template とプロジェクトの識別情報、ホスト、ポート、メソッド、パス、理由、時刻、秘密を含まない診断情報が含まれます。クエリー、ヘッダー、本文、識別子、agent CLI のログイン値は含まれません。認証情報らしい URL パスは、値を `[redacted-credential]` に置き換えます。

根拠を保持する量には上限があり、無期限に残る許可待ち一覧ではありません。操作前に観測記録が選択したログ範囲の外へ出ると、その記録を使って状態変更を認可することはできません。

## 3. CLI が不透明な完全一致候補を導出する

保留中の観測記録は、次の値が完全一致するもの同士でまとめます。

- 安定した Workspace Template ID
- 安定した Context ID と Workspace ID
- ホスト
- ポート
- メソッド
- 正規化済みの生のパス

本文の内容や有無、クエリー、ヘッダー、理由、状態、リクエスト ID、時刻、外部サービス、プロファイルの表示用根拠は、候補の識別情報を分割しません。

候補 ID は `pcy_…` という形式で、これらの要素から導出されます。内容を解釈しない不透明な値です。操作では、一覧上の位置を権限として使わず、ID をデコードしたり組み立て直したりしません。受け取った値を変更せずに使います。

規則の記録自体はスキーム項目を保存しません。現在は、重ならない固定のスキームとポートの契約によって HTTP と HTTPS の権限を分けています。この契約が変わった場合に、スキームをまたぐ安全性を推論してはいけません。

## 4. レビューと操作を分離する

`policy candidates` は機械向けの候補発見手段です。`review permissions` は人が権限を確認するための画面です。リダイレクトされた場合や機械可読形式のレビューは読み取り専用です。raw TTY の一覧では、完全一致の `Allow` または `Deny` キーは変更されていない型付き ID の判断を準備するだけで、テンプレート権限は詳細画面からしか準備できません。`review permissions --watch` は同じ上限付き読み取りを backoff 付きで繰り返し、変更のない timer refresh では一つの alternate-screen frame を保ち、Apply 後も開いたままになります。これは権限の streaming ではなく、通信を再試行しません。任意の terminal cue は固定された信頼済み OSC 9 または BEL byte だけを使い、拒否の根拠を含みません。`auto` は iTerm2 の正確な識別、または保護された cmux terminal identity の完全な組を認識します。

一時選択した各判断は、変更していない不透明な ID を保持します。`Apply` を押すと、選択済みの集合全体を再検証し、一度だけ有効化します。それより前にキャンセルすれば、何も書き込まずにすべて破棄します。Workspace Template を切り替える前に適用または破棄するため、永続ソースの昇格は journal で保護した一つの domain 世代置換のままです。表示順、字下げ、ラベルの文言、組み立て直したホストやパスは操作対象になりません。機械から呼び出す場合は、変更していない ID 一つを `policy allow --id …` または `policy deny --id …` へ渡します。

操作時に、Tobari は現在保持している根拠と現在の規則を読み直します。ID が古い、期限切れ、既存規則の対象済み、または一致しない場合、ポリシーを変更しません。

## 5. ポリシー全体を検証して有効化する

有効な完全一致操作またはレビュー済みの集合に対して、Tobari は次を行います。

1. 集約ポリシーの状態変更をロックする
2. 現在の集約リビジョンと、学習済み許可・拒否の完全なスナップショットを検証する
3. 対象 Workspace Template 専用の候補をビルドしてテストする
4. 所有者だけが書ける、`fsync` 後に名前を変更する手順で Workspace Template ソースを書く
5. **すべての** Workspace Template から内容アドレス方式の集約を生成する
6. 候補全体を OPA でテストする
7. 内容アドレス方式の集約投影をアトミックに公開する
8. リビジョン付きの完全なバンドルを、所有者ラベル付きの Docker 管理ポリシーボリュームへ公開する
9. 稼働中の OPA が、そのリビジョンと完全一致する値を報告するまで待つ
10. 新しい状態を永続化する

失敗時にはソースと直前の動作確認済み投影・状態を復元します。並行変更がある場合は黙って上書きせず、`policy_data_changed` になります。権限を狭める変更では、最初に全拒否へ移行するリビジョンを有効化します。候補の変更途中に、古く広い権限を配信しないためです。通常の有効化では、OPA コンテナを動かしたままにします。

## 6. 意図的に再試行する

有効化しても、古いリクエストは再実行されません。利用者またはエージェントが新しいリクエストを意図的に送信し、通信主体の確立とポリシー判断をもう一度通ります。

これは、冪等でないメソッドや本文で特に重要です。Tobari は、内容を考慮しない再実行が安全かどうかを判断できません。

## 許可、拒否、リセット

| 判断                                     | 意味                                                                                                   |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Workspace Template policy baseline grant | snapshot authority。固定 agent-ready data は選択可能な profile ではありません                          |
| Workspace Template policy terminal deny  | pending review に入らず candidate/DNS/Authentication/upstream work がゼロの ceiling rejection          |
| 学習済みの完全一致許可                   | 一つの Workspace Template、プロジェクト、ホスト、ポート、メソッド、パスに対する権限                    |
| 学習済みの完全一致拒否                   | 明示的にレビューした終端的な拒否。その HTTP 操作では許可より優先されます                               |
| `policy reset`                           | 学習済み許可または完全一致拒否を一つ削除し、初期または既定の評価へ戻します。許可する操作ではありません |

## 具体例

次の完全一致許可が三つあるとします。

- `PUT /review/items/1`
- `PUT /review/items/2`
- `PUT /review/items/3`

この三つは独立した完全一致規則のままです。隣接していても共有 path authority を導出しません。
`/review/admin`、別 project、別 method は、各 effect を個別に review しない限り拒否されます。

## 失敗時の動作

- 学習できない拒否は、レビュー用コマンドを提示しません。
- 不正または秘密を含むログデータは、根拠として受け入れません。
- 古い候補や参照から規則は作りません。
- Workspace Template ソースまたは集約ポリシーが一つでも不正なら、有効化を中止します。
- ソースが並行変更されていた場合は、上書きせず中止します。
- OPA の再作成に失敗した場合は、制御された復元が可能な範囲で、直前の動作確認済み権限を戻します。
- リセット後、同じリクエストは再びレビュー可能な拒否になる場合があります。「すべて許可」にはなりません。

## 保証と制限

**保証すること:** 観測しただけでは権限は変わりません。状態変更には不透明な参照一つを使います。完全一致規則は Workspace Template とプロジェクトに結び付きます。ポリシー全体の検証を、有効化より先に行います。ワイルドカードの自動作成も、リクエストの再実行もありません。本文によって許可範囲が暗黙に狭まることもありません。

**保証しないこと:** 拒否記録の無期限保持。本文単位の制御。外部サービス操作の意味解釈。ポリシーの自動最小化。人による承認判断が安全であること。OPA 再作成中の完全な無停止。

## まとめ

拒否が作るのは上限付きの根拠であり、許可ではありません。ホストはプロジェクトに結び付いた不透明な候補を導出し、完全一致の判断を明示的に選びます。影響するすべてのポリシーソースを一つの集約として検証し、アトミックに有効化します。再試行は、利用者が選んだ場合にだけ行います。
