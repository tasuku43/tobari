Tobari は、プロジェクト、Workspace、Workspace Manifest、Runtime、クラスター、
インストール環境の状態を所有範囲ごとに分けます。ライフサイクル操作が削除するのは
宣言した範囲だけです。そのため `exit`、`delete`、クラスターの停止、Runtime の再作成では、
それぞれ残るものが異なります。

永続記録から安全に再構築できる実行時状態がある一方で、欠損や不整合を推測せず
処理を止める状態もあります。コンテナやネットワークの消失は、論理 Workspace の消失を
意味しません。以下の表では、[Workspace のライフサイクル](../workspace-lifecycle/)の
境界を各保存領域に適用します。

## 管理主体と目的ごとの状態

以下のパスは、特に記載がない限り、実際に使われる XDG の設定／状態ルートからの相対パスです。

| 状態                               | 管理主体と意味                                                                                   | 寿命                                                                           |
| ---------------------------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| プロジェクトルート                 | immutable Workspace Manifest の `source_access` に従って mount する user-selected live host file | Tobari のライフサイクル操作では削除しない                                      |
| `roots/<hash>.json`                | 正規化済みプロジェクトルートと Workspace Manifest ID の組に対するルート索引                      | 論理 Workspace と一緒に作成・削除                                              |
| `instances/<id>/state.json`        | 安定した Workspace ID、Manifest との結び付き、要求／調整済み Runtime、診断用 Docker ID           | 論理 Workspace と一緒に作成・削除。Docker の観測より優先                       |
| `instances/<id>/home`              | Workspace ごとの書き込み可能なホーム領域と、agent CLI が所有するログイン状態                     | `exit` や Runtime の再作成後も残り、Workspace の削除で消える                   |
| Workspace Manifest                 | host-owned の stable ID、agent/runtime/policy/shell の desired declaration                       | Workspace やクラスターの実行環境を操作しても残る                               |
| Runtime `source/` と不変リビジョン | インストール全体で再利用するビルドソースと成功履歴                                               | Workspace と Manifest のライフサイクルを越えて残り、build だけでは展開されない |
| Manifest のポリシー原本            | exact-host domains と Advanced モードの Rego                                                     | クラスターの実行環境より長く残り、検証済みの有効化か明示編集だけで変わる       |
| 統合ポリシー生成物                 | OPA に読み取り専用でマウントする全 Manifest 用ルーター、データ、モジュールの写し                 | 原本から不可分に公開し、クラスター稼働中だけ有効                               |
| 現在有効なポリシーバンドル         | owner label 付きの Docker 管理ボリュームにある完全な OPA bundle                                  | `cluster down --purge` だけが削除し、原本から再構築する                        |
| プリンシパル台帳                   | host-issued の Workspace 送信元、Gateway endpoint、network、Manifest／project の結び付き         | Workspace network に合わせて調整し、Gateway に read-only で mount              |
| host-owned lifecycle state         | Runtime と policy が使うホスト設定、信頼情報、検査結果                                           | `cluster down` と `--purge` の後も残り、安全でなければ停止                     |
| Gateway CA state                   | Workspace 側の HTTPS 検査に使う install-local CA                                                 | 通常の `cluster down` 後も残り、共有 CA volume は `--purge` で削除             |

クラスター状態には、共有資源名、読み込み済み Manifest 数、内容アドレス方式で作った
統合データの版、生成物のパスも記録します。現在選択中の Manifest は通信制御の権限ではなく、
Workspace home のログイン状態も Manifest に含めません。

## 操作ごとに保持するもの

| 操作または出来事          | Workspace home／identity                                        | Manifest／policy                 | shared service／CA                            | project files |
| ------------------------- | --------------------------------------------------------------- | -------------------------------- | --------------------------------------------- | ------------- |
| `exit`                    | 保持                                                            | 保持                             | 稼働を続け、CA も保持                         | 保持          |
| `delete`                  | 対象 Workspace の home、Runtime 記録、container、network を削除 | Manifest と policy source は保持 | 変更なし                                      | 保持          |
| `cluster down`            | Workspace が残る間は拒否                                        | 保持                             | service と一時 network を削除、CA は保持      | 保持          |
| `cluster down --purge`    | 保持                                                            | 保持                             | service、共有 CA、active policy bundle を削除 | 保持          |
| Runtime の再作成          | identity と home は保持。container は次の entry で調整          | policy は保持                    | 変更なし                                      | 保持          |
| container／network の消失 | logical state と home は保持                                    | 保持                             | 必要に応じて Gateway を再接続                 | 保持          |

## 正本に従って復旧する

### Docker の実行環境が見つからない

永続的な Workspace 記録が有効で、container や network が見つからない場合、Runtime の資源は
記録から作り直せます。次に Workspace へ入るときに再作成して Gateway をつなぎ直し、
プリンシパル台帳を更新したうえで、既存のプロジェクトルートと home を mount します。

### 永続状態が不完全

ルート索引があるのに instance 記録がない場合、Tobari は `incomplete` を報告します。
失われた ID、Manifest との結び付き、home の関係を推測しません。明示的に作り直す前に、
完全一致する `delete` で残った記録を片付けます。

### ポリシーの有効化に失敗

ポリシー変更では、排他制御、Manifest 単位の事前検査、全 Manifest を統合した状態での完全な
テスト、内容アドレス方式での公開、OPA が正常になるまでの待機を行います。入力が不正な場合や
有効化に失敗した場合、候補の一部だけを mount しません。原本を元に戻し、直前まで正常だった
統合データと状態を保持します。

### host-owned state または Workspace state の整合性検証に失敗

必要な host state が欠落または安全でない場合、Tobari は別の権限や identity を推測せず安全側に
停止します。owner、mode、symlink、schema を使用前に検証します。

## 具体的な復旧シナリオ

ホスト再起動後、Workspace container と専用 network はありませんが、ルート索引、instance state、
home は残っています。

1. `tobari` が永続的な project root と Manifest の記録を解決する
2. Manifest が要求する Runtime image を検証する
3. 内部 network と container を再作成する
4. Gateway を接続し、Workspace の guard と principal 登録を記録に合わせる
5. 同じ project root、Manifest ID、home を持つ logical Workspace へ入る

これは状態の調整であり、新しい Workspace の作成ではありません。

## 失敗時の動作

- owner、access mode、symlink、schema、identity の不一致は、安全でない再利用より前に失敗します。
- image がない、または Runtime API に互換性がない場合、project root を変更する前に失敗します。
- 既存の Workspace state が不完全なら、別の authority や identity を暗黙に作りません。
- policy 統合データの作成に失敗した場合、直前まで正常だった判断データを保持します。
- attached Workspace は `--force` で保護を明示的に解除しない限り削除できません。
- logical Workspace が一つでも残っていれば、クラスターの停止は失敗します。

## 保証と制限

**保証すること:** ライフサイクル操作の範囲は限定され、project files は削除しません。有効な
logical state から作り直せる Docker state は記録に合わせて調整できます。Workspace home と
host-owned lifecycle state は `cluster down --purge` の後も残ります。policy の一部だけを有効化
することはありません。

**保証しないこと:** 手動削除した project files、削除済みの Workspace home、破損した host storage、
侵害された trust host、外部 service 側のログイン失効、project 移動後の自動判定。

## まとめ

コンテナの有無だけから永続的な identity や利用者データを推測することはありません。各保存領域には
管理主体と削除操作が定められています。作り直せる Docker state や生成物は記録に合わせて調整しますが、
identity、policy、Workspace state が曖昧なら安全側に停止します。

## 理解を確認する

各ライフサイクル操作の後に何が残るか、予測できるはずです。

<details>
  <summary>
    <code>delete</code> は、<code>exit</code> が保持する何を削除しますか？
  </summary>
  完全一致する Workspace の root index、instance
  state、home、container、network、principal 台帳です。 project files と
  Manifest の state は削除しません。
</details>

<details>
  <summary>
    <code>cluster down --purge</code> は何を追加で削除しますか？
  </summary>
  共有 Gateway CA volume と active policy bundle を追加で削除します。Workspace
  home、Manifest、 policy source、host-owned lifecycle state は保持します。
</details>

<details>
  <summary>
    Workspace state が不完全な場合、Tobari は新しい identity を作れますか？
  </summary>
  いいえ。完全な記録がない状態で補完すると、存在しない権限を推測するため、安全側に停止します。
</details>

<details>
  <summary>
    container が消えても instance 記録が残っている場合、どうなりますか？
  </summary>
  Workspace は論理的には存在します。次の入室時に互換性のある container
  を作り、記録と状態を合わせます。
</details>

状態遷移は[Workspace のライフサイクル](../workspace-lifecycle/)へ戻ってください。次は[実装技術](../implementation-stack/)で、各技術をその境界に置く理由を確認します。
