Tobari は、プロジェクト、Workspace、Workspace Template、Runtime、クラスター、
インストール環境の状態を所有範囲ごとに分けます。ライフサイクル操作が削除するのは
宣言した範囲だけです。そのため `exit`、`workspace delete`、クラスターの停止、Runtime の再作成では、
それぞれ残るものが異なります。

永続記録から安全に再構築できる実行時状態がある一方で、欠損や不整合を推測せず
処理を止める状態もあります。コンテナやネットワークの消失は、論理 Workspace の消失を
意味しません。以下の表では、[Workspace のライフサイクル](../workspace-lifecycle/)の
境界を各保存領域に適用します。

## 管理主体と目的ごとの状態

以下のパスは、特に記載がない限り、実際に使われる XDG の設定／状態ルートからの相対パスです。

| 状態                                                         | 管理主体と意味                                                                                   | 寿命                                                                                     |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| プロジェクトルート                                           | immutable Workspace Template の `source_access` に従って mount する user-selected live host file | Tobari のライフサイクル操作では削除しない                                                |
| `workspace-authority/authority.json`                         | schema-1 Template/Context/Policy Memory と schema-3 Workspace の atomic authority envelope       | Context は Workspace 削除後も残り、各 exact resource action が狭い削除範囲を所有する     |
| `workspace-authority-runtime/workspaces/<workspace-id>/home` | Workspace ごとの書き込み可能 home と agent CLI 所有の login state                                | `exit` や Runtime 再作成後も残り、exact Workspace delete で消える                        |
| Workspace Template revision                                  | stable ID、不変 Boundary、baseline policy、exact Runtime binding、typed defaults                 | Context、Workspace、cluster runtime より長く残り、exact Template delete でだけ消える     |
| Runtime `source/` と不変リビジョン                           | インストール全体で再利用するビルドソースと成功履歴                                               | Workspace と Workspace Template のライフサイクルを越えて残り、build だけでは展開されない |
| Workspace Template のポリシーデータ                          | 再利用可能な canonical typed policy data                                                         | complete immutable Template revision の発行でだけ変わる                                  |
| Context Policy Memory                                        | 一つの Project/Template Context が所有する完全な remembered-decision revision                    | Workspace replacement 後も残り、Context と一緒にだけ消える                               |
| 統合ポリシー生成物                                           | OPA に読み取り専用でマウントする全 Context 用ルーター、データ、モジュールの写し                  | 原本から不可分に公開し、クラスター稼働中だけ有効                                         |
| 現在有効なポリシーバンドル                                   | owner label 付きの Docker 管理ボリュームにある完全な OPA bundle                                  | `cluster down --purge` だけが削除し、原本から再構築する                                  |
| プリンシパル台帳                                             | host-issued の Workspace 送信元、Gateway endpoint、network、Context／Workspace の結び付き        | Workspace network に合わせて調整し、Gateway に read-only で mount                        |
| host-owned lifecycle state                                   | Runtime と policy が使うホスト設定、信頼情報、検査結果                                           | `cluster down` と `--purge` の後も残り、安全でなければ停止                               |
| Gateway CA state                                             | Workspace 側の HTTPS 検査に使う install-local CA                                                 | 通常の `cluster down` 後も残り、共有 CA volume は `--purge` で削除                       |

クラスター状態には、共有資源名、読み込み済み Workspace Template 数、内容アドレス方式で作った
統合データの版、生成物のパスも記録します。現在選択中の Workspace Template は通信制御の権限ではなく、
Workspace home のログイン状態も Workspace Template に含めません。

## 操作ごとに保持するもの

| 操作または出来事          | Workspace home／identity                                        | Workspace Template／policy                 | shared service／CA                            | project files |
| ------------------------- | --------------------------------------------------------------- | ------------------------------------------ | --------------------------------------------- | ------------- |
| `exit`                    | 保持                                                            | 保持                                       | 稼働を続け、CA も保持                         | 保持          |
| `workspace delete`        | 対象 Workspace の home、Runtime 記録、container、network を削除 | Workspace Template と policy source は保持 | 変更なし                                      | 保持          |
| `cluster down`            | Workspace が残る間は拒否                                        | 保持                                       | service と一時 network を削除、CA は保持      | 保持          |
| `cluster down --purge`    | 保持                                                            | 保持                                       | service、共有 CA、active policy bundle を削除 | 保持          |
| Runtime の再作成          | identity と home は保持。container は次の entry で調整          | policy は保持                              | 変更なし                                      | 保持          |
| container／network の消失 | logical state と home は保持                                    | 保持                                       | 必要に応じて Gateway を再接続                 | 保持          |

## 正本に従って復旧する

### Docker の実行環境が見つからない

永続的な Workspace 記録が有効で、container や network が見つからない場合、Runtime の資源は
記録から作り直せます。次に Workspace へ入るときに再作成して Gateway をつなぎ直し、
プリンシパル台帳を更新したうえで、既存のプロジェクトルートと home を mount します。

### 永続 authority が不完全または矛盾している

最終 authority は root index と instance record の組ではなく、一つの atomic
envelope です。envelope が不正、Context/Workspace binding が矛盾、または mutation
outcome が unknown なら fail closed します。Docker resource から replacement identity
を推測したり mutation を部分 replay したりせず、次の exact action より先に `status`
または fault が宣言した read path で保持済み事実を分類します。

### ポリシーの有効化に失敗

ポリシー変更では、排他制御、Workspace Template 単位の事前検査、全 Context を統合した状態での完全な
テスト、内容アドレス方式での公開、OPA が正常になるまでの待機を行います。入力が不正な場合や
有効化に失敗した場合、候補の一部だけを mount しません。原本を元に戻し、直前まで正常だった
統合データと状態を保持します。

### host-owned state または Workspace state の整合性検証に失敗

必要な host state が欠落または安全でない場合、Tobari は別の権限や identity を推測せず安全側に
停止します。owner、mode、symlink、schema を使用前に検証します。

## 具体的な復旧シナリオ

ホスト再起動後、Workspace container と専用 network はありませんが、authority envelope
には Context と Workspace が残り、Workspace home も保持されています。

1. `tobari` が canonical root、installation default Template、exact Context を解決する
2. Context の current Template revision と exact Runtime binding を検証する
3. 内部 network と container を再作成する
4. Gateway を接続し、Workspace guard と exact Context/Workspace principal 登録を記録に合わせる
5. 同じ Context ID、Workspace ID、home を持つ logical Workspace へ入る

これは状態の調整であり、新しい Workspace の作成ではありません。

## 失敗時の動作

- owner、access mode、symlink、schema、identity の不一致は、安全でない再利用より前に失敗します。
- image がない、または Runtime API に互換性がない場合、project root を変更する前に失敗します。
- 既存の Workspace state が不完全なら、別の authority や identity を暗黙に作りません。
- policy 統合データの作成に失敗した場合、直前まで正常だった判断データを保持します。
- attached Workspace は `--force` で保護を明示的に解除しない限り削除できません。
- logical Workspace が一つでも残っていれば、クラスターの停止は失敗します。

## 保証と制限

**保証すること:** ライフサイクル操作の範囲は限定され、project files は削除しません。有効な
logical state から作り直せる Docker state は記録に合わせて調整できます。Workspace home と
host-owned lifecycle state は `cluster down --purge` の後も残ります。policy の一部だけを有効化
することはありません。

**保証しないこと:** 手動削除した project files、削除済みの Workspace home、破損した host storage、
侵害された trust host、外部 service 側のログイン失効、project 移動後の自動判定。

## まとめ

コンテナの有無だけから永続的な identity や利用者データを推測することはありません。各保存領域には
管理主体と削除操作が定められています。作り直せる Docker state や生成物は記録に合わせて調整しますが、
identity、policy、Workspace state が曖昧なら安全側に停止します。

## 理解を確認する

各ライフサイクル操作の後に何が残るか、予測できるはずです。

<details>
  <summary>
    <code>delete</code> は、<code>exit</code> が保持する何を削除しますか？
  </summary>
  完全一致する Workspace authority record、home、container、network、principal
  台帳です。project files、Context、Policy Memory、Workspace Template
  は削除しません。
</details>

<details>
  <summary>
    <code>cluster down --purge</code> は何を追加で削除しますか？
  </summary>
  共有 Gateway CA volume と active policy bundle を追加で削除します。Workspace
  home、Workspace Template、 policy source、host-owned lifecycle state
  は保持します。
</details>

<details>
  <summary>
    Workspace state が不完全な場合、Tobari は新しい identity を作れますか？
  </summary>
  いいえ。完全な記録がない状態で補完すると、存在しない権限を推測するため、安全側に停止します。
</details>

<details>
  <summary>
    container が消えても有効な Workspace authority
    が残っている場合、どうなりますか？
  </summary>
  Workspace は論理的には存在します。次の入室時に互換性のある container
  を作り、記録と状態を合わせます。
</details>
