Tobari は、プロジェクト、Workspace、Context、クラスター、認証情報、インストール環境の
状態を、所有範囲ごとに分けます。ライフサイクル操作が削除するのは、宣言した範囲だけです。
そのため `exit`、`delete`、クラスターの停止、認証情報のログアウトや置換、実行環境の
再ビルドでは、それぞれ残るものが異なります。

永続記録から安全に再構築できる実行時状態がある一方で、欠損や不整合を推測せず
処理を止める状態もあります。コンテナやネットワークの消失が、Workspace や認証状態の
消失と同じではないのはこのためです。以下の表では、[Workspace のライフサイクル](../workspace-lifecycle/)と
[認証情報](../credentials/)の境界を各保存領域に適用します。

## 管理主体と目的ごとの状態

以下のパスは、特に記載がない限り、実際に使われる XDG の設定／状態ルートからの相対パスです。

| 状態                               | 管理主体と意味                                                                                                         | 寿命                                                                                              |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| プロジェクトルート                 | immutable Context `source_access` に従って mount する user-selected live host file                                     | Tobari のライフサイクル操作では削除しない                                                         |
| `roots/<hash>.json`                | 完全一致する（正規化済みプロジェクトルート、Context ID）の組ごとのルート索引                                           | 論理 Workspace と一緒に作成・削除                                                                 |
| `instances/<id>/state.json`        | スキーマ1の安定した識別情報、永続的な Context との結び付き、要求された実行環境と調整済みの実行環境、診断用 Docker ID   | 論理 Workspace と一緒に作成・削除。Docker を調べた結果よりも優先                                  |
| `instances/<id>/home`              | Workspace ごとの書き込み可能なホーム領域と、ツール自身が管理するログイン状態                                           | `exit` や実行環境の再作成後も残り、Workspace の削除で消える                                       |
| Context マニフェスト               | ホスト所有の安定した ID、エージェントプロファイル、正確な Runtime リビジョン参照、ポリシーモード、限定されたシェル設定 | Workspace やクラスターの実行環境を操作しても残る                                                  |
| Runtime `source/` と不変リビジョン | インストール全体で再利用するビルドソースと成功履歴                                                                     | Context と Workspace のライフサイクルを越えて残り、ビルドだけでは展開されない                     |
| Context のポリシー原本             | 一つの Context が所有する exact-host `domains/<host>/{allow,deny}.json` と、Advanced の場合は Rego                     | クラスターの実行環境より長く残り、検証済みの有効化か、Advanced モードでの明示的な編集だけで変わる |
| 統合ポリシー生成物                 | OPA に読み取り専用でマウントする、内容アドレス方式の全 Context 用ルーター、データ、モジュールの写し                    | ポリシー原本から再構築して不可分に公開する。クラスター稼働中だけ有効な判断データ                  |
| 現在有効なポリシーバンドル         | 所有者ラベル付きの Docker 管理ボリュームに置く、版管理された完全な OPA バンドル                                        | OPA が動的に読み込む。`cluster down --purge` だけが削除し、ポリシー原本から再構築する             |
| プロバイダーマニフェスト           | 所有者が管理する厳格な V1 の静的宣言と、同じ V1 権限内のレビュー済み組み込みプラン                                     | インストール環境または Context の設定として、クラスター停止後も残る                               |
| プロバイダー生成物                 | Gateway が使う、正規化済みで秘密を含まないスキーマ1の全プロバイダー用データ                                            | 完全に検証できたマニフェスト群から再生成する。一部だけを有効化しない                              |
| プリンシパル台帳                   | ホスト発行のスキーマ 1 Workspace 送信元＋Gateway エンドポイント＋ネットワークと Context／プロジェクトの結び付き        | 既存の Workspace ネットワークに合わせて調整し、Gateway には読み取り専用でマウントする             |
| 暗号化した Context 保管庫          | static secret、revision、raw handle を含む schema-1 authenticated ciphertext                                           | Workspace 削除やどちらの cluster-down でも残る。credential entry は auth mutation で更新          |
| インストール用ルート鍵             | Context 保管庫のロックを解除する鍵。macOS Keychain または所有者だけが読める Linux ファイル                             | `cluster down` と `--purge` の後も残る。保管庫だけがあり鍵がなければ、安全側に停止する            |
| Gateway CA の状態                  | Workspace 側の HTTPS 検査に使う、インストール環境固有の CA                                                             | 通常の `cluster down` 後も残り、共有 CA ボリュームは `--purge` で削除する                         |

クラスター状態には、共有資源名、読み込み済み Context 数、内容アドレス方式で作った統合データの版、生成物のパスも記録します。現在選択中の Context を通信制御の権限とはせず、実物の認証情報も含めません。

## 操作ごとに保持するもの

| 操作または出来事             | Workspace の識別情報とホーム領域                                 | Context／ポリシー | 保管庫とルート鍵                                             | 共有サービス／CA                                    | プロジェクトファイル |
| ---------------------------- | ---------------------------------------------------------------- | ----------------- | ------------------------------------------------------------ | --------------------------------------------------- | -------------------- |
| `exit`                       | 保持                                                             | 保持              | 保持                                                         | 稼働を続け、CA も保持                               | 保持                 |
| `delete`                     | 完全一致する Workspace のホーム領域と実行環境記録を含めて削除    | 保持              | Context の認証情報は保持し、プロジェクトのハンドル台帳は削除 | 変更なし                                            | 保持                 |
| `cluster down`               | すべての Workspace を削除するまで、コマンドを拒否                | 保持              | 保持                                                         | サービスと一時ネットワークを削除し、CA は保持       | 保持                 |
| `cluster down --purge`       | 前提条件は `cluster down` と同じ                                 | 保持              | 保持                                                         | サービス、共有 CA、現在有効なポリシーバンドルを削除 | 保持                 |
| `auth logout PROVIDER`       | 識別情報とホーム領域は保持。実行中の環境は再入場まで変わらない   | 保持              | プロバイダーの認証情報と全ハンドルを削除し、ルート鍵は保持   | クラスターは保持                                    | 保持                 |
| 認証情報の置換               | 識別情報とホーム領域は保持。新しい投影値の反映には再入場が必要   | 保持              | 新しい版を保存し、古いハンドルを無効化                       | クラスターは保持                                    | 保持                 |
| Context の実行環境を再ビルド | 識別情報とホーム領域は保持。結び付いたコンテナは次の入場時に調整 | ポリシーは保持    | 保持                                                         | 変更なし                                            | 保持                 |
| コンテナ／ネットワークの消失 | 論理状態とホーム領域は保持。次の入場時に資源を調整               | 保持              | 保持                                                         | 必要に応じて Gateway の接続とプリンシパル情報を修復 | 保持                 |

## 正本に従って復旧する

### Docker の実行環境が見つからない

永続的な Workspace の記録が有効で、コンテナやネットワークが見つからない場合、実行環境の資源は記録から作り直せます。次に Workspace へ入るときに再作成して Gateway をつなぎ直し、プリンシパル台帳を更新したうえで、既存のプロジェクトルートとホーム領域をマウントします。

### 永続状態が不完全

ルート索引があるのに Workspace インスタンスの記録がない場合、Tobari は `incomplete` を報告します。失われた安定した識別情報、Context との結び付き、ホーム領域の関係を推測しません。明示的に作り直す前に、完全一致する `delete` で残った記録を片付けます。

### ポリシーの有効化に失敗

ポリシー変更では、排他制御、Context 単位の事前検査、全 Context を統合した状態での完全なテスト、内容アドレス方式での公開、OPA が正常になるまでの待機を行います。入力が不正な場合や有効化に失敗した場合、候補の一部だけをマウントすることはありません。ポリシー原本を元に戻し、直前まで正常に動いていた統合データと状態を保持します。

### ルート鍵または保管庫の整合性検証に失敗

Auth Broker はロックされた状態で起動します。暗号化した保管庫があるのにインストール用の鍵がない場合、既存の暗号文を復号できず、状態を曖昧にする代わりの鍵は作りません。認証データの破損、安全でない所有者やアクセス権、シンボリックリンク、認証失敗を報告し、安全側に停止します。信頼するホスト鍵のバックアップと復旧は、運用者の責任です。

### プロバイダー生成物が不正

未知のフィールド、厳格なスキーマに合わないデータ、宛先とヘッダーの衝突、組み込み定義の上書き、曖昧な HTTP の結び付きが一つでもあれば、プロバイダー群全体を拒否します。有効に見える一部だけを有効化することはありません。

## 具体的な復旧シナリオ

ホストの再起動後、Workspace コンテナと専用ネットワークはありませんが、ルート索引、Workspace インスタンスの状態、ホーム領域は残っています。

1. `tobari` が永続的なプロジェクトルートと Context の記録を解決する
2. 結び付いた Context の実行環境イメージを検証する
3. 内部ネットワークとコンテナを再作成する
4. Gateway を接続し、Gateway／Workspace のガードを再適用して、新しい正確なエンドポイントのプリンシパル情報を記録する
5. 現在の Auth Broker ハンドルの投影データを記録と一致させる
6. 同じプロジェクト ID とホーム領域を持つ論理 Workspace へ入る

これは状態の調整であり、新しい Workspace の作成ではありません。

## 失敗時の動作

- 所有者、アクセス権、シンボリックリンク、スキーマ、識別情報の不一致は、安全でない再利用より前に失敗します。
- イメージがない、または実行環境 API に互換性がない場合、プロジェクトの実行環境を変更する前に失敗します。
- 既存の保管庫があるのにルート鍵がない場合、別の鍵を暗黙に作りません。
- ポリシー統合データやプロバイダー生成物の作成に失敗した場合、直前まで正常に動いていた判断データを保持します。
- 接続中の Workspace は、`--force` でこの保護だけを明示的に解除しない限り削除できません。
- 論理 Workspace が一つでも残っていれば、クラスターの停止は失敗します。
- ローカルでのログアウトは、プロバイダー側で認証情報が失効したことを意味しません。

## 保証と制限

**保証すること:** ライフサイクル操作が扱う範囲は限定され、プロジェクトファイルを削除しません。有効な論理状態から作り直せる Docker の状態は、記録に合わせて調整できます。Context 保管庫とルート鍵は `cluster down --purge` の後も残ります。ポリシーやプロバイダー生成物の一部だけを有効化することはありません。

**保証しないこと:** 失われたプロジェクトファイル、削除済みの Workspace ホーム領域、失われたインストール用ルート鍵、破損したホストストレージ、侵害された信頼ホストからの復旧、プロバイダー側での認証情報の失効、プロジェクト移動後の自動判定。

## まとめ

永続的な識別情報や利用者データを、コンテナの有無だけから推測することはありません。各保存領域には管理主体と削除操作が定められています。作り直せる Docker の状態や生成物は記録に合わせて調整しますが、識別情報、ポリシー、鍵、保管庫の状態が曖昧なら、安全側に停止します。

## 理解を確認する

「コンテナがない」と「Workspace がない」を同一視せず、各操作の後に何が残るかを予測できるはずです。

<details>
  <summary>
    <code>delete</code> は、<code>exit</code> が保持する何を削除しますか？
  </summary>
  完全一致する Workspace
  のルート索引、インスタンス状態、ホーム領域、コンテナ、ネットワーク、プリンシパル台帳とプロジェクト認証台帳の項目です。どちらの操作も、プロジェクトファイルと
  Context の状態は削除しません。
</details>

<details>
  <summary>
    <code>cluster down --purge</code> は何を追加で削除しますか？
  </summary>
  共有 Gateway CA ボリュームです。暗号化した Context
  保管庫とインストール用ルート鍵は保持します。
</details>

<details>
  <summary>
    保管庫があるのに鍵がない場合、Tobari は新しいルート鍵を作れますか？
  </summary>
  いいえ。代わりの鍵では既存の保管庫を復号できず、安全に解釈できないため、安全側に停止します。
</details>

<details>
  <summary>
    失われたコンテナは修復できるのに、インスタンス状態のないルート索引を推測しないのはなぜですか？
  </summary>
  コンテナは、有効な論理状態から作り直せます。インスタンス状態がなければ、正本となる識別情報と結び付きが失われています。その状態で再構築すると、存在しない権限を推測で作ることになるからです。
</details>

状態遷移は[Workspace のライフサイクル](../workspace-lifecycle/)へ戻ってください。次は[実装技術](../implementation-stack/)で、各技術をその境界に置く理由を確認します。
