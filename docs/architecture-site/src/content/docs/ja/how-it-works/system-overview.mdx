Tobari は、ネットワーク構成そのものを強制境界の一部に使います。サポートされる
構成では、各 Workspace が参加するのは専用の Docker 内部ネットワークだけです。
プロジェクト側のネットワークと外向き通信側の両方にインターフェースを持つコンポーネント
は Gateway だけです。通常の HTTP/HTTPS ソケットは、保護済みの透過経路を通って Gateway へ到達します。

プロジェクト通信、ポリシー制御、外向き通信は三つのネットワーク範囲に分かれます。
必要な範囲を横断するのは Gateway であり、OPA と Auth Broker の接続範囲はさらに
狭くなっています。許可されたリクエストは Gateway から外へ進み、Gateway または
OPA の障害時には経路が閉じます。以下の主体は[メンタルモデル](../mental-model/)で紹介しています。

## 三つのネットワーク範囲

### Workspace ごとの専用ネットワーク

Tobari は論理 Workspace ごとに、Docker の `internal` 属性を持つネットワークを一つ作ります。作業用コンテナが参加するのは、そのネットワークだけです。Gateway は別名 `gateway` で接続されます。

コンテナには Tobari の CA 証明書バンドルが渡されますが、Tobari 管理の HTTP プロキシ環境変数は渡されません。閉じた出力ポリシー、正確なプロジェクト Gateway を指す既定経路、Gateway が提供する合成 DNS により、通常の HTTP/TLS は透過リスナーへ到達します。Gateway は別の明示的プロキシリスナーを公開しません。

### 内部制御ネットワーク一つ

OPA は共有の `control` ネットワークに参加し、プロジェクトネットワークや `egress` には参加しません。そのため Workspace のプロセスは、OPA のポリシーエンドポイントを直接呼べません。

Gateway も `control` に参加し、固定の OPA エンドポイントを一つだけ呼びます。Auth Broker は `control` と `egress` に参加しますが、TCP リスナーは公開しません。ホスト上のコマンドと Gateway は、制御されたマウントと固定操作を通して、それぞれ別の Unix ソケットへ到達します。どちらのソケットも Workspace や OPA からは利用できません。

### 外向き通信ネットワーク一つ

Gateway は `egress` に参加して allow 済み destination を resolve/connect します。static Auth
Broker に provider egress task はありません。built-in GitHub acquisition は fixed trusted-host
helper で実行します。work container はこの network に参加しません。

## 許可されるリクエストの順序

重要な順序は次のとおりです。

1. Workspace の専用ネットワークから通信が入る
2. Gateway がホスト発行の通信主体を確立する
3. Gateway が本文を含まない正規化済み入力で OPA へ一度問い合わせる
4. 許可後にだけ Gateway が接続先のアドレスを名前解決し、固定する
5. Gateway が接続先への接続を一つ開き、リクエストをストリーミングする
6. Gateway が、上限を設けて秘密情報を含まない監査メタデータを記録する

アプリケーション層での自動再試行はありません。リダイレクト先への通信は独立したリクエストとして、もう一度認可を受けます。

## 同じシステム内の信頼境界

<ConceptDiagram name="trust-boundaries" />

Workspace と接続先は信頼しません。ホスト、Docker の実行基盤、Gateway、OPA、Auth Broker、所有者が管理する状態は、信頼する強制基盤です。ここで「信頼する」とは、Tobari の保証がそれらに依存するという意味であり、バグがないという意味ではありません。

## 回避を試みる具体例

### プロセスが直接ソケットを開く

TCP 接続は、保護済みの既定経路でプロジェクトの Gateway へ進みます。通常の HTTP/TLS は Gateway の透過リスナーへ振り分けられ、同じ接続先検証と OPA 判断を受けます。対応しない通信は失敗し、一般的な TCP ルーターとして転送されません。

### プロセスが `opa:8181` を呼ぶ

OPA は Workspace ネットワークに接続されていないため、コンテナからその名前やサービスへ到達できません。

### プロセスが別の Workspace を狙う

各 Workspace の内部ネットワークは分離されており、相互に到達する経路はありません。Gateway は両方へ参加しますが、Workspace 間を結ぶ一般的なルーターとしては動作しません。

ホスト上のファイルルートは、ネットワークとは別の境界です。二つの Workspace が、同じまたは重なるプロジェクトルートを意図的にマウントする場合があります。ネットワーク、ホーム、通信主体、学習済み規則は分離されますが、重なったホストファイルへの書き込みは両方から見えます。

## 失敗時の動作

- **Gateway が利用不能:** 透過経路は接続を受けられません。外部への直接経路は引き続きありません。
- **OPA が利用不能、遅延、HTTP 200 以外、上限超過、不正、不完全:** Gateway は `503 policy_unavailable` を返し、名前解決も接続先への接続も行いません。
- **集約ポリシーに未知の Context がある:** 固定された OPA の振り分け処理は拒否し、現在選択中または既定の Context へ切り替えません。
- **ドットを含むホスト名の DNS 結果が安全でない:** Gateway はグローバルでないアドレスを拒否し、別のオーソリティを暗黙に選びません。これは接続先またはプロキシの障害であり、安定した公開 JSON 障害コードではありません。
- **Workspace のコンテナまたはネットワークがない:** 次の入室時に、論理状態からランタイム資源を調整します。Docker 資源を失っても、論理 Workspace は消えません。

## 保証と制限

**サポート対象の構成で保証すること:** Workspace から外部への直接通信がないこと。Workspace から OPA、Broker ソケット、Docker ソケット、別のプロジェクトネットワークへの経路がないこと。ポリシー障害後に接続先への通信を試さないこと。共有サービスの CPU、メモリー、PID、Docker ログに上限があること。

**保証しないこと:** Workspace 間で公平に帯域や共有サービス容量を割り当てること。ホスト、Docker、カーネル、Gateway、OPA、Broker が侵害された後も保護すること。選択したプロジェクトルート配下のディスク使用量制限。HTTP 以外のプロトコルに対する一般的なネットワークポリシー。重なった選択ルート間のファイルシステム分離。

## まとめ

合成 DNS、Workspace の出力ガード、無効化された転送、Gateway のリダイレクト規則が単一のサポート対象経路を強制します。Gateway がプロジェクトネットワークからポリシーと `egress` への通信を仲介します。OPA は外向き通信経路を持たずに判断し、Auth Broker は Workspace のネットワークへ公開されません。

## 理解を確認する

便利なプロキシ設定と、外部へ直接通信できない実際の境界との違いを説明できるはずです。

<details>
  <summary>
    プロセスが <code>--noproxy '*'</code> を使うとどうなりますか？
  </summary>
  接続は Gateway の透過リスナーへ到達し、同じポリシー判断を受けます。Gateway
  を迂回する別の経路は得られず、非 HTTP 通信は閉じたまま失敗します。
</details>

<details>
  <summary>
    OPA が「パケットを通す」コンポーネントでないのはなぜですか？
  </summary>
  OPA へ到達できるのは `control` ネットワークからだけで、返すのは判断結果です。
  プロジェクト側と `egress` 側のインターフェースを持ち、その判断を強制するのは
  Gateway です。
</details>

<details>
  <summary>
    ネットワークを分けると、重なったプロジェクトルート同士でファイル変更
    が見えなくなりますか？
  </summary>
  いいえ。ネットワーク分離と、ホストファイルのマウント
  範囲が重なることは別問題です。 同じホストファイルへの書き込みは共有されます。
</details>
