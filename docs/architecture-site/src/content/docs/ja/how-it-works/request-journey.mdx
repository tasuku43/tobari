Workspace から送られた HTTP/HTTPS リクエストは、外部の接続先へ到達する前に Gateway へ入ります。Gateway はカーネルが観測した Workspace の送信元エンドポイントと、ホスト管理のスキーマ 1 登録簿から Workspace Template とプロジェクトを特定して、信頼済みの principal メタデータを作ります。リクエスト本文と agent CLI のログイン値は OPA へ送りません。

OPA が拒否した場合や判断結果が不正な場合、Gateway は接続先へ接続せず、ローカルで処理を終了します。DNS 名前解決、接続先への接続、本文の転送は、許可後に限って実行します。この順序により、ポリシーによる拒否、判断処理の障害、接続先の障害を区別できます。

## 処理順序

### 1. 保護済みの HTTP 通信を受け取る

Docker の上限付きリゾルバーが Gateway の合成 DNS へ転送し、本物のホストを名前解決せず `198.18.0.10` を返します。Workspace の出力ガードは TCP をそのプロジェクトの Gateway へ送り、Gateway が透過リスナーへ振り分けます。平文 HTTP の接続先は `Host` から得ます。HTTPS では SNI を最初の接続先とし、復号後の HTTP 接続先および元のポートとの一致を要求します。TLS の分割は [HTTPS と TLS](../https-and-tls/)で説明します。

この時点では、リクエストの内容を信頼しません。プロジェクトを名乗るヘッダーも、信頼できるプリンシパルにはなりません。

### 2. Workspace Template とプロジェクトを特定する

Gateway は kernel-observed Workspace source endpoint を host-owned schema-1 principal registry で照合します。検証済み Context ID と Workspace ID は frozen private-wire field `workspace_template_id` と `project_id` に投影します。これらは public alias ではありません。binding が欠落、未知、古い、安全でない、または曖昧なら OPA より前に停止します。

### 3. 本文を含まない判断入力を作る

Gateway はスキーマ 1 の入力を、固定の OPA エンドポイント一つへ POST します。内容は次のとおりです。

- registry から導出した cluster、Context ID、Workspace ID
- 正規化したスキーム、末尾のドットを除いた小文字のホスト、ポート
- 大文字のメソッド
- 生のパスと、デコード済みのパス区間
- 複数値を保持したクエリー
- 秘密情報を除いたヘッダーと、秘密情報を含まない認可メタデータ

リクエストとレスポンスの本文、認証情報、既知または設定済みの認証用ヘッダー値は除外します。通常のクエリーは OPA 入力に含まれます。URL に置かれた任意のデータまで除去する、汎用的な秘密情報の検出処理ではありません。

### 4. OPA へ一度だけ問い合わせる

Gateway は、時間と応答サイズに上限を設けた HTTP POST を一度だけ送り、再試行しません。HTTP 200 であり、真偽値の `allow`、空でない `reason`、`status` が `403`、真偽値の `learnable` を含む、正しい結果を一つ要求します。

OPA が判断し、Gateway がその判断を通信経路へ強制します。

### 5A. ローカルで拒否する

正しい拒否結果を受け取ると、Gateway は `403 policy_denied` を作ります。学習可能な拒否に含まれるのは、`tobari review permissions` を示す固定のホスト側案内オブジェクト、完全一致するホスト、ポート、メソッド、パス、`automatic_retry: false` だけです。

候補 ID、クエリー、本文、ヘッダー、認証情報、動的なコマンド引数は含まれません。候補の不透明な参照値は、ホスト上に保持した根拠から後で導出します。

### 5B. 許可後に続行する

許可後にだけ、Gateway は次の処理を行えます。

1. 接続先のホスト名を名前解決する
2. ドットを含むホスト名に対する、安全でない非グローバルアドレスを拒否する
3. 選択したアドレスを固定し、後の DNS 応答で接続先が変わらないようにする
4. 接続先への接続を一つ作り、元のリクエストを転送する

アプリケーションリクエストの自動再試行はありません。リダイレクトは新しいリクエストとなり、再びポリシー判断を通ります。

### 6. 結果を記録する

拒否は即座にログへ記録します。許可したリクエストは、レスポンスまたは接続エラーの後に記録します。監査スキーマ 1 には、Workspace Template／プロジェクトの識別情報を含む principal メタデータ、接続先、メソッド、秘匿化したパス、判断、理由、状態、処理時間が含まれます。クエリー、認証・cookie ヘッダーの値、本文、ログイン値は含まれません。

## 具体例：本文だけが異なる

Workspace が最初に次を送るとします。

```http
PATCH /api/items/42 HTTP/1.1
Host: example.com
Content-Type: application/json

{"state":"ready"}
```

後で、同じ Workspace Template、プロジェクト、ホスト、ポート、メソッド、パスに `{"state":"deleted"}` を送ります。

アプリケーション上の意味は大きく異なりますが、Tobari では同じ完全一致のポリシー識別情報です。本文の違いから二つ目のレビュー候補や、より狭いルールは作りません。経路が許可されていれば、どちらの本文も送れます。レビューする人は送信内容の検査を前提にせず、その経路で可能になる操作全体を評価する必要があります。

## 失敗時の動作

| 段階          | 障害                                                              | 結果                                               |
| ------------- | ----------------------------------------------------------------- | -------------------------------------------------- |
| プリンシパル  | 登録簿を読めない、または Workspace の送信元エンドポイントが未知   | 403 `project_principal_unavailable`                |
| 認証情報の値  | ポリシー識別情報には含めない                                      | OPA と監査から除外する                             |
| OPA           | タイムアウト、接続エラー、HTTP 200 以外、不正または上限超過の結果 | 503 `policy_unavailable`                           |
| 判断          | 正しい拒否結果                                                    | 403 `policy_denied`。接続先には何も届かない        |
| DNS／アドレス | 安全で利用可能なアドレスがない                                    | 接続先またはプロキシのエラー。別の接続先は選ばない |
| 接続先        | 許可後の TCP/TLS/HTTP 障害                                        | 監査結果は `upstream_error`。ポリシーは変更しない  |

既知の `Content-Length` が mitmproxy の 8 MiB 制限を超えると、通常のアドオンのヘッダーフックより前に拒否される場合があります。長さが不明な許可済み本文は、固定された製品契約に従い、総バイト数の上限なしでストリーミングされます。

## 保証と制限

**保証すること:** 通常の Gateway 試行ごとに OPA call は一度です。principal establishment、
credential preparation、allow decision、allow 後の static credential application が成功する前に
body byte を転送しません。deny では secret resolution はゼロです。application-level retry はなく、
denial/review 情報は secret-free です。

**保証しないこと:** 本文の内容に基づく認可。アプリケーション上の意味の理解。冪等性。外部サービス操作の解釈。長さが不明な許可済み本文をストリーミングする場合の総バイト数制限。低レベルな接続先障害すべてに対応する安定した Tobari JSON 障害コード。

## まとめ

Context/Workspace は登録済みで kernel-observed な Workspace source endpoint から特定します。OPA は
body-free normalized input を一度受け取って判断します。deny は Gateway 内で停止します。secret を
扱う Authentication 操作、real destination DNS、upstream connection は allow 後だけです。body は
allow 後に stream します。
