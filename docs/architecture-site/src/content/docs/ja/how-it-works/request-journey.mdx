Workspace から送られた HTTP/HTTPS リクエストは、外部の接続先へ到達する前に Gateway へ入ります。Gateway はカーネルが観測した Workspace の送信元エンドポイントと、ホスト管理のスキーマ 1 登録簿から Context とプロジェクトを特定し、本文と認証情報を含まない正規化済みの入力を OPA へ一度だけ送ります。

OPA が拒否した場合や判断結果が不正な場合、Gateway は接続先へ接続せず、ローカルで処理を終了します。認証情報の解決、DNS 名前解決、接続先への接続、本文の転送は、許可後に限って実行します。この順序により、ポリシーによる拒否、判断処理の障害、接続先の障害を区別できます。

[システム全体像](../system-overview/)には固定されたネットワーク図があります。Auth Broker の詳細は後で扱い、ここでは必要な場合に限って参加する認証処理として示します。

## 処理順序

### 1. 保護済みの HTTP 通信を受け取る

Docker の上限付きリゾルバーが Gateway の合成 DNS へ転送し、本物のホストを名前解決せず `198.18.0.10` を返します。Workspace の出力ガードは TCP をそのプロジェクトの Gateway へ送り、Gateway が透過リスナーへ振り分けます。平文 HTTP の接続先は `Host` から得ます。HTTPS では SNI を最初の接続先とし、復号後の HTTP 接続先および元のポートとの一致を要求します。TLS の分割は [HTTPS と TLS](../https-and-tls/)で説明します。

この時点では、リクエストの内容を信頼しません。プロジェクトを名乗るヘッダーも、信頼できるプリンシパルにはなりません。

### 2. Context とプロジェクトを特定する

Gateway は、カーネルが観測した Workspace の送信元エンドポイントを読み取り、ホスト管理のスキーマ 1 プリンシパル登録簿で照合します。その結果から、安定した `context_id` と `project_id` を得ます。結び付きが欠落、未知、古い、安全でない、または曖昧な場合は、OPA へ問い合わせる前に停止します。

### 3. 認証方式を準備する

選択した認証方式に応じて、Gateway はポリシー判断の前にリクエストを準備します。

- **ツール自身で管理（そのまま転送）:** 認証情報と Cookie の値を OPA 入力から除外し、許可後に転送できるよう保持します。
- **保持型の管理方式:** 秘密情報を含まない要求プロファイルを Context、プロジェクト、ホストと照合します。この時点では認証情報の本体を読みません。
- **Auth Broker:** 完全に認識できたハンドルを、転送対象のリクエストから削除します。その後、秘密情報を含まない結び付き情報を照合します。

Tobari 形式に見える不正なハンドルはここで失敗し、そのまま転送する方式には切り替わりません。

### 4. 本文を含まない判断入力を作る

Gateway はスキーマ 1 の入力を、固定の OPA エンドポイント一つへ POST します。内容は次のとおりです。

- 登録簿から導出したクラスター、Context ID、プロジェクト ID
- 正規化したスキーム、末尾のドットを除いた小文字のホスト、ポート
- 大文字のメソッド
- 生のパスと、デコード済みのパス区間
- 複数値を保持したクエリー
- 秘密情報を除いたヘッダーと、秘密情報を含まない認可メタデータ

リクエストとレスポンスの本文、Auth Broker のハンドル、解決済みの認証情報、既知または設定済みの認証用ヘッダー値は除外します。通常のクエリーは OPA 入力に含まれます。URL に置かれた任意のデータまで除去する、汎用的な秘密情報の検出処理ではありません。

### 5. OPA へ一度だけ問い合わせる

Gateway は、時間と応答サイズに上限を設けた HTTP POST を一度だけ送り、再試行しません。HTTP 200 であり、真偽値の `allow`、空でない `reason`、`status` が `403`、真偽値の `learnable`、必要に応じて有効な保持型プロファイルを含む、正しい結果を一つ要求します。

OPA が判断し、Gateway がその判断を通信経路へ強制します。

### 6A. ローカルで拒否する

正しい拒否結果を受け取ると、Gateway は `403 policy_denied` を作ります。学習可能な拒否に含まれるのは、`tobari policy review` を示す固定のホスト側案内オブジェクト、完全一致するホスト、ポート、メソッド、パス、`automatic_retry: false` だけです。

候補 ID、クエリー、本文、ヘッダー、認証情報、動的なコマンド引数は含まれません。候補の不透明な参照値は、ホスト上に保持した根拠から後で導出します。

### 6B. 許可後に続行する

許可後にだけ、Gateway は次の処理を行えます。

1. 保持型プロファイルを適用するか、同じリビジョンに対して宣言済みの Auth Broker 操作を一つ行う
2. 接続先のホスト名を名前解決する
3. ドットを含むホスト名に対する、安全でない非グローバルアドレスを拒否する
4. 選択したアドレスを固定し、後の DNS 応答で接続先が変わらないようにする
5. 接続先への接続を一つ作り、許可済みリクエストを転送する

通常のそのまま転送、保持型、静的ヘッダーを使う Auth Broker のリクエストでは、許可後に本文をストリーミングします。Datadog では、Auth Broker が有効なトークンを選ぶか、許可後に同じレコードへ固定の更新処理を一度だけ行います。Gateway が置換するのは Bearer ヘッダーだけです。AWS SigV4 はレビュー済みの例外です。許可後、Gateway はリクエスト全体を 8 MiB の上限内で保持してハッシュを計算し、非公開のホスト側コンパニオンによる固定の認証情報エクスポートを一度だけ Auth Broker へ要求します。Auth Broker がローカルで署名した後に限り、Gateway は上限付きのリクエストを一度送ります。

アプリケーションリクエストの自動再試行はありません。リダイレクトは新しいリクエストとなり、再びポリシー判断を通ります。

### 7. 結果を記録する

拒否は即座にログへ記録します。許可したリクエストは、レスポンスまたは接続エラーの後に記録します。監査スキーマ 1 には、上限付きの識別情報、接続先、メソッド、秘匿化したパス、判断、理由、秘密情報を含まないプロファイルとプロバイダーのメタデータ、状態、処理時間が含まれます。クエリー、ヘッダー、本文、ハンドル、認証情報の本体は含まれません。

## 具体例：本文だけが異なる

Workspace が最初に次を送るとします。

```http
PATCH /api/items/42 HTTP/1.1
Host: example.com
Content-Type: application/json

{"state":"ready"}
```

後で、同じ Context、プロジェクト、ホスト、ポート、メソッド、パスに `{"state":"deleted"}` を送ります。

アプリケーション上の意味は大きく異なりますが、Tobari では同じ完全一致のポリシー識別情報です。本文の違いから二つ目のレビュー候補や、より狭いルールは作りません。経路が許可されていれば、どちらの本文も送れます。レビューする人は送信内容の検査を前提にせず、その経路で可能になる操作全体を評価する必要があります。

## 失敗時の動作

| 段階             | 障害                                                                     | 結果                                                                           |
| ---------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| プリンシパル     | 登録簿を読めない、または Workspace の送信元エンドポイントが未知          | 403 `project_principal_unavailable`                                            |
| 認証情報の準備   | 不正、古い、または一致しないハンドル                                     | 403 `credential_handle_invalid`                                                |
| OPA              | タイムアウト、接続エラー、HTTP 200 以外、不正または上限超過の結果        | 503 `policy_unavailable`                                                       |
| 判断             | 正しい拒否結果                                                           | 403 `policy_denied`。接続先には何も届かない                                    |
| 許可後の認証処理 | 実行前に判明した Auth Broker、コンパニオン、更新、署名、保持型方式の障害 | 503 の認証障害。接続先には何も届かない                                         |
| 実行後の認証処理 | AWS コンパニオンまたは Datadog 更新の結果が不明                          | 409 `credential_refresh_outcome_unknown`。自動再実行も接続先への試行も行わない |
| DNS／アドレス    | 安全で利用可能なアドレスがない                                           | 接続先またはプロキシのエラー。別の接続先は選ばない                             |
| 接続先           | 許可後の TCP/TLS/HTTP 障害                                               | 監査結果は `upstream_error`。ポリシーは変更しない                              |

既知の `Content-Length` が mitmproxy の 8 MiB 制限を超えると、通常のアドオンのヘッダーフックより前に拒否される場合があります。長さが不明な許可済み本文は、固定された製品契約に従い、総バイト数の上限なしでストリーミングされます。

## 保証と制限

**保証すること:** 通常の Gateway 試行ごとに、OPA の呼び出しは一度です。プリンシパルの確立、認証情報の準備、許可判断、許可後の認証情報適用が成功する前に、リクエスト本文のバイト列を転送しません。拒否時には、認証情報の解決、Datadog の更新、AWS コンパニオンの呼び出し、署名を一度も行いません。アプリケーション層の再試行もありません。拒否とレビュー用の情報に秘密情報は含めません。

**保証しないこと:** 本文の内容に基づく認可。アプリケーション上の意味の理解。冪等性。プロバイダー操作の解釈。長さが不明な許可済み本文をストリーミングする場合の総バイト数制限。低レベルな接続先障害すべてに対応する安定した Tobari JSON 障害コード。

## まとめ

Context とプロジェクトは、登録済みでカーネルが観測した Workspace の送信元エンドポイントから特定します。OPA は、本文を含まない正規化済みの入力を一度だけ受け取って判断します。拒否時は Gateway 内で処理を止めます。秘密情報を扱う Auth Broker の操作、本物の接続先の名前解決、接続先への接続は、すべて許可後にだけ行います。通常の本文は許可後にストリーミングし、レビュー済みの AWS 処理では、許可後に上限内でリクエストを保持して署名します。
