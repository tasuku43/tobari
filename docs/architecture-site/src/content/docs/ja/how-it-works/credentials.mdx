## このページで答える問い

login が network authority を暗黙に増やすことなく、Workspace はどう authenticated request を送りますか？

**一文での答え:** Tobari は credential custody と OPA authorization を分離します。request ごとに ordinary HTTP allow が必要です。Broker route で Workspace が持つのは bound opaque handle だけで、static resolution、AWS signing、Datadog token operation は allow 後に行われます。

### 読み終わると説明できること

- 三つの authentication route と real secret の場所
- OPA の前後における exact Broker ordering
- handle が credential でも sufficient authority でもない理由
- rotation、replacement、logout、re-entry が変えるもの

**前提:** [Policy learning](../policy-learning/)と [Project identity](../project-identity/)。

## 三つの方式と、三つの管理場所

| Route                    | real secret の場所                                           | Workspace が読めるもの           | Gateway action                                                                                        | 主な用途と制限                                                                               |
| ------------------------ | ------------------------------------------------------------ | -------------------------------- | ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Tool-native passthrough  | 一つの Workspace home 内で作られた file/environment          | real tool credential             | OPA/audit から credential value を redact し、allow 後に forward                                      | universal tool flow。ただし同じ Workspace の process は tool state を読み利用できる          |
| Auth Broker              | installation root key で unlock する encrypted Context vault | project-bound opaque handle 一つ | handle を削除・binding introspect・OPA に質問し、reviewed plan に従い allow 後に resolve/refresh/sign | strict static binding と reviewed GitHub/AWS/Datadog plan だけ                               |
| Retained managed adapter | Gateway だけへ mount する owner-only Context secret file     | non-secret profile selector      | Context/project/host profile を検証し、OPA に質問し、allow 後に secret を読んで inject                | retained static bearer/fixed-header path。profile/secret provisioning は explicit host admin |

Authentication は「どの credential material が利用できるか」に答え、authorization は「この Context/project がこの HTTP effect を実行してよいか」に答えます。どちらも他方の代わりになりません。

### 判断入力、宛先、ライフサイクルの比較

| Route                    | OPA が見るもの                                                                                                  | 適用範囲                                                                                                  | replacement、logout、re-entry                                                                                                                            |
| ------------------------ | --------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tool-native passthrough  | ordinary body-free HTTP effect。Gateway は recognized credential value を decision input から削除               | tool が対応する standard HTTP/HTTPS request と exact policy rule                                          | tool が rotation/logout を所有。existing process/Workspace home の secret を Tobari は retract できない                                                  |
| Auth Broker              | ordinary body-free effect と non-secret provider metadata。handle、credential revision、primary secret は見ない | manifest の exact HTTPS target/source syntax/destination transformation と separately allowed method/path | replacement/local logout は record を進める・削除して handle を invalid にする。projection 更新には re-entry。local logout は remote revocation ではない |
| Retained managed adapter | ordinary body-free effect と selected non-secret managed profile metadata                                       | explicitly configured Context/project/host/profile と supported fixed-header path                         | host admin が managed secret を replace/remove。projected selector 更新に re-entry が必要な場合があり、existing process environment は不変               |

この比較は意図的に非対称です。passthrough tool は Workspace へ credential を渡しますが、managed/brokered route は secret-bearing custody を trusted side に保ちます。

## Provider と Tool は別の軸

Provider は外部の credential authority を示します。Tool は handle projection を受け取り、対応する request を送る Workspace client です。サポート単位は、どちらかの名前だけではなく、レビュー済みの対応ペアです。現在の built-in は 1 対 1 なので、Provider 選択後の Tool は表示されますが自動選択です。AWS login method は別の acquisition choice です。

## Auth Broker を使う処理の正確な順序

### 1. 信頼するホストで取得する

`auth login [--provider PROVIDER]` は trusted-host terminal で reviewed fixed host helper 一つを実行します。provider を省略すると、installed reviewed GitHub/AWS/Datadog login provider から明示的に選び、各 Provider と一緒に自動選択される対応 Tool を表示します。指定すれば menu を省略します。Datadog は isolated fixed-US1 pup OAuth を使います。`auth import PROVIDER` は provider が import を宣言する場合だけ、protected non-terminal stdin から bounded credential を受け取ります。secret byte は argv、environment、log、Workspace input を通りません。

Auth Broker は selected stable Context/provider の typed credential record 一つを AES-256-GCM encrypted vault へ保存します。record は static primary secret、opaque AWS host-driver state、Datadog OAuth-session state のいずれかです。installation root key は macOS Keychain または owner-only Linux XDG state file にあり、unlock 中だけ Broker memory に保持します。

login/import は network rule を追加しません。

### 2. entry 時に project-bound handle を発行する

次の matching Workspace entry で、Tobari は random `tobari-h1_…` handle を reconcile します。次へ bind します。

- stable Context ID
- stable project ID
- provider
- credential revision
- exact HTTPS target
- source header と syntax
- destination transformation
- secret-header redaction set、または compiled built-in plan 一つ

handle は manifest-declared environment entry または complete file へだけ project されます。同じ Context の別 project は別 handle を受け取ります。

### 3. Gateway が handle を認識して取り除く

exact に一つの provider binding が normalized HTTPS authority と declared source-header syntax に一致した場合だけ、Gateway は broker path を選びます。OPA/forward より前に handle を request から削除します。

URL、cookie、header name、unsupported value、ambiguous position にある Tobari-looking marker は invalid です。marker がある request は fail-closed Broker handling に固定され、passthrough へ downgrade できません。

### 4. 秘密情報なしで binding を照合する

Gateway は handle、host-derived Context/project principal、requested HTTP/header binding を Broker runtime socket へ送ります。introspection が返すのは non-secret provider/revision binding metadata だけです。

Context、project、provider、revision、target、header binding がすべて一致する必要があります。copied、stale、revoked、malformed、ambiguous handle は OPA より前に失敗します。

### 5. 通常の HTTP effect を OPA へ問い合わせる

Gateway は schema 5 body-free input を送ります。OPA が見るのは non-secret provider ID で、handle/primary credential ではありません。brokered request は broad static host/method allow を継承せず、exact Context/project-bound L7 rule が必要です。

deny では Gateway は secret-resolution call を **一度も** 行いません。

### 6. 許可後に宣言済みの操作だけを実行する

post-policy branch は provider plan で異なります。

- **Static schema 1（GitHub、Chatwork を含む）:** Gateway は同じ revision を一度 resolve し、declared destination header だけを置換します。
- **AWS schema 2:** Gateway は authorized complete request を 8 MiB cap 内で保持・hash します。Broker は fixed host AWS CLI credential export のため authenticated private companion operation 一つを開始し、same revision を再確認・persist し、standard header-based SigV4 を local で sign します。temporary AWS credential は Workspace、OPA、policy、audit、durable projection に入りません。
- **Datadog schema 2:** access token が five-minute refresh window の外にある場合だけ選択し、それ以外は exact proxy-free/no-redirect US1 token endpoint で same-record refresh 一つを実行し、refreshed state を commit してから request-local bearer value を返します。

その後 Gateway は exact application target への separately verified TLS connection を作り、upstream attempt を一度行います。

resolved static secret、temporary AWS credential/signature material、Datadog access token は trusted infrastructure 内で request-scoped です。Workspace、OPA、CLI output、error、audit へ返しません。

## ローテーション、置換、ログアウト、実行中の process

- **認証情報の置換:** credential revision を増やし、その Context/provider の prior handle をすべて atomically revoke します。
- **ログアウト:** local Context/provider credential を削除し handle を revoke します。provider へ接続せず remote revocation は保証しません。
- **Auth Broker の再起動:** service は locked state に戻ります。successful unlock が valid encrypted state を rehydrate し、locked 中は request を resolve しません。
- **再 entry:** Tobari は already-running process environment を書き換えられないため、login/import/replacement/logout 後に必要です。next entry は environment projection を作り直し、unchanged Tobari-owned complete file だけを変更します。

old running process に old handle string が残っても、revision change/logout 後は Broker が拒否します。process memory にある tool-native secret は Broker revocation ではなく、その tool の semantics に従います。

## コピーされた handle の具体例

process が Workspace A の valid handle を Workspace B に copy し、同じ host/header へ送ります。

Gateway は receiving interface から B の principal を導出します。Broker introspection は B と handle の Context/project/provider/revision/target/header binding を照合します。project mismatch により `403 credential_handle_invalid` となり、Gateway は OPA call、secret resolve、passthrough、upstream contact を行いません。

Workspace A でも valid handle だけでは不十分です。ordinary HTTP effect に OPA allow が必要です。

## 失敗時の動作

| Condition                                                                     | Result                                                                                                                     |
| ----------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| invalid/stale/copied/revoked/binding-mismatched handle                        | 403 `credential_handle_invalid`。fallback なし                                                                             |
| Broker locked/unavailable、known pre-execution companion/refresh/sign failure | 503 `credential_broker_unavailable`。upstream attempt なし                                                                 |
| AWS companion/Datadog refresh outcome が explicit/post-dispatch unknown       | non-retryable 409 `credential_refresh_outcome_unknown`。application upstream attempt なし。deliberate retry 前に reconcile |
| valid handle だが OPA deny                                                    | 403 `policy_denied`。secret resolution ゼロ                                                                                |
| managed profile が Context/project/host に bound されない                     | 403 `credential_profile_not_bound`                                                                                         |
| managed secret unreadable/invalid                                             | 503 `credential_unavailable`                                                                                               |
| vault があるのに root key missing                                             | fail closed。replacement key を作らない                                                                                    |
| running Workspace projection が mutation 後 stale                             | re-entry で reconcile。existing process environment は不変                                                                 |

## 保証と制限

**保証すること:** brokered static secret、renewable state、derived request credential は Workspace/OPA の外に残ります。handle use は Context/project/provider/revision/HTTP target に bind されます。deny では resolve、refresh、companion、signing action はゼロです。invalid Tobari marker は fallback しません。login/import/logout は network policy を編集しません。

**保証しないこと:** logout の remote provider revocation、同じ Workspace 内の process isolation、malicious process が already allowed capability を使うことの防止、同じ Workspace の process から tool-native credential を隠すこと、reviewed plan 外の OAuth/refresh/signing/provider API、Gateway/Broker/root-key backend/host compromise 後の保護。

handle 自体は already allowed route の ordinary request body data として送信できます。Tobari は arbitrary body を検索しないからです。primary credential は公開されず Broker authority も与えませんが、non-secret handle の payload exfiltration は body-inspection guarantee 外です。

## まとめ

tool-native login は一つの Workspace に real tool credential を与えます。retained managed path は static secret を Gateway に保ちます。Broker path が Workspace へ渡すのは bound handle だけで、declared static/AWS/Datadog action は OPA allow 後に行います。三つとも ordinary network authorization に依存します。

## 理解を確認する

credential custody と communication permission を分けて説明できるはずです。

  </summary>
  いいえ。opaque constrained record selector です。static/renewable credential

<details>
  <summary>
    OPA が拒否したとき、秘密情報を扱う Auth Broker の操作は何か行われますか？
  </summary>
  ありません。introspection は OPA 前に non-secret binding metadata
  を確立する場合がありますが、static resolution、Datadog token
  selection/refresh、AWS companion export、signing は allow 後だけです。
</details>

<details>
  <summary>
    <code>auth logout</code> は provider 側で認証情報を revoke しますか？
  </summary>
  いいえ。provider へ接続せず local Context/provider state を削除し、Tobari
  handle を revoke します。
</details>

<details>
  <summary>
    同じ Workspace 内の悪意ある process は、すでに許可された認証済みの
    capability を使えますか？
  </summary>
  はい。同じ Workspace の process は境界を共有します。Tobari は projection/route
  authority を制限しますが、Workspace 内の process を分離しません。
</details>
