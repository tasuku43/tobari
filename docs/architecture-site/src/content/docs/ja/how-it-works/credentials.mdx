外部サービスへログインできることと、そのサービスへ HTTP リクエストを送れることは別です。認証は「どの認証情報を使えるか」を決めます。OPA のポリシーは「この Context とプロジェクトが、この宛先・ポート・メソッド・パスへ通信してよいか」を決めます。ログイン、インポート、認証情報の置換だけで通信許可が増えることはありません。

Tobari には三つの認証情報管理方式があります。ツール自身で管理する方式では、認証情報を Workspace 内に置きます。保持型の管理方式では、ホスト管理の静的な認証情報を Gateway だけが読める場所へ置きます。Auth Broker 方式では、認証状態の本体を暗号化した Context 保管庫に残し、Workspace へは一つのプロジェクトに結び付いた不透明なハンドルだけを渡します。

どの方式でも、外部通信には OPA の許可が必要です。静的な認証情報の解決、Datadog トークンの選択または更新、AWS リクエストの署名は、通信が許可された後に限って実行します。

以下の Auth Broker の処理順は、[ポリシー学習](../policy-learning/)と[プロジェクトの識別](../project-identity/)を前提とします。

## 三つの管理方式

| 方式                             | 認証情報の本体を置く場所                                          | Workspace が読めるもの                   | Gateway の処理                                                                                                                 | 主な用途と制限                                                                               |
| -------------------------------- | ----------------------------------------------------------------- | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| ツール自身で管理（そのまま転送） | Workspace ホーム内のファイルまたは環境変数                        | ツールが保存した認証情報                 | OPA 入力と監査から値を除外し、許可後に転送する                                                                                 | 一般的な CLI の認証方式。同じ Workspace 内のプロセスは認証状態を読み、利用できる             |
| 保持型の管理方式                 | Gateway だけへマウントする、所有者専用の Context 認証情報ファイル | 秘密情報を含まないプロファイル選択子     | Context、プロジェクト、ホスト、プロファイルを検証し、OPA の許可後に固定ヘッダーへ認証情報を挿入する                            | 静的な Bearer 認証または固定ヘッダー。認証情報とプロファイルはホスト管理者が明示的に用意する |
| Auth Broker                      | インストール用ルート鍵で開く、暗号化済みの Context 保管庫         | プロジェクトに結び付いた不透明なハンドル | ハンドルをリクエストから除去し、秘密情報を含まない結び付きを確認する。OPA の許可後に、宣言済みの解決・更新・署名だけを実行する | 厳格な静的結び付きと、レビュー済みの GitHub、AWS、Datadog 処理だけ                           |

この違いは意図的です。ツール自身で管理する方式では、認証情報を Workspace の権限内へ渡します。保持型と Auth Broker 方式では、認証情報の本体を信頼する側に残します。

### OPA が受け取る情報

| 方式             | OPA が受け取るもの                                                     | OPA が受け取らないもの                                                             |
| ---------------- | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| ツール自身で管理 | 本文を含まない通常の HTTP 通信                                         | 認識した認証ヘッダーと Cookie の値                                                 |
| 保持型の管理方式 | 通常の HTTP 通信と、選択済みプロファイルの秘密情報を含まないメタデータ | 認証情報ファイルの内容                                                             |
| Auth Broker      | 通常の HTTP 通信と、秘密情報を含まないプロバイダー ID                  | ハンドル、認証情報のリビジョン、固定認証情報、AWS の一時認証情報、Datadog トークン |

## プロバイダーとツールを分ける

プロバイダーは、認証情報を発行または管理する外部サービスです。ツールは、Workspace 内でハンドルや認証設定を受け取り、HTTP リクエストを送るクライアントです。サポート対象は、プロバイダー名またはツール名だけではなく、レビュー済みの組み合わせです。現在の組み込み設定は一対一のため、プロバイダーを選ぶと対応するツールも決まります。AWS のログイン方法は、これとは別に選択します。

## Auth Broker の処理順序

### 1. 信頼するホストで認証情報を取得する

`auth login [--provider PROVIDER]` は、信頼するホストの端末で、レビュー済みの固定ヘルパーを一つ実行します。`--provider` を省略すると、インストール済みの GitHub、AWS、Datadog から明示的に選びます。対応するツールも同時に表示します。Datadog は、ほかの処理から分離した US1 固定の `pup` OAuth を使います。

`auth import PROVIDER` は、プロバイダーがインポートを宣言している場合だけ、端末以外の標準入力から上限付きで認証情報を受け取ります。認証情報のバイト列を、コマンド引数、環境変数、ログ、Workspace の入力には載せません。

Auth Broker は、選択した Context とプロバイダーに対する型付きレコードを一つ、AES-256-GCM で暗号化した保管庫へ保存します。レコードは次のいずれかです。

- 静的な認証情報
- 不透明な AWS ホストドライバーの状態
- Datadog OAuth セッションの状態

インストール用のルート鍵は、macOS Keychain または所有者専用の Linux XDG 状態ファイルに置きます。Auth Broker のメモリへ入るのは、ロックを解除している間だけです。

ログインとインポートは、HTTP 通信の許可ルールを追加しません。

### 2. Workspace へ入るときにハンドルを発行する

対応する Workspace へ入ると、Tobari はランダムな `tobari-h1_…` ハンドルを用意します。ハンドルは次へ結び付きます。

- 安定した Context ID
- 安定したプロジェクト ID
- プロバイダー
- 認証情報のリビジョン
- 完全一致する HTTPS 接続先
- 送信元ヘッダーの名前と構文
- 接続先へ送るヘッダーの変換
- 秘密情報を含むヘッダーの秘匿化対象、または組み込みの処理計画

ハンドルを配置できるのは、マニフェストで宣言した環境変数またはファイル全体だけです。同じ Context でも、プロジェクトが違えば別のハンドルを渡します。

### 3. Gateway がハンドルを取り除く

一つのプロバイダーの結び付きだけが、正規化済みの HTTPS 接続先と宣言済みの送信元ヘッダーに一致する場合、Gateway は Auth Broker の経路を選びます。OPA への問い合わせや外部への転送より前に、ハンドルをリクエストから削除します。

URL、Cookie、ヘッダー名、未対応の値、曖昧な場所にある Tobari 形式の値は不正です。不正なハンドルを、そのまま転送する認証方式へ切り替えることはありません。

### 4. 秘密情報を使わずに結び付きを確認する

Gateway は、ハンドル、ホスト側から導出した Context とプロジェクトのプリンシパル、要求された接続先とヘッダーの結び付きを、Auth Broker のランタイムソケットへ送ります。返るのは、秘密情報を含まないプロバイダー ID とリビジョンのメタデータだけです。

Context、プロジェクト、プロバイダー、リビジョン、接続先、ヘッダーの結び付きがすべて一致する必要があります。コピーされた、古い、無効化済み、不正、または曖昧なハンドルは、OPA へ問い合わせる前に失敗します。

### 5. 通常の HTTP 通信を OPA へ問い合わせる

Gateway はスキーマ 1 の、本文を含まない入力を OPA へ送ります。OPA が受け取るのは秘密情報を含まないプロバイダー ID であり、ハンドルや認証情報の本体ではありません。Auth Broker 経由のリクエストにも、Context とプロジェクトに結び付いた完全一致の HTTP ルールが必要です。

OPA が拒否した場合、Gateway は認証情報を解決する呼び出しを一度も行いません。

### 6. 許可後に、宣言済みの処理だけを実行する

許可後の処理は、プロバイダーごとの計画で決まります。

- **静的なスキーマ 1:** Gateway は同じリビジョンの認証情報を一度だけ解決し、宣言済みの接続先ヘッダーだけを置換します。GitHub や Chatwork などの静的な結び付きが該当します。
- **AWS スキーマ 1:** Gateway は許可済みリクエスト全体を 8 MiB の上限内で保持し、ハッシュを計算します。Auth Broker は認証済みの非公開コンパニオン操作を一つ開始し、固定されたホスト上で AWS CLI の認証情報をエクスポートします。同じリビジョンを確認して状態を保存し、標準のヘッダー型 SigV4 をローカルで署名します。一時的な AWS 認証情報は、Workspace、OPA、ポリシー、監査、永続的な配置先へ入りません。
- **Datadog スキーマ 1:** アクセストークンが、期限前 5 分の更新時間帯の外にあれば、そのトークンを選びます。更新時間帯内なら、プロキシとリダイレクトを使わず、完全一致する US1 トークンエンドポイントで同じレコードを一度だけ更新します。更新後の状態を確定してから、リクエスト専用の Bearer 値を返します。

その後、Gateway は完全一致するアプリケーション接続先へ、別に検証した TLS 接続を作り、リクエストを一度だけ送ります。

解決済みの静的認証情報、一時的な AWS 認証情報と署名材料、Datadog アクセストークンは、信頼する基盤内で一つのリクエストにだけ使います。Workspace、OPA、CLI 出力、エラー、監査へ返しません。

## 置換、ログアウト、再起動

- **認証情報の置換:** 認証情報のリビジョンを増やし、その Context とプロバイダーに対する古いハンドルを、途中状態を見せずに無効化します。
- **ログアウト:** ローカルの Context とプロバイダーのレコードを削除し、ハンドルを無効化します。プロバイダーへ接続しないため、外部サービス側での失効は保証しません。
- **Auth Broker の再起動:** サービスはロック状態に戻ります。ロック解除に成功すると、暗号化済みの状態を読み直します。ロック中はリクエスト用の認証情報を解決しません。
- **Workspace への入り直し:** ログイン、インポート、置換、ログアウトで Workspace へ渡すハンドルが変わった場合に必要です。実行中のプロセス環境は書き換えられないためです。次に Workspace へ入るとき、Tobari が管理する環境変数またはファイルを調整します。

実行中の古いプロセスに古いハンドル文字列が残っていても、リビジョンの変更やログアウト後は Auth Broker が拒否します。プロセスのメモリに残った、ツール自身が管理する認証情報は、そのツールの動作に従います。

## コピーしたハンドルは別プロジェクトで使えない

プロセスが Workspace A の有効なハンドルを Workspace B にコピーし、同じホストとヘッダーへ送ったとします。

Gateway は登録済みでカーネルが観測した Workspace の送信元エンドポイントから B のプリンシパルを導出します。Auth Broker は、B の Context とプロジェクトが、ハンドルに結び付いた Context、プロジェクト、プロバイダー、リビジョン、接続先、ヘッダーと一致するか確認します。プロジェクトが一致しないため `403 credential_handle_invalid` となり、Gateway は OPA の呼び出し、認証情報の解決、別方式への切り替え、外部の接続先への通信を行いません。

Workspace A でも、有効なハンドルだけでは不十分です。通常の HTTP 通信には OPA の許可が必要です。

| 条件                                                                                 | 結果                                                                                                                |
| ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| 不正、古い、コピー済み、無効化済み、または結び付きが一致しないハンドル               | 403 `credential_handle_invalid`。別方式へ切り替えない                                                               |
| Auth Broker がロック中または利用不能、実行前に判明したコンパニオン・更新・署名の障害 | 503 `credential_broker_unavailable`。接続先へ通信しない                                                             |
| AWS コンパニオンまたは Datadog 更新の実行後に結果を確定できない                      | 再試行不可の 409 `credential_refresh_outcome_unknown`。アプリケーション接続先へ通信しない。再実行前に状態を確認する |
| 有効なハンドルだが OPA が拒否                                                        | 403 `policy_denied`。認証情報の解決は行わない                                                                       |
| 保持型プロファイルが Context、プロジェクト、ホストに結び付かない                     | 403 `credential_profile_not_bound`                                                                                  |

| 保管庫があるのにルート鍵がない                                                       | 処理を拒否する。代わりの鍵は作らない                                                                                |
| 実行中 Workspace のハンドルが状態変更後に古くなった                                  | Workspace へ入り直して調整する。実行中のプロセス環境は変わらない                                                    |

## 保証と制限

**保証すること:** Auth Broker が扱う静的認証情報、更新可能な状態、リクエスト用に導出した認証情報は、Workspace と OPA の外に残ります。ハンドルは、Context、プロジェクト、プロバイダー、リビジョン、HTTPS 接続先、ヘッダー変換に結び付きます。OPA の拒否時には、解決、更新、コンパニオン、署名を実行しません。不正な Tobari 形式の値を別の認証方式へ切り替えません。ログイン、インポート、ログアウトは通信ポリシーを編集しません。

**保証しないこと:** ログアウトによる外部サービス側での失効。同じ Workspace 内のプロセス分離。悪意あるプロセスによる、すでに許可された認証済み通信の利用防止。ツール自身が管理する認証情報を、同じ Workspace のプロセスから隠すこと。レビュー済みの計画外にある OAuth、更新、署名、プロバイダー API。Gateway、Auth Broker、ルート鍵の保存基盤、ホストが侵害された後の保護。

ハンドルは秘密情報ではありません。許可済みリクエストの本文にデータとして含めて送信することは可能です。Tobari は任意の本文を検索しないためです。ただし、ハンドルから認証情報の本体を取得したり、Auth Broker の権限を得たりはできません。

## まとめ

ツール自身で管理する方式では、一つの Workspace にツールの認証情報を渡します。保持型の管理方式では、静的な認証情報を Gateway だけが読める場所へ置きます。Auth Broker 方式では、Workspace へ渡すのはプロジェクトに結び付いたハンドルだけです。宣言済みの静的認証情報、AWS、Datadog の処理は、OPA の許可後に限って実行します。三つの方式すべてが、通常の HTTP 通信ポリシーに従います。
