認証は「どの認証情報を利用できるか」を決め、認可は「この Context とプロジェクトが、この
HTTP 操作を実行してよいか」を決めます。Tobari は二つの判断を分離しています。ログイン、
インポート、認証情報の置換によってネットワーク上の許可が増えることはありません。
認証付きリクエストにも、通常の OPA 許可が必要です。

認証情報の管理方法は三つあります。ツール固有の認証情報は一つの Workspace ホーム内に置き、
保持型の管理方式は設定済みの秘密情報を Gateway 境界に保ちます。Auth Broker 方式で
Workspace が持つのは、用途を限定した不透明なハンドルだけです。静的な秘密情報の解決、AWS の署名、
Datadog トークンの操作は、許可後にだけ行います。ハンドル自体は実物の認証情報ではなく、十分な権限も
持ちません。認証情報の更新、ログアウト、投影内容の変更後に Workspace へ入り直す必要が生じる場合があります。
実行中のプロセスの環境変数は書き換えられないためです。

以下の Auth Broker の処理順は、[ポリシー学習](../policy-learning/)と[プロジェクト識別](../project-identity/)を前提とします。

## 三つの方式と、三つの管理場所

| 方式                             | 実物の秘密情報の場所                                                | Workspace が読めるもの                     | Gateway の処理                                                                                                  | 主な用途と制限                                                                                         |
| -------------------------------- | ------------------------------------------------------------------- | ------------------------------------------ | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| ツール自身で管理（そのまま転送） | 一つの Workspace ホーム内で作られたファイルまたは環境変数           | ツールの実物の認証情報                     | OPA と監査から認証情報の値を秘匿化し、許可後に転送                                                              | 汎用のツール経路。ただし同じ Workspace のプロセスはツールの状態を読み、利用できる                      |
| Auth Broker                      | インストール用のルート鍵でロックを解除する暗号化済み Context 保管庫 | プロジェクトに結び付く不透明なハンドル一つ | ハンドルを削除し、結び付きを照合して OPA へ問い合わせ、レビュー済み処理計画に従って許可後に解決・更新・署名する | 厳格な静的結び付きと、レビュー済み GitHub、AWS、Datadog 処理計画だけ                                   |
| 保持型の管理方式                 | Gateway だけへマウントする、所有者専用の Context 秘密情報ファイル   | 秘密を含まないプロファイル選択子           | Context、プロジェクト、ホスト、プロファイルを検証して OPA へ問い合わせ、許可後に秘密情報を読み込んで挿入する    | 保持型の静的な Bearer 認証／固定ヘッダー経路。プロファイルと秘密情報の準備はホスト管理者が明示的に行う |

認証は「どの認証情報を利用できるか」に答え、認可は「この Context とプロジェクトがこの HTTP 操作を実行してよいか」に答えます。どちらも他方の代わりにはなりません。

### 判断入力、宛先、ライフサイクルの比較

| 方式                             | OPA が見るもの                                                                                                           | 適用範囲                                                                                        | 置換、ログアウト、Workspace への入り直し                                                                                                                                         |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ツール自身で管理（そのまま転送） | 本文を含まない通常の HTTP 操作。Gateway は認識した認証情報の値を判断入力から削除                                         | ツールが対応する標準 HTTP/HTTPS リクエストと完全一致のポリシー規則                              | ツールが認証情報の更新とログアウトを管理する。実行中のプロセスや Workspace のホームディレクトリにある秘密情報を Tobari は回収できない                                            |
| Auth Broker                      | 本文を含まない通常の HTTP 操作と、秘密を含まないプロバイダー情報。ハンドル、認証情報のリビジョン、実物の秘密情報は見ない | マニフェストの完全一致 HTTPS 宛先、送信元ヘッダーの構文、宛先変換と、別に許可したメソッドとパス | 置換またはローカルでのログアウトは記録のリビジョンを進めるか削除し、ハンドルを無効化する。投影内容の更新には入り直しが必要。ローカルでのログアウトはリモートでの失効処理ではない |
| 保持型の管理方式                 | 本文を含まない通常の HTTP 操作と、選択済みプロファイルの秘密を含まない情報                                               | 明示的に設定した Context、プロジェクト、ホスト、プロファイルと、対応する固定ヘッダー経路        | ホスト管理者が保持型の秘密情報を置換または削除する。選択子の投影内容を更新するには入り直しが必要な場合があり、実行中のプロセス環境は変わらない                                   |

この比較は意図的に非対称です。ツール自身で管理する方式では Workspace へ認証情報を渡しますが、保持型または Auth Broker 方式では、秘密情報を扱う責任を信頼する側に保ちます。

## プロバイダーとツールは別の軸

プロバイダーは外部の認証情報発行元を示します。ツールはハンドルの投影を受け取り、対応するリクエストを送る Workspace のクライアントです。サポート単位は片方の名前だけではなく、レビュー済みの組み合わせです。現在の組み込み設定は 1 対 1 なので、プロバイダー選択後に対応ツールも表示しますが、ツール自体は自動的に選ばれます。AWS のログイン方法は、これとは別の取得方法の選択です。

## Auth Broker を使う処理の正確な順序

### 1. 信頼するホストで取得する

`auth login [--provider PROVIDER]` は、信頼するホストの端末で、レビュー済みの固定ホスト用ヘルパーを一つ実行します。`--provider` を省略すると、インストール済みでレビュー済みの GitHub、AWS、Datadog のログインプロバイダーから明示的に選びます。各プロバイダーと一緒に、自動選択される対応ツールも表示します。`--provider` を指定すればメニューは省略します。Datadog は、他から分離された US1 固定の pup OAuth を使います。`auth import PROVIDER` は、プロバイダーがインポートを宣言している場合だけ、保護された端末以外の標準入力から、上限を設けて認証情報を受け取ります。秘密情報のバイト列はコマンド引数、環境変数、ログ、Workspace 入力を通りません。

Auth Broker は、選択した安定した Context とプロバイダーの型付き認証情報レコードを一つ、AES-256-GCM で暗号化した保管庫へ保存します。レコードは、静的な実物の秘密情報、不透明な AWS ホストドライバーの状態、Datadog OAuth セッションの状態のいずれかです。インストール用のルート鍵は macOS Keychain または所有者専用の Linux XDG 状態ファイルに置き、ロック解除中だけ Broker のメモリに保持します。

ログインやインポートは、ネットワーク規則を追加しません。

### 2. Workspace に入るとき、プロジェクトに結び付いたハンドルを発行する

次に対応する Workspace へ入ると、Tobari はランダムな `tobari-h1_…` ハンドルを調整します。ハンドルは次の値に結び付きます。

- 安定した Context ID
- 安定したプロジェクト ID
- プロバイダー
- 認証情報のリビジョン
- 完全一致する HTTPS 宛先
- 送信元ヘッダーと構文
- 宛先側の変換
- 秘密情報を含むヘッダーの秘匿化対象、または組み込み済みの処理計画一つ

ハンドルの投影先は、マニフェストで宣言した環境変数項目または完全なファイルだけです。同じ Context でも、別プロジェクトには別のハンドルを渡します。

### 3. Gateway がハンドルを認識して取り除く

一つのプロバイダーの結び付きだけが、正規化済みの HTTPS 接続先と宣言済み送信元ヘッダーの構文に一致した場合に限り、Gateway は Broker 経路を選びます。OPA への問い合わせや転送より前に、ハンドルをリクエストから削除します。

URL、Cookie、ヘッダー名、未対応の値、曖昧な位置にある Tobari 形式の印は不正です。この印を含むリクエストは、安全側に閉じて失敗する Broker 処理に固定され、そのまま転送する経路へ切り替わることはありません。

### 4. 秘密情報なしで結び付きを照合する

Gateway は、ハンドル、ホストから導出した Context とプロジェクトの通信主体、要求された HTTP とヘッダーの結び付きを Broker のランタイムソケットへ送ります。照合処理が返すのは、秘密を含まないプロバイダーとリビジョンの結び付き情報だけです。

Context、プロジェクト、プロバイダー、リビジョン、宛先、ヘッダーの結び付きが、すべて一致する必要があります。コピーされた、古い、無効化済み、不正、または曖昧なハンドルは、OPA より前に失敗します。

### 5. 通常の HTTP 操作を OPA へ問い合わせる

Gateway は、スキーマ 5 に従い、本文を含まない入力を送ります。OPA が見るのは秘密を含まないプロバイダー ID であり、ハンドルや実物の認証情報ではありません。Broker 経由のリクエストは、広い静的なホストとメソッドの許可を継承しません。Context とプロジェクトに結び付いた、完全一致の L7 規則が必要です。

拒否時に、Gateway は秘密情報を解決する呼び出しを **一度も** 行いません。

### 6. 許可後に宣言済みの操作だけを実行する

許可後の分岐は、プロバイダーごとの処理計画によって異なります。

- **静的なスキーマ 1（GitHub、Chatwork を含む）:** Gateway は同じリビジョンを一度だけ解決し、宣言済みの宛先ヘッダーだけを置換します。
- **AWS スキーマ 2:** Gateway は許可済みリクエスト全体を 8 MiB の上限内で保持し、ハッシュを計算します。Broker は、固定されたホストで AWS CLI の認証情報をエクスポートするため、認証済みの非公開コンパニオン操作を一つ開始します。同じリビジョンを再確認して永続化し、標準のヘッダー型 SigV4 をローカルで署名します。一時 AWS 認証情報は、Workspace、OPA、ポリシー、監査、永続的な投影先に入りません。
- **Datadog スキーマ 2:** アクセストークンが 5 分間の更新時間帯の外にある場合は、そのトークンを選びます。時間帯内なら、プロキシを使わずリダイレクトもしない、完全一致の US1 トークンエンドポイントで同じレコードの更新を一度だけ実行します。更新後の状態を確定してから、リクエスト専用の Bearer 値を返します。

その後 Gateway は、完全一致するアプリケーション宛先へ別に検証した TLS 接続を作り、接続先への通信を一度だけ試みます。

解決済みの静的な秘密情報、一時 AWS 認証情報と署名材料、Datadog アクセストークンは、信頼する基盤内で一つのリクエストだけに使います。Workspace、OPA、CLI 出力、エラー、監査へは返しません。

## ローテーション、置換、ログアウト、実行中のプロセス

- **認証情報の置換:** 認証情報のリビジョンを増やし、その Context とプロバイダーの古いハンドルをすべてアトミックに無効化します。
- **ログアウト:** ローカルの Context とプロバイダーの認証情報を削除し、ハンドルを無効化します。プロバイダーへ接続しないため、リモート側での失効処理は保証しません。
- **Auth Broker の再起動:** サービスはロック状態に戻ります。ロック解除に成功すると、有効な暗号化状態を再び読み込みます。ロック中はリクエスト用の認証情報を解決しません。
- **Workspace への入り直し:** Tobari は実行中のプロセス環境を書き換えられないため、ログイン、インポート、置換、ログアウトの後に必要です。次に入るとき、環境への投影を作り直し、内容が変わっていない Tobari 所有の完全なファイルだけを変更します。

実行中の古いプロセスに古いハンドル文字列が残っていても、リビジョンの変更やログアウトの後は Broker が拒否します。プロセスのメモリにあるツール固有の秘密情報は、Broker の無効化ではなく、そのツールの動作に従います。

## コピーされたハンドルの具体例

プロセスが Workspace A の有効なハンドルを Workspace B にコピーし、同じホストとヘッダーへ送ります。

Gateway は受信側インターフェースから B の通信主体を導出します。Broker の照合処理は、B とハンドルの Context、プロジェクト、プロバイダー、リビジョン、宛先、ヘッダーの結び付きを比較します。プロジェクトが一致しないため `403 credential_handle_invalid` となり、Gateway は OPA の呼び出し、秘密情報の解決、そのまま転送する代替処理、接続先への通信を行いません。

Workspace A でも、有効なハンドルだけでは不十分です。通常の HTTP 操作には OPA の許可が必要です。

## 保証と制限

**保証すること:** Broker が扱う静的な秘密情報、更新可能な状態、リクエスト用に導出した認証情報は、Workspace と OPA の外に残ります。ハンドルの利用は、Context、プロジェクト、プロバイダー、リビジョン、HTTP 宛先に結び付きます。拒否時には、解決、更新、コンパニオン、署名操作を一度も行いません。不正な Tobari 形式の印から代替経路へ切り替えません。ログイン、インポート、ログアウトはネットワークポリシーを編集しません。

**保証しないこと:** ログアウトによるリモートのプロバイダー側での失効処理。同じ Workspace 内のプロセス分離。悪意あるプロセスが許可済みの権限を使うことの防止。同じ Workspace のプロセスからツール固有認証情報を隠すこと。レビュー済みの処理計画外にある OAuth、更新、署名、プロバイダー API。Gateway、Broker、ルート鍵の保存基盤、ホストが侵害された後の保護。

ハンドル自体は、許可済み経路の通常リクエスト本文にデータとして含められます。Tobari は任意の本文を検索しないためです。実物の認証情報は公開されず、Broker の権限も得られません。ただし、秘密でないハンドルを本文へ含めて持ち出すことは、本文検査の保証範囲外です。

## まとめ

ツール固有のログインは、一つの Workspace にツールの実物の認証情報を与えます。保持型の管理経路は静的な秘密情報を Gateway に保ちます。Broker 経路が Workspace へ渡すのは、結び付きのあるハンドルだけです。宣言済みの静的認証情報、AWS、Datadog の各操作は OPA の許可後に行います。三方式とも通常のネットワーク認可に依存します。

    Workspace のハンドルは実物の認証情報を含む、または同じ値ですか？
  </summary>
  いいえ。用途を制限した不透明なレコード選択子です。静的または更新可能な
  認証状態は、暗号化した Context 保管庫に残ります。
</details>

<details>
  <summary>
    OPA が拒否したとき、秘密情報を扱う Auth Broker の操作は何か行われますか？
  </summary>
  ありません。OPA より前に、秘密を含まない結び付き情報を照合する場合はあります。
  しかし、静的な秘密情報の解決、Datadog トークンの選択または更新、AWS
  コンパニオン によるエクスポート、署名は許可後にだけ行います。
</details>

<details>
  <summary>
    <code>auth logout</code> はプロバイダー側で認証情報を失効させますか？
  </summary>
  いいえ。プロバイダーへ接続せず、ローカルの Context とプロバイダーの状態
  を削除し、Tobari ハンドルを無効化します。
</details>

<details>
  <summary>
    同じ Workspace 内の悪意あるプロセスは、すでに許可された認証済みの
    権限を使えますか？
  </summary>
  はい。同じ Workspace のプロセスは境界を共有します。Tobari は投影内容
  と経路の権限を制限しますが、Workspace 内のプロセスは分離しません。
</details>

許可とログインを混同する場合は[ポリシー学習](../policy-learning/)へ戻ってください。次は[状態と復旧](../state-and-recovery/)で永続成果物を対応付けます。
