認証は利用できる identity material を決めます。認可は一つの Context/project が一つの
完全一致 HTTP effect を実行できるか決めます。login、import、置換、projection は通信
許可を追加しません。

## 経路選択と管理場所

| 方式                     | 実物の認証情報                                           | Workspace が読めるもの           | 信頼側の処理                                                                                          |
| ------------------------ | -------------------------------------------------------- | -------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Workspace 所有の互換経路 | 書き込み可能な Workspace home の tool file/process state | tool credential                  | 未宣言の binding だけで、OPA/audit から値を除き、完全一致 allow 後に転送                              |
| Broker 必須の binding    | installation root key で開く暗号化 Context vault         | project-bound opaque handle 一つ | Workspace の実認証情報を拒否し、policy 前に handle binding を確認して allow 後に reviewed plan を適用 |

Workspace 所有の認証は、Tobari が provider binding を宣言していない場合だけの明示的な互換経路です。Tobari はその state を Broker 管理や revocable だとは主張しません。同じ Workspace の process は authority を共有します。

## Provider と Tool は別の概念

Provider は credential authority、Tool は projection を受け取る Workspace client です。
V1 の組み込みは GitHub/`gh` 一組で、`auth login --provider github` の明示が必要です。
owner provider は executable helper ではなく strict stdin import と static projection を使います。

## Auth Broker の処理順序

### 1. 信頼するホストで取得する

組み込み command は sanitized temporary home から固定 GitHub helper を実行します。
`auth import PROVIDER` は install 済み owner provider に対して、保護された non-terminal
stdin から上限付き value 一つを読みます。secret byte は argv、environment、log、Workspace
input を通りません。Broker は stable Context/provider の static record 一つを暗号化保存し、
allow rule は作りません。

### 2. bound handle を発行する

対応 Workspace へ入ると、Context、project、provider、credential revision、完全一致 HTTPS
target、source syntax、destination transformation、redaction set に結び付く random handle
を配置します。project が違えば handle も異なります。

### 3. 認識、除去、照合を行う

Gateway は宣言済み binding が一つだけ一致するとき Broker path を必須にします。その binding に Workspace の実認証情報があると、OPA より前に `broker_auth_required` で失敗します。handle の場合はそれを除去し、観測した
source から Context/project identity を導出し、secret を返さない binding metadata 検査を
Broker に求めます。copy、stale、revoked、malformed、misplaced、ambiguous marker はここで
失敗し、passthrough fallback はありません。

### 4. guardrail と完全一致 policy を適用する

immutable Context preset guardrail が最優先です。terminal preset denial では candidate、DNS、
secret resolution、upstream call がゼロです。それ以外では、OPA が handle、revision、body、
credential を含まない完全一致 body-free effect と non-secret provider metadata を受け取ります。

### 5. allow 後に static revision を一度解決する

allow 後だけ、Gateway が同じ revision と完全一致 HTTP/header binding を Broker に一度要求します。
Gateway は manifest の destination header だけを置換し、完全一致 TLS destination を別に検証し、
upstream を一度だけ試みます。primary secret は trusted infrastructure 内で request-local です。

## 置換、logout、再入室

置換は revision を進め、Context/provider の過去の handle をすべて失効させます。logout は local
record と handle を削除しますが provider へ連絡しません。実行中 process environment は書き換え
られないため、再入室で projection を reconcile します。Broker restart 後は locked で、正しい
unlock まで resolution はありません。

## 失敗時の動作

| 条件                                                | 結果                                                                             |
| --------------------------------------------------- | -------------------------------------------------------------------------------- |
| 宣言済み binding に Workspace の実認証情報          | `403 broker_auth_required`。fallback、policy request、upstream attempt なし      |
| 不正、古い、copy、revoked、mismatch handle          | `403 credential_handle_invalid`。fallback、policy request、upstream attempt なし |
| Broker locked/unavailable                           | `503 credential_broker_unavailable`。upstream attempt なし                       |
| 有効 handle だが terminal guardrail または OPA deny | `403 policy_denied`。resolution/upstream work ゼロ                               |
| vault があるのに root key がない                    | fail closed。代替鍵を生成しない                                                  |
| 実行中 process が old handle を保持                 | 修復後に再入室。Broker は old revision を拒否                                    |

## 保証と制限

宣言済み binding では、Broker primary secret は Workspace、OPA、output、error、audit の外に残ります。handle は primary credential ではありませんが、範囲を限定した bearer capability です。project-bound exact であり、network grant ではありません。V1 は Context ごとの複数 account、
remote logout、dynamic credential plan、同じ Workspace 内の process 分離を提供しません。

## まとめ

Workspace 所有の state は、未宣言 binding の互換経路です。宣言済み binding は bound Broker handle を必須とし、実認証情報を policy より前に拒否します。
