Gateway は credential を準備したり OPA へ問い合わせたりする前に、リクエストの
Context と project を特定します。trusted host が作成した owner-controlled registry と、
リクエストを受けた local interface の組み合わせから principal を選びます。

caller-supplied の project ID や Context ID は authorization input になりません。そのため
header を変えても別 Workspace の learned rule は利用できず、同じ host、method、path への
通信でも、その Workspace の principal に scope された authority が必要です。この仕組みは
[システム全体像](../system-overview/)の専用 network を利用し、[HTTPS と TLS](../https-and-tls/)の intercepted flow にも同じように適用されます。

## 信頼するホストで principal を作る

logical Workspace ごとに host-side lifecycle code が次を行います。

1. stable UUIDv7 project ID と permanent Context ID を検証する
2. exact owner-labeled dedicated internal network を作成または検証する
3. Gateway をその network へ接続する
4. その exact network 上の Gateway IP address を inspect する
5. schema 2 binding を owner-only principal registry へ atomically に書く

binding には project ID、Context ID、Context name、canonical root、network name、Gateway interface IP が含まれます。project entry と address entry は一意である必要があり、unsafe loopback、link-local、multicast、unspecified address は拒否されます。

registry は Gateway へ read-only で mount されます。Workspace には書き込み権限も、その binding を作成できる Docker control も渡されません。

## リクエストごとに principal を特定する

Gateway は `flow.client_conn.sockname[0]`、つまり accepted project-network connection における自分自身の local address を観測します。この local address が一つの binding を選びます。

この詳細は重要です。この値は次のいずれでもありません。

- header で主張された client source IP
- Workspace environment の `TOBARI_ID` または `TOBARI_CONTEXT_ID`
- `x-tobari-session` または別の request field
- Context display name
- credential profile/provider name
- URL parameter

lookup 後、Gateway は registry-derived `context_id` と `project_id` を schema 5 OPA input へ入れます。固定された OPA router は Context ID で policy を選択し、learned rule は project ID も要求します。

## 偽装を試みる具体例

Workspace B が Workspace A から次の request header を copy したとします。

```http
X-Tobari-Session: project-a
X-Tobari-Context: review
Authorization: Bearer example
```

connection は変わらず Gateway の Workspace B interface に到着します。Gateway は B の Context/project binding を選択し、必要に応じ control/credential value を strip または redact します。host、port、method、path が同じでも、A のために学習した rule は B に一致しません。

request に A からコピーした broker handle が含まれる場合は、さらに厳格です。non-secret Broker introspection は、derived B principal と handle の Context、project、provider、credential revision、target、source-header binding を照合します。不一致は OPA より前に `403 credential_handle_invalid` になります。

## ネットワーク上の identity を使う理由

Workspace process は、自分の request、environment、filesystem、tool configuration を変更できます。そこに置かれた identity はすべて attacker-controlled data です。dedicated network は、信頼する host lifecycle code が interface binding を確立し、Workspace が request ごとに選べない場所を提供します。

これは、より一般的な contract を Docker で実装したものです。runtime は、connection-to-principal の信頼できる binding を提供します。policy code は、name や parsing convention から identity を再構築しません。

## 失敗時の動作

- registry が missing、unreadable、too large、wrong version、malformed、unsafe、duplicate、ambiguous の場合、Gateway は `403 project_principal_unavailable` を返します。
- incoming local interface が未登録なら、OPA または upstream I/O より前に同じ 403 を返します。
- network recreation で Gateway interface address が変わった場合、Workspace を ready にする前に lifecycle が registry を reconcile する必要があります。
- OPA にとって Context ID が unknown なら aggregate router は deny し、current/default Context へ fallback しません。
- user が Context display name/default を変えても、name ではなく stable stored ID が enforcement identity のままです。

Gateway binding parser は binding ごとの exact shape と required value を検証します。この site は、Python の general JSON parser について、より強い duplicate-key rejection property までは主張しません。

## 保証と制限

**対応 lifecycle/topology で保証すること:** caller-supplied identity は authority ではありません。project と Context は OPA より前に一緒に確立されます。learned rule と broker handle は project principal を越えられません。stale network binding は fail closed します。

**保証しないこと:** host、Docker、Gateway、registry の侵害後の耐性、重なる selected root の tenant isolation、general cryptographic remote-workload identity、Tobari lifecycle 外で手作業により作られた任意の container からの identity derivation。

## まとめ

host は、一つの exact Gateway project-network interface を stable Context/project ID へ bind します。Gateway は request ごとにその interface を観測します。header と name は caller を記述できますが、別 principal の authority を与えられません。

## 理解を確認する

shared Gateway/OPA service が shared learned permission を意味しない理由を説明できるはずです。
