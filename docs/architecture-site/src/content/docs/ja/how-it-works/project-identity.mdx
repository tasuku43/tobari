Gateway は認証情報を準備したり OPA へ問い合わせたりする前に、リクエストの
Context とプロジェクトを特定します。信頼するホストが作成した、所有者管理の登録簿と、
リクエストを受けたローカルインターフェースの組み合わせからプリンシパル（通信主体）を選びます。

呼び出し元が申告したプロジェクト ID や Context ID は、認可の入力になりません。そのため、
ヘッダーを変えても別 Workspace の学習済み規則は利用できません。同じホスト、メソッド、パスへの
通信でも、その Workspace の通信主体に限定された権限が必要です。この仕組みは
[システム全体像](../system-overview/)の専用ネットワークを利用し、[HTTPS と TLS](../https-and-tls/)で検査する通信にも同じように適用されます。

## 信頼するホストで通信主体を登録する

論理 Workspace ごとに、ホスト側のライフサイクル処理が次を行います。

1. 安定した UUIDv7 プロジェクト ID と永続的な Context ID を検証する
2. 所有者ラベルが完全一致する専用内部ネットワークを作成または検証する
3. Gateway をそのネットワークへ接続する
4. そのネットワーク上の Gateway IP アドレスを取得する
5. スキーマ 2 の結び付き情報を、所有者だけが読める通信主体登録簿へアトミックに書く

結び付き情報には、プロジェクト ID、Context ID、Context の名前、正規化済みルート、ネットワーク名、Gateway のインターフェース IP が含まれます。プロジェクト側とアドレス側の登録は、それぞれ一意である必要があります。安全でないループバック、リンクローカル、マルチキャスト、未指定アドレスは拒否します。

登録簿は Gateway へ読み取り専用でマウントされます。Workspace には、書き込み権限も、結び付き情報を作成できる Docker の制御権も渡しません。

## リクエストごとに通信主体を特定する

Gateway は `flow.client_conn.sockname[0]`、つまり受け付けたプロジェクトネットワーク接続における、自身のローカルアドレスを観測します。このアドレスが結び付き情報を一つ選びます。

この詳細は重要です。この値は次のいずれでもありません。

- ヘッダーで申告されたクライアントの送信元 IP
- Workspace 環境の `TOBARI_ID` または `TOBARI_CONTEXT_ID`
- `x-tobari-session` または別のリクエスト項目
- Context の表示名
- 認証情報のプロファイルまたはプロバイダー名
- URL パラメーター

照合後、Gateway は登録簿から得た `context_id` と `project_id` をスキーマ 5 の OPA 入力へ入れます。固定された OPA の振り分け処理は Context ID でポリシーを選び、学習済み規則はプロジェクト ID も要求します。

## 偽装を試みる具体例

Workspace B が Workspace A から次のリクエストヘッダーをコピーしたとします。

```http
X-Tobari-Session: project-a
X-Tobari-Context: review
Authorization: Bearer example
```

接続は変わらず、Gateway の Workspace B 用インターフェースに到着します。Gateway は B の Context とプロジェクトの結び付きを選び、必要に応じて制御用の値や認証情報を削除または秘匿化します。ホスト、ポート、メソッド、パスが同じでも、A のために学習した規則は B に一致しません。

リクエストに A からコピーした Broker ハンドルが含まれる場合は、さらに厳格です。秘密を含まない Broker の照合処理は、導出した B の通信主体と、ハンドルの Context、プロジェクト、プロバイダー、認証情報のリビジョン、宛先、送信元ヘッダーの結び付きを照合します。一致しない場合は、OPA より前に `403 credential_handle_invalid` になります。

## ネットワーク上の識別情報を使う理由

Workspace のプロセスは、自身のリクエスト、環境、ファイルシステム、ツール設定を変更できます。そこに置かれた識別情報は、すべて攻撃者が制御できるデータです。専用ネットワークでは、信頼するホストのライフサイクル処理がインターフェースとの結び付きを確立します。Workspace がリクエストごとに選べない場所から、識別情報を得られます。

これは、より一般的な契約を Docker で実装したものです。ランタイムは、接続と通信主体の信頼できる結び付きを提供します。ポリシー処理が、名前や構文規則から識別情報を組み立て直すことはありません。

## 失敗時の動作

- 登録簿が欠落、読み取り不能、上限超過、バージョン不一致、不正、安全でない、重複、または曖昧な場合、Gateway は `403 project_principal_unavailable` を返します。
- 受信したローカルインターフェースが未登録なら、OPA または接続先への I/O より前に同じ 403 を返します。
- ネットワークの再作成で Gateway のインターフェースアドレスが変わった場合は、Workspace を利用可能にする前に、ライフサイクル処理が登録簿を調整する必要があります。
- OPA にとって Context ID が未知なら、集約ポリシーの振り分け処理は拒否し、現在選択中または既定の Context へ切り替えません。
- 利用者が Context の表示名や既定値を変えても、強制に使う識別情報は、名前ではなく保存済みの安定した ID のままです。

Gateway の結び付き情報の解析処理は、各レコードの形式と必須値が完全に一致することを検証します。このサイトは、Python の汎用 JSON 解析処理について、重複キーを必ず拒否するという、さらに強い性質までは主張しません。

## 保証と制限

**対応するライフサイクルと構成で保証すること:** 呼び出し元が申告した識別情報に権限はありません。プロジェクトと Context は、OPA より前に一緒に確立されます。学習済み規則と Broker ハンドルは、プロジェクトの通信主体を越えられません。古いネットワーク結び付きは、安全側に閉じて失敗します。

**保証しないこと:** ホスト、Docker、Gateway、登録簿が侵害された後の耐性。重なる選択ルート間のテナント分離。リモートの処理主体を暗号学的に識別する一般的な仕組み。Tobari のライフサイクル外で手作業により作られた任意のコンテナからの識別情報導出。

## まとめ

ホストは、完全一致する一つの Gateway プロジェクトネットワークインターフェースを、安定した Context とプロジェクトの ID へ結び付けます。Gateway はリクエストごとにそのインターフェースを観測します。ヘッダーと名前で呼び出し元を記述することはできますが、別の通信主体が持つ権限は得られません。

## 理解を確認する

Gateway と OPA を共有しても、学習済みの許可まで共有されない理由を説明できるはずです。

  <summary>
    プロセスが別のプロジェクト ID をヘッダーに書いた場合、どの ID が通信主体
    として OPA へ届きますか？
  </summary>
  Gateway の受信側ローカルインターフェースと、ホストの通信主体登録簿 で選ばれた
  ID です。ヘッダーに権限はありません。
</details>

<details>
  <summary>
    Workspace A と B が同じホスト、ポート、メソッド、パスを使うとき、A
    が学習した 規則は B の通信を許可しますか？
  </summary>
  いいえ。完全一致の学習済み規則は、安定した Context ID とプロジェクト ID
  にも結び付きます。
</details>

<details>
  <summary>
    再作成されたネットワークに有効な登録簿 の結び付きがない間、どうなりますか？
  </summary>
  リクエストは `project_principal_unavailable` で安全側に閉じて失敗します。まず
  ライフサイクル処理がインターフェースの結び付きを調整する必要があります。
</details>
