Gateway は、認証情報を準備したり OPA へ問い合わせたりする前に、リクエストの Workspace Manifest とプロジェクトを特定します。呼び出し元が送ったヘッダーではなく、信頼するホストが作成した登録簿と、カーネルが観測した Workspace の送信元エンドポイントを使います。このようにホスト側の事実から確立する通信主体を、プリンシパル（principal）と呼びます。

呼び出し元が申告したプロジェクト ID や Workspace Manifest ID は、通信許可の根拠になりません。そのため、ヘッダーを書き換えても別の Workspace に許可されたルールは利用できません。同じホスト、メソッド、パスへの通信でも、その Workspace のプリンシパルに結び付いた権限が必要です。この仕組みは[システム全体像](../system-overview/)の専用ネットワークを使い、[HTTPS と TLS](../https-and-tls/)で検査する通信にも同じように適用されます。

## 信頼するホストでプリンシパルを登録する

論理 Workspace ごとに、ホスト側のライフサイクル処理が次を行います。

1. 安定した UUIDv7 プロジェクト ID と永続的な Workspace Manifest ID を検証する
2. 所有者ラベルが完全一致する専用内部ネットワークを作成または検証する
3. Gateway をそのネットワークへ接続する
4. そのネットワーク上の Workspace と Gateway の IP アドレスを取得する
5. 両方のエンドポイントが別々で、正規化済みかつ一意であることを検証する
6. スキーマ 1 の結び付き情報を、所有者だけが読めるプリンシパル登録簿へ、途中状態を見せずに書き込む

結び付き情報には、プロジェクト ID、Workspace Manifest ID、Workspace Manifest の名前、正規化済みルート、ネットワーク名、Workspace の送信元 IP、Gateway のエンドポイント IP が含まれます。プロジェクト、ネットワーク、両方のアドレスは、それぞれ一意である必要があります。ループバック、リンクローカル、マルチキャスト、未指定アドレスなど、プリンシパルとして安全に使えないアドレスは拒否します。

登録簿は Gateway へ読み取り専用でマウントされます。Workspace には、登録簿への書き込み権限も、結び付き情報を作成できる Docker の制御機能も渡しません。

## リクエストごとにプリンシパルを特定する

Gateway は `flow.client_conn.peername[0]`、つまりプロジェクトネットワークから受けた接続について、カーネルが報告する送信元アドレスを観測します。この Workspace 送信元アドレスが、登録簿の結び付きを一つ選びます。登録済み Gateway エンドポイントはライフサイクル調整時に検証し、エンドポイントの再利用を防ぎますが、リクエストのプリンシパル検索キーにはしません。

この値は、次のいずれでもありません。

- ヘッダーで申告されたクライアントの送信元 IP
- Workspace 環境の `TOBARI_ID` または `TOBARI_CONTEXT_ID`
- `x-tobari-session` または別のリクエスト項目
- Workspace Manifest の表示名
- 認証情報のプロファイルまたはプロバイダー名
- URL パラメーター

照合後、Gateway は登録簿から得た `workspace_manifest_id` と `project_id` をスキーマ 1 の OPA 入力へ入れます。固定された OPA の振り分け処理は Workspace Manifest ID でポリシーを選び、学習済みルールはプロジェクト ID も要求します。

## 偽装を試みる具体例

Workspace B が Workspace A から次のリクエストヘッダーをコピーしたとします。

```http
X-Tobari-Session: project-a
X-Tobari-Workspace Manifest: review
Authorization: Bearer example
```

接続には変わらず、カーネルが観測した Workspace B の送信元エンドポイントが付きます。Gateway は B の Workspace Manifest とプロジェクトの結び付きを選び、必要に応じて制御用の値や認証情報を削除または伏せます。ホスト、ポート、メソッド、パスが同じでも、A のために学習したルールは B に一致しません。

リクエストに A からコピーした Broker ハンドルが含まれる場合は、さらに厳格です。秘密情報を含まない Broker の照合処理は、導出した B のプリンシパルと、ハンドルに結び付いた Workspace Manifest、プロジェクト、プロバイダー、認証情報のリビジョン、接続先、送信元ヘッダーを照合します。一致しない場合は、OPA より前に `403 credential_handle_invalid` になります。

## ネットワーク上の識別情報を使う理由

Workspace のプロセスは、自身のリクエスト、環境、ファイルシステム、ツール設定を変更できます。そこに置かれた識別情報は、すべて信頼しない入力です。専用ネットワークでは、信頼するホストのライフサイクル処理が正確な送信元エンドポイントとの結び付きを確立します。Workspace がリクエストごとに選べない場所から、識別情報を得られます。

これは、ランタイムが接続とプリンシパルの信頼できる結び付きを提供し、ポリシー処理が名前や文字列の形式から識別情報を作り直さない、という契約を Docker で実装したものです。

## 失敗時の動作

- 登録簿が欠落、読み取り不能、上限超過、バージョン不一致、不正、安全でない、重複、または曖昧な場合、Gateway は `403 project_principal_unavailable` を返します。
- 受信した Workspace の送信元エンドポイントが未登録なら、OPA または接続先への入出力より前に同じ 403 を返します。
- ネットワークの再作成でいずれかのエンドポイントが変わった場合は、Workspace を利用可能にする前に、ライフサイクル処理がネットワークガードを再適用し、登録簿を調整する必要があります。
- OPA にとって Workspace Manifest ID が未知なら、集約ポリシーの振り分け処理は拒否し、現在選択中または既定の Workspace Manifest へ切り替えません。
- 利用者が Workspace Manifest の表示名や既定値を変えても、強制に使う識別情報は、名前ではなく保存済みの安定した ID のままです。

Gateway の登録簿解析処理は、各レコードの形式と必須値が完全に一致することを検証します。このサイトは、Python の汎用 JSON 解析処理について、重複キーを必ず拒否するという、さらに強い性質までは主張しません。

## 保証と制限

**サポート対象のライフサイクルと構成で保証すること:** 呼び出し元が申告した識別情報に権限はありません。プロジェクトと Workspace Manifest は、OPA より前に一緒に確立されます。学習済みルールと Broker ハンドルは、プロジェクトのプリンシパルを越えられません。古いネットワーク結び付きは拒否されます。

**保証しないこと:** ホスト、Docker、Gateway、登録簿が侵害された後の耐性。重なる作業対象ルート間の分離。リモートの通信主体を暗号学的に識別する一般的な仕組み。Tobari のライフサイクル外で手作業により作られた任意のコンテナからの識別情報導出。

## まとめ

ホストは、Workspace の送信元エンドポイント、Gateway のエンドポイント、専用ネットワークを、安定した Workspace Manifest ID とプロジェクト ID へ結び付けます。Gateway はリクエストごとに送信元エンドポイントを観測します。ヘッダーと名前で呼び出し元を説明することはできますが、別のプリンシパルが持つ権限は得られません。

## 理解を確認する

Gateway と OPA を共有しても、学習済みの許可まで共有されない理由を説明できるはずです。
