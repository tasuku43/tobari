Gateway は OPA へ問い合わせる前に、request の Context と Workspace を特定します。caller が送った header ではなく、trusted host が作成した registry と kernel-observed Workspace source endpoint を使います。このように host-side fact から確立する通信主体を principal と呼びます。

caller が申告した Context ID、Workspace ID、Template ID は通信許可の根拠になりません。そのため header を書き換えても別 Workspace に許可された rule は利用できません。同じ host、method、path でも、その Context/Workspace principal に結び付いた authority が必要です。この仕組みは[システム全体像](../system-overview/)の専用 network を使い、[HTTPS と TLS](../https-and-tls/)で検査する通信にも同じように適用されます。

## 信頼するホストでプリンシパルを登録する

論理 Workspace ごとに、ホスト側のライフサイクル処理が次を行います。

1. stable Context ID、Workspace ID、permanent Workspace-to-Context binding を検証する
2. 所有者ラベルが完全一致する専用内部ネットワークを作成または検証する
3. Gateway をそのネットワークへ接続する
4. そのネットワーク上の Workspace と Gateway の IP アドレスを取得する
5. 両方のエンドポイントが別々で、正規化済みかつ一意であることを検証する
6. スキーマ 1 の結び付き情報を、所有者だけが読めるプリンシパル登録簿へ、途中状態を見せずに書き込む

binding には Context ID、Workspace ID、Context presentation、canonical root、network name、Workspace source IP、Gateway endpoint IP が含まれます。Context、Workspace、network、両 endpoint は exact かつ一意である必要があります。loopback、link-local、multicast、unspecified address など principal として安全に使えない address は拒否します。

登録簿は Gateway へ読み取り専用でマウントされます。Workspace には、登録簿への書き込み権限も、結び付き情報を作成できる Docker の制御機能も渡しません。

## リクエストごとにプリンシパルを特定する

Gateway は `flow.client_conn.peername[0]`、つまりプロジェクトネットワークから受けた接続について、カーネルが報告する送信元アドレスを観測します。この Workspace 送信元アドレスが、登録簿の結び付きを一つ選びます。登録済み Gateway エンドポイントはライフサイクル調整時に検証し、エンドポイントの再利用を防ぎますが、リクエストのプリンシパル検索キーにはしません。

この値は、次のいずれでもありません。

- ヘッダーで申告されたクライアントの送信元 IP
- Workspace 環境の `TOBARI_ID` または `TOBARI_CONTEXT_ID`
- `x-tobari-session` または別のリクエスト項目
- Workspace Template の表示名
- 認証情報のプロファイルまたは外部サービス名
- URL パラメーター

照合後、Gateway は検証済み Context ID と Workspace ID を、frozen private schema-1 field `workspace_template_id` と `project_id` へ入れます。これらの wire name は public alias ではありません。固定 OPA router は Context の active Template baseline と Policy Memory を選び、learned rule は observed Workspace ID を保持します。

## 偽装を試みる具体例

Workspace B が Workspace A から次のリクエストヘッダーをコピーしたとします。

```http
X-Tobari-Session: project-a
X-Tobari-Workspace Template: review
Authorization: Bearer example
```

connection には変わらず kernel-observed Workspace B source endpoint が付きます。Gateway は B の Context/Workspace binding を選び、必要に応じて control value や credential を除去または redaction します。host、port、method、path が同じでも、A のために学習した rule は B に一致しません。

request に A から copy した Workspace identity が含まれる場合はさらに厳格です。Gateway は導出した B principal と host-owned Context、Workspace、target、source-header binding を OPA より前に確認します。一致しない場合は拒否されます。

## ネットワーク上の識別情報を使う理由

Workspace のプロセスは、自身のリクエスト、環境、ファイルシステム、ツール設定を変更できます。そこに置かれた識別情報は、すべて信頼しない入力です。専用ネットワークでは、信頼するホストのライフサイクル処理が正確な送信元エンドポイントとの結び付きを確立します。Workspace がリクエストごとに選べない場所から、識別情報を得られます。

これは、ランタイムが接続とプリンシパルの信頼できる結び付きを提供し、ポリシー処理が名前や文字列の形式から識別情報を作り直さない、という契約を Docker で実装したものです。

## 失敗時の動作

- 登録簿が欠落、読み取り不能、上限超過、バージョン不一致、不正、安全でない、重複、または曖昧な場合、Gateway は `403 project_principal_unavailable` を返します。
- 受信した Workspace の送信元エンドポイントが未登録なら、OPA または接続先への入出力より前に同じ 403 を返します。
- ネットワークの再作成でいずれかのエンドポイントが変わった場合は、Workspace を利用可能にする前に、ライフサイクル処理がネットワークガードを再適用し、登録簿を調整する必要があります。
- OPA にとって Context ID が未知なら aggregate router は拒否し、default Template へ fallback しません。
- 利用者が Template display name や default を変えても、enforcement identity は stable Context/Workspace ID のままです。

Gateway の登録簿解析処理は、各レコードの形式と必須値が完全に一致することを検証します。このサイトは、Python の汎用 JSON 解析処理について、重複キーを必ず拒否するという、さらに強い性質までは主張しません。

## 保証と制限

**サポート対象のライフサイクルと構成で保証すること:** 呼び出し元が申告した識別情報に権限はありません。プロジェクトと Workspace Template は、OPA より前に一緒に確立されます。学習済みルールと Authentication 識別子は、プロジェクトのプリンシパルを越えられません。古いネットワーク結び付きは拒否されます。

**保証しないこと:** ホスト、Docker、Gateway、登録簿が侵害された後の耐性。重なる作業対象ルート間の分離。リモートの通信主体を暗号学的に識別する一般的な仕組み。Tobari のライフサイクル外で手作業により作られた任意のコンテナからの識別情報導出。

## まとめ

host は Workspace source endpoint、Gateway endpoint、dedicated network を stable Context ID と Workspace ID へ結び付けます。Gateway は request ごとに source endpoint を観測します。header と name で caller を説明することはできますが、別 principal の authority は得られません。

## 理解を確認する

Gateway と OPA を共有しても、学習済みの許可まで共有されない理由を説明できるはずです。
