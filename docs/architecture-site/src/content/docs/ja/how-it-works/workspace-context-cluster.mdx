Workspace は、ディレクトリに結び付いた一つの論理的な Tobari です。その永続的な
識別情報は、正規化したプロジェクトルートと安定した Context ID の組み合わせで決まります。
プロセスを実行するランタイムコンテナは交換できます。

Context は、ランタイム、ポリシー、エージェント、認証情報に関する、ホスト所有の設定を提供します。
一つのインストール環境は強制サービスのクラスターを共有しますが、Workspace の識別情報、
ホームディレクトリ、プロジェクトネットワークは共有しません。そのため、現在選択中の Context を切り替えても
既存 Workspace は移行しません。同じプロジェクトルートに、別 Context の Workspace を
持つこともできます。周囲のネットワーク上の役割は[システム全体像](../system-overview/)で説明しています。

## 最も長く残る識別情報からランタイムの詳細へ

### Tobari と Workspace

一つの **Tobari** は、長期間存在する、信頼しない論理実行環境です。**Workspace** は、ライフサイクル操作と一覧表示で利用者に見せる、ディレクトリに結び付いた呼び名です。Tobari とは別の資源ではありません。

永続的な識別情報は、次の組み合わせで決まります。

- 正規化したホスト上のプロジェクトルート
- 安定した Context ID
- 状態、ラベル、通信主体の識別に使う、生成済みの安定した内部 Tobari ID とプロジェクト ID

プロジェクト ID は診断用であり、通常の操作で利用者が指定する操作対象ではありません。

### Context

**Context** は、安定した不透明な ID と人が読む名前を持つ、ホスト所有の実行設定です。マニフェストファイルは次を参照します。

- 互換性のあるランタイムイメージ
- 読み取り専用のエージェントプロファイル
- ガイド付きまたは高度なポリシーのソース
- 保持型の管理方式で使う認証情報の保存領域
- 暗号化した Broker 保管庫とは別に保存するプロバイダー設定

マニフェストファイル自体には、ルート鍵、Broker が管理する実物の秘密情報、保管庫の内容は含まれません。**現在選択中の Context** は、コマンドで `--context` を省略したときの既定値にすぎません。共有の強制権限ではありません。

### クラスター

インストール環境ごとの **クラスター** には、Gateway、OPA、ロック状態の Auth Broker が一つずつあります。さらに、`control` と `egress` のネットワーク、集約した反映データ、通信主体の登録簿、保持型認証情報の反映データ、CA のライフサイクルが含まれます。

Context に結び付いたすべての Workspace がこのクラスターを共有します。サービスを共有しても、プロジェクトの識別情報は失われません。Gateway はリクエストごとにプロジェクトと Context の通信主体を導出し、OPA は安定した Context ID を使って Context のポリシーへ振り分けます。

### ランタイムイメージとコンテナ

**ランタイムイメージ**は OS、ツール、エントリーポイント、ランタイム API を提供します。**ランタイムコンテナ**は、ある時点の Workspace を実行可能にします。どちらも Workspace の識別情報は定義しません。

Tobari は、独自のマウント、ネットワーク、プロキシと CA の環境変数、実行ユーザー、セキュリティと資源の制限、正常性の契約、明示的な `sleep infinity` を寿命管理用コマンドとして指定し、コンテナを作ります。イメージの `CMD` が Workspace の寿命を決めることはありません。構成のずれや消失が起きても、論理 Workspace とホームディレクトリを残したままコンテナを作り直せます。

## 現在のディレクトリから Workspace を選ぶ

Tobari は、状態や Docker を扱う前に、ホスト上の現在の作業ディレクトリを正規化します。

1. 選択中の Context に完全一致する索引登録済みルートがあれば、その Workspace を直接再利用できます。
2. 現在のディレクトリを含む上位の索引登録済みルートが一つ以上あれば、対話型の `tobari` は近い順に有効な候補をすべて表示します。
3. 利用者は、既存 Workspace の選択、現在のディレクトリでの明示的な作成、キャンセルのいずれかを選びます。
4. Tobari は入れ子の Workspace を暗黙に作りません。

`status` と `delete` は、明示した Context または現在選択中の Context の中から、現在のディレクトリに最も近い Workspace を特定します。CWD による選択は、Docker の名前や内部 ID の管理を利用者へ求める仕組みではありません。

## 同じプロジェクトルート、異なる Context

`/work/payments` が Context `default` の Workspace にマウントされているとします。Context `review` で実行すると、プロジェクトルートと Context ID の組み合わせが異なるため、同じ正規化済みルートに二つ目の Workspace を作れます。

二つの Workspace では、次が別々です。

- 安定したプロジェクト ID
- ホームディレクトリと、ツールが所有する認証状態
- ランタイムコンテナと内部ネットワーク
- プロジェクトの通信主体
- Context に限定された学習済み規則と Broker ハンドル

一方、`/work/payments` 以下のファイルは意図的に共有されます。Tobari はオーバーレイ、チェックアウトの複製、ルートのロック、ファイルシステムの完全性分離を追加しません。

## Context とランタイムを変更する

`context use --name review` が変更するのは、既定値を示すマーカーだけです。既存 Workspace の状態や Context は変更せず、Docker を起動したり、新しい集約ポリシーを有効化したりもしません。

既存 Workspace は、保存済みの Context ID に恒久的に結び付きます。Context のランタイムを再ビルドすると、その Context が要求するイメージが変わります。次に Workspace へ入るとき、結び付いた実行環境をそのイメージへ合わせますが、識別情報とホームディレクトリは残ります。カスタムイメージが見つからない、または互換性がない場合は、プロジェクトのランタイムを変更する前に失敗します。

## 失敗時の動作

- 同じ正規化済みルートと Context ID を持つ Workspace の重複作成は拒否されます。並行して作成した場合も、成功するのは一つだけです。
- 親ディレクトリの候補が曖昧なら、明示的に選ぶ必要があります。表示順には権限上の意味がありません。
- 永続的なルート索引があるのにインスタンス状態がない場合は、`incomplete` と報告します。Workspace へ入る処理は欠けたインスタンスを推測せず、完全一致する対象の削除がクリーンアップ経路になります。
- ランタイムコンテナまたはネットワークがない場合は、次に Workspace へ入るときに調整します。
- イメージが見つからない、または互換性がない場合は、プロジェクトのランタイムを作成・交換する前に安全側へ閉じて失敗します。
- 現在選択中の Context を変更しても、既存の状態が暗黙に移動することはありません。

## 保証と制限

**保証すること:** 安定した Context とプロジェクトの識別情報は、コンテナの調整後も維持されます。完全一致するプロジェクトルートと Context の組み合わせごとに Workspace は一つです。Context の選択と既存 Workspace の権限は別です。ランタイムの `CMD` は、Tobari が定める寿命の契約を置き換えられません。

**保証しないこと:** 同じルートまたは重なるルート間のファイルシステム分離。プロジェクトディレクトリを移動またはコピーした後の自動推論。任意のカスタムイメージの信頼性。設定済みのローカルイメージやカスタムイメージの自動取得。

## まとめ

Workspace は永続的な製品概念です。Context は、そこへ恒久的に結び付く、ホスト所有の設定と識別情報です。クラスターは共有の強制基盤です。ランタイムイメージが環境を提供し、ランタイムコンテナは交換可能な実装詳細です。

## 理解を確認する

Context またはランタイム状態が変わったとき、何が変わり、何が変わらないかを説明できるはずです。

<details>
  <summary>
    <code>context use</code> は既存 Workspace を移行しますか？
  </summary>
  いいえ。後続のコマンドで明示的な Context
  を省略した場合に使う既定値だけを変えます。 既存 Workspace は保存済みの Context
  ID を保持します。
</details>

<details>
  <summary>同じプロジェクトルートに二つの Workspace を作れますか？</summary>
  安定した Context ID が異なれば作れます。ランタイムと権限は別ですが、
  重なったホストファイルは共有されます。
</details>

<details>
  <summary>
    ランタイムイメージが短時間で終了する <code>CMD</code> を宣言した場合、その
    コマンドの終了時に Workspace も停止しますか？
  </summary>
  いいえ。Tobari は寿命の管理にイメージの `CMD` を使わず、検証済みの `sleep
  infinity` を寿命管理用コマンドとして渡します。
</details>

共有範囲と Workspace ごとの範囲が不明確なら、[システム全体像](../system-overview/)を復習してください。次は、これらの識別情報を[Workspace のライフサイクル](../workspace-lifecycle/)で追います。
