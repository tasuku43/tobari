このページでは、Tobari の重要なセキュリティ上の主張を、規定する契約、実施箇所、
テストへ対応付けます。一つのテストだけで主張全体を証明できない場合は、実際より広い
範囲を検証しているようには見せません。必要な設定と実装上の根拠を組み合わせて
示します。

このドキュメントが固定するコミットに対して、構成、プリンシパル、ポリシー、TLS、
認証情報、ライフサイクル、サプライチェーンの各主張を検証するための索引です。
各行を読む前に[サプライチェーン](../supply-chain/)と、関連する仕組みの説明を確認して
ください。

## 根拠が不足している箇所の読み方

単体テストは、構文解析や状態の不変条件を証明できますが、実際の Docker 構成
までは証明できません。統合テストは観測した構成を証明できますが、すべての不正文書が
拒否されることまでは証明できません。現在のテスト群は、二つの TLS ハンドシェイクを
パケットキャプチャーしていませんが、アーキテクチャと設定を組み合わせれば、二つの
TLS 接続を使う設計を説明できます。この対応表では、一つのテストが主張全体を証明
するように見せず、異なる種類の根拠を明示します。

<aside class="limitation">
  <h2>根拠の制限</h2>
  <div class="prose-block">
    クラスターの完全削除後にも保管庫とルート鍵が残ることなど、一部の保持動作は、
    削除対象の所有関係と実装から確認できます。ただし、保持されるすべてのファイルに
    専用の単独検証があるわけではありません。この表では根拠を
    過大に述べず、実装上の根拠と直接のテスト範囲を区別します。
  </div>
</aside>
