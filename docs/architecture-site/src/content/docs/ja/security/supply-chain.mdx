Tobari は Gateway と OPA を、レビュー済みの変更されないイメージダイジェスト
から起動します。CLI が使う埋め込みランタイムのスナップショットと正本のソースが一致する
ことを検査し、ランタイムのメタデータ、ライセンス、リポジトリの検証ゲートによって、
公開またはリリース前の差分を拒否します。

Workspace のデフォルトランタイムは別の契約です。リリース済み CLI は agent-ready
イメージを公開・取得せず、固定済み埋め込みアセットからローカルでビルドします。各イメージと埋め込み成果物の役割は、
先に[実装技術](../../how-it-works/implementation-stack/)で確認できます。

## 正本とスナップショットの両方がある理由

Go CLI は起動時に実行可能なポリシーや Python ソースをダウンロードせず、ランタイム
ディレクトリを展開できる必要があります。編集する正本は、Gateway が `gateway/`、
ランタイムが `runtimes/base/` にあります。
埋め込み用にバイト列と内容の一致を検査する複製は、
`internal/infra/runtimeassets/assets/` にあります。Gateway とランタイムの image contract はレビュー済みの更新・署名コードを含み、未レビューの executable が image に入ることを拒否します。

埋め込みの複製は二つ目の実装ではありません。`check-gateway-source.sh` と
`check-runtime-base.sh` が正本との差分を拒否します。
専用 Linux `tobari-expose` と `tobari-permission` helper は、固定した Go builder と
一つの機械的に検査する source/module closure からこの base に組み込みます。どちらも
host executable のコピーでも、二つ目の archive でもありません。
`check-exposure-helper-source.sh` が両 Program の closure drift を拒否します。
同期は保守担当者が明示的に行う操作です。

## 変更されない識別情報と更新される識別情報

`versions.env` は OPA、mitmproxy のビルド元、Gateway、Debian のビルド元を `@sha256:`
ダイジェストで固定します。そのダイジェストがランタイムの完全一致の識別情報です。
読みやすい OPA と mitmproxy のバージョン文字列は、ダイジェストと組み合わせてリポジトリが
宣言する情報です。

公式ベースには、ソースから導出したローカルタグを使います。存在しない場合は CLI の
固定済み埋め込み Dockerfile とアセットからビルドし、ランタイム API、ユーザー、
エントリーポイント、寿命の契約を検査します。Tobari は agent-ready base を GHCR へ
公開したり GHCR から取得したりしません。検査済みのローカルダイジェストが、状態調整で
実際に使うバイト列を記録します。

正本のソースと、検証したローカルイメージは別の事実です。ソースが変わっても、対応する
ソース由来のローカルイメージを Tobari がビルドし、状態調整が検査済みのダイジェストを
選ぶまでは、実行中のクラスターは変わりません。このソースのスナップショットが実際に使う
固定済み上流入力は、生成された[コンポーネントバージョン](../../reference/component-versions/)
の表を正本として確認できます。

このスナップショットでは、Gateway と base Runtime の正本ソースと埋め込みの
写しが完全な V1 image input です。image workflow は cache-only output で複数アーキテクチャの
ビルドを検証します。ソースのテストが成功しても、ランタイムのバイト列は公開されません。

## ビルドとリリースの制御

- Gateway と agent-ready base は固定済みソースまたは埋め込みアセットからローカルでビルドし、Tobari は公開しない
- 専用 image workflow は package-write 権限なしの cache-only output で Linux amd64 と arm64 を検証する
- 外部ワークフローのアクションは完全なコミット SHA で固定する
- リリースパッケージには CLI のバージョンとコミットを埋め込み、通常のビルドは `dev` のままにする
- base Runtime のメタデータと統合 lock には、アーキテクチャ、API、寿命を保つコマンド、
  ツールのソース、チェックサムまたは署名、ライセンスの要件を記録する
- Gateway とランタイムの image 検査では未レビュー executable と public TCP listener がないことを確認する
- 公開・リリース用の検査は、リポジトリ境界、秘密情報、ライセンス、パッケージ入力、
  変更されないサービス参照を確認する。独立したコード署名、SBOM の証明、外部から
  検証できる来歴管理の仕組みまでを保証するものではない

## 起動に失敗したときの動作

必要な識別情報が存在しない、変更されないはずの参照が可変である、互換性がない、
または検証できない場合は、状態調整を停止します。埋め込み成果物がない、または正本の
ソースと一致しない場合は、リポジトリの検証ゲートが失敗します。ポリシーや外部サービスの
投影結果が不正、ホストまたはランタイム状態が安全でない場合、依存するサービスは
準備完了になりません。障害時に、レビューしていない別のイメージへ切り替えたり、
スクリプトを動的にダウンロードしたりすることはありません。

  <h2>保証すること</h2>
  <div class="prose-block">
    レビュー済みのサービス識別情報はダイジェストで固定され、ソースとスナップショットの
    一致は機械的に確認されます。静的ドキュメントサイト自体も lockfile を使い、

<aside class="limitation">
  <h2>保証しないこと</h2>
  <div class="prose-block">
    ダイジェストが示すのはバイト列の識別情報であり、その内容に脆弱性がないことでは
    ありません。信頼するレジストリ、公式エージェント成果物の取得元、CI、ホストの
    Docker
    builder、レビュー済みの依存関係管理手順は、サプライチェーンの前提です。
  </div>
</aside>

## ここまでで説明できること

「固定されたイメージ」と「レビュー済みのソースのスナップショット」は関係しますが、別々の
制御です。

<div class="question-list">
  <details>
    <summary>
      agent-ready base が公開済みダイジェストではないのはなぜですか？
    </summary>
    <div class="prose-block">
      Tobari は固定済みレシピと完全性検査を配布し、ユーザーの Docker ホストで
      ビルドします。Gateway
      と検査済みのローカルランタイムダイジェストは別々の識別情報です。
    </div>
  </details>
  <details>
    <summary>
      正本があるのに Python/Rego のソースを埋め込むのはなぜですか？
    </summary>
    <div class="prose-block">
      CLI
      が、ネットワークを使わず決定的にファイルを展開できる必要があるためです。
      一致検査によって、埋め込みの複製が独立した実装になるのを防ぎます。
    </div>
  </details>
  <details>
    <summary>ダイジェストはイメージが安全だと証明しますか？</summary>
    <div class="prose-block">
      いいえ。ダイジェストは完全一致の識別情報を与えるだけです。レビュー、テスト、
      脆弱性検査、来歴の確認、信頼する基盤は、それぞれ別の制御です。
    </div>
  </details>
</div>
