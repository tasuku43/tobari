description: 現在の Tobari における資産、攻撃者、前提、攻撃経路、緩和策、残るリスク、安全側に倒す動作を説明します。
---

この脅威モデルでは、Workspace 内のすべてのプロセスを信頼しません。Tobari は、選択していないホストや Docker のリソースへのアクセス、別プロジェクトの識別情報の自己申告、HTTP ポリシーの迂回を制限するよう設計されています。

ホストの強制基盤、選択したプロジェクトルート、明示されたポリシーは信頼します。その基盤自体の侵害は、ここで述べる緩和策の範囲外です。詳細は [信頼境界](../trust-boundaries/) を確認してください。

## 保護する資産

- 選択したルート外にあるホストのファイル
- Docker の制御と、別 Workspace のランタイムリソース
- 安定した Workspace Manifest、Workspace ID、プロジェクト権限、ポリシーの正本
- Gateway、OPA、CA、ネットワーク、監査の完全性
- 秘密情報を除いた診断情報と構造化 CLI 出力

選択したルートは作業用のリソースであり、その Workspace 自身から保護する資産ではありません。明示的に許可した宛先へ送るデータの機密性も保証しません。

## 攻撃者ができること

Workspace 内のコードは、次のことができると仮定します。

- 選択したプロジェクトと Workspace home を読み書きする
- プロセスを起動し、同じ Workspace 内の別プロセスと連携する
- 直接ソケットを開き、Gateway の迂回を試みる
- ヘッダー、URL、Workspace ID に見える値、認証情報に見える値を偽造する
- ポリシーの拒否を発生させ、利用者のレビューと競合する
- 不正な証明書を提示し、外部接続先が制御するレスポンスを返す

攻撃者がホスト利用者、Docker Engine、カーネル、Gateway、OPA、レビュー済みイメージを制御することは想定しません。いずれかを制御できる状態は信頼基盤の侵害です。

## 攻撃経路と緩和策

### プロキシを迂回する

Workspace のネットワークは Docker の内部ネットワークだけです。出力ポリシーと既定経路が TCP をプロジェクト Gateway へ送り、対応しない通信は失敗します。Gateway が停止しても通信を許可する側には倒れません。

### 別のプロジェクトを名乗る

Gateway はリクエスト側が申告した権限を無視します。カーネルが観測した Workspace の送信元エンドポイントを、ホストが作成した principal 登録簿で解決します。偽造したヘッダーでは principal を切り替えられません。状態がない、または曖昧な場合は OPA より前に拒否します。

### 秘密情報をポリシーまたはログへ混入させる

認識可能な認証ヘッダーと cookie の値は、OPA への問い合わせと監査記録より前に削除または伏せます。Workspace 内の agent CLI が保持する値は Workspace home に残り、Tobari はホストの認証情報を継承しません。本文はポリシー入力にも監査記録にもなりません。

ただし任意の値をすべて認証情報として認識できるわけではありません。通常のクエリや安全なヘッダーに機微な文字列を置かないでください。

### 拒否を許可に変える

Gateway が返すのは拒否とホストレビューの案内だけです。変更操作は現在の状態を再検出し、完全一致規則と集約結果全体を検証してからアトミックに有効化します。Workspace が自身を許可することはできず、古い参照値で自動再送もしません。

### Workspace 間でログインファイルをコピーする

agent CLI のログインファイルを別 Workspace にコピーしても、Gateway が導出する host principal やポリシー範囲は変わりません。宛先 Workspace は自身の Workspace ID と OPA の完全一致許可を必要とします。Tobari はログインファイルの形式やリモート失効を代行しません。

### Workspace からホスト状態を読む

Workspace には Docker control mount がなく、選択した project root と永続 home の外にある host configuration/state への path もありません。host が state file を使う前に owner と mode を検査し、不一致では fail closed です。agent CLI の login file は Workspace home 内に残り、Tobari authority の source にはなりません。

## 残るリスク

- エージェントは、選択したファイルを破壊または外部へ送信できます。
- 完全一致で許可した接続先は、悪意ある内容を返せます。
- 本文を識別に使わないため、許可済みのパスは異なる本文にも適用されます。
- 安全なクエリやヘッダーのメタデータに、実装が認証情報と分類しない機微なデータが含まれる可能性があります。
- 同じ Workspace 内のプロセスは、その Workspace home にある agent CLI の状態を読めます。
- 重複するプロジェクトルートでは同じホストファイルへの変更を共有します。
- agent CLI のログアウトは外部サービス側の失効を保証せず、実行中プロセスの環境値も書き換えません。
- 証明書を固定するクライアントと未対応プロトコルは、この HTTP/HTTPS 境界では仲介しません。

## 障害時の意味

許可判断、principal、Workspace 状態、ポリシー投影、有効化の障害は、対象となる外部通信を閉じたままにします。ただしローカル処理と選択したルートへの書き込みは発生し得ます。復旧時には盲目的に再試行せず、変更操作の結果に関する契約を守ってください。

## ここまでで説明できること

プロキシの迂回、principal の偽装、ポリシーの自己承認、Workspace 間のログインファイル再利用に対して、Tobari がどう応答するかを説明できるはずです。

<div class="question-list">
  <details>
    <summary>
      Workspace B が Workspace A
      のログインファイルをコピーするとどうなりますか？
    </summary>
    <div class="prose-block">
      B の host principal は変わらず、B 自身の完全一致の OPA
      許可が必要です。Gateway は許可後だけ元の認証値を転送します。
    </div>
  </details>
  <details>
    <summary>異なる本文が別の学習済み規則にならないのはなぜですか？</summary>
    <div class="prose-block">
      本文は許可後にストリーミングされ、規則の識別には使わないためです。
    </div>
  </details>
  <details>
    <summary>答えが不明確ならどこへ戻るべきですか？</summary>
