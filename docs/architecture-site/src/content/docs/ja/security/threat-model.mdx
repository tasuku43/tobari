---

この脅威モデルでは、Workspace 内のすべてのプロセスを信頼しません。Tobari は、
選択していないホストや Docker のリソースへのアクセス、別プロジェクトの識別情報
の自己申告、HTTP ポリシーの迂回、Auth Broker 管理の認証状態やリクエスト用に導出
した認証情報の取得を試みるプロセスを制限するよう設計されています。

一方で、ホスト側の実施基盤と、利用者が選んだプロジェクトルートおよびポリシーは
信頼します。その基盤自体の侵害は、ここで述べる緩和策の範囲外です。信頼する
コンポーネント、信頼しないデータ、認証状態の位置は、先に
[信頼境界](../trust-boundaries/)で確認してください。

## 保護する資産

- 選択したルート外にあるホストのファイル
- Docker の制御と、別の Workspace のランタイムリソース
- 安定した Workspace Manifest とプロジェクトの権限、およびポリシーの定義元
- インストール用ルート鍵、暗号化した Workspace Manifest 保管庫、Auth Broker 管理の認証情報
- 有効な集約ポリシーと、プリンシパルおよびプロバイダー投影結果の完全性
- 秘密情報を除いた診断情報と、構造化された CLI 出力

選択したルートは作業用のリソースであり、その Workspace 自身から保護する資産では
ありません。通信を明示的に許可した後に送るデータの機密性も、Tobari が保証できる
資産ではありません。

## 攻撃者ができること

Workspace 内のコードは、次のことができると仮定します。

- 選択したプロジェクトと Workspace ホームを読み書きする
- プロセスを起動し、同じ Workspace 内の別プロセスと連携する
- 直接ソケットを開き、Gateway の迂回を試みる
- ヘッダー、URL、Workspace Manifest やプロジェクトに見える ID、認証情報に見える値、命令文の
  ような文字列を偽造する
- 投影された Auth Broker のハンドルをコピーし、別の Workspace から再送する
- ポリシーの拒否を発生させ、利用者のレビューと競合し、同じ HTTP 判断項目に異なる
  本文を送る
- 不正な証明書を提示し、外部接続先が制御するレスポンスを受け取る

攻撃者が、ホストの利用者、Docker Engine、カーネル、Gateway、OPA、Auth Broker、
ルート鍵の提供機構、レビュー済みイメージを制御することは想定しません。そのいずれかを
制御できる状態は、信頼基盤の侵害です。

## 攻撃経路と緩和策

### プロキシを迂回する

Workspace のネットワークは Docker の内部ネットワークだけです。閉じた出力ポリシーと既定経路が TCP をプロジェクトの Gateway へ送り、合成 DNS がポリシー判断前の本物のホスト名解決を防ぎます。Gateway は通常の HTTP/TLS を透過リスナーへ振り分け、転送処理は閉じたままです。直接ソケットでもポリシーを迂回できず、対応しない通信は失敗し、Gateway が停止しても通信を許可する側には倒れません。

### 別のプロジェクトを名乗る

Gateway はリクエスト側が申告したプロジェクト権限を無視します。カーネルが観測した Workspace の送信元エンドポイントを、ホストが作成したスキーマ 1 のプリンシパル登録簿で解決します。偽造したヘッダーでは
プリンシパルを切り替えられません。状態がない、または曖昧な場合は、OPA より前に
拒否します。

### 秘密情報をポリシーまたはログへ混入させる

設定済みで認識可能な認証ヘッダーと Auth Broker のハンドルは、OPA への問い合わせと
監査記録より前に削除するか値を伏せます。本文はポリシーの入力にも監査記録の内容にも
なりません。そのため、これらに分類される認証情報と本文は、通常の許可判断と保持する
根拠の経路へ入りません。

ただし、実装が任意の値をすべて認証情報として認識できるわけではありません。通常の
クエリや安全なヘッダーに機微な文字列を置くと、許可判断用のメタデータに含まれる
可能性があります。

### 拒否を許可に変える

Gateway が返すのは、拒否とレビュー場所の案内だけです。ホスト側の検出処理が不透明な
参照値を生成します。変更操作は現在の状態を再検出し、完全一致規則と集約結果
全体を検証し、リビジョンを確認して途中状態を見せずに有効化します。Workspace が自身を許可
することはできません。古い参照値は失敗し、リクエストが自動で再送されることも
ありません。

### Auth Broker のハンドルをコピーまたは偽造する

Tobari 形式の印があるリクエストは、Auth Broker の処理に固定されます。OPA へ問い合わせる
前の照会で、Workspace Manifest、プロジェクト、プロバイダー、認証情報のリビジョン、完全一致の
HTTPS 接続先、ヘッダーの結び付きを確認します。コピー済み、古い、または不正なハンドル
は、別方式への切り替えも秘密情報の解決も行わず拒否します。

### Workspace から Auth Broker の保管庫またはルート鍵を読む

Workspace には Broker の制御用マウントも、保管庫やルート鍵へのパスもありません。
Broker は共有されるロック状態のサービスとして動きます。Linux の鍵ファイルと保管庫のパスは、
安全でないファイル種別やアクセス権を拒否します。macOS ではキーチェーンを使います。
ロック解除用のデータは argv や環境変数ではなく、固定した標準入力から渡します。信頼基盤が
侵害されない限り、Auth Broker 管理の秘密情報はホストと Broker の管理下に残ります。

### プロバイダー設定をホスト上のコード実行に変える

所有者マニフェストは厳格なスキーマ 1 で、保護された標準入力からの取り込みだけを要求
できます。executable や dynamic credential behavior は選べません。唯一の built-in GitHub
login は identity-checked fixed trusted-host helper、sanitized temporary home、verified cleanup
を使います。provider JSON は data であり executable adapter ではありません。

## 残るリスク

- エージェントは、選択したファイルを破壊または外部へ送信できます。
- 完全一致で許可した接続先は、悪意ある内容を受け取れます。
- 本文を識別に使わないポリシーのため、許可済みのパスは異なる本文にも適用されます。
- 安全なクエリやヘッダーのメタデータに、実装が認証情報と分類しない機微なデータが
  含まれる可能性があります。秘密情報を置かないでください。
- 同じ Workspace 内のプロセスは、投影済みの権限を再利用できます。
- 重複するプロジェクトルートでは、他の部分を分離した Workspace 間でも、同じホスト
  ファイルへの変更を共有します。
- ローカルのログアウトはプロバイダー側での失効を保証せず、すでに動いている
  プロセスの環境変数も書き換えられません。
- 証明書を固定するクライアントは失敗します。未対応のプロトコルは、この
  HTTP/HTTPS 境界では仲介しません。

## 障害時の意味

許可判断、プリンシパル、Broker、保管庫、投影、有効化の障害は、対象となる外部通信を
閉じたままにします。ただし「どこでも何も起きなかった」という意味ではありません。
外向きリクエストより前のローカル処理と、選択したルートへの書き込みは発生し得ます。
復旧時には、盲目的に再試行せず、変更操作の結果に関する契約を守る必要があります。

## ここまでで説明できること

プロキシの迂回、プリンシパルの偽装、ポリシーの自己承認、ハンドルの再利用に対して、
Tobari がどう応答するかを確認します。

<div class="question-list">
  <details>
    <summary>
      Workspace B が Workspace A の有効なハンドルをコピーし、同じホスト
      へ送るとどうなりますか？何が重要ですか？
    </summary>
    <div class="prose-block">
      Broker の照会処理は、信頼できる Workspace Manifest
      とプロジェクトのプリンシパル、
      プロバイダー、認証情報のリビジョン、接続先、ヘッダーの結び付きを比較します。
      プロジェクトが一致しないため、OPA への問い合わせや秘密情報の解決より前に
      拒否されます。結び付きが有効でも、通常の HTTP 通信には OPA
      の許可が必要です。
    </div>
  </details>
  <details>
    <summary>異なる本文が別の学習済み規則にならないのはなぜですか？</summary>
    <div class="prose-block">
      本文は許可判断の後にだけストリーミングされ、規則の識別には使いません。完全一致の
      学習済み規則を識別するのは、Workspace
      Manifest、プロジェクト、ホスト、ポート、メソッド、 未加工のパスです。
    </div>
  </details>

    <summary>これらの答えが不明確なら、どこへ戻るべきですか？</summary>

    </div>
  </details>
