Tobari は、Workspace が暗黙に持つホスト、ネットワーク、ポリシー、Auth Broker
管理の認証情報に対する権限を狭めます。この主張が成立するのは、サポート対象の
Docker 構成と信頼するホストサービスが正しく動く場合だけです。選択した
プロジェクト内のコードを無害にするものではありません。

そのため、Tobari のセキュリティは「コンテナ」「プロキシ」「暗号化」といった
言葉だけではなく、範囲を限定した主張として説明します。各主張には前提、実施点、
安全側に倒す障害動作、根拠、制限があります。コンポーネントやリクエストの経路が
分からない場合は、先に [メンタルモデル](../../how-it-works/mental-model/) と
[システム全体像](../../how-it-works/system-overview/) を読んでください。

## すべての主張を六つの要素で読む

このセクションの各ページは、次の原則で書かれています。

1. **主張** — Tobari が保証する、範囲を限定した結果。
2. **前提** — あらかじめ成立していなければならない条件。
3. **実施箇所** — 主張を成立させるコードまたは構成。
4. **障害時** — 実施箇所が存在しない、または正常でない場合の動作。
5. **根拠** — 規定文書、実装、テスト。
6. **制限** — 主張が意図的に対象外とする隣接した結果。

たとえば「Workspace は公開インターネットへ直接到達できない」という説明には、
Workspace が Tobari のサポート対象となる Docker 構成で作られている、という
前提が必要です。この主張は、専用の <code>internal</code> ネットワークと、Gateway
だけが内部ネットワークと外向きネットワークの両方へ接続する構成によって実施されます。障害時に別の
経路へ切り替わることはなく、通信に失敗します。一方で、許可済みの接続先には、
Workspace から読めるデータを送信できるという制限があります。

## 信頼する計算基盤

Tobari は、ホストの利用者、ホストのファイルシステム制御、Docker Engine、カーネル、
Gateway、OPA、Auth Broker、ルート鍵の保管機構、レビュー済みのランタイム成果物を
信頼する実施基盤として扱います。Workspace 内のプロセスと外部 HTTP サービスは
信頼しません。ポリシー候補、リクエスト属性、プロバイダーマニフェスト、外部から届く
レスポンス文字列は、信頼するコードが解析する場合でも信頼しないデータです。

この区別により、偽造したプロジェクトヘッダーが権限にならない一方で、Gateway の
侵害が保証対象外になる理由が分かります。Gateway は、ホストが作成した受信インターフェース
からプロジェクトの権限を導出します。Gateway 自体が悪意ある動作をすれば、その
実施箇所は失われています。

## 四つの境界と役割

  <section>
    <h3>プロジェクトのファイル</h3>
    <div class="prose-block">
      選択したルートは作業用にマウントされます。選択していないホスト上のパスと、別の
      Workspace
      のホームは通常のマウント対象外です。選択したファイルはエージェントから保護されません。
    </div>
  </section>
  <section>
    <h3>ネットワーク</h3>
    <div class="prose-block">
      Workspace には、サポート対象となる外部への直接経路がありません。Gateway
      だけが、専用の内部ネットワークと外向きネットワークの両方へ接続します。
    </div>
  </section>
  <section>
    <h3>通信許可</h3>
    <div class="prose-block">
      OPA は正規化した HTTP 通信を判断し、Gateway がその結果を実施します。
      ポリシーが存在しない、形式が正しくない、または利用できない場合は、安全側に倒して拒否します。
    </div>
  </section>
  <section>
    <h3>Auth Broker が管理する認証情報</h3>
    <div class="prose-block">
      Auth Broker は、固定または更新可能な認証状態を、暗号化した Context
      保管庫に保持します。Workspace
      が受け取るのは利用範囲を結び付けたハンドルだけです。
      固定認証情報の解決、AWS の署名、Datadog
      トークンの更新は、ポリシーの許可後に 限って実行します。
    </div>
  </section>
</div>

## 失敗時の見え方

- Gateway がない: プロキシ接続は失敗します。
- 有効なプリンシパルがない: Gateway は OPA より前に
  <code>project_principal_unavailable</code> を返します。
- OPA が利用不能または応答が不正: Gateway は <code>policy_unavailable</code> を
  返し、外部の接続先へ接続しません。
- Auth Broker がロック中または利用不能: Auth Broker を使うリクエストは失敗し、
  秘密情報を別の方法で解決しません。
- ハンドルが不正または古い: <code>credential_handle_invalid</code> となり、
  別の認証方式へ切り替わりません。
- コンパニオンまたは更新処理を始める前に利用不能と判明:
  <code>credential_broker_unavailable</code>
  となり、外部の接続先へ接続しません。
- AWS または Datadog の処理開始後に結果が不明: 再試行不可の
  <code>credential_refresh_outcome_unknown</code>
  となります。再実行せず、信頼する ホスト側で状態を確認します。
- 不正なポリシーの有効化: Tobari は可能な限り、以前の定義元と既知の集約結果
  を保持または復元します。OPA を正常にできない場合、以前のサービスが有効だとは
  仮定せず、通信を安全側に倒して拒否し続けます。

これらは、該当する通信経路を閉じたままにする障害動作です。プロセスが行ったすべての
操作を巻き戻すという意味ではありません。選択したプロジェクト内では、ローカル
ファイルへの書き込みがすでに発生している可能性があります。

## ここまでで説明できること

Tobari のセキュリティは、一つの「安全なサンドボックス」というラベルではなく、条件付きの
境界を組み合わせたものです。
