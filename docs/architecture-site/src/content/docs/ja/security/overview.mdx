Tobari は、Workspace へ渡すホスト権限、外部通信、ポリシー変更、Auth Broker が管理する認証情報へのアクセスを制限します。これらの保証は、サポート対象の Docker 構成と、信頼するホスト側のコンポーネントが正しく動作する場合に成立します。作業対象のディレクトリ内にあるコードやファイルを、エージェントから保護する仕組みではありません。

そのため、このセクションでは「コンテナで動く」「プロキシを使う」「暗号化されている」といった説明だけで安全性を表しません。各保証について、前提、強制箇所、障害時の動作、根拠、対象外を明記します。構成要素や通信経路が分からない場合は、先に[基本モデル](../../how-it-works/mental-model/)と[システム全体像](../../how-it-works/system-overview/)を読んでください。

## セキュリティ保証の読み方

各ページでは、次の六項目をセットで示します。

1. **保証** — Tobari が成立させる、範囲を限定した結果。
2. **前提** — 保証が成立するために、あらかじめ満たす必要がある条件。
3. **強制箇所** — 保証を実際に成立させるコードまたは構成。
4. **障害時の動作** — 強制箇所が利用できない、または不正な状態になった場合の結果。
5. **根拠** — 規定文書、実装、テスト。
6. **対象外** — 保証に含まれない、最も近い範囲。

たとえば「Workspace は公開インターネットへ直接到達できない」という保証には、Workspace が Tobari のサポート対象となる Docker 構成で作られていることが前提になります。専用の `internal` ネットワークと、Gateway だけが内部ネットワークと外部向けネットワークの両方へ接続する構成が、この保証を強制します。Gateway が利用できなくても別の経路へ切り替わらず、通信は失敗します。一方、利用者が許可した接続先には、Workspace から読めるデータを送信できます。

## 信頼する基盤

Tobari は、ホストの利用者、ホストのファイルシステム制御、Docker Engine、カーネル、Gateway、OPA、Auth Broker、ルート鍵の保管機構、レビュー済みのランタイム成果物を信頼します。Workspace 内のプロセスと外部 HTTP サービスは信頼しません。ポリシー候補、リクエスト属性、プロバイダーマニフェスト、外部から返るレスポンス文字列は、信頼するコードが解析する場合でも、信頼しない入力として扱います。

この区別により、偽造したプロジェクトヘッダーが権限にならない一方で、Gateway の侵害が保証対象外になる理由が分かります。Gateway は、ホストが作成した受信インターフェースからプロジェクトを特定します。Gateway 自体が侵害されれば、その強制箇所は失われます。

## 四つの境界

<div class="comparison-grid">
  <section>
    <h3>プロジェクトのファイル</h3>
    <div class="prose-block">
      作業対象のディレクトリは、Workspace へ読み書き可能な状態でマウントします。作業対象外のホストパスと、ほかの Workspace のホームは通常のマウント対象に含めません。作業対象のファイル自体は、エージェントから保護されません。
    </div>
  </section>
  <section>
    <h3>ネットワーク</h3>
    <div class="prose-block">
      Workspace には、サポート対象となる外部への直接経路がありません。Gateway だけが、プロジェクト専用の内部ネットワークと外部向けネットワークの両方へ接続します。
    </div>
  </section>
  <section>
    <h3>HTTP 通信の許可</h3>
    <div class="prose-block">
      OPA は正規化された HTTP 通信を判断し、Gateway が結果を通信経路へ強制します。ポリシー判断を得られない、応答が不正、または関連する登録情報を確立できない場合は、接続先へ接続しません。
    </div>
  </section>
  <section>
    <h3>Auth Broker が管理する認証情報</h3>
    <div class="prose-block">
      Auth Broker は、固定された認証情報または更新可能な認証状態を、暗号化した Context 保管庫に保持します。Workspace が受け取るのは、一つのプロジェクトに結び付いた不透明なハンドルだけです。認証情報の解決、AWS の署名、Datadog トークンの更新は、HTTP 通信が許可された後に限って実行します。
    </div>
  </section>
</div>

## 障害時の動作

- Gateway が利用できない場合、プロキシ接続は失敗します。直接通信へ切り替わりません。
- 有効なプロジェクトのプリンシパルを確立できない場合、Gateway は OPA より前に `project_principal_unavailable` を返します。
- OPA が利用できない、または応答が不正な場合、Gateway は `policy_unavailable` を返し、外部の接続先へ接続しません。
- Auth Broker がロック中または利用不能な場合、Auth Broker を使うリクエストは失敗し、認証情報を別の方法で解決しません。
- ハンドルが不正または古い場合、`credential_handle_invalid` を返し、別の認証方式へ切り替わりません。
- AWS コンパニオンや Datadog の更新処理を開始する前に利用不能と判明した場合、`credential_broker_unavailable` を返し、外部の接続先へ接続しません。
- AWS または Datadog の処理開始後に結果を確定できない場合、再試行不可の `credential_refresh_outcome_unknown` を返します。自動で再実行せず、信頼するホスト側で状態を確認します。
- 不正なポリシーを有効化できない場合、直前に検証済みだった定義と集約結果を保持または復元します。OPA を正常な状態へ戻せない場合、以前のサービスが有効だと推測せず、通信を拒否し続けます。

これらは、該当する外部通信を閉じたままにする動作です。Workspace のプロセスが行ったすべての操作を巻き戻すわけではありません。作業対象のディレクトリでは、ローカルファイルへの変更がすでに発生している可能性があります。

## ここまでで説明できること

Tobari のセキュリティは、一つの「安全なサンドボックス」という言葉ではなく、前提と対象範囲が異なる複数の境界で構成されています。

<div class="question-list">
  <details>
    <summary>「Docker で動く」だけでは、なぜ保証として不十分ですか？</summary>
    <div class="prose-block">
      保証は、正確なマウント、内部ネットワーク、サービス間の接続、ホスト側の事実からのプリンシパル導出、障害時に通信を閉じる動作に依存するためです。一般的なコンテナであることだけでは、これらを確認できません。
    </div>
  </details>
  <details>
    <summary>
      「外部への直接通信は遮断される」の直後に確認すべき制限は何ですか？

      明示的に許可した接続先には、Workspace から読み取れ、許可済みの HTTP リクエストへ載せられるデータを送信できます。
    </div>
  </details>
