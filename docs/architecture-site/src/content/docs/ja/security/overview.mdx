Tobari は、Workspace へ渡すホスト権限、外部通信、ポリシー変更、agent CLI のログイン状態へのアクセスを制限します。これらの保証は、サポート対象の Docker 構成と、信頼するホスト側のコンポーネントが正しく動作する場合に成立します。作業対象のディレクトリ内にあるコードやファイルを、エージェントから保護する仕組みではありません。

そのため、このセクションでは「コンテナで動く」「プロキシを使う」「暗号化されている」といった説明だけで安全性を表しません。各保証について、前提、制御の仕組み、障害時の動作、対象外を明記します。構成要素や通信経路が分からない場合は、先に[基本モデル](../../how-it-works/mental-model/)と[システム全体像](../../how-it-works/system-overview/)を読んでください。

## セキュリティ保証の読み方

各ページでは、次の五項目をセットで示します。

1. **保証** — Tobari が成立させる、範囲を限定した結果。
2. **前提** — 保証が成立するために、あらかじめ満たす必要がある条件。
3. **仕組み** — どのコンポーネントと構成が、その保証を成立させるか。
4. **障害時の動作** — 必要なコンポーネントが利用できない、または不正な状態になった場合の結果。
5. **対象外** — 保証に含まれない、最も近い範囲。

たとえば「Workspace は公開インターネットへ直接到達できない」という保証には、Workspace が Tobari のサポート対象となる Docker 構成で作られていることが前提になります。専用の `internal` ネットワークと、Gateway だけが内部ネットワークと外部向けネットワークの両方へ接続する構成が、この保証を強制します。Gateway が利用できなくても別の経路へ切り替わらず、通信は失敗します。一方、利用者が許可した接続先には、Workspace から読めるデータを送信できます。

## 信頼する基盤

Tobari は、ホストの利用者、ホストのファイルシステム制御、Docker Engine、カーネル、Gateway、OPA、host-owned state、レビュー済みのランタイム成果物を信頼します。Workspace 内のプロセスと外部 HTTP サービスは信頼しません。ポリシー候補、リクエスト属性、外部から返るレスポンス文字列は、信頼するコードが解析する場合でも、信頼しない入力として扱います。

この区別により、偽造したプロジェクトヘッダーが権限にならない一方で、Gateway の侵害が保証対象外になる理由が分かります。Gateway は、ホストが登録し、カーネルが観測した Workspace の送信元エンドポイントからプロジェクトを特定します。Gateway 自体が侵害されれば、この境界は成立しません。

## 障害時の動作

- Gateway が利用できない場合、保護済みの接続は失敗します。直接通信へ切り替わりません。
- 有効なプロジェクトのプリンシパルを確立できない場合、Gateway は OPA より前に `project_principal_unavailable` を返します。
- OPA が利用できない、または応答が不正な場合、Gateway は `policy_unavailable` を返し、外部の接続先へ接続しません。
- agent CLI のログイン状態が利用できない場合、その CLI のログイン手順を確認します。Tobari の代替 credential store はありません。
- 不正なポリシーを有効化できない場合、直前に検証済みだった定義と集約結果を保持または復元します。OPA を正常な状態へ戻せない場合、以前のサービスが有効だと推測せず、通信を拒否し続けます。

これらは、該当する外部通信を閉じたままにする動作です。Workspace のプロセスが行ったすべての操作を巻き戻すわけではありません。作業対象のディレクトリでは、ローカルファイルへの変更がすでに発生している可能性があります。

## ここまでで説明できること

Tobari のセキュリティは、一つの「安全なサンドボックス」という言葉ではなく、前提と対象範囲が異なる複数の境界で構成されています。
