Tobari は、Workspace が暗黙に持つ host、network、policy、broker-managed
credential の authority を狭めます。この主張は、Tobari が対応する Docker
topology と trusted host service が成立する場合に限られます。選択した project
内の code を無害にするものではありません。

そのため、Tobari のセキュリティは「container」「proxy」「暗号化」といった
言葉だけではなく、範囲を限定した主張として説明します。各主張には前提、実施点、
fail-closed の動作、根拠、制限があります。component または request path が
初めてなら、先に [Mental model](../../how-it-works/mental-model/) と
[System overview](../../how-it-works/system-overview/) を読んでください。

## すべての主張を六つの要素で読む

この section の各ページは、次の原則で書かれています。

1. **Claim** — Tobari が主張する狭い outcome。
2. **Preconditions** — あらかじめ成立していなければならない条件。
3. **Enforcement point** — claim を成立させる code または topology。
4. **Failure behavior** — enforcement point が存在しない、または healthy でない場合の動作。
5. **Evidence** — governing document、implementation、test。
6. **Limitations** — claim が意図的に対象外とする近接した outcome。

「Workspace は public Internet へ直接到達できない」という説明は、Workspace が Tobari の supported Docker configuration で作られたという precondition と組み合わせて初めて意味を持ちます。enforcement は dedicated <code>internal</code> network と Gateway だけが持つ dual attachment です。失敗した場合は別経路へ切り替わるのではなく、通信できなくなります。同じくらい重要な制限は、allowed destination には Workspace が読める data を送信できることです。

## 信頼する計算基盤

Tobari は host user、host filesystem control、Docker Engine、kernel、Gateway、OPA、Auth Broker、root-key backend、reviewed runtime asset を trusted enforcement infrastructure として扱います。Workspace process と external HTTP service は untrusted です。Policy candidate、request attribute、provider manifest、external response text は、trusted code が parse する場合でも untrusted data のままです。

この区別により、偽造した project header が役に立たない一方で、compromised Gateway が対象外になる理由が分かります。Gateway は host が作成した receiving interface から project authority を導出します。Gateway 自体が malicious なら、その enforcement point は失われています。

## 四つの境界と役割

    <h3>プロジェクトの filesystem</h3>
    <div class="prose-block">

      から保護されません。

  <section>
    <h3>ネットワーク</h3>
    <div class="prose-block">
      Workspace には supported direct egress route がありません。Gateway だけが
      dedicated internal network から egress へ渡ります。
    </div>
  </section>
  <section>
    <h3>通信許可</h3>
    <div class="prose-block">
      OPA は normalized HTTP effect を判断し、Gateway が結果を enforce
      します。policy が missing、malformed、unavailable の場合は fail closed
      します。
    </div>
  </section>
  <section>
    <h3>Auth Broker が管理する認証情報</h3>
    <div class="prose-block">
      Auth Broker は static または renewable credential state を encrypted
      Context vault に保持します。Workspace が受け取るのは bound handle
      だけで、static resolve、AWS signing、Datadog token refresh は post-policy
      のままです。
    </div>
  </section>

## 失敗時の見え方

- Gateway がない: proxy connection は失敗します。
- valid principal がない: Gateway は OPA より前に <code>project_principal_unavailable</code> を返します。
- OPA が unavailable または malformed: Gateway は <code>policy_unavailable</code> を返し、upstream connection を作りません。
- Auth Broker が locked または unavailable: brokered request は失敗し、secret resolution へ fallback しません。
- handle が invalid または stale: <code>credential_handle_invalid</code> となり、passthrough へ downgrade しません。
- companion または refresh が既知の pre-execution failure: <code>credential_broker_unavailable</code> となり、upstream attempt はありません。
- AWS/Datadog operation が明示的または post-dispatch に outcome uncertain: non-retryable な <code>credential_refresh_outcome_unknown</code> となります。replay せず、trusted host で reconcile します。
- invalid policy activation: Tobari は可能な限り以前の source と既知の projection を保持または復元します。OPA を healthy にできなければ、以前の service が active だと仮定せず、通信は fail closed のままです。

これらは対象となる path の closed failure です。すべての process action が rollback されるという意味ではありません。選択した project 内の local file write はすでに発生している可能性があります。
