外部サービスへログインしても、HTTP 通信は許可されません。どの認証情報管理方式でも、Context、プロジェクト、宛先、ポート、メソッド、パスに一致する OPA の許可が別に必要です。

方式によって、Workspace から読める認証状態は異なります。ツール自身で管理する方式では、認証情報を Workspace 内に置きます。保持型の管理方式では、ホスト管理の静的な認証情報を Gateway だけが読める場所へ置きます。Auth Broker 方式では、固定または更新可能な認証状態を暗号化した Context 保管庫に残し、Workspace へはプロジェクトに結び付いた不透明なハンドルだけを渡します。

Auth Broker が認証情報を解決・更新・署名できるのは、Gateway がハンドルの結び付きを確認し、OPA が通常の HTTP 通信を許可した後だけです。詳しい処理順は[認証情報](../../how-it-works/credentials/)で、信頼する基盤の前提は[脅威モデル](../threat-model/)で説明します。

## 三つの方式で公開範囲が異なる

| 方式             | 認証情報の本体を置く場所                                           | Workspace から読めるもの                 | Gateway の役割                                                                                           | 主な制限                                                            |
| ---------------- | ------------------------------------------------------------------ | ---------------------------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| ツール自身で管理 | Workspace のホームまたは環境変数                                   | ツールが保存した認証情報                 | 認識した認証ヘッダーを OPA 入力と監査から除外し、許可後に転送する                                        | 同じ Workspace 内のプロセスは認証情報を読み、再利用できる           |
| 保持型の管理方式 | Gateway だけへマウントする、ホスト管理の Context 認証情報          | 秘密情報を含まないプロファイル選択子     | 設定済みの結び付きを確認し、許可後に固定ヘッダーへ認証情報を挿入する                                     | 対象となる認証方式を限定した静的方式                                |
| Auth Broker      | 暗号化した Context 保管庫と、リクエスト処理中の Auth Broker メモリ | プロジェクトに結び付いた不透明なハンドル | ハンドルを取り除き、秘密情報を使わずに結び付きを確認する。OPA の許可後にレビュー済みの処理だけを実行する | 同じ Workspace 内のプロセスは、配置済みの有効なハンドルを利用できる |

### OPA が見る情報

| 方式             | OPA へ渡す情報                                                         | OPA へ渡さない情報                                                                 |
| ---------------- | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| ツール自身で管理 | 認証ヘッダーを除外した、本文を含まない通常の HTTP 通信                 | 認証情報と Cookie の値                                                             |
| 保持型の管理方式 | 通常の HTTP 通信と、選択済みプロファイルの秘密情報を含まないメタデータ | Gateway 側の認証情報ファイルの内容                                                 |
| Auth Broker      | 通常の HTTP 通信と、秘密情報を含まないプロバイダー ID                  | ハンドル、認証情報のリビジョン、固定認証情報、AWS の一時認証情報、Datadog トークン |

## Auth Broker を使うリクエストの順序

この順序自体がセキュリティ上の保証です。

1. Gateway がカーネルの観測した Workspace の送信元エンドポイントから Context とプロジェクトのプリンシパルを特定します。
2. ハンドルをリクエストから取り除きます。
3. Auth Broker が、Context、プロジェクト、プロバイダー、リビジョン、HTTPS 接続先、ヘッダー変換の結び付きを、秘密情報を使わずに確認します。
4. Gateway が、本文を含まない通常の HTTP 通信を OPA へ問い合わせます。
5. OPA が拒否した場合はここで停止します。認証情報の解決、Datadog トークンの選択・更新、AWS コンパニオンの呼び出し・署名、外部の接続先への接続は行いません。
6. 許可後に限り、宣言済みの静的認証情報の解決、Datadog の固定更新処理、AWS の認証情報取得と SigV4 署名のいずれかを一度実行します。
7. Gateway が、宣言された完全一致の HTTPS 接続先へ接続します。

## ハンドルに結び付ける条件

Auth Broker のハンドルは、次のすべてに一致する必要があります。

- 安定した Context ID
- ホスト管理の登録簿から導出したプロジェクト ID
- プロバイダー ID
- 認証情報のレコードとリビジョン
- 完全一致する HTTPS ホストとポート
- 宣言済みの送信元ヘッダーの名前と構文
- 宣言済みの送信先ヘッダーと変換方式

HTTP メソッドとパスは、ハンドル自体には結び付けません。通常の通信ポリシーとして OPA が別に判断します。この分離により、有効なハンドルだけで通信許可を得ることを防ぎます。

別の Workspace からコピーしたハンドル、認証情報の置換後に残った古いハンドル、ログアウト後のハンドル、不正な形式や場所のハンドルは、OPA への問い合わせより前に拒否します。通常の認証情報としてそのまま転送する方式へ切り替えません。

## 保存とロック解除

各 Context は、暗号化した `vault.enc` を持ちます。スキーマ 1 の AES-256-GCM エンベロープは、安定した Context ID を関連データとして結び付けます。暗号化済みのスキーマ 1 データには、次を保存できます。

- 型付きの固定認証情報
- 不透明な AWS ホスト取得処理の状態
- Datadog OAuth セッションの状態
- 認証情報のリビジョン
- 実行結果を確定できない場合の永続的な処理停止情報
- ハンドルの元レコード

Linux では、インストール用ルート鍵を、所有者だけが読める `auth/keys/root.key` に保存します。macOS では名前付きの Keychain 項目を使います。Auth Broker はロック状態で起動し、状態調整処理が固定の `docker exec -i` の標準入力からロック解除データを渡します。

保管庫があるのに元のルート鍵がない場合、処理を拒否します。代わりの鍵を暗黙に作って、既存の暗号文を読めなくすることはありません。

安全でないシンボリックリンク、通常ファイル以外の対象、弱いアクセス権、未対応のスキーマ、改ざんされた暗号文、未知のプロバイダー項目、プロバイダー結び付きの衝突がある場合は、該当する設定を全体として拒否します。

## 認証情報を置き換える、ログアウトする

認証情報を置き換えるとリビジョンが進み、古いハンドルは無効になります。ログアウトはローカルのプロバイダーレコードを削除し、対応するハンドルを無効化します。どちらも、外部サービス側で認証情報が失効したことまでは保証しません。

実行中のプロセスの環境変数や、すでに開いているファイルは書き換えられません。新しいハンドルを受け取るには、Workspace から一度出て入り直します。論理 Workspace と永続ホームは、その前後で残ります。

<aside class="guarantee">
  <h2>保証すること</h2>
  <div class="prose-block">
    Auth Broker
    が管理する固定認証情報、更新可能な状態、リクエスト用に導出した認証情報は、Workspace、OPA
    入力、秘密情報を除いた監査記録には入りません。有効なハンドルだけでは、完全一致の結び付きと
    OPA の許可なしに、解決、更新、署名、外部の接続先への接続を起こせません。
  </div>
</aside>

<aside class="limitation">
  <h2>保証しないこと</h2>
  <div class="prose-block">
    ツール自身が管理する認証情報は Workspace から読めます。同じ Workspace
    内のプロセスは、すでに許可された通信に対して、配置済みの有効なハンドルを利用できます。ローカルのログアウトは、外部サービス側での失効ではありません。ホスト、Gateway、Auth
    Broker、ルート鍵の保存基盤が侵害された後の保護も対象外です。
  </div>
</aside>

認証情報の各経路を維持する実装とテストは、[実装とテスト](../verification-evidence/)にまとめています。
