認証は通信許可を与えません。どの認証情報管理方式でも、HTTP 通信には独立した
ポリシーの許可が必要です。また、Workspace から見える認証状態の範囲は
方式ごとに異なります。

Auth Broker を使う方式では、固定の秘密情報、更新可能なプロバイダーの状態、
ハンドルの元レコードを暗号化した Context 保管庫に保持します。Workspace に渡す
のは、利用範囲を結び付けたハンドルだけです。Gateway がハンドルを検証し、OPA が
通常の HTTP 通信を許可した後に限り、宣言済みの認証処理を一つ実行できます。

リクエストの流れは [認証情報](../../how-it-works/credentials/) で、信頼する認証
基盤の前提は [脅威モデル](../threat-model/) で説明します。

## 三つの方式では公開範囲が異なる

| 方式                     | 実物の秘密情報がある場所                                    | Workspace から読める値                                                     | Gateway の責務                                                           | 主な制限                                                   |
| ------------------------ | ----------------------------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------ | ---------------------------------------------------------- |
| ツール自身による受け渡し | ツールの Workspace ホームまたは環境                         | 実物の認証情報                                                             | 既知の認証ヘッダーを OPA 入力と監査記録で伏せ、許可後に転送する          | Workspace 内のプロセスが読み取り、再利用できる             |
| 保持型の管理アダプター   | Gateway だけにマウントする、ホスト管理の Context 認証情報   | 秘密情報ではないプロファイル名。Gateway 側のプロファイルはマウントされない | 設定済みの結び付きを照合し、許可後に認証情報を挿入する                   | 互換性のために残す方式。対象となるプロバイダーが限定される |
| Auth Broker              | 暗号化した Context 保管庫とリクエスト処理中の Broker メモリ | プロジェクトに結び付いた不透明なハンドル                                   | 除去、照会、許可判断の後、レビュー済みの処理に従って解決、更新、署名する | 同じ Workspace 内のプロセスは、投影済みの権限を利用できる  |

### 許可判断が見る情報と、ライフサイクル操作が変える状態

| 方式                     | OPA の許可判断へ渡す情報                                                                                         | 対象となるリクエスト先                                                                                          | ローテーションとログアウトの動作                                                                                                                 |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| ツール自身による受け渡し | 認識済みの認証情報を伏せた、正規化済みで本文を含まない通常の HTTP 通信                                           | ツールが送る HTTP/HTTPS リクエスト。Context、プロジェクトごとの完全一致ポリシーで制約する                       | ツールが管理する。プロセスからすでに読める秘密情報を Tobari は回収できない                                                                       |
| 保持型の管理アダプター   | 通常の HTTP 通信と、選択した秘密情報ではないプロファイル情報。管理対象の秘密情報は含まない                       | 設定済みの Context、プロジェクト、ホスト、プロファイル一組と、対応する固定ヘッダー経路                          | ホスト側の管理操作で秘密情報を置換または削除する。実行中の環境は書き換えられないため、投影が変わる場合は入り直して調整する                       |
| Auth Broker              | 通常の HTTP 通信と、秘密情報ではないプロバイダー識別情報。不透明なハンドル、リビジョン、実物の認証情報は含まない | プロバイダーマニフェストが定める完全一致の HTTPS 接続先とヘッダーの結び付き、および別途許可されたメソッドとパス | 置換とログアウトで古いハンドルを無効化する。現在の投影を受け取るには入り直す必要がある。ローカルのログアウトはプロバイダー側での失効を保証しない |

この順序自体が保証です。事前の照会では秘密情報を扱いません。固定認証情報の解決、
Datadog トークンの選択や更新、AWS 認証情報の書き出しと署名は、ポリシーが許可した後に
実行します。OPA が拒否した場合、いずれも動きません。Gateway が接続するのは、
宣言された完全一致の HTTPS 接続先だけです。

レビュー済みのスキーマ 2 プランも同じ順序を守ります。AWS の更新と署名は許可後に
非公開のホスト側補助処理を使います。Datadog トークンの選択または US1 固定の OAuth
更新は、許可後に Broker 内で動きます。どちらのプロバイダー処理も拒否時には動かず、
Workspace が受け取るのはプロジェクトに結び付いたハンドルだけです。

## ハンドルの結び付きを照合する項目

Auth Broker のハンドルレコードは、次のすべてに一致しなければなりません。

- 安定した Context ID
- ホストが発行するプリンシパルから導出した、安定したプロジェクト ID
- プロバイダー ID
- 認証情報のレコードとリビジョン
- 完全一致する HTTPS ホストとポート
- 宣言済みの送信元ヘッダーと構文
- 宣言済みの送信先ヘッダーと変換方式

メソッドとパスはハンドルを識別する項目ではありません。通常の HTTP 通信として
OPA が制約します。この分離により、ハンドル自体が通信許可になることを防ぎます。

## 保存とロック解除

各 Context は暗号化した <code>vault.enc</code> を持ちます。スキーマ 1 の
AES-256-GCM エンベロープは、安定した Context 識別子を関連データとして
結び付けます。暗号化されたスキーマ 2 の内容には、型付きの固定認証情報、不透明な
AWS ホスト取得処理の状態、Datadog OAuth セッションの状態、リビジョン、永続的な操作
バリア、ハンドルの元レコードを保存できます。

Linux では、インストール用の鍵は所有者だけが読める

<code>auth/keys/root.key</code> です。macOS では名前付きのキーチェーン項目
を使います。Broker はロック状態で起動し、状態調整処理が固定の
<code>docker exec -i</code> の標準入力からロック解除用データを渡します。元の鍵が
ない保管庫では、安全側に倒して処理を拒否します。代わりの鍵を黙って作り、既存の暗号文を
読み出せなくすることはありません。

安全でないシンボリックリンク、通常ファイル以外の対象、弱いアクセス権、未対応のスキーマ、
改ざんされた暗号文、未知のプロバイダー項目、プロバイダーの結び付きの衝突がある
場合は、該当する設定全体を拒否します。

## ローテーション、ログアウト、再入室

認証情報を置き換えるとリビジョンが進み、古いハンドルは無効になります。ログアウトは
ローカルのプロバイダーレコードを削除し、そのハンドルを無効にします。どちらも、
外部プロバイダー側で認証情報が失効したことまでは保証しません。また、すでに
動いているプロセスの環境変数や開いているファイルは書き換えられません。

新しいハンドルの投影を受け取るには、Workspace から一度出て入り直します。
論理 Workspace とそのホームは、入り直す前後でも残ります。

<aside class="guarantee">
  <h2>保証すること</h2>
  <div class="prose-block">
    Auth Broker が管理する秘密情報と更新可能な状態は、Workspace への投影、OPA
    の入力、秘密情報を除いた監査記録には入りません。有効なハンドルだけでは、
    完全一致の結び付きと OPA の許可なしに、解決、更新、署名、外部接続先
    への接続を起こせません。
  </div>
</aside>

<aside class="limitation">
  <h2>保証しないこと</h2>
  <div class="prose-block">
    ツール自身が管理する認証情報は Workspace から読める状態のままです。同じ
    Workspace
    内のプロセスは、すでに許可された通信に対して、投影済みの有効なハンドルを利用
    できます。ローカルのログアウトは外部プロバイダー側の失効ではありません。
  </div>
</aside>

## ここまでで説明できること

<code>auth login</code> と <code>policy allow</code> が独立した操作である理由を
確認します。

<div class="question-list">
  <details>
    <summary>
      ログインが成功しました。プロバイダーの接続先
      へ到達できるようになりますか？
    </summary>
    <div class="prose-block">
      通常のポリシーがその HTTP 通信を完全一致で許可しない限り、到達できません。
      ログインは認証情報を設定する操作であり、ポリシー規則は追加しません。
    </div>
  </details>
  <details>
    <summary>
      OPA が Auth Broker 経由のリクエストを拒否しました。Auth Broker
      は秘密情報を解決してから破棄しますか？
    </summary>
    <p>いいえ。拒否時には、秘密情報の解決処理自体が呼ばれません。</p>
  </details>
  <details>
    <summary>ローテーション後に入り直すのはなぜですか？</summary>
    <div class="prose-block">
      実行中のプロセスの環境変数は書き換えられません。入り直すことで、
      プロジェクトに結び付いた新しいハンドルの投影を反映します。
    </div>
  </details>
</div>
