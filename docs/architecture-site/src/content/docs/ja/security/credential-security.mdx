認証は通信許可を与えません。どの認証情報管理方式でも、通信には独立した
HTTP effect の許可が必要です。また、Workspace へ公開される認証状態の範囲は
方式ごとに異なります。

Auth Broker を使う方式では、static secret、renewable provider state、raw
handle record を encrypted Context vault に保持し、Workspace には bound
handle だけを渡します。Gateway が handle を検証し、OPA が ordinary HTTP
effect を許可した後に限り、宣言済みの post-policy credential action 一つを
実行できます。

request flow は [Credentials](../../how-it-works/credentials/) で、trusted
credential infrastructure の前提は [Threat model](../threat-model/) で説明します。

## 三つの方式では公開範囲が異なる

| Mode                     | primary secret の場所                                              | Workspace-readable value                                                                         | Gateway の責務                                                                 | 主な制限                                                       |
| ------------------------ | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------ | -------------------------------------------------------------- |
| Tool-native passthrough  | tool の Workspace home/environment                                 | real credential                                                                                  | known credential header を OPA/audit から redact し、allow 後に forward        | Workspace process が読み、再利用できる                         |
| Retained managed adapter | Gateway だけに mount される host-managed Context credential source | Workspace は non-secret profile name を送れる。Gateway-side profile projection は mount されない | configured binding を照合し、allow 後に inject                                 | retained compatibility path。provider-specific な scope        |
| Auth Broker              | encrypted Context vault と request-local Broker memory             | opaque project-bound handle                                                                      | strip、introspect、authorize の後、reviewed plan に従い resolve、refresh、sign | 同じ Workspace の process は projected capability を利用できる |

### 許可判断が見るものと、ライフサイクル操作が変えるもの

| Mode                     | OPA decision input                                                                                      | 対象となる request target                                                                        | rotation と logout の動作                                                                                                                                |
| ------------------------ | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tool-native passthrough  | recognized credential value を redact した後の normalized、body-free ordinary HTTP effect               | tool-compatible な HTTP/HTTPS request。それぞれ exact Context/project policy rule で制約される   | tool-owned。process がすでに読める secret を Tobari は回収できない                                                                                       |
| Retained managed adapter | ordinary effect と selected non-secret profile metadata。managed secret は含まない                      | 一つの configured Context/project/host/profile と、その supported fixed-header path              | host administration が secret を replace/remove する。running environment は書き換えられない。projection が変わる場合は re-entry で reconcile する       |
| Auth Broker              | ordinary effect と non-secret provider identity。opaque handle、revision、primary credential は含まない | provider manifest の exact HTTPS target/header binding と、独立して allowed になった method/path | replacement/logout は old handle を invalid にする。current projection の供給には re-entry が必要。local logout は provider-side revocation を約束しない |

この順序が guarantee です。introspection は non-secret で pre-policy です。static resolution、Datadog token selection/refresh、AWS credential export/signing は post-policy です。OPA が deny すると、そのどれも動きません。Gateway は declared exact HTTPS target だけへ接続します。

reviewed schema-2 plan もこの順序を維持します。AWS refresh/signing は allow 後に private host companion を使い、Datadog token selection または fixed US1 OAuth refresh は allow 後に Broker 内で動きます。どちらの provider action も denial では動かず、Workspace が受け取るのは引き続き project-bound handle だけです。

## binding の照合項目

broker handle record は、次のすべてに一致しなければなりません。

- stable Context ID。
- host principal から導出された stable project ID。
- provider ID。
- credential record と revision。
- exact HTTPS host と port。
- declared source header と syntax。
- declared destination header と transformation。

method と path は handle dimension ではありません。ordinary HTTP effect として OPA が制約します。この分離により、handle 自体が authorization になることを防ぎます。

## 保存と unlock

各 Context は encrypted <code>vault.enc</code> を持ちます。その schema-1 AES-256-GCM envelope は stable Context identity を associated data として bind します。encrypted schema-2 payload は、typed static secret、opaque AWS host-driver state、Datadog OAuth-session state、revision、durable operation barrier、raw handle を保持できます。Linux では installation key は owner-only の <code>auth/keys/root.key</code>、macOS では named Keychain item です。Broker は locked 状態で起動します。reconciliation は fixed <code>docker exec -i</code> stdin を通じて unlock material を転送します。original key のない vault は fail closed します。Tobari は replacement key を黙って作成して古い ciphertext を orphan にしません。

unsafe symlink、non-regular file、weak permission、unsupported schema、tampered ciphertext、unknown provider field、provider binding collision は、該当する configuration を拒否します。

## ローテーション、ログアウト、再 entry

credential replacement は revision を進め、old handle を invalid にします。logout は local provider record を削除し、その handle を invalid にします。どちらも remote provider が credential を revoke したとは約束しません。どちらも、すでに動いている process の environment または open file を編集できません。

Workspace を leave して re-enter し、reconciled runtime が新しい handle projection を受け取れるようにします。logical Workspace とその home は re-entry をまたいで persistence します。

<aside class="guarantee">
  <h2>保証すること</h2>
  <div class="prose-block">
    Broker-managed secret と renewable state は Workspace projection、OPA
    input、secret-free audit に入りません。valid handle だけでは、exact binding
    と OPA allow なしに resolution、refresh、signing、upstream access
    を起こせません。
  </div>
</aside>

<aside class="limitation">
  <h2>保証しないこと</h2>
  <div class="prose-block">
    Tool-native credential は Workspace-readable のままです。同じ Workspace の
    process は、すでに allowed な effect に沿って valid projected handle
    を行使できます。local logout は remote revocation ではありません。
  </div>
</aside>

## ここまでで説明できること

<code>auth login</code> と <code>policy allow</code>
が独立した操作である理由を説明できるはずです。

<div class="question-list">
  <details>
    <summary>
      login が成功しました。provider endpoint へ到達できるようになりますか？
    </summary>
    <div class="prose-block">
      normal policy が exact HTTP effect を allow
      しない限り、到達できません。login は credential material
      を設定するもので、policy rule は追加しません。
    </div>
  </details>
  <details>
    <summary>
      OPA が Auth Broker 経由のリクエストを拒否しました。Auth Broker
      は秘密情報を resolve してから破棄しますか？
    </summary>
    <p>いいえ。deny では resolution 自体が呼ばれません。</p>
  </details>
  <details>
    <summary>ローテーション後に再 entry するのはなぜですか？</summary>
    <div class="prose-block">
      running process environment は書き換えられません。re-entry により、新しい
      project-bound handle projection を reconcile します。
    </div>
  </details>
</div>
