Tobari が信頼するのは、ホスト側のライフサイクル状態、プリンシパル登録簿、ポリシー、ルート鍵、Gateway、OPA、Auth Broker です。Workspace 内のプロセスと外部サービスは信頼しません。Workspace や外部サービスが送った値を、そのまま Context やプロジェクトの権限として扱うこともありません。

作業対象のファイル、プロジェクトの権限、ポリシー変更の権限、認証情報の本体、リクエストデータは、それぞれ別の境界を通ります。各境界が成立させる保証は、先に[保証と制限](../guarantees-and-limitations/)で確認してください。

## 境界 1：作業対象のファイル

信頼するホストの利用者が、作業対象となるプロジェクトルートを選びます。Tobari は、そのディレクトリで作業できるよう、ランタイムへ読み書き可能な状態でマウントします。したがって Workspace のプロセスは、そのルート内にあるファイルを読み取り、変更、削除できます。

作業対象外のホストパスは通常のマウント対象に含めず、Docker の制御機能も Workspace へ渡しません。各 Workspace には、インスタンス状態用のディレクトリから別々の永続ホームを割り当てます。

この境界は、作業対象のディレクトリを Workspace 自身から保護するものではありません。たとえば異なる Workspace または Context が `/work/team` と `/work/team/service` を使うと、ネットワーク、ホーム、識別情報、ポリシーの結び付きが異なっていても、重複するホスト上のファイルは共有されます。

## 境界 2：プロジェクトの権限

ホストはプロジェクト専用のネットワークを作り、安定した Context ID、プロジェクト ID、基準となるルート、ネットワーク、Gateway のローカルアドレスを対応付けます。このように、どの Context とプロジェクトの権限を使うかをホスト側の事実から示す識別情報を、プリンシパル（principal）と呼びます。

Gateway は、リクエストを受信した自身のインターフェースアドレスである `flow.client_conn.sockname[0]` を使い、ホストが管理する登録簿からプリンシパルを選びます。

Workspace は `X-Project-ID: something-else` のようなヘッダーを送れますが、その文字列は信頼しないリクエストデータのままです。Gateway の受信インターフェースや、ホスト側の登録簿を書き換えることはできません。対応付けが不明または曖昧な場合、Gateway は OPA へ問い合わせる前に拒否します。

## 境界 3：ポリシーを変更する権限

OPA は、Context、プロジェクト、スキーム、宛先、ポート、メソッド、パスなど、本文を除いた正規化済みの情報で HTTP 通信を判断します。Gateway が接続を所有し、その結果を通信経路へ強制します。

Workspace へ返す拒否レスポンスは、ホスト側で実行するレビューコマンドを示すだけです。権限変更に使う不透明な参照値や、ポリシーを書き換える機能は Workspace へ渡しません。

信頼するホスト CLI だけが、不透明なレビュー参照を変更せずに使い、許可または拒否を確定できます。Tobari はポリシー全体を検証し、完全な集約結果を有効化します。表示用のラベル、行の順番、再構成した識別子は、変更操作の権限になりません。

## 境界 4：認証情報を使う権限

ツール自身が管理する認証情報は、意図的に Workspace の保存領域や環境へ渡すため、Workspace から読めます。保持型の管理方式と Auth Broker 方式では扱いが異なります。

Auth Broker 方式では、固定された GitHub、AWS、Datadog の取得処理が信頼するホスト上で動きます。ルート鍵の保管機構が Context 保管庫のロックを解除し、Auth Broker が型付きの固定または更新可能な認証状態を保持します。Workspace が受け取るのは、一つのプロジェクトに結び付いた、内容を読み取れないレコード選択用のハンドルだけです。

Gateway は、ハンドル、解決後の認証情報、更新可能な状態、通常のリクエスト本文を OPA へ送りません。固定認証情報を使う許可済み通信では、認証情報を一度だけ解決し、マニフェストで宣言された送信先ヘッダーだけを置き換えます。AWS の許可済み通信では、非公開のホスト側コンパニオンが、あらかじめ定義された認証情報の取得だけを実行し、Auth Broker がローカルで署名します。Datadog の許可済み通信では、Auth Broker が完全一致の US1 接続先に限ってトークンを選択または更新します。拒否時には、これらの認証処理を実行しません。

## 境界 5：外部から入るデータ

リクエスト URL、ヘッダー、本文、外部接続先の証明書、レスポンス、プロバイダーのアカウント名、診断情報、ポリシー候補には、攻撃者が制御する文字列が含まれる可能性があります。端末表示や構造化出力では、表示形式を壊す文字をエスケープします。それでも、表示された文字列の意味まで信頼できるとは扱いません。

リクエスト本文と、ポリシー判断に使う識別情報も分けています。本文は許可後に Gateway を通って外部の接続先へ届きますが、ポリシー候補や、秘密情報を除いた監査記録には含めません。

## 失敗と復旧

境界に関わる登録情報や状態は、外部へ作用する処理より前に検証します。プリンシパル登録簿、ポリシー、プロバイダー、ルート鍵、保管庫、ハンドルが安全な状態でない場合、関連する通信や認証処理を拒否します。

復旧時も、Workspace が送る値を権限の根拠にはしません。通常は `doctor`、`cluster status`、`auth status`、ポリシー候補の再取得、Workspace への再入室など、ホスト側の明示的なコマンドを使います。

<aside class="guarantee">
  <h2>保証すること</h2>
  <div class="prose-block">
    サポート対象の構成では、権限は Workspace
    の自己申告ではなく、ホストが管理する状態と、固定されたコンポーネントの配置から導出します。
  </div>
</aside>

<aside class="limitation">
  <h2>保証しないこと</h2>
  <div class="prose-block">
    信頼するホストの利用者は、安全でないプロジェクトルートやポリシールールを選べます。信頼するコンポーネントが侵害されれば、その境界は成立しません。一つの
    Workspace は、内部のプロセス同士や、作業対象のファイル同士を隔離しません。
  </div>
</aside>

## ここまでで説明できること

どの識別情報が権限の根拠になり、どの値が単なる信頼しない文字列や、レコードを選ぶためのハンドルにすぎないかを区別します。

<div class="question-list">
  <details>
    <summary>
      偽装した Context ヘッダーで、別のポリシーを利用できないのはなぜですか？
    </summary>
    <div class="prose-block">
      Gateway は、ホストが作成した受信インターフェースの対応付けから Context
      とプロジェクトを選びます。リクエストヘッダーは、そのインターフェースや登録簿を変更できません。
    </div>
  </details>
  <details>
    <summary>
      Auth Broker のハンドルは、認証情報の本体または独立した権限ですか？
    </summary>
    <div class="prose-block">
      いいえ。秘密情報ではない不透明なレコード選択子であり、それだけでは認証情報を利用できません。Context、プロジェクト、プロバイダー、リビジョン、接続先、ヘッダーの結び付け、OPA
      の許可がすべて一致する必要があります。
    </div>
  </details>

    <summary>
      プロジェクトルートの重なりが意図と違った場合、どこへ戻るべきですか？

      を読み直してください。作業対象として選んだルートと、それに重なるルートは、ホストファイルを相互に隔離する対象ではありません。

  </details>
