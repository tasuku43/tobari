Tobari が信頼するのは、ホスト側のライフサイクル状態、プリンシパル登録簿、ポリシー、Gateway、OPA です。Workspace 内のプロセスと外部サービスは信頼しません。Workspace や外部サービスが送った値を、そのまま Workspace Template やプロジェクトの権限として扱うこともありません。

作業対象のファイル、プロジェクトの権限、ポリシー変更の権限、認証情報の本体、リクエストデータは、それぞれ別の境界を通ります。各境界が成立させる保証は、先に[保証と制限](../guarantees-and-limitations/)で確認してください。

## 境界 1：作業対象のファイル

trusted host user が canonical project root を選びます。immutable Workspace Template `source_access` が
`read-only` または `read-write` の live bind を選び、CLI omission default は `read-write` です。
read-only bind でも host や別 Workspace Template の変更を観測します。Workspace home は writable です。

作業対象外のホストパスは通常のマウント対象に含めず、Docker の制御機能も Workspace へ渡しません。各 Workspace には、stable Workspace ID から導出する別々の owner-only 永続 home を割り当てます。

この境界は、作業対象のディレクトリを Workspace 自身から保護するものではありません。たとえば異なる Workspace または Workspace Template が `/work/team` と `/work/team/service` を使うと、ネットワーク、ホーム、識別情報、ポリシーの結び付きが異なっていても、重複するホスト上のファイルは共有されます。

## 境界 2：プロジェクトの権限

host は Workspace 専用 network を作り、stable Context ID、Workspace ID、canonical root、network、Workspace source endpoint、Gateway endpoint を schema 1 registry で対応付けます。このように、どの Context/Workspace authority を使うかを host-side fact から示す identity を principal と呼びます。

Gateway は、カーネルが観測した接続元アドレスである `flow.client_conn.peername[0]` を使い、ホストが管理する登録簿からプリンシパルを選びます。

Workspace は `X-Project-ID: something-else` のようなヘッダーを送れますが、その文字列は信頼しないリクエストデータのままです。登録済みの送信元エンドポイントや、ホスト側の登録簿を書き換えることはできません。対応付けが不明または曖昧な場合、Gateway は OPA へ問い合わせる前に拒否します。

## 境界 3：ポリシーを変更する権限

OPA は、Context、スキーム、宛先、ポート、メソッド、パスなど、本文を除いた正規化済みの情報で HTTP 通信を判断します。Workspace、root、CWD、directory は routing と provenance にだけ使われます。Gateway が接続を所有し、その結果を通信経路へ強制します。

Workspace へ返す拒否レスポンスは、ホスト側で実行するレビューコマンドを示すだけです。権限変更に使う不透明な参照値や、ポリシーを書き換える機能は Workspace へ渡しません。

信頼するホスト CLI だけが、不透明なレビュー参照を変更せずに使い、許可または拒否を確定できます。Tobari はポリシー全体を検証し、完全な集約結果を有効化します。表示用のラベル、行の順番、再構成した識別子は、変更操作の権限になりません。

## 境界 4：Workspace サービスへの attachment 所有アクセス

read-only の `tobari-expose` helper は、Workspace loopback port 一つの trusted-host review を
要求できますが、host access を開けません。別に起動した host の `tobari review services` が owner の
fresh snapshot を取得し、opaque reference 一つを live attachment owner へ渡します。その owner
だけが exact IPv4 loopback を bind し、exact numeric HTTP authority を検証し、HTTP/1.1 または
upgrade 済み WebSocket を relay し、attachment exit で access を閉じます。review process は
route lifetime を所有せず、browser channel、Host Loopback policy、application bytes はいずれも
この access を認可しません。

## 境界 5：native credential の権限

ツール自身の認証情報は Workspace の storage/environment に渡るため読めます。release surface
は host credential を継承せず、Tobari の credential service も持ちません。一方で、Workspace は
自分の persistent home と identity を使います。Gateway は認証情報と
cookie を OPA input と audit から除外し、通常の HTTP effect が許可された後だけ元の値を転送します。
deny では認証情報は接続先へ届きません。

## 境界 6：外部から入るデータ

リクエスト URL、ヘッダー、本文、外部接続先の証明書、レスポンス、外部サービスのアカウント名、診断情報、ポリシー候補には、攻撃者が制御する文字列が含まれる可能性があります。端末表示や構造化出力では、表示形式を壊す文字をエスケープします。それでも、表示された文字列の意味まで信頼できるとは扱いません。

リクエスト本文と、ポリシー判断に使う識別情報も分けています。本文は許可後に Gateway を通って外部の接続先へ届きますが、ポリシー候補や、秘密情報を除いた監査記録には含めません。

## 失敗と復旧

境界に関わる登録情報や状態は、外部へ作用する処理より前に検証します。プリンシパル登録簿、ポリシー、host-owned state、Workspace の状態が安全でない場合、関連する通信を拒否します。

復旧時も、Workspace が送る値を権限の根拠にはしません。通常は `doctor`、`cluster status`、ポリシー候補の再取得、Workspace への再入室など、ホスト側の明示的なコマンドを使います。

<aside class="guarantee">
  <h2>保証すること</h2>
  <div class="prose-block">
    サポート対象の構成では、権限は Workspace
    の自己申告ではなく、ホストが管理する状態と、固定されたコンポーネントの配置から導出します。
  </div>
</aside>

<aside class="limitation">
  <h2>保証しないこと</h2>
  <div class="prose-block">
    信頼するホストの利用者は、安全でないプロジェクトルートやポリシールールを選べます。信頼するコンポーネントが侵害されれば、その境界は成立しません。一つの
    Workspace は、内部のプロセス同士や、作業対象のファイル同士を隔離しません。
  </div>
</aside>

境界ごとの実装とテストを追う場合は、[実装とテスト](../verification-evidence/)を参照してください。

## ここまでで説明できること
