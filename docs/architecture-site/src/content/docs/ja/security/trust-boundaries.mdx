ホストが管理するライフサイクル状態、登録簿、ポリシー、ルート鍵、Gateway、OPA、
Auth Broker が、Tobari の信頼する実施領域を構成します。Workspace 内のプロセスと
外部サービスは信頼しません。そこから送られた値を使って、自己申告した
プロジェクトや Context のラベルを権限へ変えることはできません。

プロジェクトの権限、ポリシーの権限、実物の認証情報、リクエストのデータは、それぞれ
別の境界を横断します。各境界が実施する主張は、先に
[保証と制限](../guarantees-and-limitations/)で確認してください。

## 境界 1：選択したファイル

信頼するホストが、基準となるプロジェクトルートを選びます。Tobari は、そのルートで作業
できるようにランタイムへマウントします。したがって Workspace には、そのルートを
読み書きする権限があるものとして扱う必要があります。その他のホスト上のパスは通常の
マウント対象から除外し、Docker の制御機能はマウントしません。各 Workspace には、
インスタンス状態用のディレクトリから別々の永続ホームを割り当てます。

ルートを選ぶ境界は、選択したディレクトリツリーのファイル完全性を守るサンドボックスでは
ありません。異なる Workspace または Context が <code>/work/team</code> と

<code>/work/team/service</code>
を意図的に使うと、ネットワーク、ホーム、識別情報、 ポリシーの結び付き
が異なっていても、重複するホスト上のファイルは共有されたままです。

## 境界 2：プロジェクトの権限

ホストはプロジェクト専用のネットワークを作り、安定した Context ID、プロジェクト ID、
基準となるルート、ネットワーク、Gateway のローカルアドレスを含むプリンシパルの対応付け
を一つ書き込みます。このプリンシパルは、どの Context とプロジェクトの権限を使うかを
ホスト側の事実から示す識別情報です。Gateway は、自身が受信した側の事実である

<code>flow.client_conn.sockname[0]</code> から対応付けを選びます。

Workspace は <code>X-Project-ID: something-else</code> と書けますが、その文字列は
信頼しないリクエストデータのままです。Gateway のインターフェースやホスト登録簿の
検索結果は変更できません。対応付けが不明または曖昧な場合、OPA より前に失敗します。

## 境界 3：ポリシーの権限

OPA は、通常の HTTP 通信を正規化し、本文を除いた情報を受け取って判断します。
Gateway が接続を所有し、その結果を実施します。Workspace へ返す拒否レスポンスは、
ホスト側のレビュー場所を示すだけです。ポリシーを変更する権限はありません。

信頼するホスト CLI だけが、受け取ったままの不透明なレビュー参照を使って、
許可または拒否を選択し、完全な集約結果を検証して有効化できます。表示用ラベル、
行の順番、組み立て直した識別子は、操作の権限にはなりません。

## 境界 4：認証情報を使う権限

ツール自身が管理する認証情報は、意図的に Workspace の保存領域または環境へ渡すため、
Workspace から読めます。保持型の管理方式と Auth Broker 方式では扱いが異なります。
Auth Broker 方式では、固定された GitHub、AWS、Datadog の取得処理が信頼する
ホスト上で動きます。ルート鍵の保管機構が Context 保管庫のロックを解除し、Auth Broker
が型付きの固定または更新可能な認証状態を保持します。Workspace が受け取るのは、
一つのプロジェクトに結び付いた、秘密情報ではない不透明なレコード選択子です。

Gateway は、ハンドル、解決後の認証情報、更新可能な状態、通常のリクエスト本文を OPA
へ送りません。固定認証情報を使う許可済みの通信では、一度だけ秘密情報を解決し、
宣言済みの送信先ヘッダーだけを置き換えます。AWS の許可済み通信では、非公開の
ホスト側コンパニオンがあらかじめ定義された認証情報の書き出しだけを実行し、Broker が
ローカルで署名します。Datadog の許可済み通信では、Broker が完全一致の US1
接続先に限ってトークンを選択または更新します。拒否時には、秘密情報を扱うこれらの
操作は一つも動きません。

## 境界 5：外部データ

リクエスト URL、ヘッダー、本文、外部接続先の証明書、レスポンス、プロバイダーのアカウント名、
診断情報、ポリシー候補には、攻撃者が制御する文字列が含まれる可能性があります。
表示用の変換では、端末や構造化出力を壊す文字をエスケープします。表示可能な
命令文らしい内容まで、信頼できるデータになるとは主張しません。

本文のストリームと、許可判断で使う識別情報は別です。本文は許可後に Gateway を通って
外部の接続先へ届きますが、ポリシー候補や秘密情報を除いた監査レコードには含まれません。

## 失敗と復旧

境界のメタデータは、外部へ作用する処理より前に検証します。安全でない登録簿、
ポリシー、プロバイダー、ルート鍵、保管庫、ハンドルの状態では、安全側に倒して拒否します。
復旧時に Workspace が送る値を信頼することはありません。通常は <code>doctor</code>、

<code>cluster status</code>、<code>auth status</code>、ポリシー候補の再検出、再
入室など、ホスト側の明示的なコマンドを使います。

<aside class="guarantee">
  <h2>保証すること</h2>
  <div class="prose-block">
    サポート対象の構成では、権限は Workspace
    の自己申告ではなく、ホストが管理する
    状態と、固定されたコンポーネントの配置から導出します。
  </div>
</aside>

<aside class="limitation">
  <h2>保証しないこと</h2>
  <div class="prose-block">
    信頼するホストの利用者は、安全でないルートまたは規則を選べます。信頼する
    コンポーネントの侵害は、その境界を破ります。一つの Workspace は、内部の
    プロセス同士や、選択したファイル同士を隔離しません。
  </div>
</aside>

## ここまでで説明できること

どの識別子が権限の根拠で、どれが単なる信頼しない文字列やレコード選択子
なのかを区別します。

<div class="question-list">
  <details>
    <summary>
      偽装した Context ヘッダーが別のポリシーを借りられないのはなぜですか？
    </summary>
    <div class="prose-block">
      Gateway は、ホストが作成した受信インターフェースの対応付けから Context と
      プロジェクトを選びます。ヘッダーは、そのインターフェースや登録簿の項目
      を変更できません。
    </div>
  </details>
  <details>
    <summary>
      Auth Broker のハンドルは、秘密情報または独立した権限ですか？
    </summary>
    <div class="prose-block">
      いいえ。秘密情報ではない不透明なレコード選択子
      であり、実物の認証情報でも、
      それだけで十分な権限でもありません。Context、プロジェクト、プロバイダー、
      リビジョン、接続先、ヘッダーの結び付き、OPA
      の許可がすべて一致する必要があります。
    </div>
  </details>
  <details>
    <summary>
      ファイル範囲の重なりが意外だった場合、どこへ戻るべきですか？
    </summary>
    <div class="prose-block">
      <a href="../guarantees-and-limitations/">保証と制限</a>{" "}
      を読み直してください。選択したルートと重複するルートは、ファイルシステム
      の完全性を 隔離する対象外であることが明示されています。
    </div>
  </details>
</div>
