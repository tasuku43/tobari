---
title: 保証と制限
description: Tobari の主要なセキュリティ保証について、成立する前提、制御の仕組み、障害時の動作、対象外を対応付けます。
---

Tobari は、Workspace の権限を一つのプロジェクト、ホストが発行した一つのプリンシパル、Gateway を経由する HTTP/HTTPS、明示されたポリシー、利用範囲を制約した Auth Broker のハンドルへ限定します。一方、作業対象のディレクトリ内にあるファイル、許可済みの接続先へ送るデータ、同じ Workspace 内のプロセス、HTTP/HTTPS 以外の通信、重複するプロジェクトルート、侵害された信頼基盤は制御しません。

以下では、各保証を前提、制御の仕組み、障害時の動作、最も近い対象外とセットで示します。共通する信頼対象と境界は、先に[セキュリティ概要](../overview/)で確認してください。

## 保証 1：Workspace には外部への直接経路がない

**保証。** サポート対象の構成で作られた Workspace は、公開インターネットへ直接到達できません。

**前提。** Tobari が Docker の設定に従って Workspace を作成・調整し、Docker とホストのネットワークが設定どおりに動作していること。

**仕組み。** Workspace は専用の Docker `internal` ネットワークだけに参加します。出力ポリシーは既定で拒否し、唯一の既定 TCP 経路は正確なプロジェクト Gateway を指します。Gateway の転送処理は無効なまま、合成 DNS と透過リダイレクトが通常の HTTP/TLS を Gateway のポリシーリスナーへ届けます。

**障害時。** 通常の直接ソケットは別の経路ではなく、保護済みの透過経路へ入ります。Gateway が利用できない場合、HTTP 通信は失敗します。

**対象外。** Tobari が仲介するのは通常の HTTP/HTTPS です。あらゆるプロトコルの通信を遮断する仕組みではありません。また、許可された HTTP 接続先は、Workspace から読めるデータを受け取れます。

## 保証 2：Workspace は別プロジェクトの権限を自分へ付与できない

**保証。** リクエストのバイト列から、より強い権限を持つ Workspace Manifest またはプロジェクトのプリンシパルを選ぶことはできません。

**前提。** ホスト側のライフサイクル処理が Workspace 固有のネットワーク対応付けを作り、プリンシパル登録簿が破損していないこと。

**仕組み。** Gateway は、カーネルが観測した Workspace の送信元エンドポイントを、ホストが管理するスキーマ 1 のプリンシパル登録簿で検索します。そこで得た Workspace Manifest とプロジェクトの識別情報を OPA の入力に入れます。リクエスト側が自己申告したヘッダーは、権限の根拠として使いません。

**障害時。** 対応付けが不明、不正、重複、または古い場合、OPA への問い合わせや外部の接続先への接続より前に `project_principal_unavailable` を返します。

**対象外。** 二つの Workspace Manifest から、同じまたは重複するホスト上のルートを意図的にマウントできます。ネットワーク、ホーム、ポリシー上のプリンシパルは別でも、重複範囲のファイル変更は同じホスト上のファイルへ反映されます。

## 保証 3：ポリシー判断の失敗は外部通信にならない

**保証。** Gateway が外部の接続先へ接続するのは、一つの有効な OPA の許可結果を得た後だけです。

**前提。** 通信が Gateway に到達し、リクエストを現在のポリシー入力スキーマへ正規化できること。

**仕組み。** Gateway は、本文を除いて正規化した判断項目を、固定された OPA の接続先へ一度だけ送ります。外部の接続先への接続は、許可された後に初めて作ります。

**障害時。** 拒否の場合は `policy_denied` を返します。応答待ちの上限超過、接続失敗、HTTP 200 以外の応答、上限超過、不正または不完全な判断結果では `policy_unavailable` を返します。どちらの場合も外部の接続先へ接続しません。

**対象外。** 現在の学習済み完全一致ルールは、Workspace Manifest、プロジェクト、ホスト、ポート、メソッド、未加工のパスを区別します。本文、クエリー、秘密情報を含まないヘッダー、拒否理由、プロバイダー、認証情報プロファイルは区別しません。本文が異なっても、同じ HTTP 通信の完全一致ルールを利用できます。

## 保証 4：Auth Broker が管理する認証情報は Workspace に渡されない

**保証。** Workspace が受け取るのは static primary secret や request-local credential ではなく、
project-bound opaque handle 一つです。

**前提。** プロバイダーが Auth Broker の経路を使い、ルート鍵が利用でき、Workspace Manifest 保管庫とプロバイダーマニフェストの検証が成功すること。

**仕組み。** Auth Broker は static state を Workspace Manifest vault で暗号化します。handle record は
Workspace Manifest、project、provider、revision、完全一致 target、HTTP header binding に結び付きます。
Gateway は handle を除去し、non-secret introspection と Workspace Manifest policy ceiling の後に OPA へ問い合わせ、
allow 後だけ declared static resolve を実行します。

**障害時。** 不正、copy、stale、malformed、ambiguous handle は拒否し別方式へ切り替えません。
terminal guardrail または OPA deny では resolve、DNS、upstream access はゼロです。resolution 前の
Broker unavailability は upstream attempt なしの 503 です。

**対象外。** 同じ Workspace 内の悪意あるプロセスは、その Workspace へ配置されたハンドルと、すでに許可された通信を利用できます。ツール自身が管理する認証情報は、ツールが保存した場所から読めるままです。ログアウトはプロバイダー側での失効を保証しません。

## 保証 5：検証できないポリシー変更は部分的に有効化されない

**保証。** 許可または拒否の変更操作で有効化するのは、全体を検証済みの集約結果だけです。

**前提。** ホスト側の利用者が現在の不透明な候補参照をそのまま操作へ渡し、ポリシー定義元とリビジョンに競合がないこと。

**仕組み。** Tobari は各候補を再検出し、非公開の定義元と完全な集約結果を検証し、リビジョンを確認します。その後、一つの Workspace Manifest について所有者だけが変更できる定義元へ、途中状態を見せずに書き込みます。リビジョン付きの完全なバンドルを公開し、実行中の OPA がそのリビジョンを報告するまで待ちます。権限を減らす変更では、最初に全拒否へ移行するリビジョンを導入します。失敗時は、状態を直前に確認できた内容へ戻します。

**障害時。** 検証、古い参照値、競合、書き込み、集約、OPA の有効化に失敗した場合、以前の有効なポリシーを保持または復元します。以前の HTTP リクエストを再送することはありません。

**対象外。** 信頼する利用者は、危険な HTTP 通信を完全一致で意図的に許可できます。Tobari は送信データの安全性を推測しません。複数の完全一致パスを接頭辞ルールへ広げるには、専用の検証用リクエストを通した明示的な集約操作が必要です。自動ではありません。

## 明示的に保証しないもの

- 作業対象のディレクトリ内にあるファイルの完全性または機密性
- 一つの Workspace 内のプロセス間隔離
- 重複してマウントしたプロジェクトルート間の隔離
- 許可済みのリクエストによるデータ送信の防止
- HTTP/HTTPS 以外のネットワーク通信の仲介
- ホスト、カーネル、Docker、Gateway、OPA、Auth Broker、ルート鍵の提供機構、レビュー済みイメージが侵害された後の保護
- ローカルでログアウトした後の、外部プロバイダー側の認証情報失効
- 証明書を固定するクライアントとの互換性。TLS の検査を迂回するのではなく、接続に失敗することが期待されます

公開仕様と、それを維持する実装・テストの対応は、[実装とテスト](../verification-evidence/)にまとめています。
