---
title: 保証と制限
description: Tobari の主要なセキュリティ保証について、成立する前提、制御の仕組み、障害時の動作、対象外を対応付けます。
---

Tobari は、Workspace の権限を一つの Context、ホスト発行の principal、Gateway を経由する HTTP/HTTPS、明示されたポリシーに限定します。agent CLI のログイン情報は同じ Context の sibling Workspace が共有する Context Home にあり、host credential は継承しません。作業対象のファイル、許可済みの接続先へ送るデータ、同じ Context Home を共有するプロセスや sibling Workspace、HTTP/HTTPS 以外の通信、重複するプロジェクトルート、侵害された信頼基盤は制御しません。

以下の各保証では、成立する前提、強制する場所、障害時の動作、最も近い制限を対応付けます。信頼するコンポーネントと、これらの保証が共有する境界は、先に[セキュリティ概要](../overview/)を確認してください。

## 保証 1：Workspace には外部への直接経路がない

**保証。** サポート対象の構成で作られた Workspace は、公開インターネットへ直接到達できません。

**前提。** Tobari が Docker 構成を通じて Workspace を作成・調整済みで、Docker とホストのネットワークが設定どおりに動作していること。

**仕組み。** Workspace は専用の Docker `internal` ネットワークだけに参加します。出力 policy は default-drop で、既定の TCP 経路は exact project Gateway です。Gateway forwarding は無効のままで、synthetic DNS と transparent redirect が通常の HTTP/TLS を policy listener へ届けます。

**障害時。** 通常の direct socket は別経路ではなく guarded transparent route へ到達します。Gateway が利用できない場合、HTTP 通信は失敗します。

**対象外。** Tobari が仲介するのは通常の HTTP/HTTPS です。許可された接続先は Workspace から読めるデータを受け取れます。

## 保証 2：Workspace は別プロジェクトの権限を自分へ付与できない

**保証。** リクエストのバイト列から、より強い Workspace Template または project principal を選ぶことはできません。

**前提。** host lifecycle が Workspace ごとの一意な network binding を作成し、principal registry の整合性が保たれていること。

**仕組み。** Gateway はカーネルが観測した Workspace の送信元 endpoint を、ホスト管理の principal 登録簿で検索します。自己申告したヘッダーは権限の根拠ではありません。不明または不正な対応付けは OPA より前に拒否されます。

**障害時。** 未知、不正、重複、古い binding は `project_principal_unavailable` となり、OPA と upstream より前に止まります。

**対象外。** 二つの Workspace Template が同じ、または重なる host root を意図的に mount できます。network、home、policy principal は別でも、重なった範囲の file change は共有されます。

## 保証 3：ポリシー判断の失敗は外部通信にならない

**保証。** Gateway が接続先へ接続するのは、有効な OPA の許可結果を得た後だけです。

**前提。** traffic が Gateway へ到達し、request を現在の decision schema へ正規化できること。

**仕組み。** Gateway は本文を除いた正規化入力を OPA へ一度だけ送り、拒否・タイムアウト・不正応答では接続先へ接続しません。

**障害時。** deny は `policy_denied`、timeout、接続失敗、non-200、oversize、不正または不完全な decision は `policy_unavailable` です。どちらも upstream connection を作りません。

**対象外。** 現在の exact learned rule は Context、host、port、method、raw path を区別します。Workspace、root、CWD、directory は routing と provenance だけで、rule identity や compatibility を分けません。body、query、safe header、reason、provider も区別しないため、異なる body が同じ exact effect rule を利用できます。

**ログイン情報の境界。** agent CLI が Context Home に保管するログイン情報の値は、OPA の判断入力と監査記録に入りません。

**仕組み。** Gateway は認識可能な認証ヘッダーと cookie の値を除外し、通常の HTTP effect が許可された後だけ元の値を転送します。Tobari は host credential を継承せず、provider 固有の形式を解釈しません。

**障害時。** OPA deny、Gateway 障害、ポリシー不在では値を転送せず、接続先への接続も作りません。

**対象外。** 同じ Context Home を共有するプロセスと sibling Workspace は、その agent CLI state を読めます。agent CLI の logout は外部サービス側の失効を保証しません。

## 保証 4：検証できないポリシー変更は部分的に有効化されない

**保証。** 許可または拒否の変更で有効化するのは、全体を検証済みの集約結果だけです。

**前提。** 信頼する host user が現在の opaque candidate reference を選び、policy source と revision が競合していないこと。

**仕組み。** Tobari は候補を再検出し、private source、完全な all-Context projection、revision を検証します。一つの owner-only source を atomic write し、revisioned complete bundle を公開して、実行中 OPA が exact revision を報告するまで待ちます。authority reduction では最初に deny-all transition revision を入れます。

**障害時。** validation、stale reference、race、write、aggregate、OPA activation の失敗では以前の valid policy を保持または復元します。以前の HTTP request は再送しません。

**対象外。** trusted operator は危険な exact effect を意図的に許可できます。Tobari は payload safety を推測せず、first public V1 の learned exact path を自動的に広げません。

## 明示的に保証しないもの

- 作業対象のファイルの完全性または機密性
- 一つの Workspace 内のプロセス間隔離
- 重複してマウントしたプロジェクトルート間の隔離
- 許可済みリクエストによるデータ送信の防止
- HTTP/HTTPS 以外のネットワーク通信の仲介
- ホスト、カーネル、Docker、Gateway、OPA、レビュー済みイメージが侵害された後の保護
- provider 側の logout や remote revocation
- 証明書を固定するクライアントとの互換性

公開仕様と、それを維持する実装・テストの対応は、[実装とテスト](../verification-evidence/)にまとめています。
