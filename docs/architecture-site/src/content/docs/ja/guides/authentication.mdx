認証は identity material を用意しますが、通信を許可しません。Context preset の
guardrail と OPA の完全一致ポリシーが、すべての HTTP effect を引き続き判断します。

## 二つの管理方式を比較する

| 方式        | 認証情報の所有者                       | Workspace が受け取るもの                 | first public V1 の境界                               |
| ----------- | -------------------------------------- | ---------------------------------------- | ---------------------------------------------------- |
| ツール自身  | Workspace client と書き込み可能な home | client 自身の file または process state  | Tobari は仲介・検査しない。Gateway policy は適用する |
| Auth Broker | Workspace 外の暗号化 Context vault     | Context/project に結び付く random handle | 静的 primary secret 一つと完全一致 HTTPS header 置換 |

## 組み込み GitHub 取得

first public V1 の組み込み取得は一つだけで、provider の明示が必須です。

```sh
tobari auth login --provider github --context default
```

provider menu、省略値、`--tool`、別の組み込み login method はありません。Tobari は
信頼するホストで、identity を確認した固定 `gh` helper を sanitized temporary home
から実行します。レビュー済み device flow と固定 browser destination だけを使い、
browser を開けなければ手動手順を残します。GitHub product version の完全一致は
security boundary ではありません。helper は静的 credential 一つを確定し、Workspace
や Broker image には入りません。

## owner static provider を import する

install 済み owner provider manifest は、保護された stdin import だけを使えます。

```sh
trusted-secret-source | tobari auth import example --context default
```

terminal stdin は byte を読む前に拒否します。入力は上限付きで、argv、environment、
output では受け付けません。strict owner-only manifest は secret を含まない非実行
data です。shell、helper、動的 credential operation、remote fetch、任意 route、policy
rule は宣言できません。

## Auth Broker を使う一回のリクエスト

1. Gateway が観測した Workspace source から Context/project identity を導出します。
2. 宣言済み source header の handle を認識して除去します。
3. Broker が secret を返さず Context、project、provider、revision、target、HTTP binding
   を確認します。
4. preset terminal guardrail を candidate 作成より先に評価します。terminal denial では
   candidate、DNS、Broker resolution、upstream call がすべてゼロです。
5. OPA が body、handle、secret を含まない通常の完全一致 HTTP effect を判断します。
6. allow 後だけ、Broker が同じ static revision を一度解決します。Gateway は宣言済み
   header だけを置換し、完全一致 HTTPS 接続を一度だけ試みます。

不正、copy 済み、古い、位置違い、binding 不一致の handle は policy より前に失敗し、
passthrough や別の credential mode へ fallback しません。

## 置換と logout

Context/provider credential を置換すると過去の handle はすべて失効します。新しい
project 固有 projection を受け取るには Workspace へ入り直します。logout は local
state と handle を削除しますが、provider への連絡や実行中 process の書き換えはしません。

```sh
tobari auth logout github --context default
tobari auth status --context default
```

## 失敗時の動作

- `auth_login_tty_required`: 信頼するホストの terminal で login します。
- `invalid_credential_input`: 信頼する non-terminal value 一つを pipe します。
- `auth_broker_locked` / `auth_broker_unavailable`: cluster readiness を回復します。
- `root_key_missing_with_vault`: 元の root key を復元し、代替鍵を生成しません。
- `credential_handle_invalid` (`403`): Context/provider を直して入り直します。
- mutation outcome fault では replay 前に `auth status` で reconcile します。

## 保証と制限

Broker primary secret は Workspace、OPA、log、output の外に残ります。handle は
project-bound、revision は検証済み、resolution は policy allow 後の完全一致で、不正
handle に fallback はありません。V1 は dynamic credential operation、Context ごとの
複数 account、remote logout、同じ Workspace 内 process 間の分離を提供しません。

## まとめ

ツール自身の認証は Workspace が所有します。V1 の Broker 認証は静的で、明示的な
GitHub 取得または strict owner stdin import、bound opaque handle、deny-before-resolution、
allow 後の完全一致置換一回だけです。
