---
title: 認証
description: 各エージェント CLI のネイティブログインを Workspace 内で使い、認証情報とネットワーク権限を分離します。
---

Tobari では認証とネットワーク認可は別です。ログインの成功はアカウントを
特定しますが、HTTP effect を許可しません。

## release surface の認証モデル

release surface には Tobari 所有の認証 command や credential service が
ありません。Workspace に入り、エージェント CLI の
公式ログインを使います。

```sh
cd /path/to/project
tobari

# Inside the Workspace
claude
# or
codex login
# or
gh auth login
# or
aws sso login --profile your-profile
```

Claude Code と Codex はローカルでビルドされる agent-ready base に含まれます。
ネイティブ認証状態はその Workspace の永続 home に保存されます。`exit` や
container 再作成後も残り、別の Workspace とは共有されず、`tobari delete` で
削除されます。

Tobari は host home、host CLI のログイン状態、Keychain、SSH agent、認証用
環境変数を Workspace にコピーしません。

## リクエスト境界

同じ Workspace 内の全プロセスは、その Workspace の認証情報を読めます。
Gateway はどの実行ファイルが認証情報を作成・利用したかを推測しません。

1. Gateway が host 所有の Workspace Manifest/project principal を導出します。
2. 認証情報と cookie を OPA input と audit から除外します。
3. OPA が scheme、host、port、method、path の正確な effect を判断します。
4. deny では認証情報もリクエストも upstream に到達しません。
5. allow 後だけ元の header を一度の upstream 試行へ渡します。

固定の agent-ready compatibility baseline は Claude/Codex のログイン、アカウント、model、core の
有限な exact effect を含みます。native readiness が enabled の Workspace Manifest に
trusted binary が適用します。これは Workspace Manifest 全体の HTTP 権限であり、
実行ファイルの identity ではありません。plugin、connector、MCP、download、
未定義 route は引き続き deny または review 対象です。

## ネイティブログインの回帰

Claude Code は platform hello と token exchange の後、Anthropic の roles と
profile を取得します。Tobari は pinned client に必要なこれらの effect を
明示的に許可します。認証済み profile request も通常の passthrough であり、
bearer は OPA/audit に入らず、allow 後だけ保持されます。provider 所有の
`subscriptionType` と `rateLimitTier` は解釈・置換されないため、`/status` は
ネイティブの account type を表示できます。

Codex の browser login は OAuth token exchange を使います。device-code 方式は
user-code と token polling endpoint も使い、同じ post-policy passthrough 境界を
通ります。

pinned GitHub CLI 2.96.0 では、attached session が厳密な GitHub.com の web
application fallback を host browser と選択済み Workspace の localhost listener
へ bridge します。Enter、OAuth state、exchange、credential storage は引き続き
GitHub CLI が所有します。この bridge は policy permission を追加しません。
GitHub Enterprise、custom scope、SSH key upload は対象外です。

pinned AWS CLI では、attached session が default の IAM Identity Center
authorization-code URL と動的な `127.0.0.1/oauth/callback` port を選択済み
Workspace へ bridge します。PKCE、token exchange、cache は引き続き AWS CLI が
所有し、この bridge は AWS の network permission を追加しません。local callback
が利用できない場合は `aws sso login --use-device-code --profile your-profile` で
再試行できます。

## ログイン通信が deny された場合

Workspace Manifest policy の外側にある effect は、別の trusted-host terminal から通常の permission loop で
扱います。

```sh
tobari review permissions
```

正確な送信先を確認し、意図した effect だけを allow して、実行中の Workspace
で再試行します。ログインは policy rule を作らず、policy approval はログインを
実行しません。

## 保証と限界

release surface の Tobari は host 管理の認証情報を Workspace に入れず、Workspace の
認証情報を OPA、audit、denial output、log に出しません。同じ Workspace 内の
相互に敵対するプロセスの分離、すでに許可された認証済み capability の利用防止、
remote logout、provider credential schema の解釈は提供しません。

## まとめ

provider 公式のログインを Workspace 内で実行します。Workspace がネイティブ
認証情報を所有し、Gateway がその HTTP effect を外へ出せるかを決めます。
