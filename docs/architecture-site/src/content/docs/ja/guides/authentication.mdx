Tobari では、認証とネットワーク通信の許可を別々に扱います。ツールごとに認証方式を一つ選び、通常の HTTP 操作はポリシーで別に許可します。ログインまたはインポートが成功しても、ネットワークの許可規則は追加されません。

このガイドでは、三つの認証方式、レビュー済みの組み込み Broker を使う流れ、ハンドルの結び付け、認証情報の更新やログアウト後の復旧を説明します。先に[リクエストの流れ](../../how-it-works/request-journey/)と[Context](../contexts/)を確認してください。

## 三つの認証方式を比較する

| 方式                     | 実物の認証情報の場所                                         | Workspace が読めるもの                     | Gateway の動作                                                        | 主な制限                                                   |
| ------------------------ | ------------------------------------------------------------ | ------------------------------------------ | --------------------------------------------------------------------- | ---------------------------------------------------------- |
| Tool-native passthrough  | Workspace の永続ホームまたはプロセス内にあるツール所有の状態 | ツールの実物の認証情報                     | 認証情報と Cookie を OPA 入力や監査から除き、許可後に転送します       | 同じ Workspace 内のプロセスから認証情報を利用できます      |
| Auth Broker              | インストールルート鍵で保護された暗号化済み Context 保管庫    | プロジェクトに結び付いたランダムなハンドル | 秘密情報なしで結び付けを確認し、OPA の許可後に解決・更新・署名します  | 静的な完全一致の結び付けと、レビュー済みプランに限られます |
| Retained managed adapter | Context ごとの所有者専用ホスト保存領域                       | managed 方式の実物の秘密情報は読めません   | Context、プロジェクト、ホストプロファイルを検証し、許可後に注入します | 汎用のプロバイダープログラムではありません                 |

どの方式でも OPA 規則は必要です。「リクエストへ認証情報を付けられること」と「この Context、プロジェクト、メソッド、パスへの通信が許可されること」は別の保証です。

## ツール自身による認証

Workspace へ入り、ツールが標準で提供するサポート対象のログインを使います。状態は Workspace の永続ホームに保存され、`exit`、コンテナの喪失、ランタイムの再ビルド後も残ります。`tobari delete` で Workspace とともに削除されます。

Tobari はホストのホーム、Keychain、SSH エージェント、認証情報を含む環境変数、一般的な CLI 設定を Workspace へコピーしません。ツール自身が保存した状態は、同じ Workspace 内の別プロセスから読めます。

## まずプロバイダー、次に利用するツール

認証情報を取得するプロバイダーと、それを使う Workspace 内のクライアントツールは別の概念です。Tobari は、取得方法、ハンドルの投影、完全一致のリクエスト結び付け、クライアントを一つの対応関係としてサポートします。現在のレビュー済み組み込みプロバイダーに対応するツールは、それぞれ一つだけです。そのため CLI ではプロバイダーを選び、対応するツールが表示されて自動的に選択されます。不要な `--tool` 入力はありません。

## レビュー済みの組み込み認証

レビュー済みヘルパーは GitHub、二つの AWS ログインメソッド、Datadog US1 pup OAuth です。GitHub では信頼するホストで実行します。

```sh
tobari cluster up
tobari auth status --context default
tobari auth login --context default # choose an installed reviewed provider
tobari auth login --provider github --context default
tobari auth status --context default
```

ログインは、信頼するホストの対話型ターミナルで行います。省略可能な `--provider` を指定しない場合、インストール済みでレビュー済みのログイン用プロバイダーだけがメニューに表示されます。各行には、自動選択される Workspace 内のクライアントツールも表示されます。`--provider` を明示するとメニューは表示されません。AWS 専用の `--method` フラグを使うには `--provider aws` が必要です。Tobari は、識別情報を確認した GitHub CLI を、固定された引数列、無害化した非公開設定、上限付きの出力投影、検査付きの後始末という条件で実行します。Gateway と Auth Broker が `gh` を実行することはありません。取得した静的な値は Broker の制御境界を通じて保存され、CLI 出力には現れず、安定した Context 保管庫内で暗号化されます。

その Context に永続的に結び付けられた Workspace から退出し、再入室します。

```sh
tobari --context default
```

Workspace はプロジェクトごとに異なる `tobari-h1_...` ハンドルを受け取ります。組み込み GitHub マニフェストでは、サポート対象の GitHub CLI API 通信に使うため投影されますが、外部サービスへ送るトークンそのものではありません。Broker の Git 認証情報ヘルパーを使う非公開 Git 通信には、現在対応していません。

AWS では、信頼するホスト上で明示的に方式を一つ選びます。

```sh
tobari auth login --provider aws --method identity-center --context default
# or, with AWS CLI 2.32 or newer:
tobari auth login --provider aws --method console --context default
```

Identity Center 方式では、レビュー済みの商用環境用開始 URL、SSO リージョン、12 桁のアカウント ID、ロールを受け取り、固定されたデバイスログインを実行します。Console 方式では商用リージョンを一つ指定します。検証済みのデバイス間 URL だけを開き、AWS CLI はターミナルの `stdin` から通信許可コードを読み取ります。どちらも隔離した一時ホームを使い、互いに区別でき、サイズに上限のある不透明な AWS 状態だけを暗号化します。再入室後、Workspace の三つの AWS 認証情報変数には同じプロジェクトハンドルが入り、アクセス鍵の実体は入りません。リクエスト先のリージョンは、通常の Context またはコマンド設定で指定します。

Datadog では `tobari auth login --provider datadog --context default` を実行します。Tobari は非公開のファイル保存ホームで、固定されたホスト側の `pup --no-agent auth login --site datadoghq.com` を呼び出します。ブラウザーでの同意とループバックコールバックは pup が処理します。再入室後、Workspace は `DD_ACCESS_TOKEN=<project handle>` と固定された `DD_SITE=datadoghq.com` を受け取ります。有効なアクセストークンは OPA の許可後にだけ選択されます。有効期限が近い場合、Broker は固定された US1 の更新を一度だけ行い、置き換えた暗号化状態を保存します。Broker に pup はインストールされません。

## Auth Broker を使う一つのリクエスト

1. Gateway が受信側インターフェースから Context とプロジェクトプリンシパルを導出します。
2. プロバイダーが宣言したハンドルを完全一致の元ヘッダーで認識し、取り除きます。
3. Broker は秘密情報を返さずに、Context、プロジェクト、プロバイダー、認証情報のリビジョン、対象、ヘッダーの結び付けを確認します。
4. Gateway が通常の本文を含まない HTTP 操作について OPA へ問い合わせます。
5. 拒否された場合はここで停止します。認証情報の解決、Datadog トークンの選択や更新、AWS 認証情報コンパニオンの呼び出しや署名、外部の接続先への接続はいずれも行いません。
6. 静的認証情報を使う許可では、Gateway が同じリビジョンを一度だけ解決し、宣言されたヘッダーを置き換えます。
7. AWS の許可では、Gateway が許可済みの完全なリクエストを 8 MiB 以内で保持します。Broker は認証済みの非公開ホスト側コンパニオンを使い、固定された AWS CLI の認証情報エクスポートを一度実行します。リビジョンを再確認して保存し、標準ヘッダーを使う SigV4 署名をローカルで行います。
8. Datadog の許可では、十分な有効期間が残るトークンを選びます。必要な場合は、プロキシとリダイレクトを使わない、完全一致の US1 トークンエンドポイントで同じ記録を一度だけ更新します。Bearer 値を返す前に状態を保存します。
9. Gateway が完全一致の HTTPS 接続先へ一度接続します。リクエストは再実行しません。

Workspace A の有効なハンドルを B へコピーしても、ホストから導出したプロジェクトプリンシパルが一致しないため失敗します。認証情報の置換やログアウト後の古いリビジョンも失敗します。形式が不正、場所が誤っている、曖昧、結び付けが一致しない Tobari 形式のハンドルは拒否されます。Gateway が通常の認証情報としてそのまま転送することはありません。

## インストール済みスキーマ 1 プロバイダーへのインポート

所有者が管理するプロバイダーマニフェストは `stdin_import` を宣言できます。保護された、ターミナルではない `stdin` から認証情報を一つ渡します。

```sh
trusted-secret-source | tobari auth import example --context default
```

`example` はインストール済みのプロバイダー ID である必要があり、コマンドがマニフェストを作ることはありません。ターミナルの `stdin` は、1 バイトも読み取る前に拒否されます。認証情報の入力サイズには上限があり、コマンドライン引数、環境、出力からは受け取りません。利用者マニフェストでは、実行可能ヘルパー、リクエスト署名、更新、任意の経路、メソッドやパスのポリシーを追加できません。

## ローテーションとログアウト

Context とプロバイダーの認証情報を置き換えると、以前に発行したハンドルはすべて失効します。実行中のプロセスには古い環境変数が残りますが、その値は無効です。プロジェクトごとの新しいプロジェクションを受け取るには、いったん退出して再入室します。

ローカル Broker 状態を削除するには次を実行します。

```sh
tobari auth logout github --context default
tobari auth status --context default
```

ログアウトはローカルのプロバイダー記録を削除し、ハンドルを失効させます。GitHub には接続せず、リモートトークンの失効は保証しません。すでに実行中のプロセス環境も書き換えられません。次回の入室時にプロジェクションが削除されます。`cluster down --purge` はログアウトの代用ではなく、保管庫とルート鍵を保持します。

## 失敗時の動作

- `auth_login_tty_required`: 信頼するホストの対話型ターミナルでログインします。
- `invalid_credential_input`: 信頼できる値を一つ、ターミナルではない入力からパイプまたはリダイレクトで渡します。
- `auth_broker_locked` / `auth_broker_unavailable`: ホストで `tobari cluster up` を実行し、`tobari auth status` を確認します。
- `root_key_missing_with_vault`: 元のルート鍵を復元します。既存の暗号化状態に対して別の鍵を生成したり代入したりしません。
- `auth_vault_invalid`: 保管庫の内容を表示または書き換えず、完全性を診断します。
- `invalid_provider_manifest` / `ambiguous_provider_http_binding`: 厳格なマニフェスト一覧を全体として修正します。プロバイダー投影の一部だけを有効化することはありません。
- `credential_handle_invalid` (`403`): 一致する Workspace を出て再入室します。コピーしたハンドルや古いハンドルを転送しません。
- `credential_broker_unavailable` (`503`): 実行開始前に判明した可用性障害です。Broker とコンパニオンの状態を調整し、準備完了を確認した後にだけ再試行します。アプリケーションから外部の接続先への接続は行われていません。
- `credential_refresh_outcome_unknown` (`409`): 自動で再実行しません。元のリクエストの処理が終了した後、`auth status` を確認します。`ready` または `configured` なら、Gateway はアプリケーションから外部の接続先へ接続していないため、明示的に再試行できます。`not_configured` では継続的な障害が残るため、対象の AWS または Datadog プロバイダーへ再ログインするかログアウトし、退出・再入室してから再試行します。
- `auth_mutation_outcome_unknown` または変更操作後の出力障害: 別のログイン、インポート、ログアウトを行う前に `auth status` を確認します。状態を確認せずに再実行すると、確定済みの状態を重ねて更新または削除する可能性があります。

## 保証と制限

Broker は静的または更新可能な認証情報の状態を Workspace のファイルや環境と OPA の外に保ちます。ハンドルを完全一致の権限に結び付け、秘密情報を扱う操作は許可後にだけ実行します。同じ Workspace 内の悪意あるプロセス同士は分離しません。すでに許可された権限の利用を止めず、リモートログアウトも行いません。Context ごとの複数アカウントや、レビュー済みの AWS/Datadog プラン以外の更新、署名、OAuth には対応しません。

## まとめ

認証はリクエストへ付ける認証情報を提供しますが、各 HTTP 操作は OPA による通信許可で制御されます。Broker を使う Workspace が持つのは、用途を狭く結び付けた不透明なハンドルです。許可された Gateway の経路だけが、宣言済みの静的認証情報の解決、AWS 署名、Datadog トークン操作を開始できます。
