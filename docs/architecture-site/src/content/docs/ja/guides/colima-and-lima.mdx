---
title: Colima と Lima
description: Workspace のマウント範囲を広げず、プロジェクトと Tobari の状態パスを VM 上の Docker デーモンから参照できるようにします。
---

Docker が Colima または Lima VM 内で動いている場合、ホスト上に存在するパスでも Docker デーモンから見えないことがあります。選択したプロジェクトルートと Tobari の XDG 設定・状態パスを含め、すべてのバインド元をデーモンから参照できるようにしてください。

先に Tobari をインストールし、使用する Docker コンテキストを選択してください。Tobari は標準の Docker CLI アダプターを使い、Docker Desktop API には依存しません。以下の手順では、ホストのホーム全体を Workspace へマウントせずに VM の共有設定を修正します。

## パスが見える必要がある理由

CLI は信頼するホストで動きますが、選択した Docker デーモンは VM 内にある場合があります。CLI から存在するパスが VM 内にはない、または異なる場所にマウントされることがあります。

デーモンから次が見える必要があります。

- Workspace が読み書きする、選択済みの正規化されたプロジェクトルート
- サービスが使うホスト所有のポリシーと生成済みプロジェクションを含む `${XDG_CONFIG_HOME:-$HOME/.config}/tobari`
- ランタイムの具体化、プリンシパルレジストリ、Workspace 状態、host-owned lifecycle state を含む `${XDG_STATE_HOME:-$HOME/.local/state}/tobari`
- Docker 自身がアクセスする必要がある明示的なカスタムイメージ/ビルドソース

別シェルアカウントから推測せず、Tobari を呼ぶホストプロセスの環境を確認します。

```sh
printf '%s\n' "${XDG_CONFIG_HOME:-$HOME/.config}/tobari"
printf '%s\n' "${XDG_STATE_HOME:-$HOME/.local/state}/tobari"
pwd -P
```

## VM の境界を設定する

使用中のバージョンに対応する Colima または Lima の文書に従い、必要な親パスをそのまま VM へ公開します。Tobari がプラットフォーム固有のマウント設定を別のコマンドで隠すことはありません。

次を含む、最も狭く安定した共有親ディレクトリを選びます。

1. 対象のプロジェクト
2. 実際に使われる Tobari 設定ディレクトリ
3. 実際に使われる Tobari 状態ディレクトリ

デーモンからバインド元のパスが見える必要はありますが、Workspace が受け取るのは選択したプロジェクトのマウントと自分のホームだけです。Docker VM とパスを共有しても、そのパス全体を Workspace へマウントすることにはなりません。

## Workspace に入る前に検証する

対象のプロジェクトディレクトリから実行します。

```sh
tobari doctor
tobari cluster status
```

`doctor` は Workspace を作らず、ホスト側のパスが有効か、Docker のバインド設定に問題がないかを報告できます。VM の共有設定を直したら明示的に調整します。

```sh
tobari cluster up
tobari
```

復旧手段としてルート入室を繰り返さないでください。ルートの `tobari` コマンドは共有クラスターが準備済みであることを要求し、暗黙には起動しません。

## よくある症状を区別する

| 症状                                                            | 考えられる境界                                     | 確認するもの                                                                     |
| --------------------------------------------------------------- | -------------------------------------------------- | -------------------------------------------------------------------------------- |
| 結び付けソースがない、または共有されていないと Docker が報告    | VM のファイルシステム共有                          | プロジェクトと、実際に使われる XDG 親ディレクトリ                                |
| Workspace は起動するが HTTP リクエストが `403`                  | Gateway/OPA ポリシーまたは upstream の応答         | VM マウントではなく `tobari review permissions`                                  |
| Workspace が Gateway の TLS を信頼できない                      | クライアントの CA とプロキシ動作                   | ツールが注入された CA 変数を使うか。証明書ピンニングは意図的に失敗する場合がある |
| クラスターコンポーネントからポリシー/プロジェクションが見えない | XDG 設定または状態の結び付けが見えるか、その所有権 | `doctor`、`cluster status`、コンポーネントログ                                   |
| レジストリイメージが利用不可                                    | Docker VM レジストリ/ネットワークパス              | Docker コンテキストとレジストリへのアクセス。ポリシー規則は変更しない            |

## 障害と安全な復旧

- 対象の Workspace が停止中の間に VM の共有設定を直します。
- `tobari doctor` を再実行します。警告が表示されても変更操作は行われません。
- パスが見えるようになった後、`tobari cluster up` でサービスを調整します。
- 作成途中の論理 Workspace が残る場合は `tobari status` を確認します。ランタイムの `missing` または `degraded` は、次の有効な入室で調整できます。`incomplete` は削除による後始末だけが許される状態なので、`tobari delete` で削除します。
- 結び付けエラーを解決するために Workspace の状態、host-owned lifecycle state、CA 状態を削除しないでください。
- ホストネットワーク、特権モード、Docker ソケットのマウント、ホストホームを広く公開する Workspace マウントを追加しないでください。

## 保証と制限

Tobari は作成するランタイム構成を検証し、必須の結び付け元を利用できなければセットアップを失敗させます。すべての VM 製品やバージョンを設定したり、共有されていないホストパスをデーモン内から見えるようにしたりはできません。Colima、Lima、ホストのファイルシステムは、引き続き信頼基盤の一部です。

## まとめ

VM 上のデーモンから、指定したホストの結び付け元がそのまま見える必要があります。そのデーモン境界を直した後も、Tobari がランタイムへ公開するのは選択したプロジェクトと Workspace ホームだけです。

## 理解を確認する

<details>
  <summary>
    シェルからプロジェクトが見えるのに Docker が無効な結び付け
    を報告します。どちらから見えることが重要ですか？
  </summary>
  両方で解決できる必要がありますが、失敗しているのは VM 内の選択した Docker
  デーモンからの見え方です。共有パスを設定し、`doctor` を再実行します。
</details>

<details>
  <summary>
    XDG 状態の親ディレクトリを VM と共有すると、Workspace は host-owned
    lifecycle state を読めますか？
  </summary>
  いいえ。サービスマウントは狭く指定され、Workspace に親ディレクトリや
  host-owned lifecycle state のファイルは渡りません。VM
  から見えるホストパスを広げても、 Tobari のコンテナマウント契約は変わりません。
</details>
