---

通常はガイド付きポリシー学習を使います。完全一致の許可・拒否では表現できないポリシーをホスト側で管理する必要がある場合だけ、高度な Context を選びます。Rego ソースとテストを一緒に保ち、クラスター全体を明示的に検証してから変更を有効化します。

これは通常の拒否を処理するための経路ではありません。先に[ポリシーレビュー](../policy-review/)と OPA/Rego を理解してください。

## ガイド付きポリシーと高度なポリシーでは、管理方式が異なる

| ガイド付き Context                                   | 高度な Context                                               |
| ---------------------------------------------------- | ------------------------------------------------------------ |
| `policy/domains/<host>/{allow,deny}.json` だけを所有 | domain tree、`tobari.rego`、`tobari_test.rego` を所有        |
| Tobari が所有する現在の共有評価器を使用              | 保守担当者が Context 固有のポリシーロジックとテストを所有    |
| 通常は完全一致の許可・拒否、リセット、集約を使う     | 通常のモデルで不足する場合、信頼するホスト上で直接編集できる |
| Tobari のリリースに合わせて共有評価器が更新される    | 保守担当者が互換性と動作をレビューする                       |

どちらのモードでも Workspace は有効なポリシーを編集できません。Context のポリシーディレクトリは所有者だけがアクセスできるホスト状態であり、Workspace へマウントされません。

## 高度なポリシーを使う Context を意図的に作る

```sh
tobari context create --name policy-lab --mode advanced
tobari context show --name=policy-lab --format=json
tobari context use --name policy-lab
```

`context show` が報告した完全一致の保存領域パスを使います。親の Tobari 設定ディレクトリを Workspace へマウントせず、ポリシーディレクトリに認証情報をコピーしないでください。

作成しても実行中のクラスターは変わりません。新しい Context を使う前に明示的に調整します。

```sh
tobari cluster up
```

## domain data を完全一致に保つ

どちらの mode も、同じ人間が編集できる domain source を使います。正規化済みの小文字
host ごとに、所有者だけがアクセスできるファイルを正確に二つ置きます。

```text
policy/domains/api.example.com/
  allow.json
  deny.json
```

`allow.json` の field は `schema_version`、`host`、`authorities`、`methods`、
`graphql_endpoints`、`credential_profiles`、`rules` だけです。`deny.json` の
field は `schema_version`、`host`、`baseline_rules`、`rules` だけです。collection
はすべて明示的な JSON array です。未知の field、重複 key または rule ID、欠落 field、
余分なファイル、symlink、group/world が使える permission は拒否されます。

directory 名と、authority、GraphQL endpoint、credential binding、baseline rule、
learned rule 内のすべての host は完全一致する必要があります。hostname は正規化済みの
小文字 DNS 名です。末尾 dot、IP literal、大文字表現、wildcard は未対応であり、現在の
契約は exact host のみです。HTTP method は大文字で、その domain から合成された
authority だけに属します。ある host の method 許可が別 host を許可することはありません。
明示的な deny は引き続き優先されます。

host を手作業で追加するときは、非公開の sibling directory に両方のファイルを完成させ、
directory ごと `domains/` へ rename してください。片方だけを公開しないでください。既存の
一ファイルを編集する場合は atomic rename で保存する editor を使います。`cluster up` は
安定した完全 snapshot を再読し、不完全または変更中の source を fail closed にします。
通常の CLI policy mutation は未変更ファイルの byte を保ち、cross-process lock と永続
recovery journal の下で完全な `domains/` 世代を入れ替えます。

## ソースとテストを一緒に編集する

信頼するホストで、報告された `policy/tobari.rego` と `policy/tobari_test.rego` を編集します。安定した公開判断契約を保ち、意図した一致を確認するテストと、不適切な推論を検出するカナリアテストを追加します。

高度なポリシーのソースは、安定した Context ID から導出される隔離されたパッケージへ投影されます。次の名前空間を使おうとすると検証で拒否されます。

- クラスターが所有する `tobari.http/decision` ルーター
- 予約済みの `tobari.system` パッケージ
- 別 Context の名前空間
- 集約ポリシー Context データ名前空間

これは一つの信頼する OPA プロセス内で経路と名前空間を強制する仕組みです。Rego モジュール間をプロセスレベルで秘匿する仕組みではありません。

## 明示的に検証して有効化する

有効化前に読み取り専用の診断を使います。

```sh
tobari doctor
tobari cluster logs --component opa --tail 100
```

`doctor` は観測だけを行い、ソースの編集内容を有効化しません。すべての Context を含むプロジェクションを再生成し、テストして有効化するには、明示的なクラスター調整を実行します。

```sh
tobari cluster up
```

プロジェクションには、固定ルーター、Context ID ごとのデータ名前空間、共有のガイド付き評価器、書き換え済みの高度なパッケージが含まれます。すべてのソースと集約ポリシー全体がテストに合格する必要があります。有効な候補だけが公開され、障害時には以前の検証済み集約ポリシーが引き続き有効です。

通常の完全一致の許可・拒否・リセット操作も、同じ全 Context の安全境界を使い、対応 host の `allow.json` または `deny.json` にある学習済み `rules` だけを変更します。ホスト側で管理する境界ポリシーや任意の Rego は書き換えません。内容アドレス方式で生成する OPA projection の内部には `data.json` がありますが、Context source ではありません。

## 高度なポリシーが適切な例

信頼する保守担当者が、完全一致のパス規則では表現できない、秘密情報を含まないリクエストメタデータから有限の規則を作る必要があるとします。

1. 完全一致のレビューでは不足する理由を記録する
2. 一つの高度な Context に最小限の Rego 条件を書く
3. 許可すべき入力のテストデータと、不適切な推論を検出するカナリアを追加する
4. 集約ポリシー内のすべての Context を検証する
5. 合成した拒否対象と許可対象のリクエストで、最終的な動作を確認する

高度なモードを、プロバイダー SDK、リクエスト本文の読み取り、シェル実行、認証情報の読み込み、Gateway/Auth Broker 境界の迂回に使わないでください。Rego が受け取るのは正規化された判断データであり、任意の処理を実行する権限ではありません。

## 失敗時の動作

- 無効な Rego、テスト障害、禁止されたパッケージ、スキーマの不一致があると有効化されません。
- ソースの一部だけを編集しても、集約ポリシーの一部だけが有効になることはありません。
- OPA の監視やヘルスチェックに障害がある場合、リクエストは安全側に閉じて拒否されます。可用性を優先して許可することはありません。
- `cluster up` が Context ソース障害を報告したら、その完全一致の Context を直してから再試行します。
- 完全一致のポリシー変更操作とホスト編集が競合した場合、内容とリビジョンの検査で古い状態を拒否します。推測でマージすることはありません。
- 有効な Rego テストスイートが証明するのは、宣言したテストケースだけです。将来現れる未知の URL がすべて安全だとは証明しません。

## 保証と制限

Tobari はルーターと Context 名前空間を予約し、プロジェクション全体をテストしてアトミックに公開します。障害時には検証済みポリシーを保持します。高度な規則の意味と完全性は保守担当者の責任です。Tobari はプロバイダー固有の意味を解釈せず、安全なワイルドカードを推論しません。

## まとめ

高度なモードでは、ポリシーロジックの所有権が Workspace ではなく信頼する保守担当者へ移ります。Context 名前空間の強制、プロジェクション全体のテスト、アトミックな有効化は引き続き必須です。

## 理解を確認する

<details>
  <summary>通常の拒否は、最初に Rego を編集して解決すべきですか？</summary>
  いいえ。`policy review`
  と完全一致の許可・拒否を使います。高度なポリシーの編集は
  通常の完全一致モデルで表せない動作のためのものです。
</details>

<details>
  <summary>
    <code>doctor</code> は編集した Rego ファイルを有効化しますか？
  </summary>
  いいえ。観測だけを行います。明示的なクラスター調整またはサポート対象の
  完全一致のポリシー変更操作が、検証済みポリシーの有効化を担います。
</details>

<details>
  <summary>高度な Rego は Auth Broker へ認証情報を要求できますか？</summary>
  いいえ。OPA が判断するのは、正規化され、秘密情報を含まない HTTP
  メタデータです。許可後の Broker 解決は Gateway が担います。
</details>
