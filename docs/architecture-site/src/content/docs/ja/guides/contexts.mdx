Context は、ランタイム、ポリシー、エージェント設定、認証情報の設定を分けて管理する単位です。信頼するホストで作成し、`--context` を省略したコマンドが使うデフォルトを一つ選びます。デフォルトを変更しても、既存 Workspace は作成時の安定した Context ID に結び付いたままです。

Context、Workspace、共有クラスターの関係は、[Workspace、Context、cluster](../../how-it-works/workspace-context-cluster/)を参照してください。

## 現在の Context 一覧を確認する

信頼するホストで実行します。

```sh
tobari context list
tobari context show
```

`context list` はローカルにあるすべての Context と、現在のデフォルト名を示します。`context show` で `--name` を省略すると、そのデフォルトを確認します。報告には安定した ID、イメージの選択情報、エージェントプロファイル、ポリシーモード、許可済みのシェル設定、保存領域への参照、ランタイム状態が含まれます。実物の認証情報、Broker ハンドル、ルート鍵、保管庫の内容は含まれません。

表示名は Context を選ぶための読みやすい名前です。安定した Context ID は、Workspace、ポリシー、プリンシパル、Broker の記録に結び付く永続的な権限情報です。

## Context を作成する

別のガイド付き Context を作ります。

```sh
tobari context create --name review --mode guided
tobari context show --name=review
```

作成時に所有者だけがアクセスできる Context 保存領域を初期化しますが、Docker の起動、既存 Workspace の変更、共有集約ポリシーの更新は行いません。クラスターがすでに存在する場合、結果には明示的な調整が必要であることが示されます。

```sh
tobari cluster up
```

高度な Context は、信頼するホスト側で Rego を管理するという明示的な選択です。

```sh
tobari context create --name policy-lab --mode advanced
```

通常の完全一致のポリシー学習にはガイド付きモードを使います。高度なモードは Rego とテストを保守できる人向けです。[高度なポリシー](../advanced-policy/)を参照してください。

## 省略時に使う Context を変える

```sh
tobari context use --name review
tobari context show
```

`context use` が変えるのは、ホスト上のデフォルトを示す印だけです。Docker の起動、クラスターの書き換え、Workspace に結び付いた Context の変更、永続ホームの移動、認証情報のローテーションは行いません。

デフォルトを変えずに Context を明示できます。

```sh
tobari --context review
tobari status --context review
tobari delete --context review
```

同じ正規化済みプロジェクトルートでも、`(root, Context A)` と `(root, Context B)` は別の論理 Workspace です。安定したプロジェクト ID、ホーム、コンテナ、ネットワーク、プリンシパル、ポリシー権限、Broker ハンドルは別々です。ただし、どちらも同じホスト上のプロジェクトファイルをマウントします。Context の分離は、ファイルシステムを複製したり重ねたりするものではありません。

## 制限付きのシェル表示を設定する

信頼するホストで、許可リストにある変数を設定します。シェル設定が対応するのは `PS1`、`TERM`、`COLORTERM`、`NO_COLOR` だけです。

```sh
tobari context shell configure --context review --variable PS1 --source inherit
tobari context shell configure --context review --variable COLORTERM --source literal --value truecolor
tobari context shell configure --context review --variable NO_COLOR --source literal --value=
tobari context shell configure --context review --variable TERM --source default
```

`default` は、その Context にある上書き設定を削除します。`inherit` は次にシェルを開始するとき、指定したホスト上の export 済みの値だけを読み取ります。`literal` はサイズに上限のある Context 固有の値を一つ保存し、明示的な空文字列も保持します。Tobari がホスト環境、認証情報変数、起動時ファイル、ホストホームを列挙またはコピーすることはありません。`PATH`、`HOME`、`BASH_ENV`、`ENV`、`PROMPT_COMMAND` は対象外です。

設定変更後は Workspace へ再入室し、新しいシェルを開始してください。実行中のプロセス環境は変わりません。許可されない組み合わせは、変更を行う前にすべて拒否されます。

## 二つの Context の具体例

1. `/work/app` では `default` が Workspace A をすでに所有しています。
2. `review` を作成して選択します。
3. `/work/app` から再び `tobari` を実行し、`review` 結び付けを明示的に作成または選択します。
4. Workspace B は同じプロジェクトファイルと、独自のホーム/プロジェクトプリンシパルを受け取ります。
5. Context ID とプロジェクト ID が異なるため、A の学習済み規則または Broker ハンドルは B を許可しません。
6. デフォルトを `default` へ戻すと、省略されたコマンドは再び A を選びます。B は変わりません。

## 失敗時の動作

- `context_not_found`: `tobari context list` から既存名前を選びます。
- `context_exists`: 上書きせず既存 Context を確認します。
- `invalid_context`: 名前、イメージの選択情報、ポリシーモードを修正します。
- 作成後の `requires_reconcile`: 新しい Context で共有サービスを使う前に、明示的な `tobari cluster up` を実行します。
- `workspace_selection_stale`: `tobari` を再実行します。選択中に候補一覧が変わっています。
- Context イメージが無効または利用不可なら、新しい登録や調整を止めますが、既存の論理 Workspace の状態とホームは保持します。

## 保証と制限

Context の結び付けは安定しており、ホストが所有します。呼び出し元が指定したヘッダーや表示名で権限を切り替えることはできません。Context はポリシー、ホーム、ランタイム選択、プリンシパル、認証情報ハンドルを分けます。一方、同じホストディレクトリに対するファイル変更は分離しません。また、すべての Context が同じ信頼するクラスターサービスを利用します。

## まとめ

Context はホストが所有する設定と安定した権限情報であり、実行中のコンテナや共有クラスターではありません。デフォルトの変更は将来の選択だけに影響し、既存 Workspace が暗黙に Context を変えることはありません。
