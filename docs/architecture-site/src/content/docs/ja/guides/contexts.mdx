Context は、runtime、ポリシー、agent profile、認証情報の設定を分離する単位です。信頼するホストで作成し、`--context` を省略した command が使う default を一つ選びます。default を変更しても、既存 Workspace は作成時の stable Context ID に恒久的に結び付いたままです。

Context、Workspace、shared cluster の関係は、[Workspace、Context、cluster](../../how-it-works/workspace-context-cluster/)を参照してください。

## 現在の Context 一覧を確認する

信頼するホストで実行します。

```sh
tobari context list
tobari context show
```

`context list` は complete local collection を報告し、current/default name を示します。`context show` で `--name` を省略すると、その default を確認します。report には stable ID、image selector、agent profile、policy mode、allowlisted shell setting、store reference、runtime status が含まれます。primary credential、broker handle、root key、vault content は含まれません。

display name は選択に便利な text です。stable Context ID は Workspace、policy、principal、broker record に結び付く durable authority です。

## Context を作成する

別の Guided Context を作ります。

```sh
tobari context create --name review --mode guided
tobari context show --name=review
```

作成時に owner-only Context store を初期化しますが、Docker の起動、既存 Workspace の mutation、shared aggregate の更新は行いません。cluster がすでに存在する場合、result は explicit reconciliation が必要だと報告します。

```sh
tobari cluster up
```

Advanced Context は、信頼するホストが Rego を所有する明示的な選択です。

```sh
tobari context create --name policy-lab --mode advanced
```

通常の exact policy learning には Guided mode を使います。Advanced mode は Rego と test を保守できる人向けです。[Advanced policy](../advanced-policy/)を参照してください。

## 省略時に使う Context を変える

```sh
tobari context use --name review
tobari context show
```

`context use` が変えるのは host marker 一つです。Docker の起動、cluster の書き換え、Workspace Context の変更、persistent home の移動、credential の rotation は行いません。

default を変えずに Context を明示できます。

```sh
tobari --context review
tobari status --context review
tobari delete --context review
```

同じ canonical project root でも、`(root, Context A)` と `(root, Context B)` は別の logical Workspace です。stable project ID、home、container、network、principal、policy authority、broker handle は別です。ただし同じ host project file を mount するため、Context separation は filesystem overlay ではありません。

## 制限付きの shell 表示を設定する

信頼するホストで allowlisted variable を設定します。shell configuration が対応するのは `PS1`、`TERM`、`COLORTERM`、`NO_COLOR` だけです。

```sh
tobari context shell configure --context review --variable PS1 --source inherit
tobari context shell configure --context review --variable COLORTERM --source literal --value truecolor
tobari context shell configure --context review --variable NO_COLOR --source literal --value=
tobari context shell configure --context review --variable TERM --source default
```

`default` はその Context override を削除します。`inherit` は次の shell 開始時に、指定した exported host value だけを読みます。`literal` は bounded Context value 一つを保存し、explicitly empty value も保持します。Tobari は host environment、credential variable、startup file、host home を列挙・copy しません。`PATH`、`HOME`、`BASH_ENV`、`ENV`、`PROMPT_COMMAND` は対象外です。

設定変更後は Workspace へ再 entry し、新しい shell を開始してください。実行中 process の environment は変わりません。rejected combination は mutation 前にすべて失敗します。

## 二つの Context の具体例

1. `/work/app` では `default` が Workspace A をすでに所有しています。
2. `review` を作成して選択します。
3. `/work/app` から再び `tobari` を実行し、`review` binding を明示的に作成または選択します。
4. Workspace B は同じ project file と、独自の home/project principal を受け取ります。
5. Context ID と project ID が異なるため、A の learned rule または broker handle は B を authorize しません。
6. default を `default` へ戻すと、省略された command は再び A を選びます。B は変わりません。

## 失敗時の動作

- `context_not_found`: `tobari context list` から既存 name を選びます。
- `context_exists`: 上書きせず既存 Context を確認します。
- `invalid_context`: name、image selector、policy mode を修正します。
- create 後の `requires_reconcile`: 新しい Context で shared service を使う前に、明示的な `tobari cluster up` を実行します。
- `workspace_selection_stale`: `tobari` を再実行します。選択中に candidate collection が変わっています。
- Context image が invalid または unavailable なら、新しい registration/reconciliation を止めますが、既存 logical Workspace state と home は保持します。

## 保証と制限

Context binding は stable で host-owned です。caller-supplied header または display name で authority を切り替えられません。Context は policy、home、runtime selection、principal、credential handle を分けます。同じ重複 host directory への mutation は分離せず、すべて同じ trusted cluster service を利用します。

## まとめ

Context は host-owned configuration と stable authority であり、running container や shared cluster ではありません。default の変更は将来の選択だけに影響し、既存 Workspace が暗黙に Context を変えることはありません。

    cluster が停止中に <code>context use</code> を実行すると、Docker
    を起動しますか？

  いいえ。Context を検証し、default marker だけを atomically に変えます。
</details>

<details>
  <summary>
    同じ root の二つの Context を、分離されたファイルのコピーと説明できますか？
  </summary>
  いいえ。Tobari state と authority は別ですが、両方が同じ host directory を
  mount するため、file change は共有されます。
</details>

<details>
  <summary>
    Context は shell 設定で任意の <code>SERVICE_TOKEN</code> を継承できますか？
  </summary>
  いいえ。許可されるのは `PS1`、`TERM`、`COLORTERM`、`NO_COLOR`
  だけです。credential environment name は意図的に対象外です。
</details>
