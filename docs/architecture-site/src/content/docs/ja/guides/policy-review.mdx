ポリシーレビューは、保持された拒否の根拠を、ホストが所有する明示的な判断へ変える操作です。Workspace から出て、信頼するホスト上の Permission Inbox で、量を制限した秘密情報を含まない記録を確認します。raw terminal の一覧から完全一致の判断を準備し、テンプレートは詳細画面で将来範囲を確認してから選び、一つの Workspace Template についてレビュー済みの一式を一度だけ Apply します。承認はポリシーを変更しますが、拒否された通信を再試行しません。

Workspace の attachment は維持したまま、Permission Inbox は別の信頼するホスト端末で開きます。Tobari は `Ctrl+]` などの子プロセス入力 shortcut を予約せず、shell や full-screen program の terminal presentation を置き換えません。

[最初の拒否](../../start/first-denial/)では、リクエストの拒否からこのホスト側のレビューフローまでを説明しています。

## 1. 再試行を止め、Workspace から出る

学習可能な Gateway `403` は、ホストで `tobari review permissions` を実行する固定案内を含みます。候補 ID はなく、エージェント自身を承認する手段を与えません。

レビュー前に Workspace を出ます。繰り返しの再試行は権限を増やさず、同じ許可対象の上限のある根拠を更新するだけです。

## 2. 人向けのレビューフローを開く

```sh
tobari review permissions --tail 100
tobari review permissions --watch
# Disable or explicitly choose its terminal-emulator cue:
tobari review permissions --watch --notify=off
```

インストール全体を対象とする TTY キューには、取得件数を制限した Gateway ログから、保留中の通信候補が表示されます。一つを選び、次を確認します。

- Workspace Template と安定した Workspace Template ID
- プロジェクトとルート、およびホストが発行したプロジェクトプリンシパル
- スキーム、ホスト、ポート
- メソッドと正規化されたパス
- 拒否理由、時刻、保持された観測回数
- 提案される完全一致の許可または拒否

raw terminal の一覧で **a** または **d** を押すと **Allow exact** または **Deny exact** を準備し、**x** で一行の判断を解除します。完全一致の準備後は後方の未判断行だけへ進み、末尾から折り返しません。根拠の精査や、提案されたテンプレートの例と将来範囲の承認には詳細画面を開きます。どの選択も準備状態であり権限を与えません。同じ Workspace Template の候補を続けて確認し、最後に **p** を押して **Apply** を確認し、一式全体を再検証して一度だけ有効化します。Apply の前にキャンセルすると、準備した選択はすべて破棄されます。Workspace Template を切り替える前に Apply または破棄してください。これにより、ソース更新が一つの journal で保護された domain 世代置換に収まります。

`--watch` は text 出力と対話型 raw terminal を必要とします。同じ上限付き snapshot を自動更新し、不透明な型付き ID でフォーカスと準備済み判断を保ち、古くなった判断を報告し、読み取り失敗時には backoff し、Apply 成功後も開いたままになります。Apply と Apply の間は一つの alternate-screen frame を保ち、変更のない timer refresh では再描画しません。拒否された通信を再試行することはありません。

`--notify=auto|osc9|bel|off` は、以前に見ていない型付き review item が一つ以上追加された成功 refresh の注意喚起を選びます。初回 snapshot と既知 ID の再表示は通知せず、一回の refresh は最大一回だけ通知します。`auto` は iTerm2 の正確な識別、または保護された workspace identity と surface identity の両方を持つ cmux terminal では OSC 9 を使い、それ以外は BEL へ fallback します。payload は固定された信頼済み ASCII だけで、拒否の根拠を含みません。Tobari は OS、tmux、SSH の passthrough を設定しません。

## 3. 必要な場合だけ機械向けの経路を使う

リダイレクトされた環境でのレビューは読み取り専用です。

```sh
tobari review permissions --tail 100 --format json
```

出力された不透明な `pcy_...` ID を変更せず、一つの操作へコピーします。

```sh
tobari policy allow --id <pcy-id>
# or
tobari policy deny --id <pcy-id>
```

ID をデコード、正規化、再構成したり、未検査の表示文字列を付け足したりしないでください。操作時には、現在保持されている根拠を使って ID を解決します。古い参照や期限切れの参照は、類似リクエストを推測せずに失敗します。

`tobari policy candidates --format json` は機械向けに構造化された候補一覧を返し、状態を変更しません。

## 4. 有効化の仕組みを理解する

一度のレビュー済み Apply は次を行います。

1. 最新のキュースナップショットで、保持された参照をすべて解決する
2. ポリシー生成処理をロックする
3. 所有する Workspace Template 一つの学習済みデータだけを変更する
4. 非公開の Workspace Template ソースを検証する
5. すべての Workspace Template を含む完全な集約ポリシーを生成し、テストする
6. リビジョンを持つ完全なバンドルを一つ公開する
7. 実行中の OPA が完全一致のリビジョンを報告するまで待つ
8. リクエストを再実行せず確定した判断を報告する

検証または有効化の手順が一つでも失敗すれば、Tobari は以前の検証済み集約ポリシーを保持または復元します。新しい規則を部分的に有効化することはありません。

## 5. 意図的に再試行する

確定した許可後、一致する Workspace へ再入室して新しいリクエストを送ります。古い拒否されたリクエストはすでになく、Gateway は本文をキュー/再実行しません。

完全一致 rule は一つの Context が所有し、observed Workspace、scheme、host、port、method、path に結び付きます。body、timestamp、display order、request ID、credential label によって authority が広がったり分割されたりすることはありません。

## 現在のポリシーを修正する

```sh
tobari policy rules
tobari policy reset --id <policy-rule-id>
```

リセットは、CLI が管理する学習済みの判断を一つだけ削除し、その通信候補をデフォルト拒否へ戻します。許可する操作でも、リクエストを再試行する操作でも、基本ポリシーを編集する操作でもありません。

first public V1 では学習済み規則をすべて完全一致のまま保ちます。完全一致規則を
exact rule を広げる操作や休止中 fallback はありません。

## 失敗時の動作

- 空のキュー: 指定期間内に、有効かつ保留中の学習可能な拒否がありません。過去に拒否がなかったことまで証明するものではありません。
- 基本拒否または現在の完全一致の拒否: 監査根拠には残りますが保留中候補ではありません。
- スキーム、プリンシパル、クラスター、principal registry の結び付けに関する障害: 効果のない完全一致規則を作って学習対象にすることはできません。
- `policy_candidate_not_found` または古い規則参照: 現在の状態から候補を取り直し、古い参照を再利用しません。
- `policy_test_failed` または事前検査の障害: 所有者だけがアクセスできるポリシーと OPA の診断を確認します。それまでのポリシーが引き続き有効です。
- 結果が不確実な変更操作: 別の変更操作を行う前に、`tobari policy rules` と `tobari cluster status` で状態を調整します。

## 保証と制限

通常の学習ではワイルドカード規則を暗黙に作らず、観測しただけで通信を許可することもありません。完全一致の判断はプロジェクトと Workspace Template に限定され、本文を含みません。宛先と通信内容が適切かを決めるのは利用者です。Tobari は意味上の意図を推測せず、許可された通信が Workspace から読める機密データを運ぶことまでは防げません。

## まとめ

レビューは、信頼するホストで候補を確認し、完全一致の判断を明示的に準備する操作です。参照は不透明なまま扱います。一つの Workspace Template の一式を全体として有効化し、確定後の再試行は利用者またはエージェントが新しいリクエストとして開始します。

## 理解を確認する

<details>
  <summary>レビュー一覧の項目番号が操作対象にならないのはなぜですか？</summary>
  一覧の表示順は権限ではありません。操作は通信候補に結び付いた不透明な参照を
  そのまま受け取り、実行時に再検証します。
</details>

<details>
  <summary>学習した完全一致の拒否は、未処理項目として戻り続けますか？</summary>
  いいえ。解決済みのポリシーと監査根拠として残ります。将来、同じ拒否をもう一度
  レビュー対象に戻したい場合は、デフォルト拒否へリセットします。
</details>

<details>
  <summary>許可操作は元のリクエスト本文をどう扱いますか？</summary>
  何もしません。本文はポリシーや再実行のために保持されません。承認は
  ポリシーを変え、呼び出し元が新しいリクエストを送ります。
</details>
