ポリシーレビューは、保持された拒否の根拠を、ホストが所有する明示的な判断へ変える操作です。Workspace とエージェントのセッションを動かしたまま、別の信頼するホストターミナルで Permission Inbox を開き、量を制限した秘密情報を含まない記録を確認します。完全一致の詳細画面で判断を準備し、一つの Context についてレビュー済みの一式を一度だけ Apply します。承認はポリシーを変更しますが、拒否された通信を再試行しません。

[最初の拒否](../../start/first-denial/)では、リクエストの拒否からこのホスト側のレビューフローまでを説明しています。

## 1. 再試行を止め、Workspace は動かしたままにする

学習可能な Gateway `403` は、ホストで `tobari policy review` を実行する固定案内を含みます。候補 ID はなく、エージェント自身を承認する手段を与えません。

レビューのために Workspace を終了しません。元のセッションを保持し、別のホストターミナルを使います。確認前に同じリクエストを繰り返しても権限は増えません。

## 2. 人向けのレビューフローを開く

```sh
tobari policy review --tail 100
```

インストール全体を対象とする TTY キューには、取得件数を制限した Gateway ログから、保留中の通信候補が表示されます。一つを選び、次を確認します。

- Context と安定した Context ID
- プロジェクトとルート、およびホストが発行したプロジェクトプリンシパル
- スキーム、ホスト、ポート
- メソッドと正規化されたパス
- 拒否理由、時刻、保持された観測回数
- 提案される完全一致の許可または拒否

詳細画面からだけ **Allow exact** または **Deny exact** を選びます。選択を準備しただけでは権限は変わりません。同じ Context の候補を確認し、**Apply** で一式を再検証して一度だけ有効化します。Apply 前にキャンセルすると、準備した選択はすべて破棄されます。Context を切り替える前に適用または破棄します。手動 Refresh では、準備済みの判断を表示名ではなく候補 ID で照合します。同じ ID は判断と順序を保ち、消えた ID は Apply 対象から外れ、同じ表示名の別 ID へ権限を移しません。

## 3. 必要な場合だけ機械向けの経路を使う

リダイレクトされた環境でのレビューは読み取り専用です。

```sh
tobari policy review --tail 100 --format json
```

出力された不透明な `pcy_...` ID を変更せず、一つの操作へコピーします。

```sh
tobari policy allow --id <pcy-id>
# or
tobari policy deny --id <pcy-id>
```

ID をデコード、正規化、再構成したり、未検査の表示文字列を付け足したりしないでください。操作時には、現在保持されている根拠を使って ID を解決します。古い参照や期限切れの参照は、類似リクエストを推測せずに失敗します。

`tobari policy candidates --format json` は機械向けに構造化された候補一覧を返し、`tobari policy tail` は互換性のための表示を返します。どちらも状態を変更しません。

## 4. 有効化の仕組みを理解する

一度のレビュー済み Apply は次を行います。

1. 最新のキュースナップショットで、保持された参照をすべて解決する
2. ポリシー生成処理をロックする
3. 所有する Context 一つの学習済みデータだけを変更する
4. 非公開の Context ソースを検証する
5. すべての Context を含む完全な集約ポリシーを生成し、テストする
6. リビジョンを持つ完全なバンドルを一つ公開する
7. 実行中の OPA が完全一致のリビジョンを報告するまで待つ
8. リクエストを再実行せず確定した判断を報告する

検証または有効化の手順が一つでも失敗すれば、Tobari は以前の検証済み集約ポリシーを保持または復元します。新しい規則を部分的に有効化することはありません。

## 5. 意図的に再試行する

確定した許可後、元の実行中 Workspace セッションへ戻り、新しいリクエストを送ります。古い拒否されたリクエストはすでになく、Gateway は本文をキュー/再実行しません。

完全一致規則は Context ID、プロジェクト ID、スキーム、ホスト、ポート、メソッド、パスに結び付きます。本文、時刻、表示順、リクエスト ID、認証情報ラベルによって権限が広がったり分割されたりすることはありません。

## 現在のポリシーの修正または集約

```sh
tobari policy rules
tobari policy reset --id <policy-rule-id>
```

リセットは、CLI が管理する学習済みの判断を一つだけ削除し、その通信候補をデフォルト拒否へ戻します。許可する操作でも、リクエストを再試行する操作でも、基本ポリシーを編集する操作でもありません。

互換性のある完全一致の許可規則が三つ以上あると、省略可能な上限付きの集約候補が見つかる場合があります。

```sh
tobari policy compactions
tobari policy compact --id <policy-compaction-id>
```

集約は明示的に実行し、テストで検証します。ホストやメソッドのワイルドカードを作ることはなく、自動実行もされません。

## 失敗時の動作

- 空のキュー: 指定期間内に、有効かつ保留中の学習可能な拒否がありません。過去に拒否がなかったことまで証明するものではありません。
- 基本拒否または現在の完全一致の拒否: 監査根拠には残りますが保留中候補ではありません。
- スキーム、プリンシパル、クラスター、認証情報の結び付けに関する障害: 効果のない完全一致規則を作って学習対象にすることはできません。
- `policy_candidate_not_found` または古い集約: 現在の状態から候補を取り直し、古い参照を再利用しません。
- `policy_test_failed` または事前検査の障害: 所有者だけがアクセスできるポリシーと OPA の診断を確認します。それまでのポリシーが引き続き有効です。
- 結果が不確実な変更操作: 別の変更操作を行う前に、`tobari policy rules` と `tobari cluster status` で状態を調整します。

## 保証と制限

通常の学習ではワイルドカード規則を暗黙に作らず、観測しただけで通信を許可することもありません。完全一致の判断はプロジェクトと Context に限定され、本文を含みません。宛先と通信内容が適切かを決めるのは利用者です。Tobari は意味上の意図を推測せず、許可された通信が Workspace から読める機密データを運ぶことまでは防げません。

## まとめ

レビューは、信頼するホストで候補を確認し、完全一致の判断を明示的に準備する操作です。参照は不透明なまま扱います。一つの Context の一式を全体として有効化し、確定後の再試行は利用者またはエージェントが新しいリクエストとして開始します。

## 理解を確認する

<details>
  <summary>レビュー一覧の項目番号が操作対象にならないのはなぜですか？</summary>
  一覧の表示順は権限ではありません。操作は通信候補に結び付いた不透明な参照を
  そのまま受け取り、実行時に再検証します。
</details>

<details>
  <summary>学習した完全一致の拒否は、未処理項目として戻り続けますか？</summary>
  いいえ。解決済みのポリシーと監査根拠として残ります。将来、同じ拒否をもう一度
  レビュー対象に戻したい場合は、デフォルト拒否へリセットします。
</details>

<details>
  <summary>許可操作は元のリクエスト本文をどう扱いますか？</summary>
  何もしません。本文はポリシーや再実行のために保持されません。承認は
  ポリシーを変え、呼び出し元が新しいリクエストを送ります。
</details>
