---
title: トラブルシューティング
description: 観測できる症状から担当する境界を特定し、変更より先に読み取りを行う安全な復旧手順を選びます。
---

トラブルシューティングは、読み取り専用の診断から始めます。どの境界で失敗したかを特定し、その障害に対して宣言された復旧コマンドを使ってください。単にエラーを消すために、結果が不確実な変更操作を再実行したり、セキュリティ状態を削除したりしてはいけません。

以下の項目は観測できる症状ごとに分かれているため、ポリシー、認証、ランタイム、VM の障害を区別できます。先に[五つの要素からなる基本モデル](../../how-it-works/mental-model/)を確認してください。正確な障害コード、再試行可否、Catalog が宣言する復旧方法は[障害と復旧](../../reference/faults-and-recovery/)を参照してください。

## 観測から始める

信頼するホスト上の、意図したプロジェクトディレクトリから実行します。

```sh
tobari doctor
tobari cluster status
tobari status
tobari list
```

これらのコマンドは観測だけを行います。サービスの起動、ランタイムリソースの作成/削除、ポリシーの有効化、Workspace 所有のログイン状態の修復は行いません。外部サービスへのログインは、そのサービスが提供する CLI で行います。

正確な障害コードと、宣言された次の操作を記録します。すべての障害を単なる「再試行」にしないでください。

## Workspace に入れない

次の順で確認します。

1. `tobari cluster status`: 共有クラスターが設定済みで、正常であることを確認します。
2. `tobari doctor`: Docker、イメージ、パス、ポリシー、Workspace、host-owned lifecycle state の前提条件を確認します。
3. `tobari status`: 論理 Workspace が存在しないのか、ランタイム診断が `missing`、`degraded`、`unreachable`、`incomplete` のいずれなのかを区別します。
4. ルートコマンドに対話型ターミナルがあり、Workspace 内で実行していないことを確認します。

コンテナが `missing`、またはネットワークが `degraded` の場合、論理状態とホームを保持したまま、次の有効なルート入室で調整できます。`incomplete` は、インデックスとインスタンス記録が一致していない状態です。入室処理は識別情報を推測して作成しません。所定の後始末を行う `tobari delete` を使い、その後で意図的に作成してください。

`workspace_selection_stale` の場合は `tobari` を再実行し、更新された候補から選びます。`image_not_found` または `incompatible_image` の場合は、結び付けされた Workspace Manifest を調べ、次の入室より前にランタイムを修復またはビルドします。

## リクエストが HTTP 403 を返す

まずレスポンスコードを特定します。

- `policy_denied`: Workspace を出て `tobari review permissions` を実行します。一つの Workspace Manifest について完全一致の判断を確認して準備し、レビュー済みの一式を一度だけ Apply してから、意図的に再試行します。
- upstream の認証に関する `401`/`403`: provider CLI のレスポンスとして扱います。必要ならその CLI のログイン手順を使います。Tobari は upstream の認証失敗を広い許可へ変換しません。
- 基本拒否または学習済みの完全一致拒否: 保留中の候補ではなく、確定したポリシーです。`tobari policy rules` を確認し、その判断を意図的に変更する場合だけリセットします。

upstream の認証 `403` を、範囲の広い許可規則で解決しないでください。provider のレスポンスは Tobari のポリシー候補ではありません。

## Gateway または OPA が正常でない

```sh
tobari cluster status
tobari cluster logs --component gateway --tail 100
tobari cluster logs --component opa --tail 100
```

報告されたイメージ、プロジェクション、ポリシー、マウント、所有権、ヘルスチェックの問題を修正し、明示的な調整を実行します。

```sh
tobari cluster up
```

OPA を利用できなくても通信が許可されることはありません。Gateway は有効な判断なしで Upstream へ接続しません。無効なポリシー候補がある場合も、直前の検証済み集約ポリシーが引き続き有効でなければなりません。

## agent CLI のログインが利用できない

provider CLI 自身のログインコマンドを、選択した Workspace 内で実行してから通常のリクエストフローへ戻ります。Tobari はホストの認証情報を継承せず、provider の状態を保存せず、代替のログインコマンドも提供しません。

## Workspace への入室または agent CLI のログインが無効

認証情報の変更は agent CLI が所有し、実行中のプロセスは以前の環境を保持します。いったん退出し、再入室して現在のツール所有状態を受け取ります。

```sh
exit
tobari
```

それでも失敗する場合は、正しい Workspace Manifest の選択とクラスターの準備状態を確認します。別の Workspace のログインファイルを貼り付けないでください。プロジェクトと Workspace Manifest の検査は意図的なものです。

## ランタイムイメージが見つからない、または互換性がない

```sh
tobari manifest show
```

管理対象 Runtime の場合は次を実行します。

```sh
tobari runtime list
tobari runtime show --name frontend
tobari runtime build --name frontend
tobari manifest runtime set --runtime frontend@1
```

ビルド失敗時はリビジョンを追加せず Workspace Manifest も変えません。選択失敗時は以前の正確な
参照を維持します。既存の論理 Workspace 状態とホームも残ります。ホストマウント、
利用者、エントリーポイント、生存コマンド、ネットワーク制御ではなく互換性を修正してください。

## ポリシーの有効化に失敗する

次を確認します。

```sh
tobari policy rules
tobari cluster status
tobari cluster logs --component opa --tail 100
```

完全一致の許可、拒否、リセット、集約では、有効化する前に、変更した Workspace Manifest とすべての Workspace Manifest を含む完全な集約ポリシーを検証します。失敗した場合は検証済みポリシーを保持しなければなりません。同時に変更が行われた後は、不透明な参照をもう一度取得してください。表示順や古い ID を再利用しないでください。

ホスト側で管理する高度なポリシーの場合は、信頼するホスト上で Rego とテストを修正し、`tobari doctor` と明示的な `tobari cluster up` をもう一度実行します。

## Workspace を削除できない、またはクラスターを停止できない

- `project_session_attached`: セッションから退出してから `tobari delete` を実行します。`tobari delete --force` は、その接続中セッションを終了させる意図がある場合だけ使います。
- `project_not_found`: 対象のプロジェクトルートまたはその子孫ディレクトリで、選択した Workspace Manifest を使ってコマンドを実行します。
- `cluster_not_empty`: `tobari list` ですべての Workspace を確認し、対応するルート/Workspace Manifest へ戻って一つずつ削除してから `cluster down` を実行します。
- 中断された状態: `status` と `doctor` を確認します。ラベルやファイルを手動で削除せず、宣言された所定の後始末または調整コマンドを使います。

`delete` がプロジェクトファイルを削除することはありません。`cluster down --purge` は共有ランタイム/CA ボリュームを削除しますが、Workspace home、Manifest policy、host-owned lifecycle state は保持します。agent CLI の logout は provider の操作です。

## Colima または Lima からマウントが見えない

ホストシェルからは結び付け元が見えるのに Docker が見つからないと報告する場合、選択した VM デーモンでそのパスが共有されていません。対象のプロジェクトと、実際に使われる Tobari の XDG 設定および状態の親ディレクトリを共有してから、次を実行します。

```sh
tobari doctor
tobari cluster up
```

[Colima と Lima](../colima-and-lima/)を参照してください。ホストホームのマウント、ホストネットワーク、特権コンテナ、Docker ソケットでエラーを迂回しないでください。

## 変更操作の結果が不確実

`unclassified_mutation_outcome` または `mutation_output_write_failed` の場合、副作用を伴う処理がすでに完了している可能性があります。出力が失われたという理由だけで、ポリシーやライフサイクルの変更を繰り返さないでください。

まず、対応する読み取り専用コマンドで状態を確認します。

- agent login: provider CLI のログインフロー
- ポリシー: `tobari policy rules` と `tobari cluster status`
- Workspace Manifest/ランタイム: `tobari manifest show`
- Workspace: `tobari status` と `tobari list`

## 保証と制限

Catalog に記載された障害には範囲を限定した復旧方法が宣言され、読み取り専用の診断は予期しない修復を避けます。ただし診断は、信頼するホストと Docker による観測が正確であることに依存します。状態の手動削除、任意のイメージへの置き換え、広いマウントやネットワーク変更は、復旧保証とセキュリティモデルを無効にする可能性があります。

## まとめ

観測した事実から始め、所有する境界を特定し、現在の状態を読んでから、宣言された復旧だけを適用します。可用性障害では安全側に閉じたままになり、結果が不確実な変更操作は、再実行より先に状態の確認と調整が必要です。

## 理解を確認する

<details>
<summary>provider CLI のログインの最終出力が失われました。ログインをもう一度実行すべきですか？</summary>

まだ実行しません。provider はすでにログインを受理した可能性があります。次の変更操作より前に、その CLI の読み取り可能な状態を確認してください。

</details>

<details>
<summary>HTTPS リクエストがポリシーで拒否されました。まずクラスターを再起動すべきですか？</summary>

クラスターが正常で、拒否が学習可能な場合は再起動しません。Workspace を出て、ホストで完全一致の通信をレビューし、判断を行ってから、意図的に再試行してください。

</details>

<details>
<summary>Workspace コンテナが消えました。論理 Workspace を削除する必要がありますか？</summary>

いいえ。ランタイムを失っても復旧できます。次の有効なルート入室で、識別情報とホームを保持したままコンテナが再作成されます。`incomplete` 状態を後始末する場合か、Workspace を意図的に終了する場合だけ削除してください。

</details>
