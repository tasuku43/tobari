## このガイドで答える問い

**runtime image に mount、ネットワーク、Workspace の寿命を決める権限を与えず、プロジェクトへツールを追加するにはどうしますか？**

current Context の owner-only Dockerfile recipe を初期化し、信頼するホストで編集し、明示的な `runtime build` を実行します。次の Workspace entry で work container だけを reconcile し、logical identity と home を保持します。

このガイドを読み終えると recipe/build/promotion の順序、compatible image が保持すべきもの、build failure 時の動作を説明できます。

前提: current Context を把握してください。[Context](../contexts/)を参照してください。

## 1. Context を選択して確認する

runtime command は current/default Context に作用します。named Context を使う場合は先に選択します。

```sh
tobari context use --name review
tobari context show
```

Context report は selected image と managed recipe の有無を示します。この Context に恒久的に bound された既存 Workspace は、次の entry で current image を参照します。

## 2. 一度だけ初期化する

```sh
tobari runtime init --format json
tobari context show --format json
```

path を推測せず、報告された runtime recipe path を使ってください。`runtime init` は owner-only `runtime/Dockerfile` template を作ります。image build、selected image の変更、Docker service の起動、既存 recipe の上書きは行いません。

信頼するホストで recipe を編集します。最小 customization では template の base と user transition を保ち、既存 `USER root` と `USER tobari` の間に package を追加します。

```dockerfile
RUN apt-get update \
    && apt-get install -y --no-install-recommends tree \
    && rm -rf /var/lib/apt/lists/*
```

real credential を Dockerfile、build context、image layer、example に入れないでください。

## 3. ビルド、検証、昇格

```sh
tobari runtime build --format json
```

これは意図的な host Docker-build boundary 一つです。Tobari は次を行います。

1. Context runtime directory だけを build context にする
2. Context と recipe source digest から local image identity を導出する
3. bounded structured invocation で Docker build を実行する
4. resulting image を Tobari runtime contract で検証する
5. confirmed image digest を記録する
6. Context manifest の image selector を atomically に promote する

file を編集しただけでは何も変わりません。build または compatibility check に失敗すると、prior selected image が authority のままです。Docker/BuildKit が cache または unselected candidate image を保持しても、Tobari はそれを active と報告しません。

## 4. 既存 Workspace へ入り直す

この Context に bound された project から実行します。

```sh
tobari
tree --version
exit
```

entry は desired image と complete runtime spec を existing container と比較します。変化があれば、その container だけを再作成します。logical Workspace ID、canonical root、Context binding、persistent home、learned policy、project file は保持します。

image の `CMD` は Workspace lifetime を定義しません。Tobari が fixed lifetime command を与え、shell または agent command は child exec session として開始します。container loss は recoverable であり、logical Workspace は container そのものではありません。

## 互換性が意味すること

custom image は、expected non-root `tobari` user、entrypoint behavior、fixed lifetime-command capability、CA/proxy environment compatibility、writable home location、health behavior、supported architecture を含む Tobari runtime API と operational contract を保持する必要があります。

image 自身が次を与えることはできません。

- extra host mount または host home
- Docker socket access
- host networking または direct external route
- 追加 Linux capability
- 別 project principal
- `CMD` 変更による長い logical lifetime

これらの control は image metadata ではなく host lifecycle implementation が所有します。

## 失敗時の動作

- `runtime_recipe_exists`: 既存 recipe を確認します。init は上書きしません。
- `runtime_recipe_missing`: build 前に `tobari runtime init` を実行します。
- `runtime_build_failed`: Dockerfile を直し `tobari context show` を確認します。promotion 完了済みでない限り old selection が残ります。
- `image_not_found`: declared base または selected image を利用可能にして、explicit build/reconcile を再試行します。
- `incompatible_image`: required user、label/API、entrypoint、lifetime capability、architecture を復元します。
- uncertain mutation outcome: promotion failure と決めつけず、別 build 前に `tobari context show` を確認します。
- existing Workspace entry failure: prior logical state と home は残ります。Context image を直して再 entry します。

## 保証と制限

promotion は content-aware で Context-scoped です。validation failure が active selection を暗黙に置き換えることはありません。compatibility validation で image 内の任意 software を trustworthy にすることはできません。Workspace 内の process は selected project を変更し、すでに許可済みの network effect を利用できます。

## まとめ

recipe は source、`runtime build` は明示的に検証される promotion boundary、Workspace entry は reconciliation point です。runtime image は tool を提供し、host lifecycle code が authority と lifetime を所有します。

## 理解を確認する

<details>
  <summary>
    Dockerfile を編集すると実行中の Workspace は更新されますか？
  </summary>
  いいえ。`runtime build` が必要です。既存 Workspace は、promote 済み compatible
  image を次の entry で利用します。
</details>

<details>
  <summary>
    image の構成ずれにより container を再作成すると、Workspace home
    はどうなりますか？
  </summary>
  保持されます。交換可能な container とは別に mount される logical Workspace
  state です。
</details>

<details>
  <summary>
    カスタム image は Dockerfile の宣言だけで Docker socket を追加できますか？
  </summary>
  いいえ。host lifecycle code が mount と capability を固定します。
</details>
