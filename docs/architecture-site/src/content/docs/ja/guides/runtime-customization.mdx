クイックスタートでは、標準ベースランタイムに入っている `curl` だけを使って、拒否、レビュー、許可、再実行を確認しました。標準ベースランタイムは、通信制御を試し、カスタムイメージの土台にするための最小構成です。**コーディングエージェントは含めず、あらゆるプロジェクトの言語処理系やビルドツールを揃えることも目的にしていません。**

実際のリポジトリで作業する前に、必要なツールを入れたカスタムランタイムを作ります。同じ実行環境を複数のプロジェクトで共有する設定単位を、Tobari では **Context** と呼びます。ランタイムは現在の Context に結び付き、その Context を使う Workspace が次の入室時に同じイメージを参照します。

この手順は信頼するホストで行います。Workspace 内から Dockerfile を変更したり、`runtime build` を実行したりする経路はありません。

## この手順が早い段階に必要な理由

Tobari の標準ランタイムだけでも、`bash` や `curl` などを使って境界を確認できます。しかし、コーディングエージェント本体や、プロジェクトが必要とするコンパイラー、パッケージマネージャー、テストツールがなければ、実際の開発作業は始められません。

そのため、最初のポリシーレビューを体験した後は、次の順番で作業環境を作るのが基本です。

1. 現在の Context を確認する
2. Context が管理する Dockerfile を初期化する
3. コーディングエージェントと開発ツールを追加する
4. Tobari にビルドと互換性検査を実行させる
5. Workspace へ入り直し、選択されたイメージを使う

## 1. 現在の Context を確認する

まず、どの Context にランタイムを設定するか確認します。

```sh
tobari context show --format json
```

名前付きの Context を使う場合は、先に選択してから同じ確認を行います。

```sh
tobari context use --name review
tobari context show --format json
```

ランタイムはプロジェクト単体ではなく Context に結び付きます。別の目的で異なるツール構成を使う場合は、Context を分けてください。

## 2. ランタイムレシピを作る

現在の Context に、Tobari が管理する Dockerfile を一度だけ作ります。

```sh
tobari runtime init --format json
tobari context show --format json
```

`context show` が返す Dockerfile のパスを使ってください。保存先を推測する必要はありません。

`runtime init` は次だけを行います。

- 所有者だけがアクセスできるランタイムディレクトリを作る
- 公式ベースランタイムを継承する Dockerfile テンプレートを作る
- Context にレシピが存在することを記録する

この時点では、イメージをビルドせず、選択中のイメージも変えません。既存のレシピがある場合は上書きしません。

## 3. エージェントと開発ツールを追加する

Dockerfile には、既存の `USER root` と `USER tobari` が含まれています。OS パッケージやグローバル CLI は、その二行の間へ追加します。

次は、Node.js と npm を追加し、Codex CLI をインストールする例です。Codex は例であり、Tobari の必須依存ではありません。別のエージェントを使う場合は、インストール行だけを置き換えてください。

```dockerfile
USER root

RUN apt-get update \
    && apt-get install -y --no-install-recommends nodejs npm \
    && rm -rf /var/lib/apt/lists/*

RUN npm install --global @openai/codex

USER tobari
```

チームで同じイメージを再現する場合は、エージェントと主要ツールのバージョンを固定してください。上の例で使っている Codex CLI の現在の公式な導入方法は、[Codex の公式リポジトリ](https://github.com/openai/codex#installing-and-running-codex-cli)で確認できます。

プロジェクトで必要な SDK、コンパイラー、リンター、テストツールも同じ Dockerfile に追加します。`COPY` するファイルがある場合は、Context のランタイムディレクトリ内へ置いてください。`runtime build` が Docker のビルドコンテキストとして使うのは、そのディレクトリだけです。

**認証情報、API キー、トークン、個人設定は Dockerfile、ビルド引数、ビルドコンテキスト、イメージレイヤーへ入れないでください。**

## 4. ビルドして Context に選択する

Dockerfile を編集しただけでは、Workspace の実行環境は変わりません。信頼するホストで明示的にビルドします。

```sh
tobari runtime build --format json
tobari context show --format json
```

`runtime build` は、次の処理を一つの操作として行います。

1. Context のランタイムディレクトリだけをビルドコンテキストにする
2. Docker で候補イメージをビルドする
3. Tobari のランタイム契約に適合するか検査する
4. 確定したイメージダイジェストを記録する
5. 検査に通ったイメージだけを Context の選択へ反映する

ビルドまたは互換性検査に失敗した場合、それまで選択されていたイメージが有効なまま残ります。Docker や BuildKit に候補イメージやキャッシュが残っても、Tobari が選択済みとして扱うことはありません。

このビルドは、信頼するホスト側の Docker ビルドです。Workspace の Gateway ポリシーを通る通信ではありません。Dockerfile が取得するパッケージとスクリプトは、ホスト側で実行してよいものか確認してください。

## 5. Workspace に入り、実際のツールを確認する

カスタムランタイムを使うプロジェクトへ移動し、Workspace に入ります。

```sh
tobari
codex --version
codex
```

既存の Workspace が別のイメージで動いていた場合、Tobari は次の入室時に作業コンテナだけを作り直します。新しい Workspace なら、最初から選択済みのイメージで作ります。

エージェントが外部通信を始めると、クイックスタートと同じように未許可の通信は拒否されます。Workspace から出て `tobari policy review` を実行し、実際に必要な宛先・ポート・メソッド・パスだけを確認して許可してください。拒否されたリクエストは自動再送されないため、許可後にエージェント側で新しいリクエストを実行します。

## 認証情報と永続ホーム

コーディングエージェントのログイン状態や設定は、通常、そのエージェントが Workspace のホームディレクトリへ保存します。Workspace のホームは作業コンテナと別に保持されるため、ランタイムイメージを更新してコンテナを作り直しても残ります。

ただし、そのホームに保存された認証情報は、**同じ Workspace 内のほかのプロセスから隔離されません。** Tobari の Auth Broker が保護するのは、対応するプロバイダーについて明示的に Broker 経路を使った認証情報です。コーディングエージェント自身が保存する認証情報を、自動的に Auth Broker へ移すわけではありません。

したがって、次を守ってください。

- 認証情報をイメージへ焼き込まない
- ホストのホームディレクトリを追加でマウントしない
- エージェントのログイン状態を、同じ Workspace 内では共有される情報として扱う
- 不要になった Workspace は `tobari delete` で永続ホームごと削除する
- 対応する認証方式がある場合は、[認証ガイド](../authentication/)で Auth Broker の経路を確認する

## 既存 Workspace で保持されるもの

ランタイムの変更により作業コンテナを再作成しても、次は保持されます。

- 論理 Workspace ID
- 正規化されたプロジェクトルート
- Context との結び付き
- Workspace の永続ホーム
- 学習済みポリシー
- 作業対象のプロジェクトファイル

イメージの `CMD` は Workspace の寿命を決めません。Tobari が固定した生存コマンドでコンテナを維持し、シェルやコーディングエージェントは子の exec セッションとして開始します。

カスタムイメージは、Docker ソケット、追加のホストマウント、ホストネットワーク、直接の外部経路、追加 Linux 権限、別プロジェクトの識別情報を自分で取得できません。これらはホスト側のライフサイクル処理が決めます。

## 失敗時

- `runtime_recipe_exists`: すでにある Dockerfile を使います。`runtime init` は上書きしません。
- `runtime_recipe_missing`: `tobari runtime init` を実行してからビルドします。
- `runtime_build_failed`: Dockerfile とビルド出力を確認します。以前の選択は維持されます。
- `incompatible_image`: `tobari` 利用者、必要なラベルと API、エントリーポイント、アーキテクチャなど、ランタイム契約を復元します。
- `image_not_found`: ベースイメージまたは選択済みイメージを Docker から取得できる状態にして再実行します。
- 変更結果を確認できない場合: ビルドを繰り返す前に `tobari context show --format json` で現在の選択を確認します。
- 入室に失敗した場合: 論理 Workspace と永続ホームは残ります。Context のイメージを修正して再入室します。

正確な必須条件は、[ランタイムイメージ契約](../../reference/runtime-image-contract/)で確認できます。

## 保証と制限

Tobari は、互換性検査に通ったイメージだけを Context に選択し、失敗した候補で現在の選択を暗黙に置き換えません。一方、イメージに追加したソフトウェアの安全性や、パッケージ配布元の信頼性までは保証しません。

Workspace 内で動くエージェントは、作業対象のプロジェクトを読み書きでき、すでに許可された通信を利用できます。カスタムランタイムは、この権限を狭くする仕組みではなく、隔離された作業環境へ必要なツールを追加する仕組みです。

## まとめ

クイックスタートの標準ランタイムは、通信制御を確認するための土台です。実際の開発では、現在の Context に管理対象 Dockerfile を作り、エージェントと開発ツールを追加し、`runtime build` で検証済みイメージを選択します。次の入室時には必要に応じて作業コンテナだけが作り直され、Workspace のホーム、ポリシー、プロジェクトファイルは残ります。
