クイックスタートだけを完了した場合は、先に[カスタムランタイムを用意する](../../start/runtime-setup/)へ進んでください。最小のベースランタイムから、実際の Workspace 内でコーディングエージェントのコマンドを確認するまでを短い手順で説明します。

このページでは、Context による所有、イメージの採用、互換性検査、構成差分の調整、失敗からの復旧を詳しく説明します。プロジェクトへツールを追加するには、現在の Context にある所有者専用の Dockerfile レシピを初期化します。信頼するホストで編集してから、明示的に `runtime build` を実行してください。次に Workspace へ入るときは作業コンテナだけが調整され、論理 Workspace の識別情報と永続ホームは維持されます。

作業前に現在の Context を確認してください。詳しくは [Context](../contexts/)を参照してください。カスタムランタイムイメージは作業環境を提供しますが、マウント、ネットワーク、Workspace の寿命を決める権限は持ちません。

## 1. Context を選択して確認する

ランタイムコマンドは現在またはデフォルトの Context に作用します。名前付きの Context を使う場合は先に選択します。

```sh
tobari context use --name review
tobari context show
```

Context の報告には、選択したイメージと管理対象レシピの有無が示されます。この Context に恒久的に結び付いた既存 Workspace は、次の入室時に現在のイメージを参照します。

## 2. 一度だけ初期化する

```sh
tobari runtime init --format json
tobari context show --format json
```

パスを推測せず、報告されたランタイムレシピのパスを使ってください。`runtime init` は所有者だけがアクセスできる `runtime/Dockerfile` テンプレートを作ります。イメージのビルド、選択したイメージの変更、Docker サービスの起動、既存レシピの上書きは行いません。

信頼するホストでレシピを編集します。最小限のカスタマイズでは、テンプレートのベースと利用者の切り替えを保ち、既存の `USER root` と `USER tobari` の間にパッケージを追加します。

```dockerfile
RUN apt-get update \
    && apt-get install -y --no-install-recommends tree \
    && rm -rf /var/lib/apt/lists/*
```

実物の認証情報を Dockerfile、ビルドコンテキスト、イメージレイヤー、例に入れないでください。

## 3. ビルド、検証、昇格

```sh
tobari runtime build --format json
```

これは、意図的に一か所へ限定したホスト上の Docker ビルド境界です。Tobari は次を行います。

1. Context のランタイムディレクトリだけをビルドコンテキストにする
2. Context とレシピソースダイジェストからローカルイメージ識別情報を導出する
3. 引数と出力を制限した構造化呼び出しで Docker ビルドを実行する
4. 生成されたイメージを Tobari ランタイム契約で検証する
5. 確定したイメージダイジェストを記録する
6. Context マニフェストのイメージ選択情報をアトミックに昇格する

ファイルを編集しただけでは何も変わりません。ビルドまたは互換性検査に失敗すると、それまで選択されていたイメージが引き続き有効です。Docker または BuildKit がキャッシュや未選択の候補イメージを保持していても、Tobari がそれを有効なイメージとして報告することはありません。

## 4. 既存 Workspace へ入り直す

この Context に結び付いたプロジェクトから実行します。

```sh
tobari
tree --version
exit
```

入室時には、望ましいイメージと完全なランタイム仕様を既存コンテナと比較します。違いがあれば、そのコンテナだけを再作成します。論理 Workspace ID、正規化済みルート、Context の結び付け、永続ホーム、学習済みポリシー、プロジェクトファイルは保持されます。

イメージの `CMD` は Workspace の寿命を定義しません。Tobari が固定された生存コマンドを与え、シェルまたはエージェントコマンドは子の exec セッションとして開始します。コンテナを失っても復旧でき、論理 Workspace はコンテナそのものではありません。

## 互換性が意味すること

カスタムイメージは、想定された非 root の `tobari` 利用者、エントリーポイントの動作、固定された生存コマンド、CA とプロキシ環境との互換性、書き込み可能なホーム、ヘルスチェック、サポート対象のアーキテクチャを含む Tobari ランタイム API と運用契約を守る必要があります。

イメージ自身が次を与えることはできません。

- 追加のホストマウントまたはホストホーム
- Docker ソケットへのアクセス
- ホストネットワークまたは直接の外部経路
- 追加 Linux 権限
- 別プロジェクトプリンシパル
- `CMD` 変更による長い論理寿命

これらの制御はイメージメタデータではなくホストライフサイクル実装が所有します。

## 失敗時の動作

- `runtime_recipe_exists`: 既存レシピを確認します。`runtime init` は上書きしません。
- `runtime_recipe_missing`: ビルド前に `tobari runtime init` を実行します。
- `runtime_build_failed`: Dockerfile を直し `tobari context show` を確認します。採用が完了していない限り、以前の選択が残ります。
- `image_not_found`: 宣言されたベースイメージまたは選択したイメージを利用可能にして、明示的なビルドか調整を再試行します。
- `incompatible_image`: 必須の利用者、ラベルと API、エントリーポイント、生存コマンドの権限、アーキテクチャを復元します。
- 結果が不確実な変更操作: 採用に失敗したと決めつけず、別のビルドを行う前に `tobari context show` を確認します。
- 既存 Workspace への入室障害: 以前の論理状態とホームは残ります。Context のイメージを直して再入室します。

## 保証と制限

採用処理は内容を検査し、対象の Context に限定されます。検証に失敗しても、現在有効な選択が暗黙に置き換わることはありません。互換性検証は、イメージ内のあらゆるソフトウェアが信頼できることまでは保証しません。Workspace 内のプロセスは選択したプロジェクトを変更し、すでに許可済みのネットワーク通信を利用できます。

## まとめ

レシピはソース、`runtime build` は明示的に検証される採用境界、Workspace への入室は調整点です。ランタイムイメージはツールを提供し、ホストのライフサイクルコードが権限と寿命を管理します。

## 理解を確認する

<details>
  <summary>
    Dockerfile を編集すると実行中の Workspace は更新されますか？
  </summary>
  いいえ。`runtime build` が必要です。既存 Workspace は、昇格済みの互換
  イメージを次の入室で利用します。
</details>

<details>
  <summary>
    イメージの構成ずれによりコンテナを再作成すると、Workspace ホーム
    はどうなりますか？
  </summary>
  保持されます。交換可能なコンテナとは別にマウントされる論理 Workspace
  状態です。
</details>

<details>
  <summary>
    カスタムイメージは Dockerfile の宣言だけで Docker ソケットを追加できますか？
  </summary>
  いいえ。ホストライフサイクルコードがマウントと権限を固定します。
</details>
