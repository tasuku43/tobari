クイックスタートだけを完了した場合は、先に[カスタムランタイムを用意する](../../start/runtime-setup/)へ進んでください。最小のベースランタイムから、実際の Workspace 内でコーディングエージェントのコマンドを確認するまでを短い手順で説明します。

このページでは、インストール全体で共有する Runtime、成功履歴、明示的な Workspace Manifest
選択、構成差分の調整、失敗からの復旧を説明します。Workspace Manifest が持つのは準備済み
リビジョンへの正確な参照だけです。

作業前に現在の Workspace Manifest を確認してください。詳しくは [Workspace Manifest](../workspace-manifests/)を参照してください。カスタムランタイムイメージは作業環境を提供しますが、マウント、ネットワーク、Workspace の寿命を決める権限は持ちません。

## 1. Runtime を作成して確認する

Runtime の作成とビルドは Workspace Manifest から独立しています。

```sh
tobari runtime create --name frontend
tobari runtime show --name frontend
```

作成結果に所有者専用の `source_path` が表示されます。名前はインストール内で固有で、
安定した Runtime ID はリビジョンが増えても変わりません。source 自体と配下の
ディレクトリには group/other の権限ビットを付けられません。

## 2. 完全なソースツリーを編集する

報告された `source_path` 全体が Docker ビルドコンテキストです。Dockerfile の隣で
スクリプト、パッケージマニフェスト、設定ファイルを管理できます。編集だけでは
リビジョンも Workspace Manifest 参照も変わりません。上限は通常ファイル 1,024 件、
ディレクトリ 256 件、1 ファイル 32 MiB、全体 64 MiB です。リンクと特殊ファイルは
使えません。各ファイルから group/other 権限を外し、データは `0600`、所有者実行が
必要なスクリプトやバイナリは `0700` にします。

信頼するホストでレシピを編集します。最小限のカスタマイズでは、テンプレートのベースと利用者の切り替えを保ち、既存の `USER root` と `USER tobari` の間にパッケージを追加します。

```dockerfile
RUN apt-get update \
    && apt-get install -y --no-install-recommends tree \
    && rm -rf /var/lib/apt/lists/*
```

実物の認証情報を Dockerfile、ビルドコンテキスト、イメージレイヤー、例に入れないでください。

## 3. 不変リビジョンをビルドして検証する

```sh
tobari runtime build --name frontend --format json
tobari runtime history --name frontend
```

これは、意図的に一か所へ限定したホスト上の Docker ビルド境界です。Tobari は次を行います。

1. 完全な上限付きソースツリーを検証してハッシュする
2. 不変な意味的スナップショットを作る
3. 機械的に導出したローカルイメージ名で、そのスナップショットだけをビルドする
4. 生成されたイメージを Tobari ランタイム契約で検証する
5. 確定したイメージダイジェストを記録する
6. 成功したリビジョンを Runtime 履歴へアトミックに追加する

失敗または同一内容のビルドでは履歴を追加せず、すべての Workspace Manifest は変わりません。
Docker または BuildKit がキャッシュや未選択候補を保持しても、準備済み履歴とは報告しません。

## 4. Workspace Manifest へ明示的に選択する

```sh
tobari manifest runtime set --manifest review --runtime frontend@1
tobari manifest show --name review
```

同じリビジョンを複数 Workspace Manifest から再利用できます。新しいビルドで自動更新はされず、
アップグレードもロールバックも別の ordinal を明示的に選びます。

## 5. 既存 Workspace へ入り直す

この Workspace Manifest に結び付いたプロジェクトから実行します。

```sh
tobari
tree --version
exit
```

入室時には、望ましいイメージと完全なランタイム仕様を既存コンテナと比較します。違いがあれば、そのコンテナだけを再作成します。論理 Workspace ID、正規化済みルート、Workspace Manifest の結び付け、永続ホーム、学習済みポリシー、プロジェクトファイルは保持されます。

イメージの `CMD` は Workspace の寿命を定義しません。Tobari が固定された生存コマンドを与え、シェルまたはエージェントコマンドは子の exec セッションとして開始します。コンテナを失っても復旧でき、論理 Workspace はコンテナそのものではありません。

## 互換性が意味すること

カスタムイメージは、想定された非 root の `tobari` 利用者、エントリーポイントの動作、固定された生存コマンド、CA 信頼環境との互換性、書き込み可能なホーム、ヘルスチェック、サポート対象のアーキテクチャを含む Tobari ランタイム API と運用契約を守る必要があります。

イメージ自身が次を与えることはできません。

- 追加のホストマウントまたはホストホーム
- Docker ソケットへのアクセス
- ホストネットワークまたは直接の外部経路
- 追加 Linux 権限
- 別プロジェクトプリンシパル
- `CMD` 変更による長い論理寿命

これらの制御はイメージメタデータではなくホストライフサイクル実装が所有します。

## 失敗時の動作

- `runtime_exists`: `tobari runtime show` で既存 Runtime を確認します。
- `runtime_not_found`: `tobari runtime list` から名前を選びます。
- `runtime_source_invalid`: エラーが示す相対パスと実際のサイズ、件数、種別、または
  所有者専用モードを修正します。`0755` でコピーされた source は group/other の
  全ビットを外し、通常は `0700` にします。
- `runtime_build_failed`: ソースを直して `tobari runtime show` を確認します。履歴と Workspace Manifest は変わりません。
- `runtime_revision_not_ready`: `tobari runtime history` から成功済み ordinal を選びます。
- `image_not_found`: 宣言されたベースイメージまたは選択したイメージを利用可能にして、明示的なビルドか調整を再試行します。
- `incompatible_image`: 必須の利用者、ラベルと API、エントリーポイント、生存コマンドの権限、アーキテクチャを復元します。
- 結果が不確実な変更操作: 採用に失敗したと決めつけず、別のビルドを行う前に `tobari manifest show` を確認します。
- 既存 Workspace への入室障害: 以前の論理状態とホームは残ります。Workspace Manifest のイメージを直して再入室します。

## 保証と制限

採用処理は内容を検査し、対象の Workspace Manifest に限定されます。検証に失敗しても、現在有効な選択が暗黙に置き換わることはありません。互換性検証は、イメージ内のあらゆるソフトウェアが信頼できることまでは保証しません。Workspace 内のプロセスは選択したプロジェクトを変更し、すでに許可済みのネットワーク通信を利用できます。

## まとめ

Runtime ソースは変更可能な準備領域、成功リビジョンは不変、Workspace Manifest 選択は明示的、
Workspace への入室は調整点です。ランタイムイメージはツールを提供し、ホストの
ライフサイクルコードが権限と寿命を管理します。

## 理解を確認する

<details>
  <summary>
    Runtime ソースを編集またはビルドすると実行中の Workspace は更新されますか？
  </summary>
  いいえ。ビルドは履歴を追加するだけです。準備済みリビジョンを Workspace
  Manifest へ 明示的に選択すると、既存 Workspace
  は次の入室でその参照を利用します。
</details>

<details>
  <summary>
    イメージの構成ずれによりコンテナを再作成すると、Workspace ホーム
    はどうなりますか？
  </summary>
  保持されます。交換可能なコンテナとは別にマウントされる論理 Workspace
  状態です。
</details>

<details>
  <summary>
    カスタムイメージは Dockerfile の宣言だけで Docker ソケットを追加できますか？
  </summary>
  いいえ。ホストライフサイクルコードがマウントと権限を固定します。
</details>
