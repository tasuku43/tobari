## How to use this page

For each scenario, answer in your own words before opening the details. A correct answer should name the responsible component and the boundary that matters, not only say “allowed” or “denied.”

Prerequisite: follow the [Learning path](../learning-path/). If several answers are unfamiliar, return to the linked explanation rather than memorizing the text.

## 1. More than a Docker wrapper

A developer says: “Tobari is just a convenient `docker run` command.” What is missing?

<details>
<summary>Answer</summary>

The runtime container is only one recoverable implementation detail. Tobari
also maintains a Template-bound Context, that Context's replaceable Workspace,
a host-issued Context/Workspace principal, a dedicated internal network,
Gateway enforcement, OPA policy, denial review and atomic activation, and
persistent Workspace home/state. See [System overview](../../how-it-works/system-overview/).

</details>

## 2. Opening a direct socket

A program connects directly to a public IP. What happens in the supported topology?

<details>
<summary>Answer</summary>

It does not gain direct egress. The Workspace output guard sends TCP through
the project Gateway, whose transparent listener requires a valid HTTP/TLS
authority and the same OPA decision. A bare public-IP or non-HTTP connection
fails closed. See [Trust boundaries](../../security/trust-boundaries/).

</details>

## 3. Decision versus enforcement

OPA returns `allow`. Which component actually opens the upstream connection?

<details>
<summary>Answer</summary>

Gateway. OPA decides the normalized effect; Gateway enforces the decision and creates the separate upstream connection. See [Request journey](../../how-it-works/request-journey/).

</details>

## 4. OPA stops

OPA is unavailable while a request is being evaluated. Is the request allowed for availability?

<details>
<summary>Answer</summary>

No. Gateway returns a service failure and does not connect upstream. Missing, invalid, or unavailable policy decisions fail closed. See [Request journey](../../how-it-works/request-journey/).

</details>

## 5. HTTPS inspection

An HTTPS client reaches `api.example.com` through Tobari. Where does encryption end and begin again?

<details>
<summary>Answer</summary>

After transparent interception, TLS connection A runs between the Workspace client and Gateway and terminates at Gateway using the Tobari CA. After allow, Gateway creates separately verified TLS connection B to the upstream. The final hop is not plaintext HTTP. See [HTTPS and TLS](../../how-it-works/https-and-tls/).

</details>

## 6. Same effect, different body

Two requests have the same Context, scheme, host, port, method, and path, but different JSON bodies. Do they require different learned rules?

<details>
<summary>Answer</summary>

No. Request body is not a policy identity dimension and does not split candidates. Tobari does not infer permission from payload meaning. See [Policy learning](../../how-it-works/policy-learning/).

</details>

## 7. Leaving versus deleting

The agent types `exit`, then the user runs `tobari workspace delete --id WORKSPACE_REF --confirm=delete`. What is the difference?

<details>
<summary>Answer</summary>

`exit` ends the attached shell while preserving the Workspace, Context Home, runtime resources, and policy. `workspace delete` removes one exact detached Workspace and its container/network/principal/runtime state while preserving project files, Context Home and native state, Policy Memory, and Workspace Template. See [Workspace lifecycle](../../how-it-works/workspace-lifecycle/).

</details>

## 8. Switching Workspace Templates

Workspace A belongs to a Context bound to the current default Workspace Template. The user runs `tobari template default set --id TEMPLATE_REF`. Does A move to the newly selected Template?

<details>
<summary>Answer</summary>

No. `template default set` changes only the omission default. Existing Contexts retain their Workspace Template ID and existing Workspaces retain their Context ID. The same root may explicitly enter a different Context bound to another Template. See [Workspace Templates and Contexts](../../guides/workspace-templates-and-contexts/).

</details>

## 9. Same URL, another Workspace

Workspace B sends the same host, method, and path that Workspace A was allowed to use. Does A's rule automatically authorize B?

<details>
<summary>Answer</summary>

Learned rules are owned by the stable Context. If A and B are siblings in the
same Context, the same exact rule applies; if B belongs to another Context, it
needs its own matching rule. Workspace identity is observation provenance and
routing only. See [Project identity](../../how-it-works/project-identity/).

</details>

## 10. Login versus permission

`native client sign-in --provider github` succeeds. Can the Workspace immediately call every GitHub API path?

<details>
<summary>Answer</summary>

No. Login stores tool-owned credential material in the persistent Workspace
home. OPA still evaluates each ordinary HTTP effect, and an exact allow is
still required. Authentication does not enlarge authorization. See
[Authentication](../../guides/authentication/).

</details>

## 11. What the Workspace receives

The agent CLI has login state in its Context Home. Is that a Tobari policy grant?

<details>
<summary>Answer</summary>

No. The Context Home is where the agent CLI keeps its own login state and shares it with sibling Workspaces. Tobari
still evaluates each ordinary HTTP effect independently. See
[Credentials](../../how-it-works/credentials/).

</details>

## 12. Denied request

A Workspace identity is valid, but OPA denies the HTTP effect. Which credential values reach the upstream?

<details>
<summary>Answer</summary>

None. Credential values remain out of the denied path, and Gateway performs no
destination lookup or upstream connection. See [Credential security](../../security/credential-security/).

</details>

## 13. Credential data is not policy identity

A request contains a credential value in its headers. Does that value create a policy rule?

<details>
<summary>Answer</summary>

No. Credential values are removed from OPA input and audit. The exact
Context/scheme/host/port/method/path effect remains the policy identity;
Workspace and Project remain provenance. See
[Credential security](../../security/credential-security/).

</details>

## 14. Purging the cluster

The user deletes every Workspace and runs `tobari cluster down --purge`. Are Context Homes and host-owned state deleted?

<details>
<summary>Answer</summary>

No. `--purge` additionally removes the shared Gateway CA volumes. Context
Homes and host-owned state remain; logout remains the agent CLI's responsibility.
See [State and recovery](../../how-it-works/state-and-recovery/).

</details>

## 15. Project file protection

An agent deletes a file inside the selected project root. Is this a Tobari boundary failure?

<details>
<summary>Answer</summary>

Not necessarily. Immutable Workspace Template `source_access` selects `read-only` or
`read-write`, with CLI omission defaulting to `read-write`. Even read-only does
not stop host or another Workspace Template from changing the live source. See [Guarantees and limitations](../../security/guarantees-and-limitations/).

</details>

## 16. Data sent to an allowed destination

An exact destination/method/path has been allowed. Can Tobari ensure that the body contains no source code or secret readable by the Workspace?

<details>
<summary>Answer</summary>

No. The body is streamed after allow and is not an authorization identity field. An allowed upstream can receive any data the Workspace can read and chooses to send. See [Guarantees and limitations](../../security/guarantees-and-limitations/).

</details>

## 17. Trusted foundation compromise

Gateway or the Docker daemon is compromised. Does the documented Workspace guarantee still hold?

<details>
<summary>Answer</summary>

No. The host, kernel, Docker, Gateway, OPA, host-owned state backend, and
reviewed runtime configuration are trusted enforcement foundations. Agent CLI
login files remain tool-owned data, not a Tobari service. Tobari does not claim
protection after a trusted foundation is compromised. See [Threat model](../../security/threat-model/).

</details>

## 18. Runtime image command

A custom runtime image declares `CMD ["my-agent"]`, and that process exits. Does its `CMD` define the logical Workspace lifetime?

<details>
<summary>Answer</summary>

No. Tobari explicitly runs its fixed lifetime command and opens work through child exec sessions. The logical Workspace and persistent home also outlive an individual container. See [Runtime customization](../../guides/runtime-customization/).

</details>

## 19. CLI source of truth

A hand-written guide and `tobari help` disagree about an argument. Which specification governs?

<details>
<summary>Answer</summary>

`cli.Catalog` is the public command and invocation source of truth. Routing, typed argv, help, roles, effects, recovery, and generated site reference derive from it. The hand-written guide must be corrected. See [CLI reference](../../reference/cli/).

</details>

## 20. Evidence for a security claim

Someone claims that a Workspace cannot reach OPA directly and that OPA denial prevents upstream I/O. What evidence should accompany the claim?

<details>
<summary>Answer</summary>

At minimum: the governing architecture/security contract, Compose/network topology implementation and tests proving OPA joins only control, Gateway tests proving deny performs no upstream connection, and integration canaries for direct egress/control-network isolation. The [Verification evidence](../../security/verification-evidence/) table links claims to enforcement, tests, and source.

</details>

## Bonus scenario: copied Workspace file

A process copies a credential file from Workspace A into Workspace B. What checks matter?

<details>
<summary>Answer</summary>

Gateway derives B's principal from the registered Workspace source endpoint.
Different Contexts have separate Homes; siblings in one Context already share
the same Home. Copying a file never changes B's host-owned principal. Policy is
shared only when A and B belong to the same Context and the exact effect matches.

</details>

## Summary

You understand the current model when you can connect each answer to an owner:
the host selects identity, Workspace holds project authority, OPA decides,
Gateway enforces, agent CLIs own their login state, and lifecycle commands
remove only the state they own.

If an answer depended on guessing, return to the linked page. For exact arguments, schemas, paths, faults, and versions, continue to [Reference](../../reference/cli/).
