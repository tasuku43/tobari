Tobari runs the agent in a project-bound Workspace, denies undeclared HTTP and HTTPS effects at first, and lets a person review and authorize an exact effect from the trusted host before deliberately retrying it.

It is more than a command that starts a Docker container: it combines a directory-bound working environment with an enforced outbound request path. This overview introduces that boundary, its five main participants, and the limits of what it protects. No prior Tobari knowledge is required. To start using it after this overview, continue to [Install](../install/).

## Start with one boundary, not the implementation stack

An agent can read and change the selected project. That is the useful authority you gave it. Tobari narrows what sits outside that selection: other host files are not mounted, Docker control is not exposed, each Workspace has a separate internal network, and ordinary outbound HTTP or HTTPS must pass through a shared enforcement path.

<SystemMap headingLevel={2} compact />

Read the diagram in this order:

1. A process in the **Workspace** makes an ordinary HTTP or HTTPS request. A bounded synthetic DNS answer and a closed output route deliver TCP to its project Gateway without client proxy configuration.
2. **Gateway** receives the request. It derives the project principal from the kernel-observed Workspace source endpoint and host-owned registry.
3. **OPA** decides the normalized HTTP effect: Context, project, scheme, destination, port, method, and path. The request body is not a policy identity field.
4. **Auth Broker** participates only for a recognized broker handle. It can reveal non-secret binding metadata before policy. Static resolution, Datadog token selection or refresh, and AWS export and signing happen only after allow.
5. **Gateway**, not the Workspace, opens the separate connection to the **Upstream** after allow.

OPA makes the decision. Gateway enforces it by either refusing the request or creating the upstream connection.

## A concrete first encounter

Suppose an agent in `/work/example` tries:

```sh
curl -X PUT https://example.com/quickstart
```

If no rule covers that exact effect, Gateway returns a learnable `403`. It retains bounded, secret-free evidence and tells the agent where the trusted host can review it. Nothing is approved automatically. The person leaves the Workspace, runs `tobari policy review`, chooses allow or deny for the exact effect, and retries only after a confirmed decision.

The rule does not mean “the agent may use example.com.” It remains bound to the stable Context, project principal, HTTPS destination and port, HTTP method, and path represented by the reviewed effect.

## What the boundary protects

In the supported Docker topology, Tobari is designed to keep these outside an untrusted Workspace process:

- host files outside the selected project root;
- the Docker socket and Docker control plane;
- another Workspace and its persistent home;
- a direct public-Internet route that bypasses Gateway;
- broker-managed primary credentials; and
- the host-owned policy review and activation path.

When Gateway, OPA, the principal registry, or the broker binding cannot establish a valid decision, the relevant request fails closed. An OPA outage does not become an allow.

## What the boundary does not protect

Tobari deliberately does **not** promise to protect:

- files inside the selected project root from processes in that Workspace;
- data a process sends to a destination the user has allowed;
- one process in a Workspace from another process in the same Workspace;
- overlapping project roots from observing each other's host-file changes;
- the system after compromise of the host, kernel, Docker, Gateway, OPA, or Auth Broker; or
- raw TCP, UDP, HTTP/3, Git over SSH, and other non-HTTP protocols.

A client using an ordinary direct socket reaches the Gateway policy boundary;
it does not gain a direct egress route. A certificate-pinned HTTPS
client that rejects Tobari's CA fails instead of bypassing Gateway.

## Current implementation status

**Implemented now:** reusable Context-bound Workspaces, dedicated internal
project networks, Gateway/OPA mediation, exact denial review, guided and
advanced policy modes, Context runtime recipes, tool-native authentication,
the static managed adapter, strict schema-1 static Broker providers, and
reviewed built-in GitHub, AWS, and Datadog acquisition. The built-in schema-1
plans provide bounded AWS SigV4 through a private host companion and fixed
Datadog US1 OAuth refresh inside Broker.

The source tree and tests contain both schema-1 plans. Official immutable
Gateway and Auth Broker V1 indexes are not yet published and reviewed, so
`versions.env` records paired `unpublished` markers. Use the explicit
development-image path until reviewed immutable V1 digests replace them.
[Component versions](/reference/component-versions/) reports the
selected artifacts; [Supply chain](/security/supply-chain/) explains why source
and runtime identity are separate claims.

This documentation does not present arbitrary manifest-selected signing or
refresh, arbitrary OAuth helpers, provider-operation policy, Git credential
helpers, multiple accounts per provider/Context, or additional built-in plans
as current behavior.

## Summary

Tobari grants useful project access first and controls ordinary outbound web
effects separately. A Workspace cannot authorize itself: the host establishes
its identity, OPA decides, Gateway enforces, and Auth Broker performs only the
declared post-policy credential action on the allowed path.

## Check your understanding

<details>
<summary>A process opens a direct HTTPS socket. Does it reach the Internet without Gateway?</summary>

No. In the supported topology its Workspace joins only a dedicated internal
Docker network. Synthetic DNS and the Workspace output guard route ordinary
TCP through Gateway's transparent listener, where the same authority and OPA
checks apply. Unsupported non-HTTP traffic fails closed.

</details>

<details>
<summary>Does an OPA allow response itself transmit the request upstream?</summary>

No. OPA returns a decision. Gateway enforces that decision and creates the upstream connection only after allow.

</details>

<details>
<summary>Does Tobari protect the selected project from the agent?</summary>

No. The selected root is intentionally mounted read-write. Tobari narrows authority outside that selection; it does not make the project read-only.

</details>

If any answer was surprising, reread [What the boundary protects](#what-the-boundary-protects) and [What the boundary does not protect](#what-the-boundary-does-not-protect).
