---
title: Authenticate your tools
description: Authenticate the tools you actually use, then verify authentication state separately from outbound network permission.
---

The previous step made the coding agent executable available inside the Workspace. Next, configure the authentication that tool actually needs.

Keep Tobari's default setup for this first pass. You do not need to create or select another Context.

Keep these two permissions separate:

- **authentication** decides which account or credential a tool can use;
- **network policy** decides which HTTP/HTTPS requests this project may send.

A successful login does not automatically allow network traffic, and allowing traffic does not perform login.

## Choose the authentication path

### Use Tobari's supported host-side authentication

For providers supported by Tobari, authenticate on the trusted host and keep the primary credential outside the Workspace. Current built-in paths include Codex with an OpenAI account, Claude Code with an Anthropic account, GitHub, AWS, and Datadog. Owner-installed providers can also use protected stdin import when declared by their manifest.

Start the shared cluster and inspect the current state:

```sh
tobari cluster up
tobari auth status
```

Choose a provider interactively:

```sh
tobari auth login
```

Or name the provider directly:

```sh
tobari auth login --provider openai
tobari auth login --provider anthropic
# or: github / aws / datadog
```

The built-in OpenAI login uses a reviewed Codex CLI on the trusted host. The built-in Anthropic login similarly uses host-side Claude Code. At this product snapshot, those helpers require Codex 0.146.0 and Claude Code 2.1.220. The agent binary installed inside the Workspace is not treated as the trusted acquisition helper.

After login, inspect state without printing credential material:

```sh
tobari auth status
```

`auth status` observes both provider storage and whether existing Workspaces have the expected credential projection. **Do not re-enter every Workspace after every authentication mutation by default.** When a specific Workspace projection is missing or stale and re-entry is the supported recovery, the authentication result or `auth status` reports that target and action. Re-enter only when that state asks you to.

For Codex, Tobari projects a project-bound handle rather than the real token into `.codex/auth.json`. For Claude Code, the same idea is exposed through `CLAUDE_CODE_OAUTH_TOKEN`. Gateway resolves the real credential through Auth Broker only for an already authorized exact request.

See [Authentication details](../../guides/authentication/) for provider-specific acquisition, AWS and Datadog behavior, logout, import, and state recovery.

### Let the tool manage its own login

If a tool normally stores its own login state in its home directory, you can instead follow that tool's official login flow inside the Workspace:

```sh
cd /path/to/your/project
tobari

# Inside the Workspace
<agent-command> <its-login-command>
```

With this path, another process inside the same Workspace may be able to read credentials the tool stores there. When Tobari supports the provider and you want the primary credential to remain outside the Workspace, use the host-side path above instead.

## An authenticated API request can still be denied

If the authenticated tool sends an HTTP/HTTPS request that has not been allowed yet, Tobari returns `policy_denied`. That is a network-policy decision, not evidence that login failed.

You do not need to terminate the Workspace session. Leave the agent waiting and open **another trusted-host terminal** for review:

```sh
tobari policy review
```

Inspect the destination, port, method, and path, allow only the traffic you intend, then return to the original Workspace session and issue a new request. The allow operation never replays the denied request automatically.

## Start normal work

You have now completed the first-use path:

1. verified deny → review → allow → deliberate retry with `curl`;
2. built a runtime containing the real coding agent and project tools; and
3. configured the authentication those tools need and checked its Workspace activation state.

Continue normal work with the default setup. When the agent needs a new outbound effect, use the same host-side policy review loop.

For a deeper explanation, continue to the [Mental model](../../how-it-works/mental-model/) or [First denial](../first-denial/).

## Later: separate configurations when you need them

When you actually need different runtimes, authentication sets, or policy modes for different jobs, use named **Contexts**.

Read [Contexts and separate configurations](../../guides/contexts/) when that need appears. Context is not prerequisite knowledge for the first successful authenticated run.
