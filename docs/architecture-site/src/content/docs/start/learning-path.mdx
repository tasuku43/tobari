This path starts by running Tobari and then making it useful for real work. The quickstart uses only `curl` to demonstrate denial and review. Immediately afterward, you prepare a custom runtime containing the coding agent and project tools before reading the deeper architecture and security material.

The standard base runtime is the foundation for checking the boundary and building a custom image. It does not include a coding agent. Completing the quickstart alone does not necessarily produce a usable development environment.

## Five stages that build setup and understanding

1. **Install:** verify the CLI and trusted-host prerequisites, then enter the first Workspace.
2. **Make it usable:** review the first denial and add the agent and development tools to a custom runtime.
3. **Follow the processing path:** trace one request across Workspace, Gateway, OPA, Auth Broker, and upstream.
4. **Authentication, boundaries, and recovery:** understand credentials, guarantees, exclusions, and surviving state.
5. **Exact reference:** consult Catalog-generated CLI contracts, schemas, storage, versions, fault codes, and implementation.

## Recommended 10-step path

### 1. Confirm the scope and install

Read the [overview](../overview/) to identify what Tobari controls and what remains outside the boundary. Then complete [installation](../install/) and verify the CLI, Docker, and trusted-host prerequisites.

### 2. Complete the quickstart and first policy review

Use the [quickstart](../quickstart/) to see an undeclared request denied, reviewed on the host, allowed exactly, and issued again as a new request.

Then read [first denial](../first-denial/) to understand the retained information, the dimensions fixed by an exact rule, and why Tobari never replays the original request.

### 3. Prepare a custom runtime

Use [custom runtime setup](../../guides/runtime-customization/) to create the Dockerfile managed by the current Context and add the coding agent and project tools.

At this point you can enter a real repository and start the selected agent. Review the agent's external requests through the same policy flow used in the quickstart.

### 4. Organize the five components

Read the [mental model](../../how-it-works/mental-model/) to identify what Workspace, Gateway, OPA, Auth Broker, and upstream each execute and which authority each lacks.

### 5. Separate Workspace lifetime from container lifetime

Read [Workspace lifecycle](../../how-it-works/workspace-lifecycle/) to distinguish `exit`, container recreation after a runtime change, `delete`, `cluster down`, and `cluster down --purge`.

### 6. Follow one HTTP/HTTPS request

Read the [request journey](../../how-it-works/request-journey/) and follow one request from Workspace through Gateway and OPA to upstream.

Then read [HTTPS and TLS](../../how-it-works/https-and-tls/) to see `CONNECT`, Workspace-side TLS, policy evaluation, and the separate upstream TLS session as one processing path.

### 7. Understand how policy grows

Read [policy learning](../../how-it-works/policy-learning/) to connect retained denial data, opaque references, exact allow or deny decisions, complete-policy validation, and explicit compaction.

### 8. Separate authentication from network permission

Read [credentials](../../how-it-works/credentials/) and the [authentication guide](../../guides/authentication/). Logging into an external service and allowing an HTTP request are separate authorities.

Login state stored by a coding agent in the Workspace home is not isolated from other processes in the same Workspace. Auth Broker protects only credentials that use an explicitly supported broker path.

### 9. Review guarantees, exclusions, and recovery

Read [guarantees and limitations](../../security/guarantees-and-limitations/) and [trust boundaries](../../security/trust-boundaries/) to pair each guarantee with its prerequisites and exclusions.

Use [state and recovery](../../how-it-works/state-and-recovery/) and [troubleshooting](../../guides/troubleshooting/) to understand what survives exit, container recreation, failure, and deletion, and which recovery action is safe.

### 10. Check your understanding

Complete the [understanding check](../understanding-check/). Before opening an answer, explain which component decides, where processing stops, and which state remains.

## When to use the reference

Use the reference after the first working setup and basic boundary are clear.

- [CLI](../../reference/cli/) is generated from `cli.Catalog`.
- [Runtime image contract](../../reference/runtime-image-contract/) defines the required user, labels, entrypoint, architecture, and other custom-image properties.
- [Configuration and state](../../reference/configuration-and-state/) lists storage, ownership, and lifetime.
- [Faults and recovery](../../reference/faults-and-recovery/) maps fault codes to safe next actions.
- [Component versions](../../reference/component-versions/) shows the artifacts actually selected at runtime.

## Where to return when something is unclear

- If the agent command is missing, return to [custom runtime setup](../../guides/runtime-customization/).
- If Workspace and the work container appear to be the same thing, return to [Workspace lifecycle](../../how-it-works/workspace-lifecycle/).
- If OPA appears to forward traffic, return to the [request journey](../../how-it-works/request-journey/).
- If login appears to grant network permission, return to [credentials](../../how-it-works/credentials/).
- If “encrypted” appears to mean complete protection, return to [credential security](../../security/credential-security/).

## Summary

First use the quickstart to confirm the boundary, then add the agent and development tools to a custom runtime. After that, study requests, authentication, security, and recovery. This sequence produces a usable environment early while still building a precise model of who owns each authority.
