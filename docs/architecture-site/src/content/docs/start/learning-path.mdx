---
title: Learning path
description: "Learn Tobari in the order you need it: policy loop, usable runtime, authentication, internal model, and only then advanced configuration."
---

The first goal is not to understand every Tobari concept. It is to complete one useful workflow with as few new concepts as possible.

Start with the default setup. First experience the policy loop, then make the runtime useful, then authenticate the tools you actually need. Only after that should you expand into the internal architecture, security boundaries, recovery behavior, and configuration switching.

## Five learning stages

1. **See the boundary:** run one request, observe a denial, review it on the host, and retry deliberately.
2. **Make it useful:** add the coding agent and project toolchain, then authenticate them.
3. **Understand the mechanism:** follow one HTTP/HTTPS request and the policy loop in detail.
4. **Understand the boundary:** learn credential paths, guarantees, failure behavior, and recovery.
5. **Split configurations when needed:** learn Contexts, alternate runtimes, and stricter policy only after the default workflow is familiar.

## Recommended eleven-step route

### 1. Understand what Tobari controls

Read [Overview](../overview/). You only need the top-level boundary: what the Workspace can access, what remains on the trusted host, and why outbound HTTP/HTTPS goes through Gateway.

### 2. Experience the policy loop

Complete the [Quickstart](../quickstart/). It intentionally uses `curl` from the minimal base runtime so you can experience denial, host review, exact allow, and a deliberate new request without first choosing a coding agent.

### 3. Build the runtime you actually need

Follow [Prepare a custom runtime](../runtime-setup/). Add your coding agent and project tools, run `tobari runtime build`, enter a real project, and verify the agent executable inside the Workspace.

Keep the default Tobari setup. Configuration switching is not part of this step.

### 4. Authenticate the tools you installed

Follow [Authenticate your tools](../authentication-setup/). Complete the agent's own login when it manages its credentials, and use Tobari's host-side authentication for supported external providers when appropriate.

Login and network permission remain separate. A newly authenticated API request can still be denied and reviewed exactly as in Quickstart.

At this point, the first-use loop is complete: you can start normal work with the default setup.

### 5. Learn the core components

Read [Mental model](../../how-it-works/mental-model/). Now that the workflow is familiar, learn what Workspace, Gateway, OPA, Auth Broker, and the destination each do.

### 6. Follow one request precisely

Read [Request journey](../../how-it-works/request-journey/) and [HTTPS and TLS](../../how-it-works/https-and-tls/). Follow the numbered path from the Workspace, through policy evaluation, to the separately created upstream connection.

### 7. Understand policy review in detail

Read [Policy learning](../../how-it-works/policy-learning/) and [First denial](../first-denial/). Learn exact rules, opaque references, complete-policy validation, and why Tobari never automatically replays the original request.

### 8. Understand credentials and security guarantees

Read [Credentials](../../how-it-works/credentials/), [Authentication details](../../guides/authentication/), [Guarantees and limitations](../../security/guarantees-and-limitations/), and [Trust boundaries](../../security/trust-boundaries/).

This is where you expand from "I can use it" to "I can explain what it guarantees and why."

### 9. Understand lifetime and recovery

Read [Workspace lifecycle](../../how-it-works/workspace-lifecycle/), [State and recovery](../../how-it-works/state-and-recovery/), and [Troubleshooting](../../guides/troubleshooting/). Distinguish shell exit, work-container replacement, Workspace deletion, service failure, and cluster cleanup.

### 10. Learn Contexts only when you need separate configurations

If one default setup is enough, you can postpone this step.

Read [Contexts and separate configurations](../../guides/contexts/) when you need different runtimes, authentication sets, or policy modes for different jobs. Then use [Workspace, Context, cluster](../../how-it-works/workspace-context-cluster/), [Runtime customization details](../../guides/runtime-customization/), and [Advanced policy](../../guides/advanced-policy/) for the exact behavior.

Context is introduced here deliberately. It solves a real need once you have more than one configuration; it is not prerequisite knowledge for the first successful run.

### 11. Check your understanding

Complete the [Understanding check](../understanding-check/). You should be able to explain both the first-use workflow and the security boundary before opening the prepared answers.

## When to use Reference

Use Reference when you need an exact command contract, schema, path, version, or failure code. Do not start there unless you already know which part of the workflow you are trying to inspect.

- [CLI](../../reference/cli/) for exact command behavior.
- [Runtime image contract](../../reference/runtime-image-contract/) for compatibility requirements.
- [Configuration and state](../../reference/configuration-and-state/) for stores and lifetimes.
- [Provider manifest](../../reference/provider-manifest/) for provider contracts.
- [Faults and recovery](../../reference/faults-and-recovery/) for exact failure handling.

## Summary

The default learning order is:

**policy loop → runtime → authentication → normal work → mechanism → security → recovery → optional configuration switching**.

That order is intentional. A concept appears only when the user has a reason to need it.
