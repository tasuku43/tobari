Use this route to move from a minimal policy exercise to a usable coding-agent environment, then into the architecture and security model. The order is intentional: Quickstart proves that communication control works, and the next step installs the agent and project toolchain required for real work.

No prior Tobari knowledge is required. Installation is the only operational prerequisite. Each step links to the full explanation instead of repeating it here.

## Five levels of understanding

1. **Purpose and first proof:** what Tobari controls, followed by one real denial and host-side review.
2. **Usable environment:** a Context-owned runtime containing the coding agent and project toolchain.
3. **Sequences:** Workspace lifecycle, HTTP/HTTPS, policy review, and credential use in time order.
4. **Boundaries and failure:** who owns identity and state, what fails closed, and what Tobari does not protect.
5. **Exact specification:** Catalog-generated CLI, schemas, paths, versions, faults, implementation, and tests.

## Recommended eleven-step route

### 1. What Tobari controls

Read [Overview](../overview/). Be able to say what authority the agent receives, what remains on the trusted host, and which outbound effects Tobari mediates.

### 2. Run the minimal policy exercise

Complete the [Quickstart](../quickstart/). It intentionally uses `curl` from the standard base runtime so you can observe denial, host review, exact allow, and deliberate retry without first choosing a coding agent.

Quickstart does **not** install or verify an agent. Treat it as proof of the policy loop, not completion of the working environment.

### 3. Prepare the runtime you will actually use

Follow [Prepare a custom runtime](../runtime-setup/). Add the coding-agent executable, its language runtime, and the project toolchain to the current Context's managed Dockerfile. Build and validate it, then verify the agent command inside a real project Workspace.

Do not continue to real repository work until that command succeeds. The standard base runtime is intentionally minimal.

### 4. Learn the five-part mental model

Read [Mental model](../../how-it-works/mental-model/). Learn Workspace, Gateway, OPA, Auth Broker, and Upstream without yet expanding every implementation detail.

### 5. Understand Workspace lifecycle

Read [Workspace lifecycle](../../how-it-works/workspace-lifecycle/). Distinguish `exit`, `delete`, runtime replacement, `cluster down`, and `cluster down --purge`.

### 6. Follow one outbound request

Read [Request journey](../../how-it-works/request-journey/) and [HTTPS and TLS](../../how-it-works/https-and-tls/). Follow principal derivation, body-free OPA input, allow or deny, the separately owned upstream connection, and the two TLS sessions used for HTTPS inspection.

### 7. Review policy deliberately

Read [Policy learning](../../how-it-works/policy-learning/) and [First denial](../first-denial/). Explain exact rules, opaque references, all-or-nothing activation, and why the original request is never replayed automatically.

### 8. Configure authentication separately

Read [Credentials](../../how-it-works/credentials/) and the [Authentication guide](../../guides/authentication/). Keep three concerns separate: the tools installed in the runtime, authentication to an external service, and authorization for one HTTP effect.

### 9. Read guarantees with their limits

Read [Guarantees and limitations](../../security/guarantees-and-limitations/) and [Trust boundaries](../../security/trust-boundaries/). For every claim, identify its preconditions, enforcing component, failure behavior, and excluded scope.

### 10. Learn state and recovery

Read [State and recovery](../../how-it-works/state-and-recovery/) and [Troubleshooting](../../guides/troubleshooting/). Explain which state survives shell exit, runtime replacement, service failure, Workspace deletion, and cluster cleanup.

### 11. Complete the understanding check

Complete the [Understanding check](../understanding-check/). Open an answer only after explaining the scenario aloud or in writing.

## When to use Reference

Reference pages answer precise operational questions after the model is understood:

- [CLI](../../reference/cli/) is generated from `cli.Catalog`.
- [Runtime image contract](../../reference/runtime-image-contract/) defines the exact image labels, user, entrypoint, build, and selection rules.
- [Configuration and state](../../reference/configuration-and-state/) lists exact stores and lifetimes.
- [Provider manifest](../../reference/provider-manifest/) separates owner-controlled strict schema 1 from the reviewed built-in schema-2 plans.
- [Faults and recovery](../../reference/faults-and-recovery/) maps codes to safe actions.
- [Component versions](../../reference/component-versions/) is generated from repository authorities.

Do not use a path, schema, or image label as a substitute for understanding ownership. For example, knowing the runtime Dockerfile path does not explain why a successful build changes a Context selection only after compatibility validation, or why existing Workspaces observe that selection on their next entry.

## If a link describes something unexpected

Stop and return to the immediately preceding page:

- if Quickstart seems to prove that an agent is installed, return to [Prepare a custom runtime](../runtime-setup/);
- if Workspace and container seem interchangeable, return to [Workspace, Context, cluster](../../how-it-works/workspace-context-cluster/);
- if login seems to create network permission, return to [Credentials](../../how-it-works/credentials/);
- if OPA appears to forward traffic, return to [Request journey](../../how-it-works/request-journey/); and
- if “encrypted” sounds like a complete security claim, return to [Credential security](../../security/credential-security/).

## Summary

The practical order is: prove the policy loop, prepare a usable runtime, verify the agent inside a real Workspace, and only then expand into architecture, credentials, security boundaries, and recovery. This prevents a successful `curl` exercise from being mistaken for a usable coding-agent environment.

## Check your understanding

<details>
<summary>Why does runtime setup come immediately after Quickstart?</summary>

Quickstart verifies the network-control loop with `curl`, but the base runtime intentionally contains no coding agent. A real repository is usable only after the current Context selects a compatible image containing the agent and required toolchain.

</details>

<details>
<summary>Does installing an agent in the image grant authentication or network permission?</summary>

No. Runtime contents, service authentication, and HTTP authorization are separate controls.

</details>
