A learnable denial stops at Gateway before any upstream connection. Gateway retains bounded, secret-free evidence and directs the user to a host-side review queue. Only an explicit decision and complete policy validation can turn the retained effect into an exact allow or exact deny; the original request is never retried automatically.

This page follows the denial through host review and deliberate retry. Complete the [Quickstart](../quickstart/) first, or be familiar with its separation between host and Workspace commands.

<PolicyLoopMap headingLevel={2} />

## The denial, in time order

1. Gateway derives the Workspace Manifest/project principal from the kernel-observed Workspace source endpoint and the host-owned schema-1 principal registry.
2. It constructs a normalized, body-free policy input and asks OPA once.
3. OPA returns deny for an effect not covered by an allow rule.
4. Gateway does not resolve a native secret, perform DNS for the destination, or create an upstream connection.
5. Gateway returns a bounded `403` response. The response identifies the fixed host review command, not an action reference.
6. Secret-free denial evidence enters the retained review window. Repeated observations of the same exact effect coalesce instead of manufacturing new authority.

## Review is discovery; allow and deny are actions

On the trusted host:

```sh
tobari review permissions
```

The TTY flow lets you inspect pending effects, stage exact choices for one Workspace Manifest, and press **Apply** once after reviewing the set. Canceling before Apply changes nothing. A redirected review is read-only:

```sh
tobari review permissions --format json
```

Machine callers copy the opaque `pcy_...` reference unchanged into exactly one action:

```sh
tobari policy allow --id <pcy-id>
# or
tobari policy deny --id <pcy-id>
```

Display order, a host label, or a hand-built identifier is not authority. The action resolves the retained reference, verifies that it still represents the current denial, modifies owner-only policy data, tests the complete aggregate, and activates one complete revisioned bundle. If validation or activation fails, the previous known-good policy remains active.

## What “exact” means

A learned rule binds:

- stable Workspace Manifest ID;
- host-issued project ID;
- scheme;
- destination host and port;
- HTTP method; and
- path.

The request body is intentionally absent. Two requests that differ only in body content are the same policy effect. Tobari does not inspect a prompt, JSON payload, upload, or form body to infer intent.

An exact learned deny differs from baseline default deny. Baseline deny means no allow matched. An explicit exact deny records a trusted-host decision and does not keep reappearing as a pending learnable candidate. Both stop the request.

## Correcting a decision

Inspect current learned rules:

```sh
tobari policy rules
```

To remove one current decision, copy its opaque rule ID unchanged:

```sh
tobari policy reset --id <policy-rule-id>
```

Reset does not allow the effect and does not replay it. It returns that effect to default deny. A later observed denial can then be reviewed again.

First public V1 keeps learned decisions exact and never combines adjacent
observations into broader authority.

## Failure behavior

- OPA unavailable or an invalid OPA response produces a service failure and no upstream connection.
- Immutable scheme, cluster, principal, or principal-registry binding failures are diagnostics, not learnable candidates.
- An expired or stale candidate reference is rejected; rediscover the queue.
- Concurrent policy change makes a stale action fail rather than guessing.
- Invalid complete policy leaves the previously active policy unchanged.
- A confirmed mutation with uncertain output must be reconciled through read-only state before replay; do not blindly repeat mutation commands.

## Guarantees and limits

Tobari guarantees that observed traffic does not automatically become permission and that routine learned decisions remain exact and project-bound. It does not judge whether a destination is trustworthy, inspect bodies for sensitive information, or stop an already allowed effect from carrying any data the Workspace can read.

## Summary

A denial is a stopped effect plus bounded evidence. Only a trusted-host action against an opaque reference can change policy; validation is all-or-nothing, and retry is always a new deliberate request.

## Check your understanding

<details>
<summary>Two POST requests have the same project, host, port, method, and path but different JSON bodies. Are they two policy candidates?</summary>

No. The body is not a policy identity dimension, so they represent the same ordinary HTTP effect.

</details>

<details>
<summary>Does <code>policy reset</code> change an exact deny into allow?</summary>

No. It removes the learned decision and returns the effect to baseline default deny.

</details>

<details>
<summary>What happens if policy validation fails during allow?</summary>

The candidate is not partially activated. The previous known-good aggregate remains active, and the request remains denied until a later valid action.

</details>
