Tobari starts Gateway and OPA from reviewed immutable image digests. Canonical
source is checked against the embedded runtime snapshots used
by the CLI, while runtime metadata, licenses, and repository gates reject drift
before publication or release.

The default Workspace runtime is a different contract: the released CLI builds
it locally from pinned embedded assets rather than publishing or pulling an
agent-ready image. Read
[Implementation stack](../../how-it-works/implementation-stack/) first for the
role of each image and embedded asset.

## Why source and snapshot both exist

The Go CLI must materialize a runtime directory without downloading executable
policy or Python source at startup. Canonical editable Gateway code lives under
`gateway/`; runtime source under `runtimes/base/`. Byte/content-checked copies
live under `internal/infra/runtimeassets/assets/` for embedding.

The copies are not a second implementation. `check-gateway-source.sh`, `check-authbroker-source.sh`, and `check-runtime-base.sh` reject drift. The dedicated Linux `tobari-expose` and `tobari-permission` helpers are built into that base with a pinned Go builder from one mechanically checked source/module closure; neither is copied from the host executable or shipped as a second archive. `check-exposure-helper-source.sh` rejects closure drift for both Programs. Synchronization is an explicit maintainer operation.

## Immutable and moving identities

`versions.env` pins OPA, the mitmproxy build base, Gateway, and the Debian
build base by `@sha256:` digest. Each digest is the exact runtime identity;
friendly OPA/mitmproxy version strings are repository declarations paired with
those digests. Agent CLI login is stored in the Workspace home and is not a
Tobari image input.

The official base uses a source-derived local tag. It is built from the CLI's
pinned embedded Dockerfile and assets when absent, then checked for the runtime
API, user, entrypoint, and lifetime contract. Tobari does not publish or pull
the combined agent-ready base through GHCR. The inspected local digest records
the bytes that reconciliation actually uses.

Canonical source and a validated local image are two separate facts. A source
change does not alter a running cluster until Tobari builds the corresponding
source-derived local image and reconciliation selects its inspected digest. The
generated [Component versions](/reference/component-versions/) table is the
authority for the pinned upstream inputs this source snapshot actually uses.

At this snapshot, canonical Gateway and base Runtime source plus their embedded
snapshots are the complete V1 image inputs. Image workflows
validate multi-architecture construction with cache-only output. A successful
source test does not publish runtime bytes.

## Build and release controls

- Gateway and the agent-ready base are built locally from pinned source or embedded assets and are never published by Tobari.
- Focused image workflows validate Linux amd64 and arm64 with cache-only output and no package-write permission.
- External workflow actions are pinned to full commit SHAs.
- Release packaging injects CLI version and commit; ordinary builds remain `dev`.
- Base runtime metadata and its consolidated lock record architecture, API, lifetime command, tool source, checksum/signature, and licensing expectations.
- Gateway and runtime image checks prove the absence of unreviewed executables and public TCP listeners.
- Public and release guards check repository boundaries, secrets, licenses, package inputs, and immutable service references. Tobari does not claim a separate code-signing, SBOM-attestation, or externally verifiable provenance system here.

## Startup failure behavior

Missing, mutable where immutable is required, incompatible, or unverifiable images stop reconciliation. Missing embedded assets or source drift fail repository gates. Invalid policy projections or unsafe host/runtime state stop dependent services from becoming ready. Failure does not switch to a different unreviewed image or download scripts dynamically.

  <h2>Guaranteed</h2>
  <div class="prose-block">
    Reviewed service identities are digest-pinned and source/snapshot equality
    is mechanically checked. The static documentation site itself uses a

<aside class="limitation">
  <h2>Not guaranteed</h2>
  <div class="prose-block">
    A digest identifies bytes; it does not prove those bytes have no
    vulnerability. The trusted registries, official agent artifact sources, CI,
    host Docker builder, and reviewed dependency process remain part of the
    supply-chain assumption.
  </div>
</aside>

## You should now be able to explain…

…why “pinned image” and “reviewed source snapshot” are related but different controls.

<div class="question-list">
  <details>
    <summary>Why is the agent-ready base not a published digest?</summary>
    <div class="prose-block">
      Tobari distributes its pinned recipe and integrity checks, then builds on
      the user's Docker host. Gateway and the inspected local runtime digest
      remain separate identities.
    </div>
  </details>
  <details>
    <summary>Why embed Python/Rego source if canonical copies exist?</summary>
    <div class="prose-block">
      The CLI needs deterministic offline materialization. Equality checks keep
      the embedded copies from becoming independent implementations.
    </div>
  </details>
  <details>
    <summary>Does a digest prove an image is safe?</summary>
    <div class="prose-block">
      No. It provides exact identity. Review, tests, vulnerability checks,
      provenance, and trusted infrastructure are additional controls.
    </div>
  </details>
</div>
