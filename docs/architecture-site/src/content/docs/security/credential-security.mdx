Authentication does not grant network permission. Every credential mode still
depends on an independently allowed HTTP effect, and each mode exposes a
different amount of credential state to the Workspace.

In the brokered path, static secrets, renewable provider state, and raw handle
records remain in an encrypted Context vault. The Workspace receives only a
bound handle. Gateway must validate that handle and OPA must allow the ordinary
HTTP effect before one declared post-policy credential action can run.

Read [Credentials](../../how-it-works/credentials/) for the request flow and
[Threat model](../threat-model/) for the assumptions around the trusted
credential infrastructure.

## Three modes have different exposure

| Mode                    | Primary secret location                                         | Workspace-readable value                                                                                     | Gateway responsibility                                                            | Main limit                                                     |
| ----------------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| Tool-native passthrough | Tool’s Workspace home/environment                               | The real credential                                                                                          | Redact known credential headers from OPA/audit; forward after allow               | Workspace processes can read/reuse it                          |
| Static managed adapter  | Host-managed Context credential source mounted only for Gateway | A non-secret profile name can be sent by Workspace; the Gateway-side profile projection is not mounted there | Match configured binding and inject after allow                                   | Bounded static path; provider-specific scope                   |
| Auth Broker             | Encrypted Context vault and request-local Broker memory         | Opaque project-bound handle                                                                                  | Strip, introspect, authorize, then resolve, refresh, or sign by the reviewed plan | Same-Workspace process can use an already projected capability |

### What authorization sees and what lifecycle changes

| Mode                    | OPA decision input                                                                                               | Applicable request target                                                                            | Rotation and logout behavior                                                                                                                |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Tool-native passthrough | The normalized, body-free ordinary HTTP effect after recognized credential values are redacted.                  | Tool-compatible HTTP/HTTPS requests, each constrained by its exact Context/project policy rule.      | Tool-owned. A secret already readable by a process is not withdrawn by Tobari.                                                              |
| Static managed adapter  | The ordinary effect and selected non-secret profile metadata, never the managed secret.                          | One configured Context/project/host/profile and its supported fixed-header path.                     | Host administration replaces or removes the secret. Running environments are not rewritten; reconcile by re-entry where projection changes. |
| Auth Broker             | The ordinary effect plus non-secret provider identity, never the opaque handle, revision, or primary credential. | The provider manifest's exact HTTPS target/header binding plus an independently allowed method/path. | Replacement/logout invalidates old handles. Re-entry supplies current projection. Local logout does not promise provider-side revocation.   |

## Brokered request order

The order is the guarantee. Introspection is non-secret and pre-policy. Static
resolution, Datadog token selection or refresh, and AWS credential export and
signing are post-policy. If OPA denies, none of those actions runs. Gateway
connects only to the declared exact HTTPS target.

Reviewed schema-1 plans preserve that order: AWS refresh/signing uses the
private host companion after allow, while Datadog token selection or fixed US1
OAuth refresh runs inside Broker after allow. Neither provider action runs on
denial, and Workspace still receives only a project-bound handle.

## Binding dimensions

A broker handle record must agree on:

- stable Context ID;
- stable project ID derived from the host principal;
- provider ID;
- credential record and revision;
- exact HTTPS host and port;
- declared source header and syntax;
- declared destination header and transformation.

Method and path are not handle dimensions; OPA constrains them as the ordinary HTTP effect. This separation prevents a handle from becoming authorization by itself.

## Storage and unlock

Each Context has an encrypted `vault.enc`. Its schema-1 AES-256-GCM envelope
binds the stable Context identity as associated data. The encrypted schema-1
payload can hold typed static secrets, opaque AWS host-driver state, Datadog
OAuth-session state, revisions, durable operation barriers, and raw handles.
On Linux, the installation key is the owner-only `auth/keys/root.key`; on macOS
it is a named Keychain item. The Broker starts locked. Reconciliation transfers
unlock material over fixed `docker exec -i` stdin. A vault without its original
key fails closed; Tobari does not quietly create a replacement key and orphan
the old ciphertext.

Unsafe symlinks, non-regular files, weak permissions, unsupported schemas, tampered ciphertext, unknown provider fields, and provider binding collisions reject the affected configuration.

## Rotation, logout, and re-entry

Credential replacement advances the revision and invalidates old handles. Logout removes the local provider record and invalidates its handles. Neither operation promises the remote provider revoked the credential. Neither can edit the environment or open files of processes already running.

Leave and re-enter the Workspace so the reconciled runtime receives the new handle projection. The logical Workspace and its home persist across re-entry.

<aside class="guarantee">
  <h2>Guaranteed</h2>
  <div class="prose-block">
    Broker-managed secrets and renewable state do not enter Workspace
    projection, OPA input, or secret-free audit. A valid handle alone cannot
    cause resolution, refresh, signing, or upstream access without exact binding
    and OPA allow.
  </div>
</aside>

<aside class="limitation">
  <h2>Not guaranteed</h2>
  <div class="prose-block">
    Tool-native credentials remain Workspace-readable. A process in the same
    Workspace can exercise a valid projected handle along an already allowed
    effect. Local logout is not remote revocation.
  </div>
</aside>

## You should now be able to explain…

…why `auth login` and `policy allow` are independent operations.

<div class="question-list">
  <details>
    <summary>Login succeeds. Can the provider endpoint now be reached?</summary>
    <div class="prose-block">
      Not unless normal policy allows the exact HTTP effect. Login configures
      credential material; it does not add a policy rule.
    </div>
  </details>
  <details>
    <summary>
      OPA denies a brokered request. Does Broker resolve then discard the
      secret?
    </summary>
    <p>No. Resolution is not called at all on deny.</p>
  </details>
  <details>
    <summary>Why re-enter after rotation?</summary>
    <div class="prose-block">
      A running process environment cannot be rewritten. Re-entry reconciles the
      new project-bound handle projection.
    </div>
  </details>
</div>
