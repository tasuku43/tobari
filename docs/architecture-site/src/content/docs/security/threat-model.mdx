title: Threat model
description: Assets, adversaries, assumptions, attack paths, mitigations, residual risks, and closed failures for the current Tobari design.
---

This threat model treats every Workspace process as untrusted. Tobari is
designed to limit attempts to reach unselected host or Docker resources,
self-assign another project identity, bypass HTTP policy, or leak agent-owned
login values into policy and audit paths.

The host enforcement base and the user's choices of project root and policy
remain trusted. Compromise of that base is outside these mitigations. Read
[Trust boundaries](../trust-boundaries/) first for the exact placement of
trusted components, untrusted data, and credential state.

## Assets

- Host files outside the selected root.
- Docker control and other Workspace runtime resources.
- Stable Template, Context, Workspace, and Policy Memory authority.
- Host-owned lifecycle state and the persistent Workspace home containing agent-owned login files.
- Integrity of active aggregate policy and principal/authentication projections.
- Secret-free diagnostics and structured CLI output.

The selected root is a working resource, not a protected asset against its own Workspace. Payload confidentiality after an effect is explicitly allowed is also not an asset Tobari can guarantee.

## Adversary capabilities

Assume code inside a Workspace can:

- Read and modify the selected project and Workspace home.
- Start processes and coordinate with other processes in that Workspace.
- Open direct sockets and attempt to bypass Gateway.
- Forge headers, URLs, Context/Workspace-looking IDs, credential-like values, and prompt-like text.
- Copy a credential file and replay it from another Workspace.
- Trigger policy denials, race user review, and send different bodies for the same HTTP dimensions.
- Present invalid certificates or consume upstream-controlled responses.

The model does not assume the adversary controls the host user, Docker Engine,
kernel, Gateway, OPA, host-owned state provider, or reviewed images. Control of
any of those is trusted-base compromise.

## Attack paths and mitigations

### Bypass Gateway

The Workspace’s only network is Docker-internal. A closed output policy and
default route send TCP through its project Gateway; synthetic DNS prevents
pre-policy real-host resolution. Gateway redirects ordinary HTTP/TLS to its
transparent listener and drops forwarding. Result: a direct socket does not
bypass policy, unsupported traffic fails, and Gateway outage does not
fail open.

### Claim another project

Gateway ignores request-supplied project authority. It resolves the
kernel-observed Workspace source endpoint in the host-created schema-1
principal registry. Result: forged headers cannot switch principal;
missing/ambiguous state is denied before OPA.

### Smuggle a secret into policy or logs

Known credential headers are removed or redacted before OPA and audit, and
bodies are never policy input or audit content. Result: those credential and
body classes stay out of the normal decision and retained-evidence paths.
Limitation: the implementation cannot recognize every arbitrary value as a
credential; ordinary query and safe headers can still carry sensitive text into
decision metadata.

### Turn a denial into permission

Gateway returns only a denial and review location. Host discovery produces an opaque reference. Mutation rediscovers current state, validates an exact rule and whole aggregate, checks revisions, and activates atomically. Result: a Workspace cannot approve itself, stale references fail, and no request is automatically replayed.

### Copy or forge a Workspace identity

Gateway derives the principal from the kernel-observed Workspace endpoint and
checks the host-owned Context/Workspace binding before OPA. A copied
file cannot change that authority, and a mismatched source is rejected.

### Read host state through a Workspace

The Workspace has no Docker control mount and no path to host configuration or
state outside its selected root and persistent home. Ownership and mode checks
fail closed before the host uses a state file. Agent login files remain inside
the Workspace home and are not a Tobari authority source.

## Residual risks

- An agent can destroy or leak selected files.
- An allowed exact endpoint can receive malicious content.
- Body-independent policy means an allowed path applies to different bodies.
- Safe query/header metadata may contain sensitive user data the implementation does not classify as a credential; avoid placing secrets there.
- Same-Workspace processes can read the agent CLI files stored in that home.
- Overlapping roots share host file effects across otherwise separate Workspaces.
- Provider logout cannot promise remote revocation and cannot rewrite an already running process environment.
- Certificate-pinned clients fail; unsupported protocols are not mediated by this HTTP/HTTPS boundary.

## Failure semantics

Authorization, principal, Workspace state, and activation faults are closed for
the relevant external effect. Closed does not mean “nothing happened anywhere”:
local computation and selected-root writes before the outbound request remain
possible. Recovery must respect mutation outcome contracts rather than blindly
retrying.

## You should now be able to explain…

…how Tobari responds to proxy bypass, principal forgery, policy self-approval, and credential-file replay.

<div class="question-list">
  <details>
    <summary>
      Workspace B copies a credential file from Workspace A and sends a request
      to the same host. What matters?
    </summary>
    <div class="prose-block">
      Gateway derives B's principal from its registered source endpoint. A
      copied file cannot change B's Context/Workspace authority, and B still
      needs OPA to allow its own ordinary HTTP effect.
    </div>
  </details>
  <details>
    <summary>Why is a different body not a different learned rule?</summary>
    <div class="prose-block">
      The body is streamed only after authorization and is absent from rule
      identity. Workspace Template, project, host, port, method, and raw path
      are the exact learned dimensions.
    </div>
  </details>
