---
title: Audit and privacy
description: What Tobari records for policy learning and diagnosis, what it excludes, and why secret-free does not mean content-free.
---

Tobari retains bounded, secret-free decision metadata so an HTTP effect can be
explained and reviewed. Request bodies, broker handles, resolved secrets, and
configured credential headers are excluded. Ordinary URL paths, query values,
and unclassified headers are not automatically non-sensitive, so “secret-free”
does not mean that no request content can appear.

This page describes the policy and diagnostic record, not a general-purpose
data-loss-prevention system. Read [Request journey](../../how-it-works/request-journey/)
and [Credential security](../credential-security/) first for the request and
credential boundaries that produce this record.

## What enters the decision view

Gateway builds schema-1 input with the trusted principal and normalized HTTP information: scheme, normalized host, fixed port, method, raw and decoded path, multi-valued query, redacted headers, and non-secret authorization metadata. The request body is absent.

Configured/recognized secret headers and broker handles are removed or redacted. The implementation should not be described as an oracle that recognizes every secret-looking string. If a user puts confidential data in a URL path, query, or unclassified header, that value may be part of decision metadata or diagnostics.

## What retained denial evidence contains

Learnable denials use a bounded schema-1 JSON audit record with Context/project identity, host, port, method, path, decision/reason, request ID, timestamp, duration, and secret-free classification metadata. Policy discovery reads bounded Docker logs and groups candidates by the exact rule dimensions.

The body does not split candidates. Query and safe headers can appear in OPA input but do not become current learned exact-rule identity. Review references are SHA-256-derived opaque values; users act on the unchanged reference rather than list order or decoded provider notation.

## What never belongs in the public output

- Primary credentials, root keys, or decrypted vault content.
- Broker handle values.
- Request or response bodies.
- Credential-bearing upstream causes.
- Private organization/account fixtures or accidental build-machine paths. The trusted canonical project root is intentional diagnostic data and can appear in host-side output.
- Raw control characters that could corrupt terminal, TSV, JSON, or Unicode line structure.

Visible projection distinguishes controls, formats, backslashes, and Unicode line separators. It deliberately does not filter printable text merely because it looks like an instruction. External text remains untrusted data.

## Retention and privacy boundaries

Gateway logs are bounded by Docker logging configuration; discovery is a bounded window, not a complete historical ledger. Missing or expired candidate evidence means the operator cannot safely act on it. Learned V1 rules remain exact. This site has no analytics, trackers, runtime API calls, external fonts, or cookies; local theme preference is the only browser state it needs.

## Failure behavior

If audit retention fails, authorization does not change: a denied request stays denied. If a candidate becomes stale or falls outside retention, the host mutation rejects it and requires rediscovery. Diagnostics do not authorize replay.

<aside class="guarantee">
  <h2>Guaranteed</h2>
  <div class="prose-block">
    The supported policy and broker flows intentionally exclude bodies and
    recognized credential material from OPA and retained audit. Public CLI
    output has hostile-text projection and bounded schemas.
  </div>
</aside>

<aside class="limitation">
  <h2>Not guaranteed</h2>
  <div class="prose-block">
    Ordinary path, query, and unclassified header data may itself be sensitive.
    Secret-free means excluded credential/body classes, not a universal
    data-loss-prevention classifier.
  </div>
</aside>
