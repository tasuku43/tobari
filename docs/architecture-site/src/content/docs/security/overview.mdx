Tobari reduces a Workspace's ambient authority over the host, network, policy,
and broker-managed credentials. That claim applies only when Tobari's supported
Docker topology and trusted host services hold. It does not make code inside
the selected project harmless.

Security in Tobari is therefore described as bounded claims, not as a property
implied by the words “container,” “proxy,” or “encrypted.” Each claim names its
assumptions, enforcement point, closed failure, and limitation. Read
the [Mental model](../../how-it-works/mental-model/) and
[System overview](../../how-it-works/system-overview/) first if the components
or request path are unfamiliar.

## Read every claim in five parts

The pages in this section use one discipline:

1. **Claim** — the narrow outcome Tobari asserts.
2. **Preconditions** — what must already be true.
3. **Enforcement point** — the component or topology that makes the claim true.
4. **Failure behavior** — what happens when that point is missing or unhealthy.
5. **Limitations** — nearby outcomes that the claim deliberately does not cover.

“A Workspace cannot reach the public Internet directly” is useful only with its precondition: the Workspace was created by Tobari’s supported Docker configuration. Its enforcement is the dedicated `internal` network and Gateway’s unique dual attachment. Its failure behavior is loss of communication, not an alternate route. Its limitation is equally important: an allowed destination can receive data readable by the Workspace.

## The trusted computing base

Tobari treats the host user, host filesystem controls, Docker Engine, kernel, Gateway, OPA, Auth Broker, root-key backend, and reviewed runtime assets as trusted enforcement infrastructure. The Workspace process and external HTTP services are untrusted. Policy candidates, request attributes, provider manifests, and external response text remain untrusted data even when trusted code parses them.

That distinction explains why a forged project header is useless but a
compromised Gateway is out of scope. Gateway derives project authority from
the host-registered, kernel-observed Workspace source endpoint. If Gateway
itself is malicious, the enforcement point is gone.

## Four boundaries, four different jobs

<div class="comparison-grid">
  <section>
    <h3>Project filesystem</h3>
    <div class="prose-block">
      Immutable Context source access selects a read-only or read-write live
      bind. Unselected host paths and another Workspace home are outside the
      normal mount set; this is not snapshot or other-writer isolation.
    </div>
  </section>
  <section>
    <h3>Network</h3>
    <div class="prose-block">
      The Workspace has no supported direct egress route. Gateway alone crosses
      from its dedicated internal network to egress.
    </div>
  </section>
  <section>
    <h3>Authorization</h3>
    <div class="prose-block">
      OPA decides a normalized HTTP effect. Gateway enforces the result.
      Missing, malformed, or unavailable policy fails closed.
    </div>
  </section>
  <section>
    <h3>Brokered credentials</h3>
    <div class="prose-block">
      Auth Broker keeps static credential state in an encrypted Context vault. A
      Workspace receives only a bound handle; same-revision resolution is
      post-policy.
    </div>
  </section>
</div>

## What failure looks like

- No Gateway: the guarded connection fails.
- No valid principal: Gateway returns `project_principal_unavailable` before OPA.
- OPA unavailable or malformed: Gateway returns `policy_unavailable`; no upstream connection.
- Auth Broker locked or unavailable: a brokered request fails; there is no secret resolution fallback.
- Invalid or stale handle: `credential_handle_invalid`; no passthrough downgrade.
- Invalid policy activation: Tobari preserves or restores the prior source and known projection where possible; if OPA cannot be made healthy, communication remains failed closed rather than assuming the previous service is active.

These are closed failures for the affected path. They do not promise that every process action is rolled back: local file writes inside the selected project may already have happened.

  <h2>What this overview guarantees</h2>
  <div class="prose-block">
    The remaining security pages state narrower claims with explicit

<aside class="limitation">
  <h2>What this overview does not guarantee</h2>
  <div class="prose-block">
    No container boundary protects the selected project root from its own
    Workspace. No policy prevents data exfiltration to an effect the trusted
    user explicitly allowed. No claim survives compromise of the trusted base.
  </div>
</aside>
