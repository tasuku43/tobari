This reference maps Tobari's host-owned configuration, durable runtime state,
shared read-only projections, Docker resources, and selected project files to
their owners and lifetimes. A runtime container is not the source of truth for
a Workspace.

Use the operation table to determine what survives `exit`, `delete`, `cluster
down`, `cluster down --purge`, credential replacement, and runtime rebuild. For
the ownership model behind these paths, read [Workspace, Context, and
cluster](/how-it-works/workspace-context-cluster/) first.

## The three host roots

Tobari resolves standard XDG homes and adds one `tobari` directory:

```text
Configuration  ${XDG_CONFIG_HOME:-$HOME/.config}/tobari
State          ${XDG_STATE_HOME:-$HOME/.local/state}/tobari
Shared data    ${XDG_DATA_HOME:-$HOME/.local/share}/tobari
```

These are protected host paths. Tobari rejects a project root that overlaps
them. Files described as owner-only are also checked for unsafe symlinks,
unexpected file type, ownership, or permissive modes before use.

## Host-owned configuration

| Path below the configuration root                            | Contract and meaning                                                                                                                                                                                       |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `contexts/active.json`                                       | The current/default Context name. It chooses the default for omitted selectors; it is not request authority.                                                                                               |
| `contexts/<name>/context.json`                               | **Stored Context manifest schema 1.** It holds stable Context ID, immutable source access, preset origin/revision snapshot, agent profile, image, policy mode, shell settings, and runtime-build metadata. |
| `contexts/<name>/runtime/Dockerfile`                         | Optional owner-only build recipe created by `runtime init`. Editing it does not select an image.                                                                                                           |
| `contexts/<name>/policy/domains/<canonical-host>/allow.json` | Strict schema-1 authority, per-host methods, GraphQL endpoints, credential host bindings, and learned Allows for one canonical lower-case host.                                                            |
| `contexts/<name>/policy/domains/<canonical-host>/deny.json`  | Strict schema-1 baseline and learned exact Denies for the same host. Every embedded host must match the directory.                                                                                         |
| `contexts/<name>/policy/tobari.rego` and `tobari_test.rego`  | Present for Advanced policy. Guided policy uses the reviewed embedded evaluator.                                                                                                                           |
| `auth/providers/*.json`                                      | Optional strict provider-manifest v1 documents.                                                                                                                                                            |
| `principal-registry/principals.json`                         | Host-issued principal registry schema 1 with exact Workspace/Gateway endpoints, mounted read-only into Gateway by directory.                                                                               |

Do not confuse the stored manifest with public output. `context show` and other
Context-result commands emit **public Context report schema 1**. That report is
a task-owned, secret-free projection. Its version can change independently
from the persisted Context manifest.

## Durable runtime state

| Path below the state root              | Contract and lifetime                                                                                                                                            |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `roots/<hash>.json`                    | Root index schema 1. The hash binds canonical project root and stable Context ID to one Workspace ID.                                                            |
| `instances/<id>/state.json`            | Workspace instance schema 1: logical identity, permanent Context binding, last reconciled image, and diagnostic Docker identifiers.                              |
| `instances/<id>/home`                  | Independent writable Workspace home for tool-native authentication and projected broker handles. It survives exit and container recreation; `delete` removes it. |
| `state.json`                           | Shared cluster state schema 1. It records aggregate revision and shared resource identity, never credential contents or one active Context authority.            |
| `cluster-projections/<revision>/`      | Content-addressed, complete policy and managed-provider projection. OPA receives its policy directory read-only.                                                 |
| `auth/projection/providers.json`       | Normalized, non-secret provider projection schema 1. Owner manifests and reviewed built-ins use exact schema 1.                                                  |
| `auth/contexts/<context-id>/vault.enc` | Encrypted Context vault: AES-256-GCM envelope schema 1 containing payload schema 1 with typed static secrets, revisions, and raw handles.                        |
| `auth/keys/root.key`                   | Linux installation root key: exactly 32 owner-only bytes. On macOS the key is in Keychain instead.                                                               |
| `auth/projects/<project-id>.json`      | Project authentication file registry schema 1.                                                                                                                   |
| `auth/runtime/`                        | Host-owned Gateway runtime Unix-socket directory. Sockets are recreated with services; they are not durable credentials.                                         |
| `runtime/<asset-revision>/`            | Materialized embedded Compose, Gateway, OPA, and Broker runtime assets.                                                                                          |
| journal files                          | Durable markers used to reconcile interrupted multi-step project, cluster, or policy-domain source mutations.                                                    |

Context policy source consists only of the domain tree (plus Advanced Rego).
Tobari composes the domain files into an internal `data.json` only inside a generated immutable
`cluster-projections/<revision>/` directory. Wildcards, IP literals,
non-canonical hosts, host mismatches, unknown or duplicate fields, incomplete
allow/deny pairs, extra files, symlinks, and unsafe modes fail closed.

On macOS, the root-key backend is a generic Keychain password with service
`io.tobari.auth-root.v1` and account `tobari`. On Linux, XDG file protection
separates the host user from Workspaces; it does not claim protection after the
host user is compromised.

Shared read-only agent profiles live below
`${XDG_DATA_HOME:-$HOME/.local/share}/tobari/profiles`.

Auth Broker owns container-private control and runtime sockets. Fixed host
operations reach control; Gateway reaches runtime. Neither is a host-published
service or Workspace mount.

## State outside Tobari's host roots

The selected live project root is mounted according to immutable Context
`source_access`; CLI omission defaults to `read-write`. It belongs to the user,
not to Workspace lifecycle. No Tobari delete or cluster command removes it.

Docker holds runtime containers, networks, shared services, and Gateway CA
volumes. Docker inspection is evidence about current runtime resources; it does
not decide whether a logical Workspace exists. Root index and instance state do.

## What remains after each operation?

| Operation                                | What changes                                                                                                    | What remains                                                                                                                                          |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Shell `exit` or child-command completion | Only the attached exec session ends.                                                                            | Logical Workspace, work container, dedicated network, home, root index, project files, policy, and credentials.                                       |
| `delete`                                 | Removes the exact detached Workspace container, network, root index, instance state, and home.                  | Project-root files, Context configuration/policy, cluster, vault, root key, and other Workspaces.                                                     |
| `delete --force`                         | Performs the same deletion while overriding only the “attached exec exists” guard.                              | It does not broaden the target or delete project-root files.                                                                                          |
| Container or project-network loss        | The next root entry reconciles the missing owned runtime resource.                                              | Logical Workspace identity, Context binding, root index, instance state, home, and project files.                                                     |
| `cluster down`                           | Requires no logical Workspace; removes shared containers and transient shared resources.                        | Contexts, policies, provider manifests, encrypted vaults, installation root key, and Gateway CA volumes.                                              |
| `cluster down --purge`                   | Also removes only the shared Gateway/public CA volumes.                                                         | Contexts, encrypted vaults, root key, and provider configuration. It is not logout.                                                                   |
| `auth logout <provider>`                 | Removes one Context/provider credential and revokes its issued handles locally.                                 | Other providers, policy rules, project files, cluster CA, and root key. It does not guarantee remote revocation.                                      |
| Credential replacement                   | Writes a new credential revision and revokes old handles.                                                       | Workspace identity and home. Running process environments do not change; re-enter.                                                                    |
| `runtime build`                          | Builds, validates, records an immutable local image digest, then atomically selects it for the current Context. | Existing Workspace identity, home, and current container until the next entry reconciles it. A failed build leaves the prior selection authoritative. |

The default official runtime selector
`ghcr.io/tasuku43/tobari/runtime:latest` is a **moving tag**. It is refreshed
only by the documented explicit paths. It is not an immutable digest. A
successful managed runtime build separately records the inspected local image
digest in the Context manifest.

## Failure and recovery

Tobari fails closed on ambiguous state:

- A surviving root index without instance state is reported as `incomplete`.
  Entry does not guess a replacement record; exact deletion is the cleanup
  path.
- An interrupted project, cluster, or policy-domain source journal is
  reconciled under its lock before selection or mutation. Policy recovery
  accepts a staged domain generation only when its immutable aggregate
  revision is already durable; otherwise it restores the verified original.
- A mismatched aggregate revision or failed policy activation blocks dependent
  entry or policy operations until the exact cluster operation completes.
- A missing root key while an encrypted vault exists is a recovery fault.
  Tobari does not generate a replacement key and pretend the vault is new.
- Owner-label or runtime-spec disagreement does not authorize deletion or
  adoption of an unrelated Docker resource.

Run `tobari doctor` to observe prerequisites. Doctor is read-only; it does not
repair, migrate, rotate, delete, or unlock state on its own.

## Guarantees and limits

Tobari guarantees exact ownership checks and durable logical selection within
the supported host/Docker topology. It intentionally does not provide a
snapshot or integrity layer for the selected project root. Overlapping project
roots can observe each other's file changes. The Workspace home can contain
tool-native credentials and non-secret broker handles by design; it must not
contain a brokered primary secret.

## Summary

Configuration says what should exist. Durable host state says which logical
Workspace exists. Docker supplies reconciled runtime resources. The selected
project root remains user data outside the Workspace deletion boundary.

## Check your understanding

You should now be able to explain why deleting a container is not the same as
deleting a Workspace.

<details>
  <summary>Does `cluster down --purge` delete the encrypted vault or root key?</summary>

No. It removes shared runtime resources and additionally the shared CA
volumes. Vaults and the installation root key remain.

</details>

<details>
  <summary>Are the schema-1 Context manifest and schema-1 Context report the same contract?</summary>

No. One is persisted host configuration; the other is the public, task-owned,
secret-free CLI projection. Sharing V1 does not make them interchangeable.

</details>

<details>
  <summary>What survives a successful runtime rebuild?</summary>

The logical Workspace identity, root binding, project files, and Workspace
home. The next entry may recreate only the work container for the newly
selected image.

</details>
