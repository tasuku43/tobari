This reference maps Tobari's host-owned configuration, durable runtime state,
shared read-only projections, Docker resources, and selected project files to
their owners and lifetimes. A runtime container is not the source of truth for
a Workspace.

Use the operation table to determine what survives `exit`, `workspace delete`, `cluster
down`, `cluster down --purge`, credential replacement, and runtime rebuild. For
the ownership model behind these paths, read [Workspace, Workspace Template, and
cluster](/how-it-works/workspace-template-context-workspace-cluster/) first.

## The three host roots

Tobari resolves standard XDG homes and adds one `tobari` directory:

```text
Configuration  ${XDG_CONFIG_HOME:-$HOME/.config}/tobari
State          ${XDG_STATE_HOME:-$HOME/.local/state}/tobari
Shared data    ${XDG_DATA_HOME:-$HOME/.local/share}/tobari
```

These are protected host paths. Tobari rejects a project root that overlaps
them. Files described as owner-only are also checked for unsafe symlinks,
unexpected file type, ownership, or permissive modes before use.

## Host-owned sources and active authority

Editable desired sources are separated by product concept below the config
root: `templates/<template-id>/{template.yaml,policy.yaml}`,
`contexts/<context-id>/context.yaml`, and
`runtimes/<runtime-id>/{runtime.yaml,source/}`. Stable IDs name directories;
display names live in the documents. File edits never change live authority.
Template and Context Plan/Apply validate an exact source fingerprint before
publishing a new active revision. `cluster up` reads only the last-known-good
active generation.

Active authority is concept-separated below `state/authority/`: immutable
typed Template, Context, Policy-Memory, and Workspace objects; complete
content-addressed `generations/<digest>.json` manifests; a small `active.json`
pointer; and recovery journals. A reader verifies and selects one generation,
so cross-resource changes remain atomic without a monolithic editable registry.

Managed Runtime immutable revisions and receipts live below
`state/runtimes/<runtime-id>/`. Editing Runtime source changes no immutable
revision or Template. `runtime build --id RUNTIME_REF` is the only build
boundary, and adopting that revision requires a later Template edit and Apply.

## Durable runtime state

| Path below the state root                   | Contract and lifetime                                                                                                                                                            |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `authority/`                                | Immutable concept objects, complete generation manifests, verified `active.json`, tombstones, and recovery journals.                                                             |
| `runtimes/<runtime-id>/`                    | Immutable Runtime revisions, build receipts, and lifecycle state; editable source remains under the config root.                                                                 |
| Workspace home owned by the Workspace owner | Independent writable home for native login and tool configuration; it survives exit and recreation, and exact `workspace delete --id WORKSPACE_REF --confirm=delete` removes it. |
| `state.json`                                | Shared cluster state and active aggregate receipts; never credential contents or desired authority.                                                                              |
| `workspace-authority-policy/`               | Content-addressed complete policy projections and bounded activation receipt/journal state.                                                                                      |
| `runtime/`                                  | Host-owned Gateway runtime directory; sockets are recreated with services and are not durable credentials.                                                                       |
| `runtime/<asset-revision>/`                 | Materialized embedded Compose, Gateway, OPA, and runtime assets.                                                                                                                 |

Workspace Template policy source consists only of canonical typed policy data
in `policy.yaml`. The current schema is
`tobari.dev/template-policy/v1`: `boundary.methods.deny` is the terminal
Method Boundary, while the closed `semantic.protocols` and
`semantic.providers` trees hold static module rules. Tobari composes it with separate Context Policy Memory into
an internal `data.json` only inside a generated immutable
`cluster-projections/<revision>/` directory. The fixed evaluator is built into
Tobari and appears only inside the Docker-managed policy bundle. Wildcards, IP literals,
non-canonical hosts, host mismatches, unknown or duplicate fields, incomplete
source sets, extra files, symlinks, hardlinks, owner drift, and unsafe modes
fail closed.

The predecessor `v1alpha1` shape is not an ordinary readable source. Its only
decoder belongs to `template migration plan/apply`, which atomically replaces
desired source without changing active authority. A normal Template Plan/Apply
is required afterward.

Host-owned configuration and state are protected by the platform's normal
owner and mode checks. On Linux and macOS, Tobari fails closed after unsafe
ownership, symlink, or schema changes; it does not claim protection after the
host user is compromised.

Shared read-only agent profiles live below
`${XDG_DATA_HOME:-$HOME/.local/share}/tobari/profiles`.

Gateway owns its container-private runtime socket. Fixed host operations reach
only the reviewed adapter boundary; the socket is neither a host-published
service nor a Workspace mount.

## State outside Tobari's host roots

The selected live project root is mounted according to immutable Workspace Template
`source_access`; CLI omission defaults to `read-write`. It belongs to the user,
not to Workspace lifecycle. No Tobari delete or cluster command removes it.

Docker holds runtime containers, networks, shared services, and Gateway CA
volumes. Docker inspection is evidence about current runtime resources; it does
not decide whether a logical Workspace exists. The verified active authority
generation does.

## What remains after each operation?

| Operation                                                               | What changes                                                                                             | What remains                                                                                                      |
| ----------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Shell `exit` or child-command completion                                | Only the attached exec session ends.                                                                     | Workspace, work container, dedicated network, home, Context, Policy Memory, project files, and credentials.       |
| `workspace delete`                                                      | Removes the exact detached Workspace authority, container, network, home, and runtime records.           | Project-root files, Context, Policy Memory, Workspace Template, cluster, host-owned state, and other Workspaces.  |
| `workspace delete --id WORKSPACE_REF --confirm=delete --force`          | Performs the same deletion while overriding only the “attached exec exists” guard.                       | It does not broaden the target or delete project-root files.                                                      |
| Container or project-network loss                                       | The next root entry reconciles the missing owned runtime resource.                                       | Workspace identity, Context binding, active authority generation, home, and project files.                        |
| `cluster down`                                                          | Requires no logical Workspace; removes shared containers and transient shared resources.                 | Workspace Templates, policies, Workspace homes, host-owned state, and Gateway CA volumes.                         |
| `cluster down --purge`                                                  | Also removes only the shared Gateway/public CA volumes.                                                  | Workspace Templates, policies, Workspace homes, and host-owned state.                                             |
| `runtime build --id RUNTIME_REF`                                        | Snapshots, builds, validates, and appends one immutable Runtime revision.                                | Every Workspace Template binding and Workspace remains unchanged; failed and unchanged builds append no revision. |
| edit `template.yaml`; `template plan`; `template apply --plan PLAN_REF` | Reviews and atomically publishes one complete Template revision, including an exact Runtime ID+revision. | Existing Workspace identity, home, and current container until the next entry reconciles it.                      |

The default official runtime is a local image built from the CLI's pinned
embedded recipe when absent. A release-derived local tag identifies the recipe
revision; it is not an immutable digest. A successful managed Runtime build
records the inspected local image digest in installation-wide Runtime history;
Workspace Templates retain only their exact revision binding.

## Failure and recovery

Tobari fails closed on ambiguous state:

- An invalid active generation, contradictory Context/Workspace binding, or
  unknown mutation outcome fails closed. Entry does not infer a replacement
  record or delete reference from Docker state.
- An interrupted source-directory, generation, Runtime, or installation-
  migration journal is reconciled under its lock before selection or mutation.
  Recovery accepts only exact pre/post fingerprints and complete verified
  generation identities; otherwise it restores the verified original.
- A mismatched aggregate revision or failed policy activation blocks dependent
  entry or policy operations until the exact cluster operation completes.
- Missing host-owned lifecycle state is a recovery fault. Tobari does not
  silently invent a replacement authority or pretend the Workspace is new.
- Owner-label or runtime-spec disagreement does not authorize deletion or
  adoption of an unrelated Docker resource.

Run `tobari doctor` to observe prerequisites. Doctor is read-only; it does not
repair, migrate, rotate, delete, or unlock state on its own.

## Guarantees and limits

Tobari guarantees exact ownership checks and durable logical selection within
the supported host/Docker topology. It intentionally does not provide a
snapshot or integrity layer for the selected project root. Overlapping project
roots can observe each other's file changes. The Workspace home may contain
tool-native authentication state and credentials by design. Tobari does not copy
host credentials into that home or broker them in the release surface; the agent
CLI remains their owner.

## Summary

Configuration says what should exist. Durable host state says which logical
Workspace exists. Docker supplies reconciled runtime resources. The selected
project root remains user data outside the Workspace deletion boundary.

## Check your understanding

You should now be able to explain why deleting a container is not the same as
deleting a Workspace.

<details>
  <summary>Does `cluster down --purge` delete Workspace home or host-owned lifecycle state?</summary>

No. It removes shared runtime resources and additionally the shared CA
volumes. Workspace home and host-owned lifecycle state remain.

</details>

<details>
  <summary>Are the stored schema-1 Workspace Template record and the schema-1 public Template report the same contract?</summary>

No. One is persisted host configuration; the other is the public, task-owned,
secret-free CLI projection. Sharing V1 does not make them interchangeable.

</details>

<details>
  <summary>What survives a successful runtime rebuild?</summary>

The logical Workspace identity, root binding, project files, and Workspace
home. The next entry may recreate only the work container for the newly
selected image.

</details>
