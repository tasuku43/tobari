This reference records the tool, image, runtime API, CLI, schema, and source
identities declared by the product snapshot used for this documentation. The
table is generated from repository-owned sources rather than copied into prose.

A software version, OCI tag, immutable digest, runtime API, JSON schema, source
commit, and executable build identity answer different questions. Keep those
identities separate when comparing the site with a local installation.

## How to interpret each identity

| Identity type        | What it answers                                                  | What it does not answer                                    |
| -------------------- | ---------------------------------------------------------------- | ---------------------------------------------------------- |
| Tool version         | Which Go, OPA, mitmproxy, or other build input is selected.      | Which local image bytes Docker currently has.              |
| OCI tag              | Which registry channel or human selector is requested.           | Immutability. A tag can move.                              |
| OCI digest           | Which content-addressed manifest is selected.                    | Whether it satisfies the API required by this source.      |
| Runtime API          | Whether a work image declares the supported Workspace interface. | Whether every package in the image is trusted or current.  |
| Service API          | Whether Gateway or Auth Broker implements the required contract. | Whether the image was reviewed and published as a release. |
| Schema version       | Which exact JSON surface shape is in use.                        | Compatibility of another surface with the same number.     |
| CLI build identity   | Which source, resolver, and service APIs the executable selects. | The current branch name or a release that was not built.   |
| Documentation commit | Which repository snapshot supports this page.                    | A later state of `main`.                                   |

## Repository sources

The generator reads, at minimum:

- `go.mod` for the selected Go language and toolchain contract;
- `internal/infra/runtimeassets/assets/versions.env` for embedded shared
  component versions and pinned image identities;
- canonical runtime metadata below `runtimes/base/`;
- exported runtime API and schema constants in the owning Go packages;
- the CLI Catalog for public JSON output schema versions; and
- the source-build and release-injection contract for CLI build identity.

Generation is checked for drift. Updating an owning source without regenerating
the reference fails the site check.

## Tags and digests are not interchangeable

The default runtime selector is:

<pre>
  <code>{componentVersions.runtime.default_selector}</code>
</pre>

This is a moving development tag. It selects a source channel, but is not
immutable evidence. When Tobari builds a Context-owned runtime, it inspects the
resulting local image and stores its resolved digest separately.

Shared infrastructure uses the values declared in `versions.env`. When a digest
is present, it identifies immutable registry content. A neighboring tag or
human version remains descriptive. Gateway and Auth Broker source trees are
also checked against their embedded snapshots; that source equality is a
separate requirement from image identity.

## Current service API compatibility

The generated **Gateway API 4** and **Auth Broker API 3** rows describe the
interfaces required by the current source. The Gateway and Auth Broker digests
currently selected by `versions.env` are the historical API 3 and API 2
publications. Required API and selected image identity are different contracts.

A standard binary rejects that mismatch before startup. To exercise this source
snapshot, build the repository-owned development images and CLI:

```console
task build:dev
bin/tobari-dev version --format json
```

The result must identify the `development` resolver, required and selected
service APIs, and a compatible pair. Development images are not publication
authority; a future release must use reviewed immutable indexes that implement
the required APIs.

## CLI build identity

`version --format json` is the authoritative machine-readable view of the
executable you are running. It includes:

- CLI version and source commit;
- resolver channel and whether the source is a development source;
- required and selected Gateway API;
- required and selected Auth Broker API;
- the combined compatibility result; and
- the exact development build command and binary when recovery requires them.

A plain source build may still carry the human version label `dev`, but that
label alone is not enough to establish runtime compatibility. Compare the full
build identity with the documentation provenance before treating linked source
as evidence for local behavior.

## Failure and limits

- A missing or malformed governing value makes generation fail; the site does
  not display `unknown` as if it were verified.
- A digest identifies selected content. It does not prove license compliance,
  runtime health, policy correctness, or absence of vulnerabilities.
- A declared version does not prove that the local Docker cache contains the
  image. Startup preflight resolves and inspects required images.
- A runtime selector can move. Reproducible evidence must retain the resolved
  digest.
- Schema numbers are scoped to one surface and are not product release numbers.
- A compatible development pair proves interface compatibility, not release
  publication or independent review.

## Summary

Versions describe named software or interfaces. Tags select channels. Digests
identify immutable OCI content. The build identity explains which resolver and
service APIs a particular executable will use. The generated table keeps these
meanings separate and ties each source-owned value to this documentation
snapshot.

## Check your understanding

<details>
  <summary>Does OPA's software version identify the Gateway image?</summary>

No. They are separate components and identities. The generated table reports
each from its owning source.

</details>

<details>
  <summary>What does <code>tobari version --format json</code> identify?</summary>

It identifies the CLI and source, selected resolver, required and selected
Gateway/Auth Broker APIs, their compatibility, and the exact development
recovery command when applicable.

</details>

<details>
  <summary>Does a pinned image digest prove that the image is compatible with the current source?</summary>

No. Tobari separately inspects the declared API and other runtime or service
contracts. The current historical Gateway/Auth Broker pins are immutable but do
not implement the APIs required by this source.

</details>
