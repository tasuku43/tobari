This glossary defines the terms used across Tobari's execution, network,
policy, authentication, state, and CLI contracts. Logical execution state,
host-owned configuration, shared enforcement, runtime containers,
authentication, and authorization have separate names because they have
different owners and security meanings.

For a first introduction, start with [the five-part mental
model](/how-it-works/mental-model/). Return here when an exact term or a
distinction between related terms matters.

## Execution and ownership

### Tobari

The product, executable, and ownership adjective. Tobari prepares, enforces,
and manages Workspaces and the installation-local Gateway and OPA services.

### Workspace

One replaceable isolated instance owned by a Context. A Workspace has a stable
Workspace ID, an independent home, a last-successful applied-entry receipt, and
reconciled runtime resources. Leaving ends only the attached child session;
deleting the Workspace preserves its Context and Policy Memory.

### project root

The canonical host directory owned by a Context and mounted according to its
bound Workspace Template's immutable `source_access`. Tobari deliberately delegates the
ability to read and modify this root to Workspace processes. It does not snapshot, overlay, or protect
files inside it from Workspace processes.

### Workspace Template

One installation-owned reusable setup with a stable opaque ID and complete
immutable revisions. It owns the source/network Boundary, baseline policy,
exact Runtime binding, and entry/session/creation defaults. It owns neither a
Project binding nor remembered decisions.

### Context

One durable immutable binding between a canonical Project root and one
Workspace Template ID. A Context owns Policy Memory and survives replacement
or deletion of its Workspace. It has no public name or default selector; exact
nondefault actions consume a `context` reference from discovery.

### Policy Memory

The complete immutable remembered-decision revision owned by one Context. It
survives Workspace replacement, is never copied with a Template, and does not
widen the bound Template's fixed Boundary.

### current Workspace Template

The installation default used by bare root entry and bare `status`. Changing it
does not rebind any Context or Workspace and is not request authority.

### cluster

The installation-local shared Gateway, OPA, shared networks, CA volumes, and
aggregate policy projections. Each Context contributes its bound Template
baseline and Policy Memory; the cluster enforces the complete active set.

### runtime image

The OCI image that supplies the Workspace's tools and root filesystem. It must
preserve runtime API `1`, the `tobari` user, fixed lifetime capability, and
entrypoint. It does not choose mounts, network, policy, credentials, or logical
Workspace lifetime.

### work container

The Docker container currently realizing one Workspace. Tobari may recreate it
after image or runtime-spec drift while preserving the logical Workspace,
project root, and home.

### attached session

A transient shell or exact command running through a child `docker exec`
process. `exit` ends this process only. Attachment is not persisted as a
Workspace lifecycle state.

### Workspace home

The independent writable home owned by one Workspace. Agent tools store their
own login state here; Tobari does not project, resolve, or manage a second
credential authority. It survives session exit and work-container recreation,
and is removed by Workspace `workspace delete`.

## Request enforcement

### Gateway

The component that accepts transparently routed Workspace HTTP traffic, terminates
Workspace-side TLS when needed, derives the host-issued Workspace principal,
redacts secrets from decision input, asks OPA once, and—only after allow—opens
the separate upstream connection and streams the body. Gateway enforces the
decision; OPA does not forward traffic.

### OPA

Open Policy Agent. It evaluates one normalized, body-free HTTP decision input
against the loaded aggregate Rego/data projection and returns a decision. It
does not have a Workspace network route, open the upstream connection, or
resolve a native secret.

### upstream

The final HTTP or HTTPS service selected by the authorized request. For HTTPS,
Gateway creates a separately verified TLS connection to this service after the
Workspace-side TLS connection has terminated at Gateway.

### HTTP effect

The normalized authorization unit:
Context ID, Workspace ID, host, port, HTTP method, and path, plus bounded
non-secret protocol metadata. Request body content is not an identity dimension
and does not split policy candidates. The internal schema field for Workspace
identity remains `project_id`.

### TLS connection A

The intercepted HTTPS connection from Workspace to Gateway.
Gateway presents a certificate rooted in Tobari's Workspace-trusted CA and
decrypts the HTTP attributes needed for policy.

### TLS connection B

The independent verified HTTPS connection from Gateway to the upstream.
Intercepting connection A does not mean Gateway sends plaintext HTTP to the
final HTTPS destination.

### Tobari CA

The certificate authority whose public certificate is installed into the
Workspace trust bundle so Gateway can terminate Workspace-side TLS. Trusting
the CA is a transport prerequisite, not an allow rule. Certificate-pinned
clients fail rather than bypass Gateway.

### fail closed

Refuse the effect when required identity, policy, authentication, schema, state, or
ownership evidence is missing, invalid, ambiguous, or unavailable. In the
request path, this means no unauthorized upstream connection.

## Workspace identity

### Workspace ID

A stable host-issued opaque ID for one Workspace. It is not the project root
and is not accepted from a Workspace header as authority. Internal persistence
and enforcement protocols retain the schema-V1 field `project_id` for this
same value.

### Workspace Template ID

The stable host-issued UUIDv7 identity of a Workspace Template. It remains distinct from
the mutable display name and from the current Workspace Template marker.

### Context ID

The stable host-issued identity of one Project-root/Workspace-Template binding.
It owns Policy Memory and is distinct from both Workspace Template ID and
Workspace ID.

### Workspace principal

The trusted pairing of stable Context ID and Workspace ID derived by
Gateway from the exact kernel-observed Workspace source endpoint on a dedicated
network. It scopes policy. Internal implementation and protocol names retain
`project principal` where required by their schema-V1 contract.

### principal registry

The host-owned schema-1 mapping from exact Workspace source endpoint, Gateway
endpoint, and dedicated network to Workspace Template/Workspace identity. Gateway receives
only this directory read-only. Frozen private compatibility fields may retain
older wire labels; they carry the validated Context and Workspace identities
and are not public aliases.
Caller-supplied `X-Tobari-*` text cannot replace the mapping.

### dedicated Workspace network

One Docker internal network belonging to one Workspace. The work container and
one Gateway interface join it. The Workspace cannot join OPA, a peer Workspace,
or a normal external network through the supported topology.

## Policy

### baseline deny

The default policy result when no allow rule matches. It can produce learnable
secret-free evidence for an otherwise valid request. It is not a learned exact
deny entry.

### learned allow

An explicitly activated exact rule for one
Context/Workspace/host/port/method/path effect. It is created only by a trusted
host action after full policy validation and atomic activation.

### learned deny

An explicitly activated exact denial. Unlike the baseline default, it appears
in the learned rule inventory and can be explicitly reset.

### policy candidate

A deterministic proposal folded from retained learnable-denial evidence. It is
not authority and is not an automatic mutation. Body content does not create a
different candidate.

### opaque reference

A validated value produced by a discovery command and consumed unchanged by
one matching action. It is not decoded, reconstructed, shortened, or replaced
by display order.

### policy review

The trusted host-side flow that inspects a candidate and deliberately selects
allow, deny, or no action. Gateway's denial response only points to this flow.

### policy activation

The host process that locks policy state, validates each Context's bound
Workspace Template baseline and Policy Memory, tests the complete all-Context projection, publishes it atomically, reconciles
OPA, and retains or restores the known-good projection on failure.

### reset

Removal of one selected learned decision so matching falls back to default
deny. Reset is not allow and does not retry a request.

## Authentication and credentials

### authentication

An agent CLI establishes or stores login material in its own persistent
Workspace home. Authentication answers which credential the tool presents; it
does not answer whether an HTTP effect may leave the Workspace.

### authorization

OPA's decision about the ordinary HTTP effect, enforced by Gateway. A successful
provider login does not grant network permission.

### tool-native credentials

Credential files and environment values owned by the agent CLI inside one
Workspace. Tobari never inherits host credentials, removes credential values
from OPA input and audit, and forwards the original values only after policy
allow. Processes in the same Workspace can read the tool's state by design.

### Workspace identity

The host-derived Context and Workspace authority used for policy evaluation.
It is independent of an agent CLI's login state and cannot be changed by a
request header.

## State and public contracts

### active authority generation

The verified content-addressed manifest selecting immutable Template, Context,
Policy-Memory, and Workspace objects plus optional default Template selection.
Its small owner-only pointer is atomically published only after the complete
generation is durable. Bare `status` reads this authority without creating or
repairing it; Docker state is observation, not authority.

### AppliedEntry

The last-successful Workspace receipt for one exact Context, Template entry
slice, and Runtime revision. It does not imply that the cluster, execution
material, container, or attachment is currently ready.

### aggregate policy projection

The content-addressed complete projection assembled from all Workspace Templates and
mounted read-only into OPA. One Workspace Template's change becomes authority only after
the whole candidate validates and activates.

### Catalog

The `cli.Catalog` public source of truth for command path, typed inputs,
effects, roles, outputs, reference flow, mutations, failures, and recovery.
Routing, help, and generated CLI reference derive from it.

### command role

`utility`, `discover`, or `act`. Discovery may produce opaque references. An
action has exactly one reference-bound or command-owned fixed-target mode.

### operation effect

`read`, `create`, or `write`. Every externally visible operation declares one;
unknown effects fail closed.

### mutation contract

The declared intent, target binding, impact dimensions, and confirmed outcome
required before and after an external create or write.

### source snapshot

The canonical Gateway source tree. The CLI embeds a byte-checked runtime
snapshot for orchestration. Drift checks prevent the embedded copy from becoming
a second editable implementation.

## Common distinctions

| Do not collapse                            | The difference                                                                                                                  |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| Workspace and work container               | The Workspace is durable logical state; the container is replaceable runtime.                                                   |
| Workspace Template and cluster             | Workspace Template scopes one setup and its authority; the cluster runs shared enforcement for every loaded Workspace Template. |
| authentication and authorization           | A credential can exist while OPA still denies the HTTP effect.                                                                  |
| CA trust and policy allow                  | CA trust enables inspection; allow authorizes one normalized effect.                                                            |
| Workspace identity and tool login          | Host-derived identity is separate from agent-owned login state.                                                                 |
| `exit` and `workspace delete`              | Exit ends a child session; delete removes the logical Workspace and home.                                                       |
| `cluster down --purge` and provider logout | Purge removes shared runtime and CA volumes; provider logout remains a provider-CLI operation.                                  |
| tag and digest                             | A tag can move; a digest identifies immutable OCI content.                                                                      |
| stored authority and report schema         | The stored Workspace Template record and public Template report are distinct schema-1 contracts.                                |

## Failure and limits

These definitions describe the supported implementation. They do not broaden
Tobari's threat model. In particular, “untrusted Workspace” does not mean that
the selected project root is protected from that Workspace, or that data
cannot be sent to an explicitly allowed destination.

When two terms appear to conflict, do not choose one by display order or
convenience. Return to the governing contract and the exact boundary. Tobari
fails closed when trusted identity, schema, ownership, policy, or credential
state is missing or ambiguous; vocabulary is not a fallback source of
authority.

## Summary

Tobari separates durable execution identity, host configuration, shared
enforcement, runtime realization, credential possession, and network
authorization. Use the exact term for the exact boundary.

## Check your understanding

You should now be able to explain Tobari without using “container,” “Workspace Template,”
and “Workspace” as synonyms.

<details>
  <summary>A process has a valid Workspace identity. Is it authenticated and authorized?</summary>

It has a credential capability candidate, not complete authority. Authentication must
match Workspace Template, project, provider, revision, and HTTP binding; OPA must
separately allow the ordinary HTTP effect before the declared resolve, refresh,
or signing action.

</details>

<details>
  <summary>The installation default Workspace Template changes. Does an existing Context or Workspace move to it?</summary>

No. A Context's Workspace Template ID binding and a Workspace's Context ID
binding are permanent. The installation default is used only by bare root entry
and bare `status`.

</details>

<details>
  <summary>Who actually opens an allowed upstream connection: Gateway or OPA?</summary>

Gateway. OPA evaluates and returns a decision; it does not forward traffic.

</details>
