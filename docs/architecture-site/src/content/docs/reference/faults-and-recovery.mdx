This reference defines Tobari's stable fault kinds, exact codes, process exit
codes, retry metadata, and Catalog-owned recovery actions. The generated table
comes from exact-command agent help, so it stays aligned with the public CLI
contract.

Classify a failure by `kind` and `code`, then use its declared next action.
Never infer that a mutation is safe to repeat from an upstream message or a
rate-limit timer. For diagnosis that begins with a visible symptom, use
[Troubleshooting](/guides/troubleshooting/); this page begins with the machine
fault.

## Public fault envelope

With `--error-format json`, a CLI failure is schema 2:

```json
{
  "schema_version": 2,
  "error": {
    "kind": "canceled",
    "code": "operation_canceled",
    "message": "The operation was canceled.",
    "phase": "precondition",
    "change_state": "none",
    "retryable": true,
    "retry_after": null,
    "next_actions": [
      {
        "command": "doctor",
        "reason": "Retry when the caller is ready."
      }
    ]
  }
}
```

`message` is safe human text, not an upstream response body. Wrapped causes
remain available inside the implementation for classification but are omitted
from the public projection because they may contain a request URL, credential,
or unstable provider prose.

`phase` is `precondition`, `observation`, `mutation`, `verification`,
`attachment`, or `presentation`. `change_state` is `not_applicable`, `none`,
`partial`, `confirmed`, or `unknown`. These fields report the strongest fact
proved by the layer that owns the boundary; they do not form a second cause
taxonomy. For a mutation, `partial`, `confirmed`, and `unknown` always lead
first to a declared read-only reconciliation command.

## Stable kinds and exit codes

| Kind             | Exit | Recovery class                                                                            |
| ---------------- | ---: | ----------------------------------------------------------------------------------------- |
| `invalid_input`  |    2 | Correct the invocation before any effect.                                                 |
| `internal`       |    3 | Inspect a Tobari implementation or local adapter failure.                                 |
| `authentication` |    4 | Establish or repair identity/credential state. This does not grant network authorization. |
| `permission`     |    5 | The caller lacks permission for the requested operation.                                  |
| `not_found`      |    6 | Discover or create the required local target.                                             |
| `ambiguous`      |    7 | Make one explicit selection; do not choose by display order.                              |
| `rate_limited`   |    8 | Respect authoritative rate-window evidence, then reassess logical retry safety.           |
| `unavailable`    |    9 | Restore a required component or external prerequisite.                                    |
| `rejected`       |   10 | The request was understood but violates the current contract or state.                    |
| `canceled`       |   11 | The caller stopped the operation; reconcile mutations before replay.                      |
| `unsupported`    |   12 | Use a documented supported path.                                                          |
| `contract`       |   13 | Producer and consumer contracts disagree; fail closed and repair the contract.            |

Success is exit 0. The kind is deliberately broader than the code: several
task-specific codes can share one recovery class.

## How to decide whether to retry

Use this order:

1. Determine whether the operation is read-only or a mutation.
2. Read `retryable` and any `retry_after`.
3. For a mutation, read `phase` and `change_state`; reconcile `partial`,
   `confirmed`, or `unknown` through the declared read.
4. Follow only the declared next action.
5. Retry deliberately after the precondition is restored.

`retry_after` describes an observed rate window. It does not prove that a
create or write did not complete. Conversely, a non-retryable fault can still
name a read-only reconciliation action such as `status`, `template show`, or
`doctor`.

Mutation results cross a completion boundary after a confirmed side effect.
Later cancellation cannot turn that success into replay permission. An
unclassified mutation outcome becomes
`unclassified_mutation_outcome` and directs the caller to read-only
reconciliation.

## Request-path failures are fail closed

Not every network failure is a CLI fault envelope. A Workspace observes an
HTTP response or a failed connection from Gateway:

| Observation                                                    | Meaning                                                                                                                          | Upstream contacted?                                                        |
| -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Learnable HTTP `403` denial                                    | The normalized Context/Workspace/host/port/method/path did not match an allow rule. Review on the host, then retry deliberately. | No.                                                                        |
| Non-learnable HTTP `403` denial                                | The request is outside a learnable boundary or its identity is invalid. It cannot become a candidate.                            | No.                                                                        |
| Policy service unavailable or invalid decision (`503`)         | Gateway could not obtain one valid OPA decision.                                                                                 | No.                                                                        |
| Upstream DNS, TLS, connection, or response failure after allow | Authorization succeeded, but the separate upstream operation failed.                                                             | A connection may have been attempted; Gateway does not replay the request. |

A policy denial can become a candidate only from retained, secret-free
evidence. The Gateway response contains host-side navigation guidance, not a
candidate reference and not permission.

## Fault-contract failures

The public boundary has two last-resort contract codes:

- `invalid_fault_contract` replaces a structured fault whose kind, code,
  message, timing, or next action is malformed.
- `undeclared_fault_contract` replaces a command fault whose code, kind,
  phase, change state, or retryability does not match that command's Catalog
  declaration.

These codes prevent unstable internal errors from silently becoming public API.
They are implementation diagnostics, not provider-specific failures.

## Guarantees and limits

Tobari guarantees stable classification only for the supported public
boundary. Docker, OPA, provider, or OS text shown as bounded diagnostics is not
a stable fault code and must not be parsed. A recovery command can restore a
precondition; it cannot promise remote revocation, external-service
availability, or safe replay of an arbitrary HTTP body.

## Summary

A fault kind selects a recovery class; a code identifies the exact condition.
Retryability and rate timing do not replace mutation reconciliation. Gateway
denials, OPA failures, and invalid Workspace identities all fail before unauthorized
upstream traffic.

## Check your understanding

You should now be able to explain why “try it again” is not a universal recovery
instruction.

<details>
  <summary>An OPA request times out. Does Gateway send the request upstream while policy recovers?</summary>

No. Gateway requires one valid decision. Policy unavailability fails closed
before the upstream connection.

</details>

<details>
  <summary>A write reports cancellation. Is exit code 11 enough to justify replay?</summary>

No. Inspect the mutation outcome and current state first. Cancellation can
occur after an external effect.

</details>

<details>
  <summary>Can you append a provider error string to a Catalog recovery command?</summary>

No. Recovery commands are exact checked paths. Upstream prose is untrusted
data, not argv.

</details>
