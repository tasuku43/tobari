## What question does this page answer?

**Which Tobari commands exist, and what is the exact contract of each command?**

The short answer is: the public command specification lives in the Go
`cli.Catalog`. The reference below is generated from that Catalog through
Tobari's machine-readable help. It is not a separately maintained command
list.

After reading this page, you should be able to:

- choose a command by its user outcome instead of by an internal provider
  operation;
- tell a read, create, or write effect apart before invoking it;
- identify required inputs, defaults, conflicts, prerequisites, and output
  coverage;
- follow opaque references from discovery to one exact action; and
- handle a declared fault without constructing unchecked command text.

If these terms are new, read [the mental model](/how-it-works/mental-model/)
before using the complete contract.

## How to read the contract

Every command has one exact path and one complete specification:

| Field             | Meaning                                                                                                              |
| ----------------- | -------------------------------------------------------------------------------------------------------------------- |
| Outcome           | The user task the command closes.                                                                                    |
| Role              | `utility`, `discover`, or `act`.                                                                                     |
| Effect            | `read`, `create`, or `write`. Unknown effects are invalid.                                                           |
| Inputs            | Typed positional arguments and flags, including cardinality, omission behavior, bounds, dependencies, and conflicts. |
| Output            | Formats, fields, JSON envelope and schema version, delivery mode, and collection coverage.                           |
| Prerequisites     | State that must already exist before the operation can succeed.                                                      |
| Failures          | Stable kind, code, retryability, and catalog-owned next actions.                                                     |
| References        | Opaque values produced by discovery or consumed unchanged by an action.                                              |
| Mutation contract | Intent, target binding, impact, and confirmed outcome for a create or write.                                         |

`utility` performs a self-contained task. `discover` returns candidates and,
where required, opaque references. `act` changes one target. An action either
consumes exactly the required opaque reference or uses one command-owned fixed
target. It does not rediscover or decode an identifier.

The root agent-help view is intentionally a small capability index. Use an
exact command or namespace selector for the full contract:

```console
tobari help --format agent
tobari help policy --format agent
tobari help policy allow --format agent
```

Dash-prefixed flag values use the equals form. A dash-prefixed positional value
follows the positional-only marker. The generated invocation grammar below is
authoritative for the built commit.

## Failure and recovery rules

A normal command failure can be rendered as text or as error JSON schema 1.
The machine form contains:

```json
{
  "schema_version": 1,
  "error": {
    "kind": "canceled",
    "code": "operation_canceled",
    "message": "The operation was canceled.",
    "retryable": true,
    "retry_after": null,
    "next_actions": [
      {
        "command": "doctor",
        "reason": "Retry when the caller is ready."
      }
    ]
  }
}
```

Treat `kind` as the broad recovery class and `code` as the exact programmatic
condition. `retryable: true` is permission to consider a retry, not proof that
a mutation is safe to replay. `retry_after` is rate-window evidence and is
independent from logical replay safety. For an interrupted mutation, inspect
the command's outcome contract and reconcile state before retrying.

Recovery commands come from the Catalog. They are exact command paths, or
`help <exact-path-or-namespace>`. Do not append untrusted text from an upstream
error.

Two fail-closed diagnostics protect the fault boundary itself:
`invalid_fault_contract` replaces a malformed structured fault, and
`undeclared_fault_contract` replaces a command fault that does not match its
Catalog declaration. These diagnostics indicate a Tobari contract defect, not
an ordinary provider response.

## Limits of this reference

- Human wording may improve without changing a stable machine field.
- The Catalog describes the supported public CLI. It does not expose raw
  vendor routes, Docker commands, broker protocols, or arbitrary HTTP calls.
- The generated contract describes command behavior. It does not make an
  external service available or grant network permission.
- A complete delivery mode does not imply exhaustive provider history.
  Collection coverage is declared separately.
- The source build normally reports version `dev`. Release automation injects
  a release version and source commit; this page does not invent a release
  number.

## Summary

The Catalog is the public CLI source of truth. Generated help exposes its
typed grammar, output, reference flow, mutation facts, failures, and recovery.
The site reads that contract; it does not create a second registry.

## Check your understanding

You should now be able to explain why a copied list of command names is not an
adequate CLI reference.

<details>
  <summary>Why does `policy allow` consume an opaque reference?</summary>

Discovery and action are separate. The reference binds the host-side action
to one reviewed candidate without asking the action to rediscover, decode, or
reconstruct its identity.

</details>

<details>
  <summary>Does `retryable: true` make every failed write safe to repeat?</summary>

No. It classifies the fault. A mutation may already have completed, so its
structured outcome and the current state must be reconciled before replay.

</details>

<details>
  <summary>Where do you look for an argument's default and conflicts?</summary>

In exact-command agent help, generated from the command's Catalog inputs.
The root help index intentionally omits that detail.

</details>
