title: JSON schemas and versioned contracts
description: Public JSON envelopes, persisted documents, internal protocols, strict parsers, and compatibility boundaries.
---

This reference lists Tobari's versioned JSON surfaces and their compatibility
boundaries. A public CLI report, persisted manifest, Gateway policy input,
audit line, and Broker socket frame are separate contracts even when they
describe related objects.

Each version belongs to one specific surface. A statement such as “the Context
schema is 5” is incomplete until it identifies stored configuration, public
output, or another named contract. The owning parser, Catalog entry, or
protocol implementation is the source of truth for each surface below.

## “Schema” does not always mean JSON Schema

Tobari uses explicit `schema_version` fields and strict readers for many JSON
contracts. The repository does not currently publish a formal JSON Schema
document for every surface. In particular, provider manifest v1 is enforced by
the Go parser and validator, with a canonical synthetic fixture recorded in the
harness ledger. That fixture's digest proves fixture identity; it is not a
general-purpose JSON Schema.

For public CLI output, the Catalog declares the JSON envelope and schema
version. Contract tests execute the renderer and compare the produced
`schema_version` to the Catalog. For persisted or internal documents, the
owning domain or infrastructure reader defines validation and compatibility.

generated on the [CLI reference](/reference/cli/). Do not infer a field from
another envelope merely because the two objects share a name.

### Context version boundary

This distinction is important:

```text
Host configuration
  contexts/<name>/context.json
  Context manifest schema 5

CLI presentation
  {"schema_version": 8, "context": ...}
  public Context report schema 8
```

The report adds task-owned runtime, cluster, complete shell-setting, and
secret-free authentication interpretation. It is not the bytes
stored in `context.json`.

## Persisted host contracts

| State                                  | Current contract          |
| -------------------------------------- | ------------------------- |
| Context manifest                       | Schema 4                  |
| Root index and Workspace instance      | Schema 2                  |
| Shared cluster state                   | Schema 3                  |
| Project principal registry             | Schema 2                  |
| Guided policy data                     | `tobari.schema_version` 2 |
| Aggregate policy projection marker     | Schema 1                  |
| Owner provider manifest                | Schema 1                  |
| Reviewed built-in provider manifest    | Schema 1 or 2             |
| Normalized provider projection         | Schema 2                  |
| Encrypted Context vault                | Envelope 1; payload 2     |
| Workspace authentication file registry | Schema 1                  |
| Base runtime metadata                  | Schema 1                  |

Readers reject malformed, oversized, unsafe, or unsupported state according to
the owning contract. Strictness is surface-specific: do not assume that every
JSON reader accepts or rejects an unknown field in the same way. Provider
documents, principal state, broker frames, and critical runtime state use
explicit fail-closed validation.

Legacy compatibility is also surface-specific. For example, the Context store
has deliberate upgrades from earlier manifest versions, while legacy
singleton state can require cleanup with an older Tobari. A future version is
not automatically accepted.

## Gateway, OPA, audit, and broker contracts

| Boundary                                     |                                               Current contract | Important content rule                                                                                                              |
| -------------------------------------------- | -------------------------------------------------------------: | ----------------------------------------------------------------------------------------------------------------------------------- |
| Gateway credential configuration             |                                                       Schema 2 | Context-aware managed projection; contains paths/metadata, not policy authority.                                                    |
| Gateway → OPA decision input                 |                                                       Schema 5 | Host-derived principal plus normalized HTTP attributes. No body and no client secret headers.                                       |
| Guided/Advanced source policy input          | Source schema 4; legacy source schema 3 accepted for migration | Aggregate generation rewrites the supported source to runtime input schema 5 before complete validation.                            |
| Gateway audit line                           |                                                       Schema 2 | Secret-free normalized decision evidence.                                                                                           |
| Gateway learnable-denial navigation response |                                                       Schema 1 | Fixed host review guidance; no candidate ID, query, body, or secret.                                                                |
| Broker control protocol                      |                                                       Schema 1 | Bounded newline-delimited JSON over the host control Unix socket.                                                                   |
| Broker runtime protocol                      |                                                       Schema 1 | Introspection is non-secret; a post-allow static resolve, Datadog token action, or AWS signing response uses Gateway's Unix socket. |
| Private host companion frames                |                                                       Schema 1 | Authenticated, direction-bound, strictly sequenced frames carry only the compiled post-policy AWS operation.                        |
| Workspace broker handle                      |                                               Handle version 1 | Opaque `tobari-h1_…` value; never decode it into authority.                                                                         |

OPA output is a decision consumed by Gateway. OPA does not open an upstream
connection. A wrong or unavailable policy response fails closed before
upstream connection.

Both Broker protocols use bounded newline-delimited JSON frames. Unlock and
credential-import operations carry their declared, length-bounded raw payload
after the control frame; those secret-bearing bytes are not JSON metadata.

## Compatibility rules for consumers

- Select behavior by the exact envelope and `schema_version`.
- Treat unknown versions as unsupported. Do not silently coerce them to the
  newest known shape.
- Preserve absent versus explicit empty, zero, or false when the contract says
  the distinction matters.
- Treat opaque references and handles as exact bytes. Do not decode, normalize,
  truncate, or reconstruct them.
- Do not infer identity or relationships from labels, array order, proximity,
  or human indentation.
- Do not read internal state files as a substitute for a supported public CLI
  result.

## Failure and limits

A schema mismatch is a contract or compatibility failure, not permission to
guess. Tobari preserves known-good policy or runtime selection when candidate
validation fails. Invalid broker frames and invalid Tobari-looking handles fail
closed. Public errors omit arbitrary wrapped upstream prose because it may
contain URLs, response bodies, or credentials.

This page records current contracts; it is not a promise that every internal
format is a public extension point. Only the Catalog and explicitly documented
external contracts are supported public boundaries.

## Summary

Schema versions are local to a boundary. Stored Context schema 4 and public
Context report schema 8 are both correct because they govern different
documents. Exact readers and tests, not a shared number, define compatibility.

## Check your understanding

You should now be able to explain why a schema number is incomplete without
its surface.

<details>
  <summary>Is `synthetic-provider-v1.json` a formal JSON Schema?</summary>

No. It is the canonical synthetic fixture used with the strict Go parser,
validator, normalization, and tests.

</details>

<details>
  <summary>Can an Advanced policy written for source input schema 4 be sent unchanged to runtime OPA input schema 5?</summary>

No. Aggregate generation validates the supported source contract, rewrites
it into the Context-isolated runtime schema 5 projection, then tests the
complete candidate before activation.

</details>

<details>
  <summary>May a client decode an opaque reference to recover an ID?</summary>

No. It must preserve and return the exact validated value to the command that
consumes its reference kind.

</details>
