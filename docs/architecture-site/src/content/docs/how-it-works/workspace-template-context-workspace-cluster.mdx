title: Workspace Template, Context, Workspace, and cluster
description: Understand reusable desired setup, Project memory, applied instances, and shared enforcement.
---

Tobari separates four product lifetimes:

| Concept            | Owner and lifetime                                     | Authority                             |
| ------------------ | ------------------------------------------------------ | ------------------------------------- |
| Workspace Template | reusable installation setup                            | TemplateID + semantic revision digest |
| Context            | one location-free TemplateID binding                   | ContextID                             |
| Policy Memory      | remembered decisions for one Context                   | ContextID + semantic digest           |
| Workspace          | replaceable ProjectRoot-bound instance for one Context | WorkspaceID + ContextID               |

A Template revision is desired setup. A Context resolves the current revision
of its bound Template and owns learned policy. A Workspace records the last
successful AppliedEntry. Docker observation is evidence, not any of these
authorities.

## Independent activation

- Template mutation publishes desired state only.
- `cluster up` activates one complete projection for every Context, with
  separate Template-policy and Policy-Memory receipts.
- bare root reconciles one CWD-owned Workspace; `context use` only changes the
  location-free current selector.
- status, list, show, doctor, and completion never reconcile.

The installation current Context supplies Context-aware omissions and binds
creation at a root without a Workspace. If it already owns a Workspace at
another root, explicit create-here publishes a sibling Workspace without
changing current. Existing Workspace selection comes
only from CWD and follows the Workspace's permanent Context binding. An exact
option is an invocation-local override:

```sh
tobari context list --format json
tobari context use --id CONTEXT_REF
```

ContextID uniqueness is the only Context uniqueness rule. Multiple Contexts
may bind the same Template. ProjectRoot belongs only to Workspace authority;
each Context retains independent Policy Memory.

## Failure and retry

Desired, active, applied, and observed facts remain separate after failure.
Attached pending adoption blocks before Docker and asks the user to end the
active session. Unknown mutation outcome routes to read-only classification and
never grants replay. Missing Runtime material routes to `review runtimes`,
which owns the exact restore reference.

The shared cluster is infrastructure, not a fifth durable product authority.
It runs Gateway and OPA for the complete Context projection and preserves the
last known-good aggregate when candidate activation fails.
