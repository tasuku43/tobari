Tobari uses network topology as part of its enforcement boundary. In the
supported topology, each Workspace joins only its own Docker-internal project
network. Gateway is the only component with both a project-network interface
and an egress interface. Ordinary HTTP/HTTPS sockets have only the guarded
transparent path to the public Internet, which converges at Gateway.

Three network scopes keep work traffic, policy control, and external egress
separate. Gateway crosses the necessary scopes; OPA and Auth Broker have
narrower attachments. An allowed request can leave through Gateway, while a
Gateway or OPA failure closes the path. The [five-part mental model](/how-it-works/mental-model/) introduces the participants shown below.

## Three network scopes

### A dedicated network for each Workspace

Tobari creates one Docker network per logical Workspace with Docker's `internal` property. The work container joins only that network. Gateway is connected to it with the alias `gateway`.

The container receives the Tobari CA bundle, but no Tobari-managed HTTP proxy
variables. A closed output policy, a default route through the exact project
Gateway, and Gateway-backed synthetic DNS deliver ordinary HTTP/TLS to the
transparent listener. Gateway exposes no separate explicit-proxy listener.

### One internal control network

OPA joins the shared `control` network, not project networks or egress. Workspace processes therefore cannot call OPA's policy endpoint directly.

Gateway also joins control so it can call one fixed OPA endpoint. Auth Broker
joins control and egress, but exposes no TCP listener. Host commands and Gateway
reach its distinct Unix sockets through controlled mounts and fixed operations;
neither socket is available to a Workspace or OPA. A separate Broker-private
companion socket exists only inside the Auth Broker container namespace and is
bridged by one authenticated reverse `docker exec -i` session to the resident
trusted-host companion. It is not mounted into a Workspace or published on the
host.

### One egress network

Gateway joins `egress` so it can resolve and connect to an allowed destination.
Auth Broker uses egress only for its compiled post-policy Datadog refresh plan
at one exact US1 token endpoint. Interactive GitHub, AWS, and Datadog
acquisition runs through fixed drivers directly on the trusted host, not over
Broker egress. A work container never joins this network.

The essential ordering is:

1. traffic arrives through the Workspace's dedicated network;
2. Gateway establishes the host-issued principal;
3. Gateway asks OPA once with body-free normalized input;
4. only after allow does Gateway resolve and pin an upstream address;
5. Gateway opens one upstream connection and streams the request; and
6. Gateway records bounded, secret-free audit metadata.

There is no application-layer automatic retry. Redirects are independent requests and must be authorized again.

## Trust boundaries in the same system

<ConceptDiagram name="trust-boundaries" />

The Workspace and upstream are untrusted. The host, Docker execution substrate, Gateway, OPA, Auth Broker, and their owner-controlled state are trusted enforcement infrastructure. “Trusted” means Tobari's claims depend on them; it does not mean they cannot contain bugs.

## Concrete bypass attempts

### The process opens a direct socket

Its TCP connection follows the guarded default route to the project Gateway.
Ordinary HTTP/TLS is redirected to Gateway's transparent listener and receives
the same authority validation and OPA decision. Unsupported traffic fails;
none of it is forwarded as general routed TCP.

### The process calls `opa:8181`

OPA is not attached to the Workspace network, so the name/service is not reachable from that container.

### The process targets another Workspace

Each Workspace has a distinct internal network. There is no peer route. Gateway joins both, but it does not act as a general router between them.

Host file roots are a different boundary: two Workspaces may intentionally mount the same or overlapping project roots. Their networks, homes, principals, and learned rules remain separate, while writes to overlapping host files are visible to both.

## Failure behavior

- **Gateway unavailable:** transparent ingress cannot accept the connection. Direct egress is still absent.
- **OPA unavailable, slow, non-200, oversized, malformed, or incomplete:** Gateway returns `503 policy_unavailable`; it does not resolve or connect upstream.
- **Unknown Context in the aggregate policy:** the fixed OPA router denies; it does not fall back to the current/default Context.
- **Unsafe dotted-host DNS result:** Gateway rejects non-global addresses and does not silently choose a different authority. This is an upstream/proxy failure, not a stable public JSON fault code.
- **A Workspace container or network is missing:** the next entry reconciles runtime resources from logical state. Loss of Docker resources does not erase the logical Workspace.

## Guarantees and limitations

**Guaranteed under the supported topology:** no direct Workspace egress; no Workspace route to OPA, Broker sockets, Docker socket, or another project network; no upstream attempt after policy failure; bounded shared-service CPU, memory, PIDs, and Docker logs.

**Not guaranteed:** fair bandwidth or fair shared-service capacity between Workspaces; protection after host, Docker, kernel, Gateway, OPA, or Broker compromise; disk quota below a selected project root; general network policy for non-HTTP protocols; filesystem isolation between overlapping selected roots.

## Summary

Synthetic DNS, the Workspace output guard, disabled forwarding, and Gateway
redirect rules enforce the single supported route. Gateway mediates one
project network to policy and egress. OPA decides
without egress, and Auth Broker is not exposed to Workspace networking.

## Check your understanding

You should now be able to explain how the transparent route and output guard form the no-direct-egress boundary.

<details>
  <summary>
    What happens if a process connects without proxy configuration?
  </summary>
  Its connection reaches Gateway's transparent listener and receives the same
  policy checks. It does not gain an alternate path around Gateway; non-HTTP
  traffic fails closed.
</details>

<details>
  <summary>Why is OPA not the component that “lets packets through”?</summary>
  OPA is reachable only on the control network and returns a decision. Gateway
  owns the project and egress interfaces and enforces that decision.
</details>

<details>
  <summary>
    Does separate networking prevent two overlapping roots from seeing each
    other's file changes?
  </summary>
  No. Network isolation and host-file mount overlap are separate concerns.
  Writes to the same selected host files remain shared.
</details>
