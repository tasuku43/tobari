Tobari keeps project, Workspace, Workspace Template, cluster, and installation
state in separate ownership scopes. Lifecycle actions remove only the scope
they declare: `exit`, `workspace delete`, cluster teardown, and runtime rebuild therefore
preserve different artifacts.

Some runtime state is safe to reconstruct from durable records; other missing
or inconsistent state makes recovery stop rather than guess. This distinction
is why container or network loss is not equivalent to losing Workspace or
tool login state. The tables below apply the [Workspace lifecycle](/how-it-works/workspace-lifecycle/) and [credential](/how-it-works/credentials/) boundaries to each store.

## State by owner and purpose

Paths below are relative to the effective XDG configuration/state roots unless noted.

| State                                                    | Owner and meaning                                                                                           | Lifetime                                                                                    |
| -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Project root                                             | User-selected live host files mounted according to immutable Workspace Template `source_access`             | Never deleted by Tobari lifecycle commands                                                  |
| Config `templates/`, `contexts/`, and `runtimes/`        | Concept-separated editable desired source; file edits are inactive until reviewed Apply or Runtime build    | Missing or invalid source is drift and never deletes last-known-good active authority       |
| State `authority/`                                       | Immutable concept objects, complete generation manifests, verified active pointer, tombstones, and journals | Context survives Workspace deletion; each exact resource action owns its narrower removal   |
| `workspace-authority-runtime/contexts/<context-id>/home` | Context-owned writable home and tool-native login state                                                     | Survives exit/runtime recreation/Workspace deletion; removed by exact Context delete        |
| Workspace Template revision                              | Host-owned stable ID, reviewed editable Boundary, static policy, exact Runtime revision, and typed defaults | Survives Context, Workspace, and cluster runtime operations until exact Template deletion   |
| Runtime `source/` and immutable revisions                | Reusable installation-wide build source and successful history                                              | Survive Workspace Template and Workspace lifecycle; builds never roll out implicitly        |
| Workspace Template policy data                           | Reusable canonical typed policy data, owned by one Workspace Template                                       | Survives cluster runtime; changes only through a complete immutable Template revision       |
| Context Policy Memory                                    | Complete immutable remembered-decision revision owned by one location-free Template Context                 | Survives Workspace replacement; removed only with the Context                               |
| Aggregate policy projection                              | Content-addressed all-Context router/data/module snapshot mounted read-only into OPA                        | Rebuilt and atomically published; transient cluster authority derived from sources          |
| Active policy bundle                                     | Revisioned complete OPA bundle in an owner-labeled Docker-managed volume                                    | Hot-loaded by OPA; removed only by `cluster down --purge`, then rebuilt from policy sources |
| Principal registry                                       | Host-issued schema-1 Workspace source + Gateway endpoint + network → Context/Workspace binding              | Reconciled with existing Workspace networks; mounted read-only into Gateway                 |
| Context-owned agent state                                | Tool configuration and login state in the persistent Context Home                                           | Survives exit/runtime recreation and Workspace deletion; removed by Context delete          |
| Installation state                                       | Host configuration and trust material used by the runtime and policy                                        | Survives cluster down/purge; unsafe or missing state fails closed                           |
| Gateway CA state                                         | Installation CA used for Workspace-side HTTPS interception                                                  | Survives ordinary cluster down; shared CA volumes are removed by `--purge`                  |

Cluster state also records shared resource names, loaded Workspace Template count, content-addressed aggregate revision, and projection paths. It never turns the current Workspace Template into enforcement authority and never contains a primary credential.

## What each operation preserves

| Operation/event                    | Workspace identity and home                                 | Workspace Template/policy                      | Workspace state and host-owned state | Shared services/CA                                    | Project files |
| ---------------------------------- | ----------------------------------------------------------- | ---------------------------------------------- | ------------------------------------ | ----------------------------------------------------- | ------------- |
| `exit`                             | Preserved                                                   | Template, Context, and Policy Memory preserved | Preserved                            | Running; CA preserved                                 | Preserved     |
| `workspace delete`                 | Workspace identity/runtime removed; Context Home preserved  | Template, Context, and Policy Memory preserved | Installation state preserved         | Shared services unchanged                             | Preserved     |
| `cluster down`                     | Command is refused until all Workspaces are deleted         | Preserved                                      | Preserved                            | Services/transient networks removed; CA preserved     | Preserved     |
| `cluster down --purge`             | Same prerequisite                                           | Preserved                                      | Preserved                            | Services, shared CA, and active policy bundle removed | Preserved     |
| Workspace Template runtime rebuild | Identity/home remain; bound container reconciles next entry | Policy preserved                               | Preserved                            | Shared services unchanged                             | Preserved     |
| Container/network loss             | Logical state/home remain; resources reconcile next entry   | Preserved                                      | Preserved                            | Gateway attachment/principal is repaired as needed    | Preserved     |

## Recovery follows the source of truth

### Docker runtime is missing

If the durable Workspace record is valid but its container or network is missing, runtime resources are derived state. The next entry can recreate them, reconnect Gateway, update the principal registry, and mount the existing root/home.

### Durable authority is incomplete or contradictory

The active authority is one verified content-addressed generation whose small
pointer is atomically published after all immutable objects and the manifest.
An invalid generation, a mismatched Context/Workspace binding, or an unknown
mutation outcome fails closed. Tobari does not infer a
replacement identity from Docker resources or partially replay a mutation;
`status` or the fault's Catalog-declared read path must classify the retained
facts before any exact action is selected.

### Policy activation fails

Policy mutation uses a lock, private Workspace Template preflight, complete all-Context aggregate test, content-addressed publication, and OPA health wait. Invalid input or activation failure restores source and retains the previous known-good aggregate/state rather than mounting a partial candidate.

### host-owned state or Workspace state integrity fails

If required host state is missing or unsafe, Tobari does not create a replacement
that would reinterpret existing authority. Ownership, modes, symlinks, and schema
are checked before use; failure is reported and remains closed.

## Concrete recovery scenario

After a host restart, the Workspace's container and dedicated network are gone,
but the active authority generation still contains its Context and Workspace, and the
Context Home remains.

1. `tobari` resolves the canonical root's Workspace and its exact Context under the installation default Template.
2. It validates the Context's current Template revision and exact Runtime binding.
3. It recreates the internal network and container.
4. It connects Gateway, reapplies the Gateway/Workspace guards, and records the new exact Context/Workspace principal.
5. It reconciles the current host-owned principal registration.
6. It enters the same logical Workspace with the same Context ID, Workspace ID, and home.

This is reconciliation, not a new Workspace.

## Failure behavior

- Ownership, mode, symlink, schema, or identity mismatch fails before unsafe reuse.
- Missing image or incompatible runtime API fails before project runtime mutation.
- Missing or contradictory host-owned authority never silently creates another identity.
- Failed policy generation retains prior known-good authority.
- Attached deletion fails unless `--force` explicitly overrides that one guard.
- Cluster teardown fails while any logical Workspace remains.

## Guarantees and limitations

**Guaranteed:** lifecycle commands have narrow owner scopes; project files are never removed; derived Docker state can be reconciled from valid logical state; Template, Context, Policy Memory, Context Home, and host-owned state survive cluster purge; partial policy projections do not activate.

**Not guaranteed:** recovery from lost project files, a manually deleted Context Home, lost installation state, corrupted host storage, compromised trusted host, remote credential revocation, or automatically inferred project moves.

## Summary

Durable identity and user data are not inferred from container presence. Each state store has one owner and removal operation. Reconstructible Docker/projection state is reconciled; ambiguous identity, policy, or Workspace state fails closed.

## Check your understanding

You should now be able to predict state retention without equating “container gone” with “Workspace gone.”

<details>
  <summary>What does `workspace delete` remove that `exit` preserves?</summary>
  The exact Workspace authority record, container, network, Workspace-private
  runtime state, and principal-registry entry. Neither operation deletes project
  files, the Context Home or native state, Policy Memory, or Workspace Template
  state.
</details>

<details>
  <summary>What additional state does `cluster down --purge` remove?</summary>
  The shared Gateway CA volumes. It still preserves Context Homes and host-owned
  lifecycle state.
</details>

<details>
  <summary>
    What happens when required host-owned lifecycle state is missing?
  </summary>
  No. Tobari fails closed because inventing a replacement would reinterpret
  existing Workspace identity or policy authority.
</details>

<details>
  <summary>
    Why can a lost container be repaired but contradictory authority is not
    guessed?
  </summary>
  The container is derived from a validated Context/Workspace record. Missing or
  contradictory identity and binding information would make reconstruction
  invent authority.
</details>
