An outbound request starts on the Workspace's dedicated network and reaches
Gateway before it can reach any upstream. Gateway first establishes the
host-issued project principal, removes credential values from decision data,
and sends one normalized input to OPA.

A deny or invalid decision stops locally. Only an allow lets Gateway resolve
and pin the destination, open a separate upstream connection, and stream
ordinary body bytes. This ordering keeps policy denial, policy failure, and
upstream failure distinct.

The [system overview](/how-it-works/system-overview/) shows the fixed network map.
Authentication values remain request data owned by the agent CLI; this trace
focuses on the network and policy path.

## The processing order

### 1. Receive guarded HTTP traffic

Docker's bounded resolver forwards to Gateway's synthetic DNS, which
returns `198.18.0.10` without resolving the real host. The Workspace output
guard routes TCP through its project Gateway; Gateway redirects it to the
transparent listener. Plain HTTP authority comes from `Host`; HTTPS authority
starts with SNI and must remain consistent with the decrypted HTTP authority
and original port. [HTTPS and TLS](/how-it-works/https-and-tls/) explains the TLS split.

At this point, request bytes are untrusted. A project-looking header is not a principal.

### 2. Establish Workspace Manifest and project identity

Gateway reads the kernel-observed Workspace source endpoint and looks it up in
the host-owned schema-1 principal registry. The result supplies stable
`workspace_manifest_id` and `project_id`. Missing, unknown, stale, unsafe, or ambiguous
bindings stop here, before OPA.

### 3. Build one normalized, body-free decision

Gateway posts schema 1 input to one fixed OPA endpoint. It includes:

- registry-derived cluster, Workspace Manifest ID, and project ID;
- normalized scheme, lowercase host without a trailing dot, and port;
- uppercase method;
- raw path and decoded path segments;
- multi-valued query; and
- redacted non-secret headers plus non-secret authorization metadata.

It excludes request and response bodies, authentication and cookie values, and other
known/configured sensitive-header values. The registry-derived Workspace Manifest and
project identity are trusted principal metadata and are intentionally included. The
ordinary query is part of OPA input, so do not treat OPA input as a generic secret
scrubber for arbitrary data placed in a URL.

### 4. Ask OPA exactly once

Gateway sends one bounded HTTP POST with a finite timeout and no retry. It requires HTTP 200 and one valid result containing a boolean `allow`, non-empty reason, status `403`, boolean `learnable`, and valid optional managed profile.

OPA decides. Gateway enforces.

### 5A. Deny locally

On a valid deny, Gateway creates `403 policy_denied`. A learnable denial includes only a fixed host-side navigation object naming `tobari review permissions`, the exact host, port, method, and path, and `automatic_retry: false`.

It contains no candidate ID, query, body, headers, credential, or dynamic command argument. The candidate's opaque reference is derived later from retained host evidence.

### 5B. Continue after allow

Only after allow may Gateway:

1. resolve the upstream hostname;
2. reject unsafe non-global results for dotted hosts;
3. pin the selected address so a later DNS answer cannot change the connection; and
4. create one upstream connection and forward the authorized request, including
   the original agent-owned credential values.

There is no automatic application request retry. Redirects become new requests and pass through policy again.

### 6. Record the outcome

Denials are logged immediately. An allowed request is logged after response or connection error. Audit schema 1 contains bounded Workspace Manifest/project identity, authority, method, redacted path, decision, reason, status, and timing. It does not contain query, authentication/cookie header values, body, or credential values.

## Concrete example: two different bodies

Suppose a Workspace first sends:

```http
PATCH /api/items/42 HTTP/1.1
Host: example.com
Content-Type: application/json

{"state":"ready"}
```

and later sends the same Workspace Manifest/project/host/port/method/path with `{"state":"deleted"}`.

The bodies may have very different application meaning, but Tobari's exact policy identity is the same. The body does not create a second review candidate or a narrower rule. If that route is allowed, either body can be sent. The reviewer must evaluate the route-level capability, not infer payload inspection.

## Failure behavior

| Stage           | Failure                                                         | Result                                                   |
| --------------- | --------------------------------------------------------------- | -------------------------------------------------------- |
| Principal       | Registry unreadable or Workspace source endpoint unknown        | 403 `project_principal_unavailable`                      |
| Credential data | Credential values are not part of policy identity               | Request data remains absent from OPA and audit           |
| OPA             | Timeout, connection error, non-200, invalid or oversized result | 503 `policy_unavailable`                                 |
| Decision        | Valid deny                                                      | 403 `policy_denied`; upstream untouched                  |
| DNS/address     | No safe usable address                                          | Upstream/proxy error; no alternate authority is invented |
| Upstream        | TCP/TLS/HTTP failure after allow                                | Audit marks `upstream_error`; policy is unchanged        |

A known `Content-Length` greater than mitmproxy's 8 MiB limit may be rejected before the ordinary addon header hook. Allowed unknown-length bodies stream without a total-byte limit in the pinned product contract.

## Guarantees and limitations

**Guaranteed:** one OPA call per ordinary Gateway attempt; no request-body byte
forwarded before principal and decision succeed; credential values remain absent
from OPA and audit; no application-level retry; secret-free
denial/review projection.

**Not guaranteed:** body-aware authorization, application semantic understanding, idempotence, provider-operation interpretation, total-byte limits for allowed unknown-length streaming bodies, or a stable Tobari JSON fault for every low-level upstream failure.

## Summary

Identity comes from the registered Workspace source endpoint. OPA sees a normalized body-free
ordinary request and answers once. Deny stops locally. Allow is the prerequisite
for destination resolution and the upstream connection. Ordinary bodies stream
after allow.

<details>

    What is the difference between `policy_denied` and `policy_unavailable`?
  </summary>
  `policy_denied` is a valid deny decision and may be reviewable.
  `policy_unavailable` means Gateway did not receive one valid decision; it
  fails closed and is not a permission proposal.
