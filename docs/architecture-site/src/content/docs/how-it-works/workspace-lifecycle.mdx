A Workspace outlives the shell attached to it. `exit` ends only that exec
session; the logical Workspace, home, runtime records, and Workspace Manifest binding
remain available for the next entry. `delete` removes one logical Workspace
and its owned state. Cluster teardown is separate and is allowed only after all
Workspaces have been deleted.

Container or network loss does not automatically mean that the logical
Workspace is gone: entry reconciles replaceable runtime state against durable
records. `delete --force` has a narrower recovery purpose, and `cluster down
--purge` is neither Workspace deletion nor credential logout. See [Workspace,
Workspace Manifest, cluster, and runtime](/how-it-works/workspace-manifest-workspace-cluster/) for the
identities used in this lifecycle.

## State changes in order

### Absent → attached

Running `tobari` from the selected directory chooses an existing Workspace or
explicitly creates one for the canonical root and Workspace Manifest. Creation durably
records identity and home, reconciles the dedicated network and container,
installs the fail-closed Gateway/Workspace network guards, registers exact
Workspace and Gateway endpoints, waits for readiness, and starts an
interactive `docker exec` shell.

The attached shell is transient process state. It is not the Workspace lifetime process.

While attached, the read-only `tobari-expose` helper can request trusted-host
review for one exact Workspace-loopback development service. Run
`tobari-expose PORT` inside the Workspace, then `tobari review services` in a separate
host terminal. Allow once returns exact
`http://127.0.0.1:<random-port>` access for HTTP/1.1 and WebSocket Upgrade. The
attachment—not the helper or reviewer—owns the listener and streams. Exit
closes them; approval does not become Workspace Manifest policy or a remembered decision.

### Attached → detached but existing

Shell `exit`, an exact agent command finishing, or a nonzero child exit ends only the exec process. Tobari preserves:

- the root index and instance record;
- the permanent Workspace Manifest binding and project ID;
- the per-Workspace home and tool-owned login state;
- the runtime container and dedicated network;
- learned policy scoped to that Workspace Manifest/project; and
- Workspace Manifest-owned broker credentials and this project's current handle projection.

It does not preserve pending service requests, host service listeners, or
active service relays; those are attachment-owned and close on exit.

There is no persisted “paused” state. Detached means no observed attached exec session; the logical Workspace still exists.

### Detached → attached again

The next `tobari` entry resolves the same logical record and reconciles runtime drift before entering. It may recreate the container or network, update the desired Workspace Manifest image, reissue current project-bound broker handle projections, and repair principal registration without changing identity or home.

### Detached → absent

`delete` first confirms that no exec session is attached. It verifies exact owner, role, and project labels before removing only that Workspace's container and network. It then removes its root index, instance state, home, and project-auth projection/registry entry. Project files in the mounted root are never removed.

### Attached → absent with `--force`

Normal deletion rejects an attached Workspace. `delete --force` overrides only that attached-session guard. It does not relax Docker ownership/identity checks, broaden the target, or authorize deleting project files.

## Runtime loss and drift

Logical state, not Docker inspection, determines existence.

- **Container lost:** next entry creates a compatible replacement and remounts the existing root/home.
- **Network lost:** next entry recreates the internal network, reconnects Gateway, reapplies both guards, and writes the new endpoint binding before readiness.
- **Workspace Manifest runtime rebuilt:** next entry compares desired runtime identity and recreates only the project container when needed.
- **Resource/security contract changed:** the desired-spec hash changes and triggers reconciliation.
- **Root index exists but instance state is missing:** this is `incomplete`, not an invitation to guess. Entry fails; exact deletion cleans it up.

Durable journals cover interrupted creation and deletion so a partial file set is not silently treated as a second Workspace.

## Cluster lifecycle is separate

`cluster down` is rejected while any logical Workspace instance remains. Delete all Workspaces first.

After that:

| Operation              | Removes                                                                               | Preserves                                                                           |
| ---------------------- | ------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `cluster down`         | Shared Gateway, OPA, Auth Broker containers and transient shared networks/projections | Workspace Manifests, policy sources, encrypted vaults, root key, Gateway CA volumes |
| `cluster down --purge` | The same shared runtime resources, shared CA volumes, and active policy-bundle volume | Workspace Manifests, policy sources, encrypted vaults, installation root key        |

Purge means a later cluster start establishes new shared CA state. It does not revoke provider credentials or delete encrypted vaults. Use `auth logout <provider>` for local credential removal and handle revocation.

## Concrete example

You enter `/work/service`, run a tool-native login, and then type `exit`.

1. The tool's login files remain in that Workspace's persistent home.
2. The project files and logical records remain.
3. A later entry resumes the same Workspace and home.
4. If the container was manually removed meanwhile, Tobari recreates it and remounts that home.
5. If you instead run `delete` while detached, the Workspace home is deleted. The project root remains.

## Failure behavior

- An attached exec makes ordinary `delete` fail before removal.
- Wrong/missing ownership labels prevent resource deletion.
- Runtime incompatibility fails before project resource mutation.
- Container/network loss never silently deletes logical state.
- `cluster down` fails while any instance record remains.
- Interrupted mutation recovery can require the exact lifecycle command; it does not invent completion.
- A successful mutation followed by cancellation is reported through the mutation-complete boundary so it is not presented as safely replayable.

## Guarantees and limitations

**Guaranteed:** session exit is not deletion; deletion targets one exact Workspace; project files are preserved; runtime resources can be recreated without changing logical identity; purge does not masquerade as logout.

**Not guaranteed:** restoration of manually deleted project files or a manually deleted Workspace home; automatic migration after moving a root; preservation of tool-native login after Workspace deletion; remote provider revocation after local logout.

## Summary

An attached session, a logical Workspace, its Docker runtime, the shared cluster, and Workspace Manifest credential state have different lifetimes. Use `exit` to leave, `delete` to remove the Workspace, `cluster down` to stop shared services after deletion, and `auth logout` to remove a provider credential.

    Does `exit` stop the runtime container or erase tool login state?
  </summary>
  No. It ends only the attached exec session. The container, logical record,
  home, and tool-owned state remain.
</details>

<details>
  <summary>What extra authority does `delete --force` grant?</summary>
  Only permission to override the attached-session guard. Exact target and
  ownership checks still apply, and project files remain untouched.
</details>

<details>
  <summary>
    Does `cluster down --purge` delete the encrypted vault and root key?
  </summary>
  No. It additionally removes shared CA and active policy-bundle volumes. Vaults
  and the installation root key survive.
</details>

<details>
  <summary>
    What happens if the runtime container disappears but the instance record
    remains?
  </summary>
  The Workspace still exists logically. The next entry reconciles a replacement
  container.
</details>
