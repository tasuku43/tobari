A Workspace outlives the shell attached to it. `exit` ends only that exec
session; the logical Workspace, home, runtime records, and permanent Context
binding remain available for the next entry. `workspace delete` removes one
replaceable Workspace and its owned state while preserving the Context and its
Policy Memory. Cluster teardown is separate and is allowed only after all
Workspaces have been deleted.

Container or network loss does not automatically mean that the logical
Workspace is gone: entry reconciles replaceable runtime state against durable
records. `workspace delete --id WORKSPACE_REF --confirm=delete --force` has a narrower recovery purpose, and `cluster down
--purge` is neither Workspace deletion nor removal of a Workspace-owned login. See [Workspace,
Workspace Template, cluster, and runtime](/how-it-works/workspace-template-context-workspace-cluster/) for the
identities used in this lifecycle.

## State changes in order

### Absent → attached

Running `tobari` from the selected directory resolves the installation default
Template and the exact Context for the canonical root, then chooses or creates
that Context's Workspace. Creation durably records the Workspace identity and
home in the final authority model, reconciles the dedicated network and container,
installs the fail-closed Gateway/Workspace network guards, registers exact
Workspace and Gateway endpoints, waits for readiness, and starts an
interactive `docker exec` shell.

The attached shell is transient process state. It is not the Workspace lifetime process.

While attached, the read-only `tobari-expose` helper can request trusted-host
review for one exact Workspace-loopback development service. Run
`tobari-expose PORT` inside the Workspace, then `tobari review services` in a separate
host terminal. Allow once returns exact
`http://127.0.0.1:<random-port>` access for HTTP/1.1 and WebSocket Upgrade. The
attachment—not the helper or reviewer—owns the listener and streams. Exit
closes them; approval does not become Workspace Template policy or a remembered decision.

### Attached → detached but existing

Shell `exit`, an exact agent command finishing, or a nonzero child exit ends only the exec process. Tobari preserves:

- the atomic authority envelope and exact Workspace record;
- the permanent Workspace-to-Context binding and Workspace ID;
- the per-Workspace home and tool-owned login state;
- the runtime container and dedicated network;
- Policy Memory owned by the surviving Context; and
- Workspace-owned agent login state in the persistent home.

It does not preserve pending service requests, host service listeners, or
active service relays; those are attachment-owned and close on exit.

There is no persisted “paused” state. Detached means no observed attached exec session; the logical Workspace still exists.

### Detached → attached again

The next `tobari` entry resolves the same Context and Workspace and reconciles
runtime drift before entering. It may recreate the container or network, apply
the Context's current Template entry slice, reissue Context/Workspace identity
projections, and repair principal registration without changing Workspace ID,
Context binding, or home.

### Detached → absent

`workspace delete` first confirms that no exec session is attached. It verifies
the exact opaque Workspace reference and owner labels before removing only that
Workspace's authority record, container, network, home, and principal-registry
entry. Its Context, Policy Memory, Template, and mounted project files remain.

### Attached → absent with `--force`

Normal deletion rejects an attached Workspace. `workspace delete --id WORKSPACE_REF --confirm=delete --force` overrides only that attached-session guard. It does not relax Docker ownership/identity checks, broaden the target, or authorize deleting project files.

## Runtime loss and drift

Logical state, not Docker inspection, determines existence.

- **Container lost:** next entry creates a compatible replacement and remounts the existing root/home.
- **Network lost:** next entry recreates the internal network, reconnects Gateway, reapplies both guards, and writes the new endpoint binding before readiness.
- **Workspace Template Runtime changed:** next entry compares the current exact Runtime binding and recreates only the work container when needed.
- **Resource/security contract changed:** the desired-spec hash changes and triggers reconciliation.
- **Authority is invalid or contradictory:** entry fails closed and reports the
  Catalog-declared read-only classifier; it does not infer a Workspace from
  Docker resources or manufacture an exact delete reference.

Durable journals cover interrupted creation and deletion so a partial file set is not silently treated as a second Workspace.

## Cluster lifecycle is separate

`cluster down` is rejected while any logical Workspace instance remains. Delete all Workspaces first.

After that:

| Operation              | Removes                                                                               | Preserves                                                                                        |
| ---------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `cluster down`         | Shared Gateway, OPA containers and transient shared networks                          | Workspace Templates, policy sources, Workspace-owned homes, host-owned state, Gateway CA volumes |
| `cluster down --purge` | The same shared runtime resources, shared CA volumes, and active policy-bundle volume | Workspace Templates, policy sources, Workspace-owned homes, host-owned lifecycle state           |

Purge means a later cluster start establishes new shared CA state. It does not
delete Workspace-owned homes or project files. Provider login and logout remain
the provider CLI's responsibility.

## Concrete example

You enter `/work/service`, run a tool-native login, and then type `exit`.

1. The tool's login files remain in that Workspace's persistent home.
2. The project files and logical records remain.
3. A later entry resumes the same Workspace and home.
4. If the container was manually removed meanwhile, Tobari recreates it and remounts that home.
5. If you instead run `workspace delete` while detached, the Workspace home is deleted. The project root remains.

## Failure behavior

- An attached exec makes ordinary `workspace delete` fail before removal.
- Wrong/missing ownership labels prevent resource deletion.
- Runtime incompatibility fails before project resource mutation.
- Container/network loss never silently deletes logical state.
- `cluster down` fails while any Workspace authority remains.
- Interrupted mutation recovery can require the exact lifecycle command; it does not invent completion.
- A successful mutation followed by cancellation is reported through the mutation-complete boundary so it is not presented as safely replayable.

## Guarantees and limitations

**Guaranteed:** session exit is not deletion; deletion targets one exact Workspace; project files are preserved; runtime resources can be recreated without changing logical identity; purge does not masquerade as logout.

**Not guaranteed:** restoration of manually deleted project files or a manually deleted Workspace home; automatic migration after moving a root; preservation of tool-native login after Workspace deletion; remote provider revocation.

## Summary

An attached session, a logical Workspace, its Docker runtime, the shared cluster, and Workspace-owned login state have different lifetimes. Use `exit` to leave, `workspace delete` to remove the Workspace, and `cluster down` to stop shared services after deletion.

You should now be able to predict what survives each lifecycle operation.

<details>
  <summary>
    Does `exit` stop the runtime container or erase tool login state?
  </summary>
  No. It ends only the attached exec session. The container, logical record,
  home, and tool-owned state remain.
</details>

<details>
  <summary>
    What extra authority does `workspace delete --id WORKSPACE_REF
    --confirm=delete --force` grant?
  </summary>
  Only permission to override the attached-session guard. Exact target and
  ownership checks still apply, and project files remain untouched.
</details>

<details>
  <summary>
    Does `cluster down --purge` delete Workspace home and host-owned lifecycle
    state?
  </summary>
  No. It additionally removes shared CA and active policy-bundle volumes.
  Workspace homes and host-owned lifecycle state survive.
</details>

<details>
  <summary>
    What happens if the runtime container disappears but valid Workspace
    authority remains?
  </summary>
  The Workspace still exists logically. The next entry reconciles a replacement
  container.
</details>
