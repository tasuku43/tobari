Tobari's outbound path has five participants: Workspace, Gateway, OPA, Auth
Broker, and Upstream. A project-bound Workspace can reach an HTTP or HTTPS
upstream only through Gateway. Gateway asks OPA whether the ordinary request is
allowed and talks to Auth Broker only when a broker-managed credential is part
of the request.

That separation is what makes Tobari more than a Docker wrapper. Gateway
enforces the network decision, OPA decides policy, and Auth Broker keeps
broker-managed primary credentials outside the Workspace. Authentication does
not grant network authorization.

If Tobari's user-facing outcome is new to you, begin with the [overview](/start/overview/). No Docker, proxy, or policy knowledge is needed for the map below.

## Read the map by conversation

### 1. Workspace: where project work runs

A [Workspace](/reference/glossary/#workspace) is the human-facing name for one long-lived, directory-bound Tobari. It runs tools against the selected project root and has its own persistent home. Its runtime container is replaceable; the logical Workspace is not the container.

Treat every process in the Workspace as untrusted. It may read and modify the selected project root. It does not receive a general route to the public Internet, Docker control, another Workspace, or a broker-managed primary credential.

### 2. Gateway: the enforcement point

Gateway accepts the Workspace's proxy traffic. It establishes the trusted Context and project identity, normalizes the HTTP request, asks OPA once, and enforces the answer. On deny, Gateway returns a local response without opening the upstream connection. On allow, Gateway creates the separate upstream connection and streams the request.

OPA does not forward packets. Gateway does.

### 3. OPA: the decision point

[OPA](/reference/glossary/#opa) evaluates the ordinary HTTP effect. The decision includes the trusted Context/project principal, scheme, host, port, method, and path. The input also carries query values and redacted non-secret headers, but no request body or credential value.

OPA returns a structured allow or deny. An unavailable or malformed decision is not treated as permission.

### 4. Auth Broker: credential custody, not permission

Auth Broker is relevant only to the brokered authentication route. It keeps
typed static or renewable credential state in an encrypted Context vault and
gives a Workspace an opaque, project-bound handle. Gateway may inspect
non-secret binding metadata before policy. Only after OPA allows the ordinary
HTTP effect may Broker resolve one static secret, select or refresh a Datadog
token, or use the private host companion and sign one bounded AWS request.

Login can create credential state. It does not add a policy rule.

### 5. Upstream: the requested destination

The upstream service receives a request from Gateway only after the effect is allowed. For HTTPS, the final hop is a separately verified TLS connection. An allowed upstream may receive any data the Workspace can read and chooses to send on that allowed route; Tobari does not inspect request bodies for meaning.

## One concrete request

Suppose a tool in a Workspace sends `PUT https://example.com/api/items/42`.

1. The tool sends the request through the configured HTTP proxy.
2. Gateway derives project identity from the receiving network interface, not from a caller header.
3. Gateway builds a body-free policy input and calls OPA.
4. If no current rule matches, OPA denies. Gateway returns `403 policy_denied` and leaves the upstream untouched.
5. A trusted host user can review the retained exact effect.
6. If that exact Context/project/host/port/method/path is allowed and deliberately retried, Gateway makes the upstream connection.

The first request is not an application for automatic permission. It is an attempted effect that either matches current authority or fails.

## Failure behavior

| Failure                     | Observable result                        | What does **not** happen                            |
| --------------------------- | ---------------------------------------- | --------------------------------------------------- |
| No matching rule            | `403 policy_denied`                      | No upstream connection and no automatic allow       |
| OPA unavailable or invalid  | `503 policy_unavailable`                 | No fallback decision                                |
| Gateway unavailable         | Proxy connection fails                   | No direct Internet fallback                         |
| Invalid broker handle       | `403 credential_handle_invalid`          | No passthrough fallback and no upstream request     |
| Auth Broker unavailable     | `503 credential_broker_unavailable`      | No resolve, refresh, signing, or upstream action    |
| AWS/Datadog outcome unknown | `409 credential_refresh_outcome_unknown` | No automatic replay or application upstream attempt |

## Guarantees and limitations

### What this model guarantees

Within the supported Docker topology, a Workspace has no direct external
route. Gateway must receive an allow decision before it forwards the request.
Brokered static secrets, renewable state, and derived request credentials stay
outside the Workspace and OPA.

### What this model does not guarantee

It does not protect files inside the selected project root from the Workspace. It does not stop an allowed destination from receiving Workspace-readable data. It assumes the host, Docker Engine or VM, kernel, Gateway, OPA, Auth Broker, and their trusted state are not compromised. It does not provide general SSH, raw TCP, UDP, QUIC, DNS, malware, or same-Workspace process isolation.

## Summary

Remember one path: **Workspace → Gateway → upstream**, with **OPA deciding** and
**Auth Broker performing one declared credential action only when needed and
only after allow**. Gateway is the component that closes or opens the path.

## Check your understanding

You should now be able to explain why authentication, policy decision, and network forwarding are three separate jobs.

<details>
  <summary>
    If OPA says allow, which component actually connects upstream?
  </summary>
  Gateway. OPA returns the decision; it does not forward the request.
</details>

<details>
  <summary>
    Does a successful broker login authorize traffic to that provider?
  </summary>
  No. Login creates Context-owned credential state. The ordinary HTTP effect
  still needs an OPA allow decision.
</details>

<details>
  <summary>
    What can a Workspace process do to the selected project root?
  </summary>
  It can read, modify, and delete files there. The selected root is delegated
  writable authority, not protected content.
</details>
