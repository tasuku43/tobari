Tobari's standard outbound path has four participants: Workspace, Gateway,
OPA, and Upstream. A project-bound Workspace can reach an HTTP or HTTPS
destination only through Gateway. Gateway asks OPA whether the ordinary exact
request effect is allowed, then either refuses it locally or opens a separate
upstream connection.

Authentication and network permission remain separate. Claude Code and Codex
store their native login state in the Workspace home. Gateway treats their
Authorization and cookie values as secret request data: they are absent from
OPA and audit, and are forwarded unchanged only after allow.

## Read the map by participant

### 1. Workspace: where project work and native login run

A Workspace is one long-lived, directory-bound Tobari with a persistent home.
Processes can read and modify the selected project root and can read native
credentials stored in that same Workspace. They do not receive another
Workspace's home, host credentials, Docker control, or a direct public route.

### 2. Gateway: the enforcement point

Gateway receives transparently routed HTTP traffic, derives the Context and
project principal from host-owned registration, removes secret request values
from decision and audit data, asks OPA once, and enforces the answer. On deny,
it performs no destination DNS lookup or connection. On allow, it forwards the
original request—including its authentication—over one separate connection.

### 3. OPA: the decision point

OPA evaluates the ordinary HTTP effect: trusted principal, scheme, host, port,
method, and path. It receives no request body or credential value. An
unavailable or malformed decision is not permission.

### 4. Upstream: the requested destination

The upstream receives a request only after allow. An allowed destination can
receive any data the Workspace can read and chooses to send; Tobari does not
inspect request bodies for meaning.

## One concrete request

Suppose a tool sends `PUT https://example.com/api/items/42`.

1. The guarded route delivers the request to Gateway.
2. Gateway derives the principal and builds a body-free, secret-free decision input.
3. OPA returns one allow or deny result.
4. On deny, Gateway returns `403 policy_denied` without touching the destination.
5. A trusted-host user may review the retained exact effect and deliberately retry.
6. On allow, Gateway forwards the original request once and relays the response.

Native login does not create a policy rule, and policy approval does not create
or refresh a credential.

## Failure behavior

| Failure                    | Observable result        | What does **not** happen                    |
| -------------------------- | ------------------------ | ------------------------------------------- |
| No matching rule           | `403 policy_denied`      | No destination DNS or upstream connection   |
| OPA unavailable or invalid | `503 policy_unavailable` | No fallback decision                        |
| Gateway unavailable        | Guarded connection fails | No direct Internet fallback                 |
| Provider rejects login     | Provider-owned failure   | Tobari does not synthesize account metadata |

## Experimental Broker profile

Repository builds made with `task build:dev` retain the Auth Broker research
path. That compile-time profile has a third service, provider bindings, handles,
vaults, and host-side `auth` commands. None of those surfaces exists in the
standard catalog, topology, embedded standard runtime assets, or release.

## Guarantees and limitations

The supported standard topology guarantees that Gateway receives an allow
before forwarding ordinary HTTP/HTTPS and that secret request values stay out
of OPA and audit. It does not protect project files from the Workspace, isolate
processes within one Workspace, stop exfiltration to an allowed destination,
or protect a compromised host, kernel, Docker Engine, Gateway, or OPA.

## Summary

Remember one path: **Workspace → Gateway → Upstream**, with **OPA deciding**.
The Workspace owns native authentication; Gateway owns whether the associated
HTTP effect can leave.

## Check your understanding

<details>
  <summary>If OPA says allow, which component connects upstream?</summary>
  Gateway. OPA returns a decision; it does not forward the request.
</details>

<details>
  <summary>
    Does successful native login authorize every provider route?
  </summary>
  No. Each HTTP effect still needs an existing exact permission.
</details>

<details>
  <summary>
    Can another process in the same Workspace read native login state?
  </summary>
  Yes. The Workspace is the isolation boundary; Tobari does not provide
  process-level credential isolation inside it.
</details>
