Each implementation technology sits at a specific Tobari boundary. Go owns the
host CLI, fixed provider acquisition, and validated orchestration. Docker
realizes process, network, and mount boundaries. mitmproxy and a Python addon
enforce the HTTP/TLS flow, while OPA and Rego decide generic effects.

A separate Python Auth Broker owns encrypted credential state and post-policy
resolve, refresh, or signing actions over narrow sockets. Keeping these jobs in
separate processes prevents forwarding, policy, and credential custody from
collapsing into one authority. Canonical source, embedded snapshots, immutable
OCI images, and digest pinning then carry those boundaries into the runtime
supply path.

This implementation-oriented page follows the product flow through [State and recovery](/how-it-works/state-and-recovery/) and is optional for ordinary use.

## Technology follows the trust boundary

### Go CLI

The public `tobari` executable is written in Go. It owns canonical path selection, domain validation, effects and mutation contracts, application use cases, host state, Docker orchestration, deterministic rendering, and the public command Catalog.

Go does not make arbitrary provider API requests above infrastructure. It passes one cancellation context through bounded adapters and keeps credential-bearing types in infrastructure.

### Docker Engine and Docker Compose

Docker Engine supplies runtime containers, read-only/read-write mounts, users, capability drops, read-only root filesystems, resource limits, internal networks, labels, volumes, and process execution.

Docker Compose owns only the shared Gateway, OPA, and Auth Broker services plus shared networks and CA volumes. Per-Workspace containers and networks are reconciled by the runtime adapter because their exact root/Context identity and lifecycle are application concerns.

Docker is trusted infrastructure. “Runs in a container” is not itself a security argument; the exact mounts, network attachments, socket absence, labels, users, and failure tests are.

### mitmproxy Gateway and Python addon

Mitmproxy supplies transparent HTTP/TLS interception, streaming hooks, and upstream TLS. Tobari's Python addon adds product-specific principal lookup, credential preparation, body-free OPA input, fail-closed result validation, post-allow credential action, DNS address classification/pinning, and audit.

Python is used here because mitmproxy's reviewed extension boundary is a Python addon. Gateway owns enforcement; it does not embed policy rule interpretation or vault storage.

### OPA and Rego

OPA is the shared policy decision service. Rego expresses default deny, initialized authority, Context routing, exact learned allow/deny rules, credential metadata constraints, and safe prefix compaction semantics.

OPA receives no request body or credential value and has no egress interface. Keeping decision logic separate makes the decision input/result contract testable without granting OPA network forwarding authority.

### Python Auth Broker, host drivers, companion, and Unix sockets

The Auth Broker is a separate non-root Python daemon because credential
encryption, handle issuance, introspection, and post-policy actions form a
distinct trusted boundary. It has no TCP listener and contains no GitHub CLI,
AWS CLI, or `pup` executable.

Separate owner-only control and runtime Unix sockets divide host lifecycle
operations from Gateway's narrow request-time access. Workspace and OPA mount
neither socket. The runtime protocol can introspect a binding before policy and
run only the provider's declared post-policy operation after allow; it is not a
generic network API.

Interactive GitHub, AWS, and Datadog acquisition runs through fixed Go
infrastructure drivers on the trusted host. Each resolves an identity-checked
executable from conventional installation roots, uses fixed argv and a
sanitized private environment, bounds visible output, and verifies temporary
state cleanup before committing typed state through Broker control.

AWS alone uses the resident same-binary host credential companion after policy
allow. Broker's private `/run/tobari-auth/companion/bridge.sock` is connected
through one authenticated, encrypted, direction-bound reverse
`docker exec -i` session. The companion exposes no listener or mounted host
socket and implements only the compiled AWS CLI credential-export operation.
Datadog refresh does not use the companion: Broker makes one strict proxy-free,
no-redirect HTTPS exchange with the exact US1 token endpoint after allow.

### Encrypted Context vault and root key

Each Context vault uses a schema-1 AES-256-GCM envelope with a random nonce and
Context/schema-associated data. Its encrypted schema-1 payload stores typed
static secrets, opaque AWS state, Datadog OAuth state, revisions, durable task
barriers, and raw handles. The installation root key is external to the vault:
macOS Keychain or an owner-only Linux XDG file. Encryption limits storage
exposure across the container/Workspace boundary but does not protect against
a compromised host user, root-key backend, Broker, or Gateway.

### OCI images and GHCR

Gateway, Auth Broker, OPA, mitmproxy base, and runtime base are OCI image boundaries. Runtime service identities use immutable digests recorded in embedded version metadata. Moving `main` and `latest` tags are development/publication conveniences, not runtime authority.

The current exact versions and digests are generated in [Component versions](/reference/component-versions/) from `go.mod`, `versions.env`, and runtime metadata rather than copied into this page.

## From editable source to runtime image

<ConceptDiagram name="image-supply" />

Gateway and Auth Broker each have one editable canonical public source tree:

- `gateway/`
- `authbroker/`

The CLI embeds a runtime snapshot under `internal/infra/runtimeassets/assets/`. Byte-for-byte drift checks reject a changed snapshot that does not match canonical source. The embedded assets also include Compose, OPA policy, runtime entrypoints, image identities, and license material.

CI builds multi-architecture OCI images from canonical sources. Normal runtime uses reviewed immutable digests. Pull-request image validation does not receive package-write permission; publication is a separate controlled workflow.

## Concrete request mapped to technologies

For one allowed HTTPS call:

1. **Go** has already reconciled the Workspace's Docker network, exact endpoint registry, CA, DNS setting, and Gateway/Workspace network guards.
2. **Docker/Linux networking** prevents direct egress and delivers TCP to Gateway's transparent ingress.
3. **mitmproxy** terminates TLS A and exposes request headers to the addon.
4. **Python Gateway addon** derives the source-bound principal, validates one consistent authority, and posts schema 1 input.
5. **OPA/Rego** returns allow or deny.
6. For a broker handle, **Python Auth Broker over Unix socket** performs
   non-secret introspection before policy and the declared static, AWS, or
   Datadog action only after allow.
7. For AWS, the **private host companion** performs one fixed credential
   export and Broker signs locally. For Datadog refresh, **Broker HTTPS** reaches
   only the exact token endpoint. Ordinary/static requests need neither path.
8. **mitmproxy** establishes verified TLS B and streams the ordinary request or
   sends the one bounded signed AWS request.
9. **Docker logs** retain bounded secret-free audit evidence for host-side Go review.

No one technology implements the complete promise.

## Failure behavior

- Missing/incompatible runtime or service image fails validation before unsafe creation.
- Digest/label/API/user/entrypoint mismatch fails closed.
- Canonical source and embedded snapshot drift fails repository checks.
- Invalid Rego or all-Context aggregate fails before activation.
- OPA or Broker outage produces a closed Gateway response.
- Docker/host outage removes the enforcement substrate; Tobari does not claim protection under its compromise.
- Missing root key with an existing vault prevents unlock rather than replacing the key.

## Guarantees and limitations

**Guaranteed by contracts and tests:** fixed component roles, immutable normal
service identities, byte-checked canonical source snapshots, separate
credential sockets, no provider CLI in Broker, no companion listener/socket
mount, no OPA egress, exact Compose topology, and preflight of runtime
compatibility.

**Not guaranteed:** that an image digest alone makes code safe; isolation after Docker/kernel/host compromise; provenance of a user-selected custom image; availability of GHCR or external registries; security review of arbitrary tools installed by a custom runtime recipe.

## Summary

Tobari's behavior is a composition: Go validates and orchestrates, Docker realizes boundaries, Gateway enforces HTTP/TLS flow, OPA/Rego decide, Broker owns credential custody, and immutable OCI identities plus source/snapshot checks make the shipped runtime reviewable.

## Check your understanding

You should now be able to connect a product claim to a concrete technology boundary.

<details>
  <summary>Why is OPA separate from Gateway?</summary>
  OPA owns deterministic decision logic without forwarding or egress authority.
  Gateway owns request/TLS/network enforcement and validates the decision
  result.
</details>

<details>
  <summary>
    Why does Auth Broker use a Unix socket instead of a Workspace-facing HTTP
    API?
  </summary>
  It narrows reachability to fixed host control operations and Gateway's runtime
  mount. Workspace and OPA receive no socket or TCP route to the Broker.
</details>

<details>
  <summary>
    Does an immutable image digest prove the implementation is secure?
  </summary>
  No. It fixes the reviewed bytes and prevents moving-tag substitution. Safety
  still depends on code, configuration, tests, trust assumptions, and the
  runtime substrate.
</details>
