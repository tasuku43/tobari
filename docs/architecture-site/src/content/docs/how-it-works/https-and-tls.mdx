An HTTPS request through Tobari uses two TLS connections. The client keeps its
ordinary HTTPS URL, resolves a fixed synthetic address, and the guarded
Workspace route delivers its TCP connection to Gateway's transparent listener.
The client establishes TLS connection A with Gateway under the Tobari CA.
Gateway terminates that connection so it can authorize the decrypted HTTP
attributes.

After policy allows the request, Gateway creates a separate, verified TLS
connection B to the upstream. The final destination therefore still receives
HTTPS rather than plaintext HTTP. Trusting the Tobari CA does not grant policy
permission, and a certificate-pinned client that rejects interception fails
instead of bypassing Gateway. The preceding [request journey](/how-it-works/request-journey/) places this TLS split in the full processing order.

## The HTTPS exchange in order

### 1. The client reaches Gateway

The client keeps its ordinary HTTPS URL. Synthetic DNS returns `198.18.0.10`,
its default TCP route points to the project Gateway, and Gateway redirects the
connection to its transparent listener. TLS SNI supplies the initial HTTPS
authority. Reaching this listener does not grant network permission.

### 2. Gateway establishes TLS connection A

Gateway accepts the intercepted TLS handshake and presents a leaf certificate signed by Tobari's installation CA. The Workspace runtime builds an ephemeral client trust bundle from the system CA set plus the public Tobari CA.

The client therefore establishes **TLS connection A** with Gateway. Gateway terminates this TLS session and can see the decrypted HTTP method, authority, path, query, and headers needed for the generic decision contract.

### 3. Gateway authorizes the decrypted HTTP request

Gateway derives Context/Workspace identity, requires transparent SNI, HTTP
authority, and original port to be consistent, removes or redacts credential
material, and sends one body-free normalized input to OPA. The request body is
not a policy identity dimension. CA trust does not skip this decision.

On deny or decision failure, connection B is never created for that request.

### 4. Gateway establishes TLS connection B

After allow and any credential action, Gateway resolves and pins the upstream address. It then creates **TLS connection B** to the requested upstream and validates the upstream certificate under mitmproxy's normal verification behavior.

The final service receives encrypted TLS from Gateway. Plaintext exists inside the trusted Gateway process because policy needs HTTP attributes; it is not sent as plaintext across the final network hop.

### 5. Gateway streams the authorized message

Gateway forwards headers and streams the allowed body through connection B. The response returns over B, is visible to Gateway, and is re-encrypted over A for the Workspace client.

## A concrete certificate example

Imagine `curl https://api.example.com/v1/data` inside a Workspace.

- `curl` trusts the combined runtime bundle, including the Tobari CA.
- The certificate it sees for `api.example.com` belongs to TLS A and is generated under that CA.
- Gateway sees `GET /v1/data` and asks OPA.
- On allow, Gateway independently validates the real `api.example.com` certificate over TLS B.

If the same client pins the upstream certificate or public key, the certificate presented on A does not match the pin. The connection fails. Tobari does not disable pinning, create a direct route, or silently switch to transparent pass-through.

## CA trust is not authorization

These are separate questions:

| Question                                                            | Mechanism                                         | Meaning                                            |
| ------------------------------------------------------------------- | ------------------------------------------------- | -------------------------------------------------- |
| Can the client establish an intercepted HTTPS session with Gateway? | Runtime trusts the Tobari CA                      | Gateway can receive the decrypted request          |
| May this ordinary HTTP effect reach upstream?                       | OPA decision, enforced by Gateway                 | Context/Workspace/host/port/method/path is allowed |
| May a Workspace-owned credential value be forwarded?                | Prior OPA allow and the declared request boundary | One request may receive the original header value  |

A working CA solves only the first row.

## Failure behavior

- **Tobari CA missing or not trusted by the client:** TLS A fails before an application request can be authorized.
- **Certificate pinning:** TLS A fails because Gateway's generated leaf does not match the pin.
- **OPA deny or outage:** Gateway does not create the authorized upstream path; deny is local.
- **DNS or address validation failure:** TLS B is not attempted to an unsafe substitute.
- **Upstream certificate failure:** TLS B fails; Tobari does not mark the policy rule denied or retry insecurely.
- **Client opens an ordinary direct socket:** the guarded transparent route reaches Gateway's decision; it does not create a TLS bypass.

## Guarantees and limitations

**Guaranteed in the supported flow:** two distinct TLS connections; generic HTTP attributes available to policy; upstream TLS verification remains enabled; policy deny closes the upstream path; pinning is not bypassed.

**Not guaranteed:** compatibility with every TLS stack, custom certificate store, or pinned client; end-to-end TLS directly between the Workspace process and final service; privacy of plaintext from trusted Gateway; HTTP/3/QUIC interception.

The repository's tests validate intercepted HTTPS behavior, scheme normalization, CA use, and failed direct bypass. They do not packet-capture and assert both handshakes byte by byte, so the two-connection claim is also grounded in the architecture decision and fixed mitmproxy configuration.

## Summary

Guarded transparent ingress leads to TLS A between client and Gateway. Gateway
authorizes decrypted HTTP attributes. Only after allow
does it resolve the real host and create separately verified TLS B to upstream.
CA trust, policy authority, and credential authority remain distinct.
