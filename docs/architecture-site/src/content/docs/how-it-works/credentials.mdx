Authentication makes credential material available; authorization decides
whether one Context/project may perform one HTTP effect. Tobari keeps those
decisions separate, so login, import, or credential replacement never adds a
network permission. Every authenticated request still needs an ordinary OPA
allow.

Tobari supports three custody routes. Tool-native credentials live inside one
Workspace home, the retained managed adapter keeps a configured secret at the
Gateway boundary, and the Auth Broker gives the Workspace only a bound opaque
handle. On the Broker route, static resolution, AWS signing, or Datadog token
work happens only after allow; the handle is neither the primary credential nor
sufficient authority by itself. Rotation, logout, and projection changes can
also require Workspace re-entry because an existing process environment is not
rewritten.

The Broker ordering below builds on [policy learning](/how-it-works/policy-learning/) and [project identity](/how-it-works/project-identity/).

## Three routes, three custody choices

| Route                    | Where the real secret lives                                   | What Workspace can read                         | Gateway action                                                                                                     | Main use and limitation                                                                                                     |
| ------------------------ | ------------------------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| Tool-native passthrough  | Files/environment created inside one Workspace home           | The real tool credential                        | Redacts credential values from OPA/audit; forwards after allow                                                     | Universal tool flow, but every process in that Workspace can read/use the tool state                                        |
| Auth Broker              | Encrypted Context vault, unlocked under installation root key | One project-bound opaque handle                 | Removes handle, introspects binding, asks OPA, then resolves, refreshes, or signs by the reviewed plan after allow | Strict static bindings plus reviewed GitHub, AWS, and Datadog plans only                                                    |
| Retained managed adapter | Owner-only Context secret files mounted only into Gateway     | Non-secret profile selector, not managed secret | Validates Context/project/host profile, asks OPA, reads/injects secret after allow                                 | Retained static bearer/fixed-header path; profile configuration and secret provisioning remain explicit host administration |

Authentication answers “what credential material is available?” Authorization answers “may this Context/project perform this HTTP effect?” Neither answer substitutes for the other.

### Decision input, target, and lifecycle compared

| Route                    | What OPA sees                                                                                                                          | Where it applies                                                                                                                | Replacement, logout, and re-entry                                                                                                                                      |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tool-native passthrough  | The ordinary body-free HTTP effect. Gateway removes recognized credential values before the decision input.                            | Standard HTTP/HTTPS requests supported by the tool and an exact policy rule.                                                    | The tool owns rotation and logout. Tobari cannot retract a secret already present in an existing process or Workspace home.                                            |
| Auth Broker              | The ordinary body-free effect plus non-secret provider metadata. OPA sees neither the handle, credential revision, nor primary secret. | Only the manifest's exact HTTPS target, source syntax, destination header transformation, and a separately allowed method/path. | Replacement or local logout advances/removes the record and invalidates its handles. Re-enter to receive reconciled projection; local logout is not remote revocation. |
| Retained managed adapter | The ordinary body-free effect plus the selected non-secret managed profile metadata.                                                   | The explicitly configured Context/project/host/profile and supported fixed-header path.                                         | Host administration replaces or removes the managed secret. Re-entry may be needed for projected selectors; an existing process environment is not rewritten.          |

The comparison is deliberately asymmetric: a passthrough tool gives the Workspace the credential, while managed and brokered routes keep secret-bearing custody on the trusted side of the boundary.

## Provider and Tool are separate axes

Provider identifies the external credential authority. Tool identifies the
Workspace client that receives the handle projection and emits the matching
request. The supported unit is their reviewed pairing, not either name alone.
The current built-ins are one-to-one, so Tool is visible but automatic after
Provider selection. AWS login method is a separate acquisition choice.

## Brokered flow in exact order

### 1. Acquire on the trusted host

`auth login [--provider PROVIDER]` runs one reviewed fixed host helper in a trusted-host
terminal. Omitting the provider presents the installed reviewed GitHub, AWS,
and Datadog login providers for an explicit choice and displays the one
supported client Tool selected with each Provider; supplying one skips the
menu. Datadog uses isolated fixed-US1 pup OAuth. `auth import
PROVIDER` accepts a bounded credential from protected non-terminal stdin only
when that provider declares import. Secret bytes do not use argv, environment,
logs, or Workspace input.

The Auth Broker stores one typed credential record for the selected stable
Context/provider in an AES-256-GCM encrypted vault. That record is a static
primary secret, opaque AWS host-driver state, or Datadog OAuth-session state.
The installation root key is held in macOS Keychain or an owner-only Linux XDG
state file and is retained in Broker memory only while unlocked.

Login or import does not add a network rule.

### 2. Issue a project-bound handle on entry

On the next matching Workspace entry, Tobari reconciles a random `tobari-h1_…` handle. It binds:

- stable Context ID;
- stable project ID;
- provider;
- credential revision;
- exact HTTPS target;
- source header and syntax;
- destination transformation; and
- secret-header redaction set or one compiled built-in plan.

The handle is projected only into manifest-declared environment entries or complete files. A different project in the same Context receives a different handle.

### 3. Recognize and remove at Gateway

Gateway selects the broker path only when exactly one provider binding matches the normalized HTTPS authority and declared source-header syntax. It removes the handle from the request before OPA or forwarding.

A Tobari-looking marker in a URL, cookie, header name, unsupported value, or ambiguous position is invalid. The marker commits the request to fail-closed Broker handling; it cannot downgrade into passthrough.

### 4. Introspect without the secret

Gateway sends the handle plus its host-derived Context/project principal and requested HTTP/header binding to the Broker runtime socket. Introspection returns only non-secret provider/revision binding metadata.

Context, project, provider, revision, target, and header binding must all match. A copied, stale, revoked, malformed, or ambiguous handle fails before OPA.

### 5. Ask OPA about the ordinary HTTP effect

Gateway sends schema 5 body-free input. OPA sees the non-secret provider ID, not the handle or primary credential. A brokered request does not inherit a broad static host/method allow; it needs the exact Context/project-bound L7 rule.

On deny, Gateway performs **zero** secret-resolution calls.

### 6. Run exactly the declared action after allow

The post-policy branch depends on the provider plan:

- **Static schema 1, including GitHub and Chatwork:** Gateway resolves the same
  revision once and replaces only the declared destination header.
- **AWS schema 2:** Gateway first retains the already-authorized complete
  request within the 8 MiB cap and hashes it. Broker starts one authenticated
  private companion operation for the fixed host AWS CLI credential export,
  rechecks and persists the same revision, and signs standard header-based
  SigV4 locally. Temporary AWS credentials never enter Workspace, OPA, policy,
  audit, or durable projection.
- **Datadog schema 2:** Broker selects an access token only when it remains
  outside the five-minute refresh window; otherwise it performs one
  same-record refresh at the exact proxy-free, no-redirect US1 token endpoint
  and commits refreshed state before returning one request-local bearer value.

Gateway then creates the separately verified TLS connection to the exact
application target and makes one upstream attempt.

Any resolved static secret, temporary AWS credential/signature material, or
Datadog access token is request-scoped in trusted infrastructure and is never
returned to the Workspace, OPA, CLI output, error, or audit.

## Rotation, replacement, logout, and running processes

- **Credential replacement** increments the credential revision and atomically revokes all prior handles for that Context/provider.
- **Logout** removes the local Context/provider credential and revokes its handles. It does not contact the provider and therefore does not guarantee remote revocation.
- **Broker restart** returns the service to locked state. A successful unlock rehydrates valid encrypted state; no request resolves while locked.
- **Re-entry** is required after login, import, replacement, or logout because Tobari cannot rewrite the environment of an already-running process. The next entry recreates environment projection and changes only unchanged Tobari-owned complete files.

An old running process may still contain the old handle string, but the Broker rejects it after revision change/logout. Tool-native secrets already held in process memory follow the tool's own semantics, not Broker revocation.

## Concrete copied-handle scenario

A process copies a valid handle from Workspace A into Workspace B and sends it to the same host and header.

Gateway derives B's principal from the registered, kernel-observed Workspace
source endpoint. Broker introspection compares B against the handle's
Context/project/provider/revision/target/header binding. The project mismatch
produces `403 credential_handle_invalid`; Gateway does not call OPA, resolve
the secret, use passthrough, or contact upstream.

Even in Workspace A, a valid handle is insufficient by itself. The ordinary HTTP effect must also receive an OPA allow.

## Failure behavior

| Condition                                                                        | Result                                                                                                                     |
| -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Invalid, stale, copied, revoked, or binding-mismatched handle                    | 403 `credential_handle_invalid`; no fallback                                                                               |
| Broker locked/unavailable, or known pre-execution companion/refresh/sign failure | 503 `credential_broker_unavailable`; no upstream attempt                                                                   |
| AWS companion or Datadog refresh outcome is explicit/post-dispatch unknown       | Non-retryable 409 `credential_refresh_outcome_unknown`; no application upstream attempt; reconcile before deliberate retry |
| Valid handle but OPA deny                                                        | 403 `policy_denied`; zero secret resolution                                                                                |
| Managed profile not bound to Context/project/host                                | 403 `credential_profile_not_bound`                                                                                         |
| Managed secret unreadable or invalid                                             | 503 `credential_unavailable`                                                                                               |
| Root key missing while a vault exists                                            | Fail closed; no replacement key is generated                                                                               |
| Running Workspace has stale projection after mutation                            | Re-enter to reconcile; existing process environment is unchanged                                                           |

## Guarantees and limitations

**Guaranteed:** brokered static secrets, renewable state, and derived request
credentials remain outside Workspace and OPA; handle use is bound to
Context/project/provider/revision/HTTP target; deny causes zero resolve,
refresh, companion, or signing actions; invalid Tobari markers never fall back;
login/import/logout do not edit network policy.

**Not guaranteed:** remote provider revocation on logout; isolation between processes inside one Workspace; prevention of a malicious process using an already allowed capability; secrecy of a tool-native credential from other same-Workspace processes; OAuth/refresh/signing/provider APIs beyond the reviewed plans; protection after Gateway, Broker, root-key backend, or host compromise.

The handle itself can be sent as ordinary request body data on an already allowed route because Tobari does not search arbitrary bodies. That reveals no primary credential and grants no Broker authority, but payload exfiltration of the non-secret handle is outside the body-inspection guarantee.

## Summary

Tool-native login gives one Workspace the real tool credential. The retained
managed path keeps a static secret at Gateway. The Broker path gives the
Workspace only a bound handle and performs its declared static, AWS, or
Datadog action after OPA allow. All three still depend on ordinary network
authorization.

## Check your understanding

You should now be able to explain credential custody separately from communication permission.

<details>
  <summary>
    Does the Workspace handle contain or equal the primary credential?
  </summary>
  No. It is an opaque, constrained record selector. Static or renewable
  credential state remains in the encrypted Context vault.
</details>

<details>
  <summary>Which secret-bearing Broker actions occur on an OPA deny?</summary>
  None. Introspection may establish non-secret binding metadata before OPA;
  static resolution, Datadog token selection/refresh, AWS companion export, and
  signing occur only after allow.
</details>

<details>
  <summary>Does `auth logout` revoke the credential at the provider?</summary>
  No. It removes local Context/provider state and revokes Tobari handles without
  contacting the provider.
</details>

<details>
  <summary>
    Can a malicious same-Workspace process use an already permitted
    authenticated capability?
  </summary>
  Yes. Same-Workspace processes share that boundary. Tobari limits projection
  and route authority; it does not isolate processes inside one Workspace.
</details>
