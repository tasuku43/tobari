Authentication answers what identity material is available. Authorization
answers whether one Context/project may perform one exact HTTP effect. Login,
import, replacement, and projection never add network permission.

## Two custody choices

| Route       | Real credential location                                | Workspace can read              | Trusted action                                                                 |
| ----------- | ------------------------------------------------------- | ------------------------------- | ------------------------------------------------------------------------------ |
| Tool-native | Tool files or process state in writable Workspace home  | The tool credential             | Redact recognized values from OPA/audit and forward only after exact allow     |
| Auth Broker | Encrypted Context vault under the installation root key | One project-bound opaque handle | Introspect binding before policy, then resolve one static revision after allow |

Tool-native authentication remains a deliberate product path. Tobari does not
pretend that state is brokered or revoke it. Processes in the same Workspace
share its authority.

## Provider and Tool stay distinct

Provider identifies the credential authority. Tool identifies the Workspace
client receiving the projection. V1 has one reviewed built-in pairing,
GitHub/`gh`; it still requires `auth login --provider github`. Owner providers
use strict stdin import and static projection rather than executable helpers.

The canonical V1 plan stores one static primary secret, issues project-specific
handles, and declares exact HTTPS target/header bindings. An owner manifest is
non-secret and non-executable. It cannot select shell, provider code, remote
fetch, dynamic credential behavior, or network policy.

## Brokered flow in exact order

### 1. Acquire on the trusted host

The built-in command runs the fixed GitHub helper from a sanitized temporary
home. `auth import PROVIDER` reads one bounded value from protected non-terminal
stdin for an installed owner provider. Secret bytes never use argv,
environment, logs, or Workspace input. The Broker commits one encrypted static
record for the stable Context/provider. No allow rule is created.

### 2. Issue a bound handle

On matching Workspace entry, Tobari projects a random handle bound to Context,
project, provider, credential revision, exact HTTPS target, source syntax,
destination transformation, and redaction set. A different project receives a
different handle.

### 3. Recognize, remove, and introspect

Gateway selects the Broker path only when exactly one binding matches. It
removes the handle, derives Context/project identity from the observed source,
and asks Broker to validate binding metadata without returning the secret. A
copied, stale, revoked, malformed, misplaced, or ambiguous marker fails here
with no passthrough fallback.

### 4. Apply guardrail and exact policy

The immutable Context preset guardrail is authoritative. A terminal preset
denial creates no candidate and performs no DNS, secret resolution, or upstream
call. Otherwise OPA receives the exact body-free effect and non-secret provider
metadata—not the handle, revision, body, or credential.

### 5. Resolve one static revision after allow

Only after allow, Gateway asks Broker once for the same revision and exact
HTTP/header binding. Gateway replaces only the manifest-declared destination
header, verifies the exact TLS destination separately, and makes one upstream
attempt. The primary secret is request-local in trusted infrastructure.

## Rotation, logout, and re-entry

Replacement advances the revision and revokes every earlier handle for that
Context/provider. Logout removes the local record and handles but does not
contact the provider. Re-entry reconciles the projection because an existing
process environment cannot be rewritten. A Broker restart returns to locked
state; no resolution occurs until valid unlock.

## Failure behavior

| Condition                                             | Result                                                                            |
| ----------------------------------------------------- | --------------------------------------------------------------------------------- |
| Invalid, stale, copied, revoked, or mismatched handle | `403 credential_handle_invalid`; no fallback, policy request, or upstream attempt |
| Broker locked or unavailable                          | `503 credential_broker_unavailable`; no upstream attempt                          |
| Valid handle but terminal guardrail or OPA deny       | `403 policy_denied`; zero resolution and upstream work                            |
| Root key missing while a vault exists                 | Fail closed; never generate a substitute key                                      |
| Running process holds an old handle                   | Re-enter after repair; Broker rejects the old revision                            |

## Guarantees and limitations

The Broker primary secret stays outside Workspace, OPA, output, errors, and
audit. Handles are exact, project-bound selectors rather than credentials or
network grants. V1 does not offer multiple accounts per Context, remote logout,
dynamic credential plans, or peer-process isolation inside one Workspace.

## Summary

Tool-native state remains Workspace-owned. Brokered V1 credentials are static:
one bound handle, deny-before-resolution, and one exact replacement after allow.
