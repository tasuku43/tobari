title: Credentials
description: Understand native Workspace authentication and the post-policy credential boundary.
---

## Standard ownership

An agent CLI creates and stores its native authentication state inside the
persistent Context Home mounted into every Workspace owned by that Context. Tobari does not inherit or
copy host credentials, and the release surface has no Tobari-owned
authentication command or credential service.

Every process in every Workspace of the same Context can read that state. Another Context has a
different Home. Workspace deletion preserves the tool-owned state for its
replacement; exact Context deletion retires it.

## Post-policy forwarding

Gateway treats authentication as secret request data, not policy identity. It
removes Authorization, API-key, and cookie values from OPA input and audit,
asks OPA about the ordinary exact HTTP effect, and forwards the original values
only after allow. Deny performs no DNS or upstream connection.

This means login and permission are independent:

- native login does not add a policy rule;
- an allow does not create or refresh a credential;
- a same-Context Workspace process can exercise an authenticated effect if policy
  allows it;
- Tobari does not infer authority from `claude`, `codex`, or another process
  name.

## Agent-ready login effects

The fixed agent-ready compatibility baseline contains exact Claude
hello/token/profile/roles effects and
Codex browser/device token effects. The Claude regression preserves provider
profile metadata, including subscription and rate-limit classification, after
native token exchange.

## Security limit

Native Context authentication protects the host and other Context homes;
it is not process-level secret isolation among sibling Workspaces. Exact network
policy remains the control over where an authenticated request can go.
