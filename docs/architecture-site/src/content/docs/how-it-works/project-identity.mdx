Before Gateway prepares credentials or asks OPA, it identifies the request's
Workspace Manifest and project. It selects that principal from the kernel-observed
Workspace source endpoint and an owner-controlled registry populated by the
trusted host.

Caller-supplied project or Workspace Manifest IDs are never authorization inputs. Changing
a header therefore cannot claim another Workspace's learned rules, and the same
host, method, and path from a different Workspace still needs authority scoped
to its own principal. This mechanism builds on the dedicated networks in the
[system overview](/how-it-works/system-overview/) and applies equally to the
intercepted flows described in [HTTPS and two TLS connections](/how-it-works/https-and-tls/).

## Principal creation on the trusted host

For each logical Workspace, host-side lifecycle code:

1. validates the stable UUIDv7 project ID and permanent Workspace Manifest ID;
2. creates or verifies the exact owner-labeled dedicated internal network;
3. connects Gateway to that network;
4. inspects the Workspace and Gateway IP addresses on that exact network;
5. validates that both endpoints are distinct, canonical, and unique; and
6. atomically writes a schema 1 binding to the owner-only principal registry.

Each binding contains project ID, Workspace Manifest ID, Workspace Manifest name, canonical root,
network name, Workspace source IP, and Gateway endpoint IP. Project, network,
and address entries must be unique; unsafe loopback, link-local, multicast, or
unspecified addresses are rejected.

The registry is mounted read-only into Gateway. A Workspace receives neither write access to it nor Docker control that could author the binding.

## Principal resolution on each request

Gateway observes `flow.client_conn.peername[0]`: the kernel-reported source
address for the accepted project-network connection. That Workspace source
address selects one binding. The registered Gateway endpoint is checked by
lifecycle reconciliation and prevents endpoint reuse; it is not the request
principal key.

This detail matters. The value is not:

- the client source IP claimed in a header;
- `TOBARI_ID` or `TOBARI_CONTEXT_ID` from the Workspace environment;
- `x-tobari-session` or another request field;
- a Workspace Manifest display name;
- a credential provider name; or
- a URL parameter.

After lookup, Gateway places the registry-derived `workspace_manifest_id` and `project_id` in schema 1 OPA input. The fixed OPA router selects policy by Workspace Manifest ID; learned rules also require the project ID.

## Concrete forgery attempt

Workspace B copies these request headers from Workspace A:

```http
X-Tobari-Session: project-a
X-Tobari-Workspace Manifest: review
Authorization: Bearer example
```

The connection still has Workspace B's kernel-observed source endpoint.
Gateway selects B's Workspace Manifest/project binding and strips or redacts
control/credential values as required. A rule learned for A does not match B
even if host, port, method, and path are identical.

If the request contains a copied broker handle from A, the result is stricter still: non-secret Broker introspection checks the derived B principal against the handle's Workspace Manifest, project, provider, credential revision, target, and source-header binding. The mismatch becomes `403 credential_handle_invalid` before OPA.

## Why network identity is used

A Workspace process can modify its request, environment, filesystem, and tool
configuration. Any identity located there is attacker-controlled data. The
dedicated network gives trusted host lifecycle code a place to establish an
exact source-endpoint binding that the Workspace cannot choose per request.

This is a Docker implementation of a more general contract: the runtime supplies a trustworthy connection-to-principal binding. Policy code does not reconstruct identity from names or parsing conventions.

## Failure behavior

- Registry missing, unreadable, too large, wrong version, malformed, unsafe, duplicate, or ambiguous: Gateway returns `403 project_principal_unavailable`.
- Incoming Workspace source endpoint not registered: the same 403 occurs before OPA or upstream I/O.
- Network recreation changes either endpoint: lifecycle must reapply the network guard and reconcile the registry before the Workspace becomes ready.
- Unknown Workspace Manifest ID at OPA: the aggregate router denies and never falls back to the default Manifest.
- User changes Workspace Manifest display name/default: stable stored IDs, not names, remain enforcement identity.

The Gateway binding parser validates the exact per-binding shape and required values. The site does not claim a stronger duplicate-key rejection property for Python's general JSON parser.

## Guarantees and limitations

**Guaranteed under supported lifecycle/topology:** caller-supplied identity is not authority; project and Workspace Manifest are established together before OPA; learned rules and broker handles cannot cross project principals; stale network bindings fail closed.

**Not guaranteed:** resistance after host, Docker, Gateway, or registry compromise; tenant isolation for overlapping selected roots; a general cryptographic remote-workload identity; identity derived from arbitrary manually created containers outside Tobari lifecycle.

## Summary

The host binds one exact Workspace source endpoint, Gateway endpoint, and
dedicated network to stable Workspace Manifest/project IDs. Gateway observes the source
endpoint on every request. Headers and names can describe a caller, but they
cannot grant another principal's authority.

You should now be able to explain why shared Gateway/OPA services do not mean shared learned permission.

<details>
  <summary>
    A process writes another project ID into a header. Which ID reaches OPA as
    principal?
  </summary>
  The ID selected by Gateway's kernel-observed Workspace source endpoint and the
  host principal registry. The header is not authority.
</details>

<details>
  <summary>
    Workspace A and B use the same host, port, method, and path. Does A's
    learned rule authorize B?
  </summary>
  No. Exact learned rules also bind stable Workspace Manifest and project IDs.
</details>

<details>
  <summary>
    What happens while a recreated network has no valid registry binding?
  </summary>
  Requests fail closed with `project_principal_unavailable`; lifecycle must
  reapply the network guard and reconcile the endpoint binding first.
</details>
