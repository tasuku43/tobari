A learnable policy denial stops the request and leaves secret-free evidence; it
does not ask the Workspace to approve itself. On the trusted host, Tobari
validates that retained evidence and derives an opaque exact candidate for
review. The user explicitly chooses allow or deny.

Applying that choice validates the complete policy and atomically activates a
new revision. Failed or stale activation preserves the previous policy, and
the original request runs again only when the user or tool deliberately
retries it. Baseline deny, a learned exact deny, reset, and compaction remain
different states and operations. The loop relies on the established [project identity](/how-it-works/project-identity/) and the ordering in [one request through Tobari](/how-it-works/request-journey/).

## 1. Denial is not a permission request

OPA is deny-by-default for effects that match neither initialized static authority nor learned allow rules. This does not mean every first request is denied: the initialized policy contains limited static rules. A request outside current authority may be classified as learnable only after its schema, principal, scheme-specific fixed port, and credential binding are valid and no terminal deny matches.

Gateway returns `403 policy_denied`. A learnable response names only the trusted-host review location and exact visible effect. It explicitly says there is no automatic retry.

## 2. Evidence is retained without payload or secrets

Gateway writes bounded schema 1 denial audit into its rotated Docker logs. Candidate discovery reads a bounded tail and accepts only strict validated deny records.

Evidence includes Context/project identity, host, port, method, path, reason, timestamp, and non-secret diagnostics. It omits query, headers, body, handle, credential revision, and primary credential. A handle-bearing URL path is replaced as a whole with `/[redacted-auth-handle]`.

Evidence retention is bounded, not an infinite durable permission inbox. If an observation falls outside the selected log window before action, it can no longer authorize a mutation.

## 3. The CLI derives an exact opaque candidate

Pending observations group by exactly:

- stable Context ID;
- stable project ID;
- host;
- port;
- method; and
- normalized raw path.

Body content, body presence, query, headers, reason, status, request ID, timestamp, provider, and profile display evidence do not split the identity.

The candidate ID has the `pcy_…` shape and is derived from those dimensions. It is opaque: actions accept it unchanged rather than decoding, reconstructing, or using list position as authority.

The rule record itself does not store a scheme field. Current HTTP and HTTPS authority remains separated by the fixed, non-overlapping scheme/port contract. Do not infer arbitrary cross-scheme safety if that contract changes.

## 4. Review and action stay separate

`policy candidates` is the machine discovery surface. `policy review` is the human Permission Inbox. Redirected/machine-readable review is read-only; on a TTY, the list is still non-mutating while the user opens details and stages **Allow exact** or **Deny exact** choices for one Context.

Each staged choice retains the unchanged opaque ID. Pressing **Apply** revalidates the complete staged set and activates it once; canceling first discards every choice without a write. Apply or discard before switching Context so durable source promotion remains one atomic file replacement. Display order, indentation, label text, or a reconstructed host/path is never the target. Machine callers continue to delegate one unchanged ID to `policy allow --id …` or `policy deny --id …`.

At action time, Tobari re-reads current retained evidence and current rules. A stale, expired, already-covered, or mismatched ID produces no policy mutation.

## 5. Validate and activate as one complete policy

For a valid exact action or reviewed set, Tobari:

1. locks aggregate policy mutation;
2. verifies the current aggregate revision and complete learned allow/deny snapshot;
3. builds and tests a private candidate for the target Context;
4. writes the Context source with owner-only fsync-and-rename semantics;
5. generates a content-addressed aggregate from **every** Context;
6. tests the complete candidate with OPA;
7. atomically publishes the content-addressed aggregate projection;
8. publishes a revisioned complete bundle to the owner-labeled Docker-managed policy volume;
9. waits for the running OPA to report that exact revision; and
10. persists the new state.

On failure it restores source and the prior known-good projection/state. A concurrent change produces `policy_data_changed` rather than silently overwriting it. Authority-reducing changes first activate a deny-all transition revision, so stale broader authority is not served while the candidate changes. Routine activation keeps the OPA container running.

## 6. Retry deliberately

Activation never replays the old request. The user or agent deliberately issues a new request, which passes through principal establishment and policy again.

This matters for non-idempotent methods and bodies: Tobari cannot know whether blind replay would be safe.

## Allow, deny, reset, and compaction

| Decision                 | Meaning                                                                                                              |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| Initialized/static allow | Installation policy present before observation; not a learned project rule                                           |
| Baseline deny            | Host/method/path boundary that is terminal and never enters pending review                                           |
| Learned exact allow      | One Context/project/host/port/method/path capability                                                                 |
| Learned exact deny       | One explicitly reviewed terminal rejection; it wins over an allow for that effect                                    |
| `policy reset`           | Removes one learned allow or exact deny and returns the effect to initialized/default evaluation; it is not an allow |
| Explicit compaction      | Replaces at least three compatible exact sibling rules with a reviewed safe prefix rule                              |

Compaction is never automatic. It groups only the same Context/project/host/port/method, rejects shallow or unsafe prefixes, retains positive examples and source IDs, and checks an outside-prefix canary. Tobari does not invent a wildcard from one denial.

## Concrete example

Three exact allows exist for:

- `PUT /review/items/1`
- `PUT /review/items/2`
- `PUT /review/items/3`

Tobari may discover a `pcx_…` compaction proposal for `/review/items/` when all other boundaries match. Nothing changes until a host action selects that opaque proposal. `/review/admin` remains outside the prefix and serves as a negative boundary; a different project or method also remains denied.

## Failure behavior

- Non-learnable denial offers no review command.
- Malformed or secret-bearing log data is rejected as evidence.
- Stale candidate/reference creates no rule.
- Any invalid Context source or aggregate aborts activation.
- Concurrent source change aborts rather than overwrites.
- OPA recreation failure restores previous known-good authority as far as the controlled rollback can do so.
- Reset can make the same request reviewable/denied again; it never means “allow all.”

## Guarantees and limitations

**Guaranteed:** observation alone changes no authority; mutations use one opaque reference; exact rules are Context/project-bound; whole-policy validation precedes activation; no automatic wildcard or request replay; body does not silently narrow the grant.

**Not guaranteed:** infinite denial retention, body-level control, provider-operation semantics, automatic policy minimization, safe human approval decisions, or zero service interruption during OPA recreation.

## Summary

Denial produces bounded evidence, not permission. The host derives a project-bound opaque candidate, explicitly chooses an exact outcome, validates every affected policy source as one aggregate, activates atomically, and retries only by choice.

    Do two requests with different bodies create two candidates?
  </summary>
  No. Body presence and content are not candidate identity. One exact rule
  covers any body on that exact Context/project/host/port/method/path.
</details>

<details>
  <summary>What authority does list position in `policy review` have?</summary>
  None. The act consumes one validated opaque reference unchanged after explicit
  detail selection.
</details>

<details>
  <summary>
    What is the difference between baseline deny and learned exact deny?
  </summary>
  Baseline deny is initialized terminal policy and never becomes a candidate.
  Learned exact deny records an explicit host review for one exact project-bound
  effect and can later be reset.
</details>

<details>
  <summary>Does successful activation retry the denied request?</summary>
  No. The caller deliberately sends a new request, which is evaluated again.
</details>
