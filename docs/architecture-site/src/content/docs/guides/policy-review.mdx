Policy review turns retained denial evidence into an explicit host-owned decision. Leave the Workspace, inspect the bounded secret-free Permission Inbox on the trusted host, stage domain-valid choices from its raw list and typed detail, and Apply the reviewed set once. Approval changes policy; it never retries the denied traffic.

Keep the Workspace attached and open Permission Inbox in a separate trusted-host terminal. Tobari reserves no `Ctrl+]` or other child-input shortcut and does not replace a shell or full-screen program's terminal presentation.

[First denial](../../start/first-denial/) explains how the request reaches this host-side review flow.

## 1. Stop retrying and leave the Workspace

A learnable Gateway `403` contains fixed guidance to run `tobari review permissions` on the host. It contains no candidate ID and gives the agent no way to approve itself.

Exit the Workspace before review. Repeated retries do not increase authority; they only refresh bounded evidence for the same effect.

## 2. Open the human review flow

```sh
tobari review permissions
```

The installation-wide TTY queue displays pending effects from its bounded Gateway-log window. Select one item, then inspect:

- Workspace Template and Project root;
- scheme, host, and port;
- method and normalized path;
- exact or typed path-template match; and
- the domain-valid Allow or Deny outcomes.

Press **a** or **d** on an exact row to stage **Allow** or **Remember deny**, and **x** to clear it. Open detail to inspect the typed effect. A path-template item offers only **Allow matching paths** because Deny is not valid for that shape. Every choice remains staged and grants no authority. Press **p** to inspect the final ordered review, then confirm **Apply** to revalidate and activate the set once. Canceling before Apply discards every staged choice. Manual refresh also discards the staged set before reading a fresh snapshot, so a replacement item never inherits authority by label.

The release command has no watch or notification mode. Reopen it after a new denial. It does not retry the denied request.

## 3. Use the machine path only when needed

Redirected review is read-only:

```sh
tobari review permissions --format json
```

Copy the emitted opaque `pcy_...` ID unchanged into one action:

```sh
tobari policy allow --id <pcy-id>
# or
tobari policy deny --id <pcy-id>
```

Do not decode, normalize, reconstruct, or append unchecked display text. The action resolves the ID against current retained evidence. A stale or expired reference fails instead of selecting a similar request.

`tobari policy candidates --format json` is the dedicated structured discovery view. It performs no action.

## 4. Understand activation

One reviewed Apply:

1. resolves every retained reference against a fresh queue snapshot;
2. locks policy generation;
3. changes only the owning Context's Policy Memory;
4. validates the private Workspace Template source;
5. generates and tests the complete all-Context aggregate;
6. publishes one revisioned complete bundle;
7. waits until the running OPA reports that exact revision; and
8. reports the confirmed decision without replaying the request.

If any validation or activation step fails, Tobari retains or restores the previous known-good aggregate. It does not partially activate the new rule.

## 5. Retry deliberately

After a confirmed allow, re-enter the matching Workspace and issue a new request. The old denied request is gone; Gateway never queues or replays its body.

An exact rule is owned by one Context and binds the observed Workspace, scheme,
host, port, method, and path. Body, timestamp, display order, request ID, and
credential label do not widen or split its authority.

## Correct current policy

List the exhaustive current learned decisions:

```sh
tobari policy rules
```

Reset one opaque learned-rule reference:

```sh
tobari policy reset --id <policy-rule-id>
```

Reset removes only that CLI-owned learned decision and returns the effect to default deny. It is not an allow, request retry, or baseline-policy edit.

First public V1 keeps every learned rule exact. It has no widening operation,
No operation or dormant fallback widens exact rules.

## Failure behavior

- Empty queue: no valid pending learnable denial exists in the requested retained window; this is not proof that no historical denial occurred.
- Baseline deny or current exact deny: remains audit evidence but not a pending candidate.
- Scheme, principal, cluster, or principal-registry binding failure: not learnable through an ineffective exact rule.
- `policy_candidate_not_found` or a stale rule reference: rediscover current state; do not reuse an older reference.
- `policy_test_failed` or preflight failure: inspect owner-only policy and OPA diagnostics. The prior policy remains authoritative.
- Uncertain mutation output: use `tobari policy rules` and `tobari cluster status` to reconcile before another mutation.

## Guarantees and limits

Routine learning cannot silently create wildcard rules or authorize from observation alone. Exact decisions are project/Workspace Template scoped and body-free. The user still decides whether the destination and effect are appropriate; Tobari cannot infer semantic intent or prevent an allowed effect from carrying sensitive readable data.

## Summary

Review is trusted-host discovery plus explicit staged typed decisions. References remain opaque, the confirmed set activates once, and every retry is a new request initiated by the user or agent after confirmation.

## Check your understanding

<details>
<summary>Why is the item number in the review list not an action target?</summary>

List order is presentation, not authority. The action consumes the opaque reference that binds the retained effect and is revalidated at execution time.

</details>

<details>
<summary>Does a learned exact deny keep returning as a pending item?</summary>

No. It remains current resolved policy and audit evidence. Reset it to default deny if you intentionally want a future matching denial to become reviewable again.

</details>

<details>
<summary>What does approval do with the original request body?</summary>

Nothing. The body was not retained for policy or replay. Approval changes policy; the caller must issue a new request.

</details>
