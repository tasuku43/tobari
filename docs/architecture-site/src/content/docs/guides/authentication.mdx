---
title: Authentication
description: Use each agent CLI's native login inside its Workspace while keeping credentials separate from network permission.
---

Authentication and network authorization are separate in Tobari. A successful
login identifies an account; it does not grant an HTTP effect.

## Standard authentication model

The standard profile has no provider binding, credential projection, Auth
Broker, or `tobari auth` command. Enter the Workspace and use the agent CLI's
official login:

```sh
cd /path/to/project
tobari

# Inside the Workspace
claude
# or
codex login
```

Claude Code and Codex are part of the locally built agent-ready base. Their
native state is written below that Workspace's persistent home. It survives
`exit` and container recreation, is not shared with another Workspace, and is
removed by `tobari delete`.

Tobari never copies the host home, host CLI login state, Keychain, SSH agent,
or credential environment into the Workspace.

## Request boundary

Every process in one Workspace can read that Workspace's native credential.
Gateway does not infer which executable created or uses it. For an HTTP request:

1. Gateway derives the host-owned Context/project principal.
2. It removes authentication and cookies from OPA input and audit evidence.
3. OPA decides the ordinary exact scheme, host, port, method, and path effect.
4. On deny, the credential and request do not reach upstream.
5. On allow, Gateway forwards the original header in one upstream attempt.

The immutable `builtin/agent-ready` preset includes a finite set of exact
Claude/Codex login, account, model, and core effects. It is Context-wide HTTP
authority—not executable identity. Plugins, connectors, MCP, downloads, and
unmatched routes remain denied or reviewable.

## Native-login regression

Claude Code login performs platform hello and token exchange, then reads its
Anthropic roles and profile. Tobari explicitly allows these pinned effects.
The authenticated profile request remains ordinary passthrough: its bearer is
absent from OPA/audit and preserved only after allow. Provider-owned
`subscriptionType` and `rateLimitTier` responses are not decoded or replaced,
so `/status` can report the native account type correctly.

Codex browser login uses its OAuth token exchange. Its device-code variant also
uses the exact user-code and token polling endpoints. Both follow the same
post-policy passthrough boundary.

## Login can still be denied

If an effect is outside the preset, use the normal permission loop from a
separate trusted-host terminal:

```sh
tobari policy review
```

Inspect the exact destination and allow only the effect you intend, then retry
in the still-running Workspace. Login never creates a policy rule, and policy
approval never performs login.

## Experimental Broker research

`task build:dev` retains a compile-time experimental Auth Broker and its
`auth` commands for repository research. It is not present in the standard
catalog, Compose topology, Gateway image, component lock, or release. No
environment variable or runtime input can activate it in a standard binary.

## Guarantees and limits

Standard Tobari keeps host-managed credentials out of Workspaces and keeps
Workspace authentication out of OPA, audit, denial output, and logs. It does
not isolate mutually hostile processes inside one Workspace, prevent use of an
already allowed authenticated capability, perform remote logout, or interpret
provider credential schemas.

## Summary

Run the provider's own login in the Workspace. The Workspace owns the native
credential; Gateway owns whether its HTTP effects can leave.
