Authentication and network authorization are separate in Tobari. Choose one explicit authentication path for the tool, then authorize its ordinary HTTP effects separately. A successful login or import never adds a network allow rule.

This guide compares Broker-required bindings with Workspace-owned compatibility, shows the reviewed built-in broker flows, and covers handle binding, rotation, and logout. Read [Request journey](../../how-it-works/request-journey/) and [Contexts](../contexts/) first.

## Compare the two runtime routes

| Path                          | Where the primary credential lives                              | What the Workspace can read                                             | Gateway behavior                                                                                                     | Main limit                                                      |
| ----------------------------- | --------------------------------------------------------------- | ----------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| Workspace-owned compatibility | Tool-owned state in that Workspace's persistent home or process | The real tool credential                                                | Only for an undeclared binding: removes auth/cookie fields from OPA and audit, then forwards after allow             | Credential is available to processes in the same Workspace      |
| Broker-required binding       | Encrypted Context vault under an installation root key          | A random project-bound handle, not static or renewable credential state | Rejects real Workspace credentials; introspects the handle, asks OPA, then resolves, refreshes, or signs after allow | Exact declared bindings plus the closed reviewed built-in plans |

No path changes the OPA rule requirement. “The request is authenticated” and “this Context/project/method/path may connect” are different claims.

## Workspace-owned compatibility

For a provider binding Tobari has not declared, enter the Workspace and use the tool's normal supported login or inject a credential through its environment/files. Its state is stored below the Workspace's persistent home and survives `exit`, container loss, and runtime rebuild. It is isolated from other Workspace homes and removed by `tobari delete`.

Tobari does not copy the host home, Keychain, SSH agent, credential environment, or general CLI configuration into the Workspace. Compatibility state is readable by other processes within that same Workspace boundary. A real credential at a declared binding is rejected as `broker_auth_required`; running a tool's local login does not override that routing rule.

## Provider first, Tool second

A credential Provider and the Workspace client Tool that uses it are different
abstractions. Tobari supports a complete pairing: acquisition, handle
projection, exact request binding, and the client that emits that request.
Today every reviewed built-in pairing has one supported client Tool. The CLI
therefore asks for the Provider, shows the Tool, and selects it automatically.
It does not pretend that the two concepts are identical, and it does not add a
redundant `--tool` input.

## Reviewed built-in authentication

The reviewed helpers are GitHub, two AWS login methods, Datadog US1 pup OAuth,
OpenAI Codex device auth, and Anthropic Claude setup-token acquisition.
Chatwork uses protected stdin import. For GitHub, on the trusted host:

```sh
tobari cluster up
tobari auth status --context default
tobari auth login --context default # choose an installed reviewed provider
tobari auth login --provider github --context default
tobari auth status --context default
```

Login requires an interactive trusted-host terminal. Omitting optional
`--provider` presents only installed reviewed login providers; an explicit
`--provider` skips that menu. Each menu row names its automatically selected
Workspace client Tool. The AWS-only `--method` flag requires
`--provider aws`. Tobari runs the trusted host's identity-checked GitHub CLI
with fixed argv, sanitized private configuration, bounded projected output,
and checked cleanup. Neither Gateway nor Auth Broker runs `gh`; the acquired
static value is committed through Broker control and encrypted in the stable
Context vault without appearing in CLI output.

Leave and re-enter a Workspace permanently bound to that Context:

```sh
tobari --context default
```

The Workspace receives a distinct `tobari-h1_...` handle. For the built-in GitHub manifest it is projected for supported GitHub CLI API use, but it is not the upstream token. Private Git transport through a broker Git credential helper is not currently supported.

For AWS, choose one explicit trusted-host method:

```sh
tobari auth login --provider aws --method identity-center --context default
# or, with AWS CLI 2.32 or newer:
tobari auth login --provider aws --method console --context default
```

Identity Center collects the reviewed commercial start URL, SSO region,
12-digit account ID, and role and runs fixed device login. Console login asks
for one commercial region, opens only the validated cross-device URL, and lets
AWS CLI read the authorization code from terminal stdin. Both use an isolated
temporary home and encrypt only distinct bounded opaque AWS state. After
re-entry, the Workspace's three AWS credential variables contain the same
project handle—not access key material. Request region remains ordinary
Context or command configuration.

For Datadog, run `tobari auth login --provider datadog --context default`. Tobari invokes
fixed host `pup --no-agent auth login --site datadoghq.com` in a private
file-backed home; pup owns browser consent and the loopback callback. After
re-entry, the Workspace receives `DD_ACCESS_TOKEN=<project handle>` and fixed
`DD_SITE=datadoghq.com`. A valid access token is selected only after OPA allow;
near expiry, Broker performs one bounded fixed-US1 refresh and persists the
replacement encrypted state. Pup is not installed in Broker.

For OpenAI, run `tobari auth login --provider openai --context default` with a
stable Codex CLI installed on the trusted host. Tobari records its version but
accepts it only when the fixed device-auth command and strict V1 state contract
succeed. The separately pinned Workspace Codex projection is unchanged. For Anthropic, run
`tobari auth login --provider anthropic --context default` with exactly Claude
Code 2.1.220. Codex uses the reviewed device-auth flow and a strict private
auth file; Claude captures one setup token through a private PTY. Chatwork is
configured through `auth import chatwork`, not the interactive selector.

## What happens on one brokered request

1. Gateway derives the Context/project principal from the kernel-observed Workspace source endpoint.
2. It matches the exact provider binding. A real Workspace credential at that binding fails as non-learnable `broker_auth_required` before OPA or external I/O.
3. It strictly recognizes the provider-declared handle in the exact source header and removes it.
4. Broker introspection verifies Context, project, provider, credential revision, target, and header binding without returning the secret.
5. Gateway asks OPA about the ordinary body-free HTTP effect.
6. On deny, processing stops. There is no static resolution, Datadog/OpenAI
   token selection/refresh, AWS companion call/signing, or upstream connection.
7. On a static allow, Gateway resolves the same revision once and replaces the
   declared header.
8. On an AWS allow, Gateway captures the complete authorized request within
   8 MiB. Broker uses the authenticated private host companion for one fixed
   AWS CLI credential export, rechecks/persists the revision, and signs
   standard header-based SigV4 locally.
9. On a Datadog allow, Broker selects a sufficiently valid token or performs
   one same-record strict refresh at the exact proxy-free, no-redirect US1
   token endpoint and commits state before returning a bearer value.
10. On an OpenAI allow, Broker selects or refreshes the same-account token and
    returns only its validated account ID for the reviewed supplemental header.
11. Gateway creates one exact HTTPS upstream connection. It does not replay.

Copying a valid handle from Workspace A to Workspace B fails because the host-derived project principal no longer matches. A stale revision after replacement/logout also fails. Any malformed, misplaced, ambiguous, or binding-mismatched Tobari-looking handle is rejected; Gateway does not fall back to passthrough.

## Import for an installed schema-1 provider

Owner-controlled provider manifests may declare `stdin_import`. Supply one credential through protected non-terminal stdin:

```sh
trusted-secret-source | tobari auth import example --context default
```

`example` must already be an installed provider ID; the command does not create a manifest. Terminal stdin is rejected before reading bytes. Credential input is bounded and is never accepted in argv, environment, or output. User manifests cannot add executable helpers, request signing, refresh, arbitrary routes, or method/path policy.

## Rotation and logout

Replacing a Context/provider credential revokes every previously issued handle. A running process still holds its old environment value, but that value is invalid. Leave and re-enter to receive a new project-specific projection.

To remove local broker state:

```sh
tobari auth logout github --context default
tobari auth status --context default
```

Logout removes the local provider record and revokes its handles. It does not contact GitHub or guarantee remote token revocation. It also cannot rewrite the environment of an already running process; next entry removes the projection. `cluster down --purge` is not a substitute for logout and preserves vaults/root key.

## Failure behavior

- `auth_login_tty_required`: run login from a trusted-host interactive terminal.
- `invalid_credential_input`: pipe or redirect exactly one trusted non-terminal value.
- `auth_broker_locked` or `auth_broker_unavailable`: run host-side `tobari cluster up`, then inspect `tobari auth status`.
- `root_key_missing_with_vault`: restore the original root key. Do not generate or substitute a new key over existing encrypted state.
- `auth_vault_invalid`: diagnose integrity without printing or rewriting vault contents.
- `invalid_provider_manifest` or `ambiguous_provider_http_binding`: correct the entire strict manifest collection; no partial provider projection activates.
- `credential_handle_invalid` (`403`): leave and re-enter the matching Workspace; a copied or stale handle must not be forwarded.
- `broker_auth_required` (`403`): policy review cannot recover a real credential at a declared binding. Run `auth status`, configure the provider through `auth login` or `auth import`, and re-enter when the handle projection is missing or stale.
- `credential_broker_unavailable` (`503`): this is a known pre-execution
  availability class. Reconcile Broker/companion state and retry only after
  readiness; no application upstream attempt was made.
- `credential_refresh_outcome_unknown` (`409`): do not replay automatically;
  after the original request settles, inspect `auth status`. Ready/configured
  permits an explicit retry because Gateway made no application upstream
  attempt. `not_configured` retains a durable barrier: re-login or logout the
  affected AWS/Datadog provider, then leave and re-enter before retrying.
- `auth_mutation_outcome_unknown` or an output failure after mutation: inspect `auth status` before another login/import/logout. Blind replay may rotate or remove confirmed state twice.

## Guarantees and limits

For declared bindings, the broker keeps static and renewable credential state out of Workspace
files/environment and OPA, binds handles to exact authority, and performs
secret-bearing actions only after allow. It does not isolate mutually hostile
processes inside one Workspace, stop use of an already allowed capability,
perform remote logout, support multiple accounts per Context, or implement
refresh/signing/OAuth beyond the closed reviewed built-in plans. A handle is not
the primary secret, but it is still a scoped bearer capability and should not
be published or logged. Workspace-owned compatibility makes no
primary-secret-isolation claim.

## Summary

Authentication supplies identity material; OPA authorization still controls
each HTTP effect. Brokered Workspaces hold opaque, narrowly bound handles. Only
an allowed Gateway path can trigger the declared static resolve, AWS signing,
or Datadog token action.

## Check your understanding

<details>
<summary>Login succeeds while no GitHub API path is allowed. What happens on the first API call?</summary>

The credential exists and a handle may be projected, but OPA denies the ordinary HTTP effect. Gateway performs no secret resolution and does not connect upstream.

</details>

<details>
<summary>Can Workspace B use a copied handle from Workspace A if both use the same Context and host?</summary>

No. The handle is also bound to A's project ID. Gateway derives B's different
principal from the registered Workspace source endpoint, and broker validation
fails.

</details>

<details>
<summary>Does <code>auth logout</code> revoke the token at the provider?</summary>

No. It removes local broker state and revokes Tobari handles. Remote revocation is outside the command's contract.

</details>
