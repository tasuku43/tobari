Authentication supplies identity material. It never grants network permission:
the Context preset guardrail and exact OPA policy still decide every HTTP
effect.

## Compare the two custody paths

| Path        | Credential owner                           | Workspace receives                      | First public V1 boundary                                           |
| ----------- | ------------------------------------------ | --------------------------------------- | ------------------------------------------------------------------ |
| Tool-native | The Workspace client and its writable home | The client's own files or process state | Tobari does not broker or inspect it; Gateway policy still applies |
| Auth Broker | Encrypted Context vault outside Workspace  | A random Context/project-bound handle   | One static primary secret and exact HTTPS header replacement       |

Use tool-native login when a client already owns a suitable login flow. Use the
Broker only when the provider manifest's static projection and exact header
binding express the complete task.

## Built-in GitHub acquisition

First public V1 has one reviewed built-in acquisition path and requires the
provider explicitly:

```sh
tobari auth login --provider github --context default
```

There is no provider menu, omission default, `--tool`, or alternative built-in
login method. Tobari runs the fixed, identity-checked `gh` helper from a
sanitized temporary home on the trusted host. It uses the reviewed device flow,
opens only the fixed browser destination when possible, and preserves a manual
fallback. Exact GitHub product-version equality is not a security boundary.
The helper commits one bounded static credential; it never enters Workspace or
the Broker image.

## Owner static provider import

An installed owner provider manifest may use only protected stdin import:

```sh
trusted-secret-source | tobari auth import example --context default
```

Terminal stdin is rejected before reading. Input is bounded and never accepted
through argv, environment, or output. The strict owner-only manifest is
non-secret, non-executable data: no shell, helper, refresh, signing, remote
fetch, arbitrary route, or policy rule can be declared.

## One brokered request, in order

1. Gateway derives Context/project identity from the observed Workspace source.
2. It recognizes and removes the handle from the exact declared source header.
3. Broker introspection verifies Context, project, provider, revision, target,
   and HTTP binding without revealing the secret.
4. The preset terminal guardrail runs before candidate creation. A terminal
   denial performs zero candidate, DNS, Broker resolution, or upstream work.
5. OPA decides the ordinary exact HTTP effect without body, handle, or secret.
6. Only after allow, Broker resolves the same static revision once. Gateway
   replaces only the declared header and makes one exact HTTPS attempt.

An invalid, copied, stale, misplaced, or binding-mismatched handle fails before
policy and never falls back to passthrough or another credential mode.

## Rotation and logout

Replacing a Context/provider credential revokes all prior handles. Re-enter the
Workspace to receive the new project-specific projection. Logout removes local
state and handles but does not contact the provider or rewrite an already
running process:

```sh
tobari auth logout github --context default
tobari auth status --context default
```

## Failure behavior

- `auth_login_tty_required`: run built-in login from a trusted-host terminal.
- `invalid_credential_input`: pipe exactly one trusted non-terminal value.
- `auth_broker_locked` or `auth_broker_unavailable`: restore cluster readiness;
  no credential-bearing upstream attempt occurred.
- `root_key_missing_with_vault`: restore the original root key; never generate
  a replacement over encrypted state.
- `credential_handle_invalid` (`403`): repair the matching Context/provider and
  re-enter. Do not reinterpret or forward the value.
- Mutation outcome faults require `auth status` reconciliation before replay.

## Guarantees and limits

Brokered primary secrets stay outside Workspace, OPA, logs, and output. Handles
are project-bound, revisions are checked, resolution is post-policy and exact,
and invalid handles have no fallback. V1 does not provide dynamic credential
operations, multiple accounts per Context, remote logout, or isolation between
peer processes in one Workspace.

## Summary

Tool-native authentication remains Workspace-owned. V1 brokered authentication
is static: explicit GitHub acquisition or strict owner stdin import, a bound
opaque handle, deny-before-resolution, and one exact post-allow replacement.
