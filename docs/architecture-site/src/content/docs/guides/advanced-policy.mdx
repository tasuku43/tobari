title: Advanced policy
description: Maintain trusted-host Rego only when routine exact policy learning cannot express the required boundary.

Most users should stay with Guided policy learning. Use an Advanced Context only when a host-authored policy shape cannot be expressed by the exact allow/deny workflow. Keep its Rego source and tests together, then activate changes through explicit complete-cluster validation.

This is not the normal first-denial path. Before continuing, be comfortable with [Policy review](../policy-review/) and OPA/Rego.

## Guided and Advanced are different ownership models

| Guided Context                                             | Advanced Context                                                    |
| ---------------------------------------------------------- | ------------------------------------------------------------------- |
| Owns `policy/data.json` only                               | Owns `data.json`, `tobari.rego`, and `tobari_test.rego`             |
| Uses the current Tobari-owned shared evaluator             | Maintainer owns Context-local policy logic and tests                |
| Routine exact allow/deny/reset/compaction is the main path | Direct host edit is possible when the routine model is insufficient |
| A Tobari release updates evaluator logic                   | Maintainer must review compatibility and behavior                   |

Neither mode lets a Workspace edit active policy. Context policy directories remain owner-only host state and are not mounted into Workspaces.

## Create an Advanced Context deliberately

```sh
tobari context create --name policy-lab --mode advanced
tobari context show --name=policy-lab --format=json
tobari context use --name policy-lab
```

Use the exact store paths reported by `context show`. Do not mount the parent Tobari configuration directory into a Workspace and do not copy credentials into the policy directory.

Creation does not change a running cluster. Reconcile explicitly before using the new Context:

```sh
tobari cluster up
```

## Edit source and tests together

On the trusted host, edit the reported `policy/tobari.rego` and `policy/tobari_test.rego`. Keep the stable public decision contract and add tests for both intended matches and negative canaries.

Advanced source is projected into an isolated package derived from the stable Context ID. Validation rejects attempts to claim:

- the cluster-owned `tobari.http/decision` router;
- reserved `tobari.system` packages;
- another Context's namespace; or
- the aggregate Context data namespace.

This is routing and namespace enforcement inside one trusted OPA process. It is not process-level confidentiality between Rego modules.

## Validate and activate explicitly

Before activation, use read-only diagnosis:

```sh
tobari doctor
tobari cluster logs --component opa --tail 100
```

`doctor` observes; it does not publish a source edit. Run the explicit cluster reconciliation to regenerate, test, and activate the all-Context projection:

```sh
tobari cluster up
```

The projection owns one fixed router, Context-ID data namespaces, the shared Guided evaluator, and rewritten Advanced packages. Every source and the complete aggregate must pass. Only a valid candidate is published. A failure leaves the prior known-good aggregate authoritative.

Routine exact allow/deny/reset operations use the same all-Context safety boundary and alter only learned collections in `data.json`. They do not rewrite host-authored boundary policy or arbitrary Rego.

## A suitable advanced use case

Suppose a trusted maintainer needs a finite rule derived from non-secret request metadata that exact path rules cannot represent. The maintainer:

1. documents why exact review is insufficient;
2. writes the smallest Rego condition in one Advanced Context;
3. adds positive fixtures and negative-inference canaries;
4. validates every Context in the aggregate; and
5. confirms the resulting behavior with a denied and an allowed synthetic request.

Do not use Advanced mode to implement a provider SDK, read request bodies, invoke a shell, load credentials, or bypass the Gateway/Auth Broker boundary. Rego receives normalized decision data, not arbitrary effect execution authority.

## Failure behavior

- Invalid Rego, test failure, forbidden package, or schema mismatch prevents activation.
- A partial source edit never becomes a partially active aggregate.
- OPA watch/health failure leaves requests fail closed; it does not preserve availability by allowing.
- If `cluster up` reports a Context source failure, correct that exact Context before retrying.
- If an exact policy mutation races with a host edit, content/revision checks reject stale state rather than merging by guess.
- A valid Rego test suite still proves only its declared cases; it does not establish that every unknown future URL is safe.

## Guarantees and limits

Tobari reserves the router and Context namespaces, tests the whole projection, publishes atomically, and retains known-good policy on failure. The maintainer remains responsible for the meaning and completeness of Advanced rules. Tobari does not interpret provider semantics or infer safe wildcards.

## Summary

Advanced mode moves policy-logic ownership to a trusted maintainer, not to the Workspace. Context namespace enforcement, whole-projection tests, and atomic activation remain mandatory.

## Check your understanding

<details>
<summary>Should a routine denial be solved by editing Rego first?</summary>

No. Use `policy review` and an exact allow or deny. Advanced editing is for behavior the routine exact model cannot express.

</details>

<details>
<summary>Does <code>doctor</code> activate an edited Rego file?</summary>

No. It is observational. Explicit cluster reconciliation or a supported exact policy mutation owns validated activation.

</details>

<details>
<summary>Can Advanced Rego request a credential from Auth Broker?</summary>

No. OPA decides normalized non-secret HTTP metadata. Gateway owns the post-allow broker resolution boundary.

</details>
