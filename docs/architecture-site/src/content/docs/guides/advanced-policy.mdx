title: Advanced policy

Most users should stay with Guided policy learning. Use an Advanced Workspace Template only when a host-authored policy shape cannot be expressed by the exact allow/deny workflow. Keep its Rego source and tests together, then activate changes through explicit complete-cluster validation.

This is not the normal first-denial path. Before continuing, be comfortable with [Policy review](../policy-review/) and OPA/Rego.

## Guided and Advanced are different ownership models

| Guided Workspace Template                           | Advanced Workspace Template                                         |
| --------------------------------------------------- | ------------------------------------------------------------------- |
| Owns `policy/domains/<host>/{allow,deny}.json` only | Owns the domain tree, `tobari.rego`, and `tobari_test.rego`         |
| Uses the current Tobari-owned shared evaluator      | Maintainer owns Workspace Template-local policy logic and tests     |
| Routine exact allow/deny/reset is the main path     | Direct host edit is possible when the routine model is insufficient |
| A Tobari release updates evaluator logic            | Maintainer must review compatibility and behavior                   |

Neither mode lets a Workspace edit active policy. Workspace Template policy directories remain owner-only host state and are not mounted into Workspaces.

## Create an Advanced Workspace Template deliberately

```sh
tobari template create --name policy-lab
tobari template show --name=policy-lab --format=json
tobari template default set --id TEMPLATE_REF
```

Use the exact store paths reported by `template show`. Do not mount the parent Tobari configuration directory into a Workspace and do not copy credentials into the policy directory.

Creation does not change a running cluster. Reconcile explicitly before using the new Workspace Template:

```sh
tobari cluster up
```

## Keep domain data exact

Both modes use the same human-editable domain source. Each canonical lower-case
host has exactly two owner-only files:

```text
policy/domains/api.example.com/
  allow.json
  deny.json
```

`allow.json` has exactly `schema_version`, `host`, `authorities`, `methods`,
`graphql_endpoints` and `rules`. `deny.json` has exactly
`schema_version`, `host`, `baseline_rules`, and `rules`. Every collection is an
explicit JSON array. Unknown fields, duplicate keys or rule IDs, missing
fields, extra files, symlinks, and group/world permissions are rejected.

The directory name and every host in an authority, GraphQL endpoint,
Workspace binding, baseline rule, or learned rule must be identical.
Hostnames are canonical lower-case DNS names. Trailing dots, IP literals,
uppercase forms, and wildcards are unsupported; the current contract is exact
host only. HTTP methods are uppercase and belong only to authorities composed
from this domain, so a method allowed for one host cannot authorize another.
Explicit deny retains precedence.

When adding a host manually, prepare a complete private sibling directory with
both files and rename the directory into `domains/`; do not expose a half pair.
Use an editor that saves one existing file by atomic rename. `cluster up`
re-reads a stable complete snapshot and fails closed on an incomplete or
changing source. Routine CLI policy mutations preserve unchanged file bytes
and swap a complete `domains/` generation under a cross-process lock and
durable recovery journal.

## Edit source and tests together

On the trusted host, edit the reported `policy/tobari.rego` and `policy/tobari_test.rego`. Keep the stable public decision contract and add tests for both intended matches and negative canaries.

Advanced source is projected into an isolated package derived from the stable Workspace Template ID. Validation rejects attempts to claim:

- the cluster-owned `tobari.http/decision` router;
- reserved `tobari.system` packages;
- another Workspace Template's namespace; or
- the aggregate Workspace Template data namespace.

This is routing and namespace enforcement inside one trusted OPA process. It is not process-level confidentiality between Rego modules.

## Validate and activate explicitly

Before activation, use read-only diagnosis:

```sh
tobari doctor
tobari cluster logs --component opa --tail 100
```

`doctor` observes; it does not publish a source edit. Run the explicit cluster reconciliation to regenerate, test, and activate the all-Context projection:

```sh
tobari cluster up
```

The projection owns one fixed router, Workspace Template-ID data namespaces, the shared Guided evaluator, and rewritten Advanced packages. Every source and the complete aggregate must pass. Only a valid candidate is published. A failure leaves the prior known-good aggregate authoritative.

Routine exact allow/deny/reset operations use the same all-Context safety boundary and alter only the matching host's learned `rules` collection in `allow.json` or `deny.json`. They do not rewrite host-authored boundary policy or arbitrary Rego. A generated content-addressed OPA projection contains an internal `data.json`; it is not Workspace Template source.

## A suitable advanced use case

Suppose a trusted maintainer needs a finite rule derived from non-secret request metadata that exact path rules cannot represent. The maintainer:

1. documents why exact review is insufficient;
2. writes the smallest Rego condition in one Advanced Workspace Template;
3. adds positive fixtures and negative-inference canaries;
4. validates every Workspace Template in the aggregate; and
5. confirms the resulting behavior with a denied and an allowed synthetic request.

Do not use Advanced mode to implement a provider SDK, read request bodies, invoke a shell, load credentials, or bypass the Gateway credential-redaction boundary. Rego receives normalized decision data, not arbitrary effect execution authority.

## Failure behavior

- Invalid Rego, test failure, forbidden package, or schema mismatch prevents activation.
- A partial source edit never becomes a partially active aggregate.
- OPA watch/health failure leaves requests fail closed; it does not preserve availability by allowing.
- If `cluster up` reports a Workspace Template source failure, correct that exact Workspace Template before retrying.
- If an exact policy mutation races with a host edit, content/revision checks reject stale state rather than merging by guess.
- A valid Rego test suite still proves only its declared cases; it does not establish that every unknown future URL is safe.

## Guarantees and limits

Tobari reserves the router and Workspace Template namespaces, tests the whole projection, publishes atomically, and retains known-good policy on failure. The maintainer remains responsible for the meaning and completeness of Advanced rules. Tobari does not interpret provider semantics or infer safe wildcards.

## Summary

Advanced mode moves policy-logic ownership to a trusted maintainer, not to the Workspace. Workspace Template namespace enforcement, whole-projection tests, and atomic activation remain mandatory.

## Check your understanding

<details>
<summary>Should a routine denial be solved by editing Rego first?</summary>

No. Use `review permissions` and an exact allow or deny. Advanced editing is for behavior the routine exact model cannot express.

</details>

<details>
<summary>Does <code>doctor</code> activate an edited Rego file?</summary>

No. It is observational. Explicit cluster reconciliation or a supported exact policy mutation owns validated activation.

</details>

<details>
<summary>Can Advanced Rego request a credential from an agent CLI?</summary>

No. OPA decides normalized non-secret HTTP metadata. Agent CLIs own login state in
the Workspace home, and Gateway forwards original credential values only after
OPA allows the request; it does not resolve credentials through a service.

</details>
