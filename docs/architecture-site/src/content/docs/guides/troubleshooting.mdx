---
title: Troubleshooting
description: Start from an observable symptom, identify the owning boundary, and choose a safe read-before-write recovery.
---

Start troubleshooting with read-only diagnostics. Identify which boundary owns the failure, then use the recovery command declared for that fault. Do not replay uncertain mutations or remove security state merely to clear an error.

The sections below are organized by observable symptom so policy, authentication, runtime, and VM failures stay distinct. Review the [five-part mental model](../../how-it-works/mental-model/) first. For exact codes, retryability, and Catalog-declared recovery, use [Faults and recovery](../../reference/faults-and-recovery/).

## Begin with observations

From the trusted host and intended project directory:

```sh
tobari doctor
tobari cluster status
tobari status
tobari workspace list
```

These commands observe; they do not start services, create/delete runtime resources, activate policy, or repair agent CLI login state. Login remains the provider CLI's own operation inside the Workspace.

Record the exact fault code and declared next action. Do not reduce every failure to “retry.”

## I cannot enter a Workspace

Check in this order:

1. `tobari cluster status`: the shared cluster must already be configured and healthy.
2. `tobari doctor`: inspect Docker, image, path, policy, Workspace, and host-owned lifecycle prerequisites.
3. `tobari status`: distinguish absent logical state from `missing`, `degraded`, `unreachable`, or `incomplete` runtime diagnostics.
4. Confirm the root command has an interactive terminal and is not already running inside a Workspace.

`missing` container or `degraded` network can be reconciled by the next valid
root entry while preserving logical state and home. Invalid or contradictory
authority is different: entry refuses to invent identity or an action reference.
Follow the fault's one read-only `Next`; use `workspace delete` only after
`workspace list` or `status` has produced the exact Workspace reference.

For `workspace_selection_stale`, rerun `tobari` and choose from the refreshed candidates. For `image_not_found` or `incompatible_image`, inspect the bound Workspace Template and fix/build the runtime before another entry.

## A request returns HTTP 403

First identify the response code:

- `policy_denied`: leave the Workspace and run `tobari review permissions`. Inspect and stage exact choices for the owning Context, apply the reviewed set once, then retry deliberately.
- A provider `401`/`403`: treat it as an upstream response. Leave the Workspace only if the provider CLI requires it, then use that CLI's documented login flow. Tobari never turns an upstream authentication response into a broader allow rule.
- A baseline or learned exact deny: it is terminal policy, not a pending candidate. Inspect `tobari policy rules`; reset only if changing that decision is intentional.

Do not solve an upstream authentication `403` by creating a broad allow rule. A provider response is not a pending Tobari policy candidate.

## Gateway or OPA is unhealthy

```sh
tobari cluster status
tobari cluster logs --component gateway --tail 100
tobari cluster logs --component opa --tail 100
```

Correct the reported image, projection, policy, mount, ownership, or health issue, then run explicit reconciliation:

```sh
tobari cluster up
```

OPA unavailable never becomes allow. Gateway does not connect upstream without a valid decision. An invalid policy candidate should leave the previous known-good aggregate active.

## A provider login is unavailable

Run the provider's own login command from inside the selected Workspace, then
return to the ordinary request flow. Tobari does not inherit host credentials,
store provider state, or provide a replacement login command.

## A Workspace entry or agent login is invalid

Credential changes are owned by the agent CLI and a running process keeps its old
environment. Exit and re-enter to receive the current tool-owned state:

```sh
exit
tobari
```

If it still fails, inspect the exact Context, Workspace Template selection, and
cluster readiness. Do not copy login files between Workspaces; Context and
Workspace checks are intentional.

## Runtime image is missing or incompatible

```sh
tobari template show
```

For a managed Runtime:

```sh
tobari runtime list
tobari runtime show --name frontend
tobari runtime build --id RUNTIME_REF
tobari template runtime set --id TEMPLATE_REF --runtime RUNTIME_REVISION_REF
```

A failed build appends no revision and changes no Workspace Template. A failed selection
keeps the previous exact binding. Existing logical Workspace state and home
remain. Correct compatibility instead of changing host mounts, user,
entrypoint, lifetime command, or network controls.

## Policy activation fails

Inspect:

```sh
tobari policy rules
tobari cluster status
tobari cluster logs --component opa --tail 100
```

Exact allow/deny/reset validates the changed Context Policy Memory and the
complete all-Context aggregate before activation. A failure retains known-good
policy. Rediscover opaque references after any concurrent change; do not reuse
display order or stale IDs.

If legacy executable-policy state is reported, follow the reset/recreate
recovery. Tobari does not translate or execute that state.

## I cannot delete a Workspace or stop the cluster

- `project_session_attached`: exit the session, then run `tobari workspace delete --id WORKSPACE_REF --confirm=delete`. Use `tobari workspace delete --id WORKSPACE_REF --confirm=delete --force` only when terminating that exact attached session is intentional.
- `project_not_found`: run the command from the intended project root/ancestor and selected Workspace Template.
- `cluster_not_empty`: `tobari workspace list` every Workspace, return to the appropriate root/Workspace Template, and delete each before `cluster down`.
- Interrupted state: inspect `status` and `doctor`; use the declared exact cleanup or reconcile command rather than manually deleting labels/files.

`workspace delete` never removes project files. `cluster down --purge` removes shared runtime and CA volumes but preserves Workspace home, Template policy and Context Policy Memory, and host-owned lifecycle state; agent CLI logout remains a provider operation.

## Colima or Lima cannot see a mount

If Docker reports a bind source missing even though the host shell can see it, the selected VM daemon lacks path sharing. Share the exact project and resolved Tobari XDG config/state parents, then run:

```sh
tobari doctor
tobari cluster up
```

See [Colima and Lima](../colima-and-lima/). Do not work around the error with a host-home mount, host network, privileged container, or Docker socket.

## Mutation outcome is uncertain

For `unclassified_mutation_outcome` or `mutation_output_write_failed`, the side effect may already have completed. Do not repeat a policy or lifecycle mutation merely because output was lost.

Reconcile through the matching read path first:

- agent login: the provider CLI's own login flow;
- policy: `tobari policy rules` and `tobari cluster status`;
- Workspace Template/Runtime: `tobari template show`;
- Workspace: `tobari status` and `tobari workspace list`.

## Guarantees and limits

Catalog faults declare bounded recovery, and read-only diagnostics avoid surprising repair. Diagnosis still depends on accurate trusted-host/Docker observations. Manual deletion of state, arbitrary image substitution, or broad mount/network changes can invalidate recovery guarantees and the security model.

## Summary

Start with what you observed, identify the owning boundary, read current state, and apply only the declared recovery. Availability failures remain closed, and uncertain mutations must be reconciled before replay.

## Check your understanding

<details>
<summary>A provider login lost its final output. Should you run it again?</summary>

Not yet. The provider may already have accepted the login. Reconcile the
Workspace-owned state before repeating a mutating login action.

</details>

<details>
<summary>An HTTPS request gets a policy denial. Should you restart the cluster first?</summary>

No, not when the cluster is healthy and the denial is learnable. Leave the Workspace, review the exact effect on the host, decide, then retry deliberately.

</details>

<details>
<summary>A Workspace container disappeared. Must you delete the logical Workspace?</summary>

No. Runtime loss is recoverable. A valid next root entry recreates the container while preserving identity and home. Delete only for an `incomplete` cleanup state or when ending the Workspace intentionally.

</details>
