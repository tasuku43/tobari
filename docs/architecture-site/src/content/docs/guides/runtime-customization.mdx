The quickstart uses only `curl` from the standard base runtime to demonstrate denial, review, allow, and deliberate retry. The standard base runtime is deliberately small: it is a foundation for checking the boundary and building a custom image. **It does not include a coding agent and is not intended to provide every project-specific language runtime or build tool.**

Before using Tobari on a real repository, build a custom runtime with the tools you need. Tobari calls the reusable configuration shared by Workspaces a **Context**. Runtime selection belongs to the current Context, and every Workspace bound to that Context consults the same selected image on its next entry.

Perform this procedure on the trusted host. A Workspace has no control path for editing the managed Dockerfile or running `runtime build`.

## Why this step comes early

The standard runtime is enough to inspect the boundary with tools such as `bash` and `curl`. It is not enough to begin real development when the coding agent, compiler, package manager, or test tools required by the project are absent.

After completing the first policy review, the normal setup order is:

1. inspect the current Context;
2. initialize its managed Dockerfile;
3. add the coding agent and development tools;
4. let Tobari build and validate the image; and
5. re-enter the Workspace with the selected image.

## 1. Inspect the current Context

First confirm which Context will own the runtime:

```sh
tobari context show --format json
```

To use a named Context, select it first and inspect it in the same way:

```sh
tobari context use --name review
tobari context show --format json
```

Runtime selection belongs to a Context rather than directly to one project. Use separate Contexts when different work requires different toolsets.

## 2. Create the runtime recipe

Initialize the managed Dockerfile once for the current Context:

```sh
tobari runtime init --format json
tobari context show --format json
```

Use the Dockerfile path returned by `context show`; there is no need to guess the storage location.

`runtime init` only:

- creates an owner-only runtime directory;
- writes a Dockerfile template based on the official runtime; and
- records that the Context has a managed recipe.

It does not build an image or change the current image selection. It refuses to overwrite an existing recipe.

## 3. Add the agent and development tools

The generated Dockerfile contains existing `USER root` and `USER tobari` lines. Add operating-system packages and global command-line tools between those lines.

The following example installs Node.js, npm, and Codex CLI. Codex is only an example; it is not a Tobari dependency. Replace the install line when you use another coding agent.

```dockerfile
USER root

RUN apt-get update \
    && apt-get install -y --no-install-recommends nodejs npm \
    && rm -rf /var/lib/apt/lists/*

RUN npm install --global @openai/codex

USER tobari
```

For a reproducible team image, pin the coding agent and other important tools to reviewed versions. The current official Codex installation methods are documented in the [Codex repository](https://github.com/openai/codex#installing-and-running-codex-cli).

Add the SDKs, compilers, linters, and test tools required by the project to the same Dockerfile. Files used by `COPY` must be placed inside the Context runtime directory because `runtime build` uses only that directory as its Docker build context.

**Never put credentials, API keys, tokens, or personal configuration in the Dockerfile, build arguments, build context, or image layers.**

## 4. Build and select the image

Editing the Dockerfile does not change a Workspace. Run the explicit build on the trusted host:

```sh
tobari runtime build --format json
tobari context show --format json
```

`runtime build` performs one operation that:

1. uses only the Context runtime directory as the build context;
2. builds a candidate image with Docker;
3. validates it against the Tobari runtime contract;
4. records the confirmed image digest; and
5. selects only the compatible image for the Context.

A failed build or compatibility check leaves the previous image selected. Docker or BuildKit may retain a candidate image or cache, but Tobari does not report it as active.

This is a trusted-host Docker build, not Workspace traffic governed by Gateway policy. Review every package source and build script that the Dockerfile executes.

## 5. Enter the Workspace and verify the real tool

Move to a project that uses this Context and enter the Workspace:

```sh
tobari
codex --version
codex
```

If an existing Workspace used a different image, Tobari recreates only the work container on the next entry. A new Workspace starts directly from the selected image.

When the agent begins external communication, undeclared requests are denied just as they were in the quickstart. Leave the Workspace, run `tobari policy review`, and allow only the destination, port, method, and path that the agent actually needs. Tobari never replays the denied request; issue a new request from the agent after the permission is active.

## Credentials and persistent home

A coding agent normally stores login state and configuration in the Workspace home directory. The home is persistent state mounted separately from the work container, so it survives runtime-image changes and container recreation.

However, credentials stored there are **not isolated from other processes in the same Workspace.** Auth Broker protects only credentials that use an explicitly supported broker path. Tobari does not automatically move a coding agent's own stored credentials into Auth Broker.

Therefore:

- never bake credentials into the image;
- never add the host home as a mount;
- treat agent login state as shared within the same Workspace;
- use `tobari delete` to remove the persistent home when the Workspace is no longer needed; and
- when a supported path exists, consult the [authentication guide](../authentication/) for Auth Broker setup.

## What an existing Workspace preserves

When a runtime change recreates the work container, Tobari preserves:

- the logical Workspace ID;
- the canonical project root;
- the Context binding;
- the persistent Workspace home;
- learned policy; and
- project files.

The image `CMD` does not define Workspace lifetime. Tobari supplies the fixed lifetime command and starts shells or coding agents as child exec sessions.

A custom image cannot grant itself the Docker socket, extra host mounts, host networking, direct external access, added Linux capabilities, or another project's identity. The host lifecycle implementation owns those controls.

## Failure behavior

- `runtime_recipe_exists`: use the existing Dockerfile; `runtime init` does not overwrite it.
- `runtime_recipe_missing`: run `tobari runtime init` before building.
- `runtime_build_failed`: inspect the Dockerfile and build output. The previous selection remains.
- `incompatible_image`: restore the required `tobari` user, labels and API, entrypoint, architecture, and other runtime-contract requirements.
- `image_not_found`: make the base or selected image available to Docker and retry.
- uncertain mutation result: inspect `tobari context show --format json` before starting another build.
- Workspace entry failure: the logical Workspace and persistent home remain. Repair the Context image and enter again.

See the [runtime image contract](../../reference/runtime-image-contract/) for the exact required properties.

## Guarantees and limits

Tobari selects only an image that passes compatibility validation and does not silently replace the active image with a failed candidate. It does not establish that arbitrary software added to the image or its package source is trustworthy.

An agent inside the Workspace can still read and write the selected project and use already allowed communication. Custom runtime setup adds required tools to the isolated work environment; it does not narrow the authority already granted to that Workspace.

## Summary

The standard quickstart runtime is the foundation used to inspect network control. For real development, create the managed Dockerfile for the current Context, add the agent and development tools, and run `runtime build` so Tobari selects a validated image. On the next entry, Tobari recreates only the work container when necessary and preserves the Workspace home, policy, and project files.
