If you have only completed Quickstart, begin with [Prepare a custom runtime](../../start/runtime-setup/). That page covers the shortest path from the minimal base runtime to a verified coding-agent command inside a real Workspace.

This page covers Runtime ownership, immutable revision history, explicit Workspace Template
selection, drift reconciliation, and failure recovery. Runtime source is
installation-wide and reusable; a Workspace Template stores only one exact ready revision
binding.

Before starting, identify the current Workspace Template; see [Workspace Templates](../workspace-templates-and-contexts/). A custom runtime image provides the working environment, but it does not gain authority over mounts, networking, or Workspace lifetime.

## 1. Create and inspect a Runtime

```sh
tobari runtime create --name frontend
tobari runtime show --name frontend
```

The create report gives the owner-only `source_path`. Names are unique within
the installation and the stable Runtime ID does not change across revisions.
The source path itself and every directory below it must have no group/other
permissions.

## 2. Edit the complete source tree

Use the reported path instead of guessing it. The directory is a complete
Docker build context: manage Dockerfile-adjacent scripts, package manifests,
and configuration there as ordinary files. Links and special files are not
accepted. The complete boundary is 1,024 regular files, 256 directories, 32
MiB per file, and 64 MiB total. Every file must have no group/other permission
bits; use `0600` for data or `0700` when a copied script or binary needs owner
execute. Editing source changes no Workspace Template and creates no revision.

Edit the recipe on the trusted host. A minimal customization keeps the template's base and user transitions intact, for example adding a package between its existing `USER root` and `USER tobari` lines:

```dockerfile
RUN apt-get update \
    && apt-get install -y --no-install-recommends tree \
    && rm -rf /var/lib/apt/lists/*
```

Do not put real credentials in the Dockerfile, build context, image layers, or examples.

## 3. Build and validate an immutable revision

```sh
tobari runtime build --id RUNTIME_REF --format json
tobari runtime history --name frontend
```

This is one deliberate host Docker-build boundary. Tobari:

1. validates and hashes the complete bounded source tree;
2. writes an immutable semantic snapshot;
3. builds only that snapshot with a mechanically derived local image identity;
4. validates the resulting image against the Tobari runtime contract;
5. records the confirmed image digest; and
6. atomically appends the successful revision to Runtime history.

Failed and unchanged builds append no revision, and every Workspace Template remains
unchanged. Docker/BuildKit may retain cache or an unselected candidate image;
Tobari does not misreport those as ready history.

## 4. Explicitly pin a Workspace Template

```sh
tobari template plan --id TEMPLATE_REF
tobari template apply --plan TEMPLATE_CHANGE_PLAN_REF
tobari template show --name review
```

The same revision may be pinned by several Workspace Templates. A later build does not
upgrade them. Edit each Template source and review a complete Apply explicitly
for upgrade or rollback.

## 5. Re-enter an existing Workspace

From a project bound to this Workspace Template:

```sh
tobari
tree --version
exit
```

Entry compares the desired image and complete runtime spec with the existing
container. If they changed, Tobari recreates only that container. It preserves
the Workspace ID, permanent Context binding, persistent home, Context Policy
Memory, Workspace Template, and project files.

The image's `CMD` does not define Workspace lifetime. Tobari supplies its fixed lifetime command and opens each shell or agent command through a child exec session. Container loss is recoverable; the logical Workspace is not the container.

## What compatibility means

A custom image must preserve the declared Tobari runtime API and operational contract, including the expected non-root `tobari` user, entrypoint behavior, fixed lifetime-command capability, CA trust environment compatibility, writable home location, health behavior, and supported architecture.

The image cannot grant itself:

- extra host mounts or the host home;
- Docker socket access;
- host networking or a direct external route;
- added Linux capabilities;
- a different Context/Workspace principal; or
- a longer logical lifetime by changing `CMD`.

Those controls are owned by the host lifecycle implementation, not image metadata.

## Failure behavior

- `runtime_exists`: inspect the existing Runtime with `tobari runtime show`.
- `runtime_not_found`: choose a name from `tobari runtime list`.
- `runtime_source_invalid`: correct the relative path and actual size, count,
  entry kind, or owner-only mode named by the error. Source copied as `0755`
  must lose all group/other bits (normally becoming `0700`).
- `runtime_build_failed`: correct the source and inspect `tobari runtime show`; history and Workspace Templates remain unchanged.
- `runtime_revision_not_ready`: choose a successful ordinal from `tobari runtime history`.
- `image_not_found`: make the declared base or selected image available, then retry the explicit build/reconcile step.
- `incompatible_image`: restore the required user, labels/API, entrypoint, lifetime capability, and architecture.
- An uncertain selection outcome: inspect `tobari template show` before selecting again.
- Existing Workspace entry failure: prior logical state and home remain; fix the Workspace Template image and re-enter.

## Guarantees and limits

History is content-aware and append-only, and failed validation cannot silently
replace a Workspace Template binding. Compatibility validation cannot make arbitrary
software inside the image trustworthy. Anything running in the Workspace can
still modify the selected project and use already allowed network effects.

## Summary

Runtime source is mutable preparation, successful revisions are immutable,
Workspace Template selection is explicit, and Workspace entry is the reconciliation
point. Runtime images provide tools; host lifecycle code owns authority and lifetime.

## Check your understanding

<details>
<summary>Does editing or building Runtime source update Workspaces?</summary>

No. Build creates history only. A Workspace Template must explicitly select the ready
revision, and its Workspaces observe that binding on their next entry.

</details>

<details>
<summary>What happens to the Workspace home when image drift recreates its container?</summary>

The home is preserved. It is logical Workspace state mounted separately from the replaceable container.

</details>

<details>
<summary>Can a custom image add the Docker socket by declaring it in its Dockerfile?</summary>

No. Host lifecycle code fixes mounts and capabilities. Image contents do not select those privileges.

</details>
