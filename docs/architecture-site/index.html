Bounded autonomy, made legible.

01 / dependency direction

Four layers. One inward pull.

The public CLI is the composition root. Application code interprets user tasks, infrastructure performs bounded effects, and the domain keeps the vocabulary pure. The direction is a constraint, not a suggestion.

Dependencies point from the CLI to the application and domain, from the application to the domain, and from infrastructure to domain. The domain has no outward dependency.

02 / trust boundaries

Trust changes at the edge of the Workspace.

The host owns setup and exact resource selection. Agent processes are untrusted and can work inside the explicitly mounted root. Gateway and OPA are trusted enforcement components; the agent never receives their control surface.

The trusted host creates a Workspace with one writable root, one persistent tool-owned home, and one dedicated internal network. The untrusted agent uses an explicit proxy to reach the trusted Gateway. Gateway asks trusted OPA for a decision before reaching an upstream service.

03 / Workspace lifecycle

CWD first. Reusable by design.

A Workspace is selected by its canonical project root, not by a name or diagnostic ID. A session is temporary; the logical Workspace remains until the host deliberately deletes it.

  1. 01

    enter

    Start from the current directory

    An exact root is reused directly. If ancestor roots exist, Tobari lists every containing Workspace nearest-first and requires an explicit reuse or create-here choice.

    tobari
  2. 02

    reconcile

    Bind one bounded runtime

    The selected root, dedicated internal network, persistent home, compatible image, and Gateway attachment converge under ownership checks.

    canonical root → one Workspace
  3. 03

    work

    Let the agent move inside it

    Concurrent processes can modify the mounted root. Direct egress, host-home mounts, Docker control, and another Tobari remain outside the supported path.

    exit ≠ delete
  4. 04

    finish

    Detach, reuse, or remove

    A child exit detaches the session and leaves the Workspace reusable. delete ends the exact CWD-local Workspace; --force only overrides an attached-session guard.

04 / policy learning

A denial is a handoff, not a hidden grant.

The ordinary loop keeps the agent moving without turning routine work into Rego administration. Observation creates evidence; only an explicit, tested, project-bound action changes authority.

  1. 01

    attempt

    Agent requests

    A supported HTTP/HTTPS effect leaves the Workspace through the explicit proxy.

  2. 02

    decide

    Gateway asks OPA

    The request is normalized, credentials are redacted from policy input, and default deny wins unknowns.

  3. 03

    evidence

    Useful denial

    Bounded host, port, method, path, and reason are retained. Secrets, raw bodies, and credentials are not.

  4. 04

    trusted host

    Review one candidate

    policy review presents the Permission Inbox. An explicit TTY decision delegates one opaque reference.

  5. 05

    activate

    Test, activate, retry

    Allow or deny tests the target Context source and complete all-Context candidate, atomically activates OPA, and makes the next retry meaningful.

!

Not every denial is learnable

Baseline denies, unavailable bodies, wrong scheme or port, stale principals, and other orthogonal failures remain diagnostics rather than ineffective candidates.

✓

Exact means exact

Learned permission stays bound to the observed Context, project, host, port, method, and path. A prior allow never becomes permission for a similar request.

05 / Context runtime

Customize the runtime without moving the boundary.

Each Tobari permanently belongs to one stable Context. Multiple Contexts share one Gateway and one OPA while runtime, home, network, policy, and managed credentials retain their explicit boundaries.

One understandable setup per Tobari. Its stable identity is host-bound; the current Context is only an omitted-input default.

The through-line

Make the safe path the easy path.

Tobari’s architecture keeps autonomy inside a declared boundary: the CLI expresses a task, the layers keep ownership visible, the Gateway and OPA enforce one network edge, Workspace state stays reusable, and policy growth requires a human decision that can be tested and retried.
